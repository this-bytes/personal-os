# WI-021 — A delegation addressed to a participant is not silently dropped

**Owner:** Cog
**Verifier:** Probe

## Problem

Found in Cog's report on WI-009, and left alone there because the item said to
stay inside it. The MCP tool's argument is named `targetParticipantIds`, but
the routing engine matches it against agent _connection_ ids
(`enabledConnectionIds.has(id)` at `routing.ts:131`). A client that passes real
participant ids has them silently dropped, and the message falls through to
the mention path instead — so a delegation aimed at one participant arrives
somewhere else, or nowhere, and nothing says so.

A delegation that is silently redirected is the same class of failure as the
one WI-009 fixes: the request goes to the wrong party, and the reason string
does not admit it.

## Acceptance criteria

- [ ] The published argument and the engine agree. Either the engine honours
      the published argument, or the report says plainly which side is wrong
      and why, and the change stops there — changing a published argument is
      a contract change, and that needs the owner, a migration plan and a
      `CONTRACTS.md` entry.
- [ ] A delegation addressed to a participant reaches that participant, or is
      refused with a reason that says so. It is never silently dropped.
- [ ] The reason string names the target that was refused, the way WI-009's
      does.

      MCP `conversation.post` tool, the way WI-009's covers the named-target
      path.
- [ ] The `CONTRACTS.md` entry for the tool, if its argument changes, lands
      before the change ships.

same file and the same commit. The fix is in the tree and it works: the
translation sits at the boundary in `service.ts:419-429`, and the MCP-level

(`coordinator-routing.test.ts:236-251`) and _"refuses a non-coordinator that
names a target, and says which rule refused it"_ (`:253-269`) both pass.

**Criteria 1, 2, 4 and 5 are met by the tree** — the published argument is
now honoured, so **no contract change is needed**.

**Criterion 3 is not met, and the reason is a collision between two items.**

- This item's criterion 3: _"The reason string names the target that was
  refused, the way WI-009's does."_
- WI-009's criterion: _"a refusal must name who was refused."_

Probe measured the string that satisfies WI-009: `names the sender? true`,
`names the target? false`. It reads _"Only the coordinator may delegate in
coordinator mode. Codex is not the coordinator, so no participant was woken."_
— the sender is named, and the participant whose wake-up was refused is not.

**Chief's ruling: the string must name both, and the change is made in this
item.** WI-009 is accepted with the string it has, because its criterion is
met and its behaviour is pinned by three tests. This item's criterion asks for
one more fact in the same sentence — the agent the owner addressed — and it is
the right ask: an owner who addresses Scout and is refused must be told that
Scout was not woken, or the request went somewhere else and the reason does
not admit it.

**The constraint, said out loud:** WI-009's pinned tests may be **updated to
hold the new wording**. They may not be removed, and the behaviour they hold
— the coordinator acts, the named agent is not woken, the reason says so — may
not change. One file, one live item: WI-009 is closed, so `routing.ts` is
free for this item.
