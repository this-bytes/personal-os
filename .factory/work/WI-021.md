# WI-021 — A delegation addressed to a participant is not silently dropped

**Owner:** Cog
**Verifier:** Probe
**State:** triage — the defect is now **proven** by three red tests committed in
`a7e39e9`, and the dispatch still waits for WI-009's verification to land; it
is the same file
**Dispatched:** not dispatched — `apps/server/src/modules/conversations/routing.ts` is claimed by WI-009 until it lands

## Problem

Found in Cog's report on WI-009, and left alone there because the item said to
stay inside it. The MCP tool's argument is named `targetParticipantIds`, but
the routing engine matches it against agent _connection_ ids
(`enabledConnectionIds.has(id)` at `routing.ts:131`). A client that passes real
participant ids has them silently dropped, and the message falls through to
the mention path instead — so a delegation aimed at one participant arrives
somewhere else, or nowhere, and nothing says so.

A delegation that is silently redirected is the same class of failure as the
one WI-009 fixes: the request goes to the wrong party, and the reason string
does not admit it.

## Acceptance criteria

- [ ] The published argument and the engine agree. Either the engine honours
      the published argument, or the report says plainly which side is wrong
      and why, and the change stops there — changing a published argument is
      a contract change, and that needs the owner, a migration plan and a
      `CONTRACTS.md` entry.
- [ ] A delegation addressed to a participant reaches that participant, or is
      refused with a reason that says so. It is never silently dropped.
- [ ] The reason string names the target that was refused, the way WI-009's
      does.
- [ ] A test covers a delegation addressed by participant id, through the
      MCP `conversation.post` tool, the way WI-009's covers the named-target
      path.
- [ ] The `CONTRACTS.md` entry for the tool, if its argument changes, lands
      before the change ships.
