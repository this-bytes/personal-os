# WI-019 — How to check a committed file, so the check is not a false red

**Owner:** Wren
**State:** accepted
**Dispatched:** 2026-10-21

## Problem

`prettier --check --stdin-filepath <path>` reports the file as failing and
prints `(stdin)` rather than the path — on files that are provably clean, so
a bot that checks a committed blob that way is told the committed tree is
badly formatted when it is not.

**The cause is `npx` on a pipe, not prettier's stdin mode.** Wren measured
this and Chief reproduced it independently. The same pipe, the same file, the
same formatter:

```
git show HEAD:README.md | npx prettier --check --stdin-filepath README.md
  → (stdin), exit 1

git show HEAD:README.md | node node_modules/prettier/bin/prettier.cjs --check --stdin-filepath README.md
  → exit 0

git show HEAD:README.md > blob.md
npx prettier --check blob.md
  → All matched files use Prettier code style!, exit 0
```

The pipe carries the file's own bytes, and the same pipe straight into
prettier's CLI is clean. `npx` is the difference. A file redirect instead of
a pipe is clean too, and so is checking the working tree.

**This correction is Wren's, and it is right.** The first draft of this item
blamed the command shape and called prettier's stdin mode at fault. The
symptom was right and the cause was wrong, and a document that names the
wrong cause sends the next reader to look in the wrong place.

## The second way it cries wolf

`prettier --write` is not idempotent on every markdown file. Chief hit it on
a work item while writing this one: an inline code span broken across two
lines.

```
      with `status: 'unknown'`, `capabilities: null` and `lastConnectedAt:
    null` (`apps/server/src/modules/agents/service.ts:212`). WI-008's
```

A markdown code span keeps its content literally, newlines and indentation
included, so the span's content is that newline and those four spaces. When
prettier re-wraps the paragraph it changes the continuation line's
indentation, which changes the content of the code span, which changes the
file, which makes prettier want to change it again.

**It converges on the second pass. It does not fail forever.** Chief measured
it on the real file, `.factory/work/WI-013.md` as committed at `82f6812`:

```
pass 0 (as committed)  3ec0af9
pass 1                 9a8d3e9  → --check exit 1
pass 2                 a35eef4  → --check exit 0
pass 3..6              a35eef4  → --check exit 0
```

So the honest statement is: a `format:check` run right after one
`npm run format` fails on a file that is not wrong. The first draft of this
item said `format:check` "can then never pass", and that was wrong — it took
two passes to settle, and it settled. The fixed version, `2f2dd8c`, is stable
from the first pass.

Either way the fix is one line of writing: do not break an inline code span
across lines.

## Why now

It has already cost this factory real time. Wren's first read of its own
committed clause was a false red, and it had to compare the file line by line
against prettier's own output to establish that there was nothing wrong with
it. A gate that cries wolf is worse than no gate: it sends the next reader
chasing a defect that does not exist, and it teaches them to discount the
output of that gate. It is a line in a document every bot reads.

## Accepted — 2026-10-21, on Probe's review

**State: accepted.** Probe verified the item and found no defect: every
sentence in the two lines is true, and it reproduced each one against the
tools rather than against the item.

```
npm run format:check → All matched files use Prettier code style!
npm run typecheck    → exit 0
npm run test         → exit 0 — 243 passed
the method the document describes, on a committed file → clean, exit 0
  method 1 — the working tree:        exit 0
  method 2 — the blob in a temp file: exit 0
```

**The two findings Probe raised, answered.**

_Observation — the rule says that the `npx` wrapper changes the answer, not
what it changes._ Probe measured the wrapper handing prettier 11,290 bytes
with 251 CRLF, where the blob is 11,033 bytes with none, and concluded that
the wrapper converts the piped newlines, and that `endOfLine: lf` is what
makes prettier see a difference.

**Chief could not reproduce that, and the contract must not say it.** The
bytes handed to a program on the pipe are the file's own in every path Chief
measured — 11,033 bytes, 251 LF, 0 CRLF — whether piped to `node` directly,
piped to a `.cmd` shim, or piped under `cmd.exe`. And prettier's own output
is byte-identical to the blob, 11,033 bytes, LF, no CRLF, in both the `npx`
path and the direct path. No conversion happens here.

What is observable, and what the next editor of the rules section should
write:

- The false red needs the `npx` wrapper **and** a PowerShell pipeline. The
  same command under `cmd.exe` exits 0. The same pipe into prettier's CLI
  directly exits 0 under PowerShell too.
- The remedy is right on every platform: check the working tree, or write
  the blob to a temporary file with its real extension and check that file.
- **Do not attribute it to a newline conversion.** It does not happen here,
  and a rule that names the wrong mechanism sends the next reader to the
  wrong place — which is the failure this item was opened to stop.

_Question — should the rule be scoped to Windows?_ The symptom is the
`npx`-on-a-PowerShell-pipeline combination, and PowerShell is a Windows
thing; the same command under `cmd.exe` is correct. But the advice — check
the working tree, or write the blob to a temp file — is right everywhere,
and a reader on Linux is not being misled into thinking their file is
broken, because the rule says the _invocation_ is wrong, not the file.

**Chief's ruling: the remedy stays universal, and the scope of the symptom
gets one clause.** The second rule, about the inline code span, is genuinely
platform-independent and stays exactly as it is.

**What the product can now do.** Any bot that checks a committed file knows
the two ways the format gate reports a problem that is not there, and knows
what to do instead of chasing a defect that does not exist.
