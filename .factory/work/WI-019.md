# WI-019 — How to check a committed file, so the check is not a false red

**Owner:** Wren
**State:** triage
**Dispatched:** 2026-10-21

## Problem

`prettier --check --stdin-filepath <path>` reports the file as failing, and
prints `(stdin)` rather than the path. It does this on files that are
provably clean, so a bot that checks a committed blob that way is told the
committed tree is badly formatted when it is not.

Chief reproduced it on `README.md` at `734c563`:

```
git show HEAD:README.md | npx prettier --check --stdin-filepath README.md
(stdin)
EXITCODE=1

npx prettier --check README.md
Checking formatting...
All matched files use Prettier code style!
EXITCODE=0
```

The same file, the same formatter, the same commit — one method says it is
clean and the other says it is not, and the one that is wrong is the one that
looks like a gate.

## The second way it cries wolf

`prettier --write` is not idempotent on every markdown file, and when it is
not, `format:check` can never pass. Chief hit it on a work item while
writing this one: an inline code span broken across two lines.

```
      with `status: 'unknown'`, `capabilities: null` and `lastConnectedAt:
    null` (`apps/server/src/modules/agents/service.ts:212`). WI-008's
```

A markdown code span keeps its content literally, newlines and indentation
included, so the span's content is that newline and those four spaces. When
prettier re-wraps the paragraph it changes the continuation line's
indentation, which changes the content of the code span, which changes the
file, which makes prettier want to change it again. Pass one rewrites it,
pass two rewrites it back:

```
prettier --write  .factory/work/WI-013.md  50ms
prettier --write  .factory/work/WI-013.md  50ms
git diff          -    null` (`apps/server/...
                  +  null` (`apps/server/...
```

and `format:check` fails forever, on a file that is not wrong, in a way that
looks exactly like a formatting mistake. The fix is one line of writing: do
not break an inline code span across lines.

## Why now

It has already cost this factory real time. Wren's first read of its own
committed clause was a false red, and it had to compare the file line by line
against prettier's own output to establish that there was nothing wrong with
it. A gate that cries wolf is worse than no gate: it sends the next reader
chasing a defect that does not exist, and it teaches them to discount the
output of that gate. It is a line in a document every bot reads.

## Acceptance criteria

- [ ] `AGENTS.md`, in the part that says how to run the gates, says that
      `prettier --check --stdin-filepath` reports `(stdin)` as failing on
      files that are clean, and says how to check a committed file instead:
      write it to a temporary file with its real extension and check that, or
      check the working tree.
- [ ] The line names the false red exactly — `(stdin)`, exit 1 — so a reader
      who has already seen it recognises it and does not go looking for a
      defect.
- [ ] The same part of `AGENTS.md` says that an inline code span must not be
      broken across lines in markdown, because prettier's formatter is not
      idempotent on one and `format:check` can then never pass. It says why
      in a sentence: a code span keeps its content literally, newlines and
      indentation included.
- [ ] `npm run format:check` still passes.

## Not in scope

- No change to the formatter, to the format gate, or to the configuration.
- No new script. This is a line in a document, not a project.
- No change to the other role briefs in `.factory/`. If the bots who read
  those need it too, that is Wren's call to make in the same edit.

## Gates

- The method the document describes, run on a committed file, reports it
