# WI-167 — A picture the owner attaches reaches the runtime

**Owner:** the implementing agent, one session.
**Verifier:** an independent reviewer is named in the dispatch brief.
**State:** accepted and closed — the installed Codex 0.163.0 read a picture the
owner attached and answered from it, the room showed the picture, and the
demonstration's own finding — the route validating against a stale copy of the
contract's content parts — is fixed and proved by a test.
**Branch:** `wi/167-content-images`, cut from `origin/main` at `3ed54a9`.

## Problem

A picture the owner attached never crossed the adapter boundary, and the
product said so in a way that was true and wrong at the same time:

> You cannot see `marker.png`, because its bytes are not text.

That is true. It is not the whole truth: both protocols the product speaks have
a shape for a picture, and the runtime can read one. The owner attached a
picture, and the agent answered as if it had not seen it.

Three things were missing, and all three are the product's own:

1. **The turn part had no image kind.** `AgentTurnPart` was a union with one
   kind, `file`, and the file's content is text. A picture had no shape to
   cross in.
2. **The resolver gave up on bytes.** `apps/worker/src/content-parts.ts` read
   the resource as UTF-8 and left a file out with the reason _"the file is not
   text"_ when the bytes were not text.
3. **The routes had nowhere to put one.** The ACP protocol's prompt is a list
   of content blocks and one of them is `{type:'image', mimeType, data}`; the
   pinned App Server protocol's `UserInput` takes `{type:'image', url|fileId}`
   and `{type:'localImage', path}`. Neither route was asked.

The adapters' matrix said so in its own words, before anything was built:

> The protocol has an `image` block that takes bytes, and that mapping is its
> own work.

## The fix

- **The part.** A picture is a part of its own, and it travels as bytes: the
  bytes are in the part, for the same reason the text was — an adapter is given
  a resource id it cannot follow, and a path it cannot open.
- **The capability.** A picture travels on a capability of its own,
  `acceptsImages`, because a route that takes a file's words is not thereby a
  route that takes a picture's bytes. Absent means absent.
- **Each route's own shape.** The ACP route sends the protocol's `image`
  block. The Codex App Server route sends the bytes as an image by url — a data
  url, and not a local image by path, because a path is a path on the runtime's
  machine and this picture is not on it.
- **The reason is the true one.** A turn that could not carry a picture says
  that the route cannot carry pictures, and not that the bytes are not text.
- **The panel refuses what cannot be carried**, and names the agent that
  cannot take it.

## What was measured first

The runtime's half, before anything was designed: a probe drove the installed
Codex 0.163.0 through both of the protocol's image shapes, with one picture —
a PNG that says `IMAGE-MARKER-4F2` — and the runtime read it either way. The
choice between the two shapes was therefore not about what the runtime accepts,
and the product's own rule decided it: the bytes travel.
