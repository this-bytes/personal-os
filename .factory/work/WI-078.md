## The problem

**`CONTRACTS.md` publishes a shape the code refuses.** The contract publishes

```ts
interface ResolveExecutionInput {
  outcome: 'completed' | 'failed';
  note?: string;
}
```

**with no bound on the note.** The code bounds it:

```ts
const resolveSchema = z.object({
  outcome: z.enum(['completed', 'failed']),
  note: z.string().max(2_000).optional(),
});
```

(`apps/server/src/api/executions.ts:5-10`)

**So a client written against the published shape may send a longer note and
be refused with `validation_failed`** — a refusal the contract does not
promise and cannot explain. **This is a gap against WI-031's own acceptance
criterion 7**, which asks that _"the published shape matches the code exactly,
member for member, checked against the implementation, not against the
proposal above."_ Four fields against three is not member for member; a string
against a capped string is not either.

**Probe found it while verifying WI-031 and routed it here rather than letting
it go unrecorded** — which is the behaviour the factory wants from a verifier,
and the reason this item exists at all.

**Measure the cap yourself before you write it.** The number above is what the
code says today; the code is the authority and the brief is not.
