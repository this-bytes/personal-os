# WI-128 — The owner can set the autonomy policy, not only read it

**Owner:** worker, under Chief.
**Verifier:** a verifier who wrote none of this.

**State:** accepted — 2026-10-22, on Probe's verdict (`task_55ff886ce54c`), with the lead's

## The gap

The effective policy is readable — `GET /api/autonomy-policy` returns it with the level
that decided each value, and the `autonomy.read` MCP tool returns it too — and it was
**writable nowhere**.

- `autonomyPolicy` appeared **nowhere** in `apps/server/src/api/`.
- `PATCH /api/workspaces/:id` validated its body with a schema naming `name`,
  `description` and `autonomyMode` and nothing else. `parseBody` calls `safeParse` on a
  non-strict Zod object, so a client that sent `autonomyPolicy` got a **200 and no
  change** — the field was silently stripped, not refused.
- The **service** already accepted it: `update()`'s patch type named `autonomyPolicy`,
  and WI-118's write-both-ways logic already wrote a policy and the mode column together.
  **The write path existed in the service and was unreachable through the API.**
- `goals.autonomyPolicy` was worse: `POST /api/goals` accepted `workspaceId`, `title` and
  `description` only, and goals have no update route at all.

So F5 in WI-082's verdict stood: **every limit, every action list and every approval list
could only be set by editing the database.** And the contract said the limits _are_
enforced — the worker holds a turn to the effective policy, the MCP surface refuses an
action the policy does not allow, and the daily cap bites. **All of that machinery was
there, and the owner had no way to feed it.**

## What this item does

**It gives the owner a write path for the workspace's own policy.** It does not change
what any limit means, and it does not touch the goal's policy.

1. **`PATCH /api/workspaces/:id` accepts `autonomyPolicy`.** Validated against a newly
   published patch shape, `autonomyPolicyPatchSchema`
   (`packages/contracts/src/autonomy.ts:34`). The two action lists are constrained to the
   published vocabulary — `message.send`, `tool.call`, `artifact.create` — because the
   contract already says a policy that names something the system does not understand
   _refuses it rather than passing it_, and a silent strip is not a refusal.
2. **A change merges into the policy; it does not replace it.** The owner says "the turn
   limit is twenty" and the action list they set earlier stays
   (`apps/server/src/modules/workspaces/service.ts:109`). **An absent list is left alone
   and an empty list clears it**, so clearing is still deliberate.
3. **The mode still writes both ways.** A patch that names a mode sets the column the
   panel shows _and_ the policy the resolver reads; a patch that names no mode leaves
   both alone (`apps/server/src/modules/workspaces/service.ts:113`). WI-118's rule is
   unchanged: the mode the owner sets is the mode that is in force.
4. **The change is in the audit trail.** `workspace.updated` carries the policy the owner
   sent, so the trail says what was set and not only that something was.

## What this item does not do

- **The goal's policy is still unwritable.** Goals have no update route and this item
  does not add one. Recorded in the contract as a known limitation, not left to be
  found.
- **The mode is still enforced nowhere.** `manual` does not gate delegation (WI-124).
  This item is about the owner being able to _state_ the policy, not about the mode
  becoming a control.
- **The effective policy is still composed, not written.** The route writes the
  _workspace's own_ policy. The effective policy is what the resolver computes out of
  the workspace's, the goal's and the conversation's; there is no such row to write.

## The contract changes

- The route table's `PATCH /api/workspaces/:id` row names the field it now accepts.
- A new entry, **the autonomy-policy write**: the patch shape, the merge rule, the
  action vocabulary, the mode rule, and the goal's limitation.
- A note in the autonomy policy section pointing at it, because the policy section is
  where a reader looks for what a policy _is_.
- A migration note: there was nothing before this write, so there is nothing to migrate.

## The proof

`apps/server/src/__tests__/autonomy-policy-write.test.ts` — eight cases:

- the owner sets the limits and the action list, and the policy in force reads them back
  with the workspace named as the level that decided them;
- a second change merges rather than replaces;
- an empty list clears, deliberately;
- the mode lands in both of the places a workspace keeps it;
- the mode alone still lands in both;
- an action the system does not know is refused with `422 validation_failed`, and the
  policy is untouched by the refusal;
- a limit that is not a limit is refused;
- the change is in the audit trail.

**Four mutation proofs**, each restored afterwards:

| Mutation                                                         | What it takes away       | Caught by                                                  |
| ---------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------- |
| the policy change replaces the policy instead of merging into it | the merge                | "merges a change into the policy rather than replacing it" |
| the route stops accepting the policy at all                      | the write path           | "sets the limits and the action list the policy carries"   |
| the policy no longer sets the mode column                        | the write-both-ways rule | "writes the mode into both of the places it is kept"       |
| an action the system does not know is accepted                   | the closed vocabulary    | "refuses an action the system does not know"               |

## One gate was corrected rather than satisfied

WI-085's attack suite asserts that only the schema, the resolver and the two CRUD
services may name the `autonomyPolicy` column — decision 1's _"no enforcement point
reads a policy row itself"_. **The route that writes a policy names the field of a
published request body, and that is the same category as the two services already
allowed**: it reads no row and it resolves nothing. The service reads the row and writes
it, and the resolver is still the only place a policy is resolved.

So `apps/server/src/api/workspaces.ts` joined the suite's allowed set, with the reason
written beside it. **The substance of the gate is unchanged** — a file that _read_ the
column would still be an offender, and the suite's other thirty-two cases are untouched.
**This is recorded here rather than left to be found**, because it changes a test another
session wrote, and the owner of that test has been told.
