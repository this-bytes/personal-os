# WI-044 — The licence check that covers this repository's own sources

Opened by Chief, from the review that corrected WI-034
Numbered — WI-044, taken by the session that owns the number
space. WI-030 through WI-038 are this session's; WI-024 through WI-029 and
WI-039 through WI-043 are the other Chief session's.

## The problem

The owner's answer of 2026-10-21 08:54 was that **the borrow rule becomes a
check, not a claim**. WI-038 is that check, and it reads the **dependency
set**: the licences recorded in WI-036, against the licences in the lockfile.
A licence that changes, or an unapproved licence that arrives, fails the
build.

**That check cannot see this repository's own tree.** Source vendored into
the repository — a file copied in, a snippet inlined, a font, a fixture of
real code — carries its own licence, and the dependency-set check looks at
the lockfile, so it never sees it. The owner's own hard case is exactly this:
the rule is about what this repository borrows, and a vendored file is
borrowed.

**So the check the owner funded is narrower than the rule the owner meant**,
and the gap is a want rather than a defect: nothing is broken, and nothing
is being done about it.

## Acceptance criteria

- [ ] **The set of things the check looks at is published**, and it says
      plainly what it does not look at, so the rule and the check agree.
- [ ] **The vendored sources in this repository are inventoried**, each with
      the licence read from the file it was read from — the same discipline
      as WI-036, applied to the tree rather than the lockfile.
- [ ] **A vendored source with an unapproved licence fails the build**, with
      the file named and the licence it carries. A check that reads the
      lockfile and stops there is not this criterion.
- [ ] **The rule's wording covers the tree as well as the lockfile**, in the
      place the rule is written, so the next reader is not told the rule is
      stronger than the check.
- [ ] A test or check proves a deliberately vendored unapproved source fails.
      A gate that has never been seen to fail is a gate that cannot fail.

## Not in scope

- **The dependency gate itself.** That is WI-038, and it lands first.
- **The recorded licences.** That is WI-036.
- **Removing what is vendored.** This item checks what is there. Whether
  something should be vendored at all is a different question, and it is
  the owner's.
- **This repository's own licence.** Still undecided, by the owner's word.

## Gates

- `npm run format:check`
- The check must be seen to fail when a vendored unapproved source is added,
  which is the only proof that it can fail.

## Notes

**Why it is funded but not dispatched.** The owner's answer funded the
_dependency_ gate, and the dependency gate is the cheaper half of the rule.
This half is the one that needs an inventory before it can have a check, and
the inventory is worth doing **once the repository's visibility is decided**:
the owner's answer was "private for now — decide visibility later", and a
vendored-source licence matters most at the moment the repository goes
public. Numbered now so it is not lost; dispatched when the visibility
decision lands and the inventory can be written against a settled repository.

**What it would have been, if it were a defect.** It is not one: nothing
violates the rule today, because the rule does not say this. It is a want
that came out of a review, and the review that found it is the record
behind it.
