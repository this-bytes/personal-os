## Problem

An agent connection in the panel is a transport: a name, an adapter type, an
opaque config reference and an enabled flag
(`packages/contracts/src/agent.ts:21-28`). The panel shows a capability
badge and a tool count (`apps/web/src/pages/Agents.tsx:183-210`). There is
nowhere for the owner to say **what this agent is** — its role, its standing
instructions — and nowhere for the agent to be told, per conversation, who it
is speaking as.

The consequence is that "talking to an agent" is indistinguishable from
"calling an endpoint". `systemPrompt` exists on exactly one adapter shape,
the `model` one (`packages/contracts/src/adapter-config.ts:92`), so the CLI
and ACP adapters — the ones that matter — have no place to carry a role at
all.

This is the largest single piece of the owner's open priority want, W-2:
_"talking to agents is the job that should genuinely better"_.

## Why now

W-2 is the one want still marked `open` in `.factory/INTAKE.md`, and the
priority job the owner named when they scoped this factory. Everything else
in the queue is either a smaller slice of W-2 or a defect in the ledger
around it.

The plugin's insight, which this item translates, is that a bot is a
_persona_ — a named role with standing instructions — and the panel is where
a relationship with an agent lives, so it should be shaped like one. It also
matches how this factory itself runs: named bots with briefs.

## The contract shape, sized by Chief

The owner settled the direction; the shape is mine to size. Proposed, for the
owner's approval:

```ts
// packages/contracts/src/agent.ts
/** What an agent is, and how it should behave. */
export const personaSchema = z.object({
  /** One line, shown to the owner. */
  role: z.string().min(1).max(200).optional(),
  /** Standing instructions, shown to the agent. */
  instructions: z.string().max(8_000).optional(),
});
export type Persona = z.infer<typeof personaSchema>;
```

- `agentConnectionSchema` gains `persona: personaSchema.optional()` — the
  **base** persona.
- `participantSchema` (`packages/contracts/src/conversation.ts:27-34`) gains
  `personaOverride: personaSchema.optional()` — the override lives on the
  participant, so it names the agent it applies to through the existing
  `agentConnectionId`, and one conversation can treat one participant
  differently without touching the rest.

**Resolution — most specific first, whole entity.** If the participant's
override sets `role` or `instructions`, the override _is_ the persona and the
connection's base is not consulted; otherwise the connection's base is the
persona; otherwise the agent runs with its runtime's own default framing.

> Chief's note, and the one thing to overrule if it is wrong: I read
> "override" as replacement rather than per-field merge, because a merge
> invites a half-overridden persona — a conversation that sets only `role`
> silently keeping the connection's `instructions` is a stranger. If the owner
> prefers per-field, it is a one-line change to the resolver and nothing else
> moves.

**One resolver, one truth.** The resolution lives in the contracts package as
a pure function, so the server, the worker and the web client cannot disagree
about which persona is in force.

**Injection.** The resolved persona is prepended to the turn context the
worker already builds (`apps/worker/src/executor.ts:234-240`, which passes
`context: contextText` into `AgentTurnInput`). No new field on
`AgentTurnInput` is needed, and no adapter is asked to re-implement a harness.

**Display.** A persona is shown with its source, so the panel never shows an
overridden value as if it were the base. The source is one of
`conversation` | `connection` | `default`.

## Acceptance criteria

- [ ] An agent connection can carry a role and standing instructions, and both
      are returned by `GET /api/agents/:id`.
- [ ] A conversation can override the persona for a named agent participant.
- [ ] The resolved persona is the conversation override where one is set, and
      the connection's base otherwise; a conversation with neither uses the
      runtime's own default.
- [ ] The panel shows **which** persona is in force, and names its source —
      a conversation that overrides the role does not silently display the
      connection's value.
- [ ] The role is shown on the agent card (`apps/web/src/pages/Agents.tsx`),
      in the conversation header (`apps/web/src/pages/ConversationDetail.tsx`)
      and in the waiting list (`apps/web/src/components/WaitingList.tsx`).
- [ ] The resolved instructions reach the adapter on the next turn, without the
      owner retyping them.
- [ ] The persona frames the turn only — it does not replace or duplicate the
      external runtime's own harness or instruction file.
- [ ] `CONTRACTS.md` carries the persona entry, with a migration note.
- [ ] `npm run typecheck` and `npm run test` pass, and the behaviour is
      covered by a named test.

## Not in scope

- **Per-agent memory scope.** A separate candidate (C-11), and a second
  published-contract change. The owner's decision on persona placement
  explicitly excluded it.
- Changing how the worker builds a turn beyond adding the resolved persona to
  the context it already builds.
- Any avatar, skin, colour or appearance.
- A second instruction system that can contradict the runtime's own.
- Message reactions and per-agent usage statistics (C-13) — cosmetic, and
  they solve nothing the owner is blocked on.

## Accepted — 2026-10-21

**What the product can now do.** An agent the owner talks to has a persona:
the connection sets the base, a conversation may override it, and the panel
says **which persona is in force and where it came from**. The owner's own
rules are framed into the agent's turn by one channel at the head of the
context, and no adapter reads the persona — it frames the turn, it never
competes with the runtime's own harness.

**Three parties, separated.** Cog wrote it, Probe verified it, Chief accepted
it.

**What Probe verified.** All nine of the item's acceptance criteria are met
against the code and the published contract, and the three things Chief had

- the persona is **one channel at the head of the context**, with no adapter

- an override **replaces the base whole** — the base is never consulted

**Chief's answers to Probe's two questions.**

1. **The agent card's badge stays as it is.** It reads `connection`, and that
   is right: the badge names the **source**, and the owner asked for exactly
   that — which persona is in force, and where it came from. The card shows
   the connection's base because that _is_ the agent's standing persona; a
   conversation's override is shown where the conversation is. The case Probe
   raises — every conversation overrides, so the base is in force nowhere — is
   the card telling the truth about the connection, not about the
   conversations.
2. **The conversation header is not pinned separately, and here is why.** It
   resolves through the same `resolvePersona` call and renders the same shared
   `PersonaBadge` component that the waiting-list test now pins. A second
   page-level test of the same resolver is duplication, not coverage. The day
   the header stops using the shared badge is the day it needs its own pin.

## Notes

**Published boundary.** Two published interfaces change, and they are quoted
in `CONTRACTS.md` in full:

- `CONTRACTS.md:142-148` — `interface AgentConnection { id, name, adapterType,
configRef, enabled }` gains `persona`.
- `CONTRACTS.md:38-44` — `interface Participant { id, conversationId, type,
agentConnectionId?, displayName }` gains `personaOverride`.

The factory stops there for owner approval. The migration plan is part of the
contract change, not an afterthought: both new fields are optional, so a
connection and a participant written before this item stay valid, and
`resolvePersona` returns `default` for them. Nothing is rewritten, so the
migration is additive and the plan is one paragraph.

display criterion touches `apps/web/src/components/WaitingList.tsx`, which is

criterion itself; if WI-004 is still held when this item is otherwise
complete, the waiting-list line moves to a follow-up item and **this item is
not held open waiting for it**. The criterion that matters — the panel shows
which persona is in force — is met here regardless.
