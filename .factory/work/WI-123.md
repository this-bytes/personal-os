# WI-123 — Publish `approval.decided`, so a decided approval can leave the waiting list

**Numbered:** 2026-10-22. **WI-123** is the number this item took. It is the
next free number in the block published in `.factory/INTAKE.md` after WI-122
was taken, and it was read immediately before it was taken.

## The decision

The owner was asked whether the product should publish an `approval.decided`
event, because `POST /api/approvals/:id/decide` publishes nothing, so a
decided approval has a way into the waiting list and no way out of it. The
owner answered:

> **Yes — publish it, and the contract changes with it.**

So the event is published, and the change to the published contract comes with
it: a migration note, because a published contract is not changed without one.

## The defect

An approval is raised, the owner decides it, the decision is recorded, and the
turn either continues or closes. All of that is durable and all of it is
queryable. But **nothing is published.** A client that watches the event
stream learns that an approval was raised — or does it — and then learns
nothing about the answer.

The waiting list therefore has a way in and no way out. A client that shows
"waiting for you" cannot be told, by the stream, that the answer has arrived.
It has to poll, or it has to re-read the approval, and neither is what an
event stream is for.

## What this item does

1. **A published `approvalSchema`.** The approval crosses the server-to-client
   boundary when it is decided, so its shape belongs in `packages/contracts`
   with the rest of the published shapes. The server's own `Approval` type
   stops being a private copy of a shape that now has a published owner.
2. **An `approval.decided` server event.** It carries the approval, so a
   client that receives it can take the item off the waiting list.
3. **The event is published where the decision is recorded.** In
   `decideApproval`, right after the audit entry, so the published event and
   the recorded decision cannot disagree about which one happened first.
4. **The contract changes with it.** The event vocabulary gains a member, the
   contract's route table gains the row, and a migration note says what a
   client that was not expecting the event should do — which is nothing, since
   the event is additive.

## The acceptance criteria

- [x] **The shape is published.** `approvalSchema` is in `packages/contracts`
      and the server's `Approval` is derived from it, so the two cannot drift.
- [x] **The event is published.** Deciding an approval publishes an
      `approval.decided` event on the stream.
- [x] **The event is published once, at the right moment.** The event follows
      the decision and the audit entry, and it is published whether the turn
      continued or closed — the outcome does not change the fact that it was
      decided.
- [x] **The contract changes with it.** The vocabulary, the route table and a
      migration note.
- [x] **The tests prove it.** A test that decides an approval and reads the
      event back out of the stream, and a test that proves the event is not
      published when nothing was decided.

## The proof

The event is published by the same code path that records the decision, so
there is one place where the fact is created and one place where it is
published. The test reads the event back out of the event log rather than
asserting on the return value of the publish call, so it proves the event
reached the stream a client reads.

## What this item does not do

It does not change what an approval means, how long one lives, or who may
decide one. It does not change the HTTP response of the decide route, which
already returns the approval, the execution, the outcome and the detail. It
adds the published form of a fact the product already records.
