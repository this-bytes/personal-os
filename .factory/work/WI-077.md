## The problem, in the owner's words

**"Plan and implement the agents adaptor domain in personal-os. Make this
congestive with the chat domain."**

The chat domain runs on one spine: the server decides, the worker runs. The
agents/adapter domain does not. It is the one place in the product where the
API server runs agent code in its own process, and the rules say it must not.

Measured, not described:

- `apps/server/src/modules/agents/service.ts:293-297` — the server builds the
  adapter (`registry.create(...)`) and calls `adapter.connect(...)` inside the
  API request.
- `packages/agent-adapters/src/acp.ts:50-51` — `connect()` calls `this.spawn()`,
  which **starts the agent process**. In the API server, not in the worker.
- `packages/agent-adapters/src/a2a.ts` — `connect()` fetches the remote agent
  card, an outbound request from the API server.
- `apps/server/src/runtime.ts:1` — the server imports the adapter registry, so
  the dependency is in the build, not only in a comment.
- `AGENTS.md` — _"The API server never runs an agent. It creates an
  `executions` row and enqueues a job. The worker runs it. If you find yourself
  importing an adapter into `apps/server`, stop and reconsider."_
- `apps/worker/src/index.ts:8-12` — the worker's own reason for existing: _"a
  failing or compromised agent CLI must never be able to take the API server
  down."_

The ACP probe is the sharp end of it. A connection to a broken agent CLI is
probed by the API server: the server spawns the agent's process, holds its
stderr, and reads its handshake — with the server's secret key in the same
process.

## What the chat domain does instead, and what "congruent" means here

The chat domain's shape, in `apps/server/src/modules/conversations/dispatch.ts`:

1. The server decides — `planRouting` in `routing.ts`, a pure function with its
   own test file.
2. The server records — an `executions` row.
3. The server enqueues — a `chat.turn` job.
4. The worker runs — `executeChatTurn` in `apps/worker/src/executor.ts:173`.
5. The worker writes the result — a message row, and an event.
6. The server streams — the client learns it from the event log.

The adapter domain skips steps 4 and 5. This item gives it the same six steps.
"Congruent" is taken in the repo's own sense: **one spine, one place where each
rule lives.**

## Acceptance criteria

- [x] **The API server cannot run an adapter.** No file under `apps/server/src`
      imports `@personal-os/agent-adapters`, and the server package no longer
      depends on it. The dependency graph enforces the rule; the rule is not
      only in a comment.
- [x] **A probe is a queued request.** `POST /api/agents` and
      `POST /api/agents/:id/probe` record the request and enqueue an
      `agent.probe` job. They do not connect.
- [x] **The worker runs the probe.** It builds the adapter, connects, and writes
      the capabilities, the status and the error to the connection row; it
      closes the execution row; it publishes the `agent.status` event.
- [x] **The probe has a deadline.** It is the adapter's own `timeoutSeconds`,
      the same one its turns get. The worker runs one job at a time, so an
      agent that accepts a connection and then says nothing must not stop
      every other piece of work in the product.
- [x] **The client learns the result from the event stream**, which it already
      folds into its cache (`apps/web/src/state/events.tsx:108-124`).
- [x] **The rule is published.** `CONTRACTS.md` Contract 2 says where a probe
      runs and how the owner sees the answer; the HTTP surface table says the
      route records a request.
- [x] **A test proves it.** A worker test proves the probe writes the
      capabilities; a server test proves the route enqueues and does not
      connect; a boundary test proves the server cannot import an adapter.
- [x] `npm run typecheck`, `npm run test`, `npm run format:check`,
      `npm run build` and `npx tsx scripts/smoke.ts` pass.

## Not in scope

- **The domain map.** `docs/domains.md` and the boundary check land with
  WI-046, which is the strategy session's merge. This item does not compete
  with it: it adds no module directory, so the map does not change.
- **The routing rules.** Which agent answers which message stays in the chat
  domain's `routing.ts`. The adapter domain decides whether an adapter _can_ be
  reached, never who speaks.
- **Probing on edit.** A configuration edit still leaves the connection
  `unknown` until it is probed. That is today's behaviour and it is not the
  defect.
- **The measures route.** It counts work, not probes, and does not change.
