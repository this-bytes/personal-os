# WI-148 — The browser suite runs the worker, so the chat is proved end to end

**Owner:** the contract lane — the session that owns `CONTRACTS.md` while its
slices are in flight.
**Verifier:** Probe, who reviews the slice before it is accepted.
**State:** accepted — the browser suite runs the worker, so the owner's message
reaches the worker and the agent's answer lands in the room. It landed in the
merge `14724cd` and on `main` at `19bedad`: the harness is
`scripts/e2e-server.mjs` and the proof is `apps/web/e2e/agent-answer.spec.ts`.
Closed under ADR 0012 on 2026-10-23.
**Branch:** none — the slice landed on `main`.
**Base:** `6c2ea06`

## Problem

**The browser suite could prove everything around a turn and none of the turn.**

`scripts/e2e-server.mjs` started the API server and nothing else. The server
never runs an agent — it writes an `executions` row and enqueues a job, and
`apps/worker/src/index.ts` is what claims the job and runs the adapter. **With no
worker in the suite, no agent ever answered.** The chat-surface test could show
the owner's own Markdown in the transcript and `turn.admitted` in the trace,
because both of those are written by the server before the worker is involved.

That is the difference between a room and a conversation. The goal's acceptance
is a working end-to-end chat experience inside Personal OS, and the one thing
the suite could not show was the answer.

## What changed

**The harness starts the worker, after the server is answering** — the order the
deployment uses (`deploy/compose.yaml` gives the worker
`depends_on: server: condition: service_healthy`). The worker opens the
database the server has already migrated, and the two share one SQLite file in
WAL mode, exactly as they do in the deployment.

**The key that opens the encrypted configuration is made in the harness.** Both
processes read `secret.key` out of the data directory, and either one would
generate a key if the file were not there yet. The harness writes it into the
environment of both, so the worker cannot end up with a different key from the
server and be unable to read what the server wrote.

## The proof

`apps/web/e2e/agent-answer.spec.ts` — the owner's message reaches the worker,
the worker runs the adapter, and the answer lands in the room:

- the reply is a message of its own, marked `agent`, and it names the adapter
  that wrote it (`echo`);
- nothing is still `streaming` when it arrives, and the trace shows
  `message.completed`.

The chain is the product's own: the server admits the turn and enqueues the
job, the worker claims the job and runs the adapter, the adapter's events are
written to the event log, and the server streams them to the browser.

## The one existing test that had to change

`apps/web/e2e/chat-surface.spec.ts` stopped a turn and expected the panel to
say _"it will not run"_ — true while there was no worker, because the turn
stayed in the queue. **With a worker, the turn starts**, so the stop now reaches
a turn that is in flight and the panel says _"the runtime may finish the
current turn"_. The test uses an echo agent with a delay so the turn is
deterministically running when the stop arrives.

The queued case is not lost: `apps/server/src/__tests__/turn-activity.test.ts`
proves it where the queue is under the test's control, and it is named in the
browser test's comment.

## Scope and compatibility

**Owned paths**

- `scripts/e2e-server.mjs` — the harness starts the worker.
- `apps/web/e2e/agent-answer.spec.ts` — the proof.
- `apps/web/e2e/chat-surface.spec.ts` — the stop case, updated to the world
  with a worker.

**Compatibility.** No published shape changed, and no product behaviour changed:
the worker was always the thing that ran the agent. What changed is that the
browser suite now runs the half of the product that answers.

## Acceptance criteria

- [x] The browser suite runs the worker, in the deployment's order.
- [x] A browser test proves the owner's message reaches the worker, the worker
      runs the adapter, and the answer lands in the room as the agent's message.
- [x] The suite is green, and no existing proof was weakened — the queued-turn
      case moved to the server test that owns the queue.
- [x] The runtime is named honestly: the adapter here is the built-in `echo`
      agent, not one of the five named runtimes.

## Not in scope

- **The five native runtimes.** The presets exist and every one of them is
  marked unverified; running one of them is the R1 acceptance demonstration and
  is not done here.
- **Steering.** `delivery: 'steer'` was published and routed and nothing acted on
  it when this item was written. **WI-152 has since made it work**, and it is
  published as implemented and held by the claim row
  `the-steer-and-queue-wi-152`. It is still out of this item's scope.
- **Attachments.** They had no client surface when this item was written.
  **WI-151 has since given them one**, and it is published as implemented and

## 2026-10-23 — The lead: the stop case holds the turn it asks of

**The case was racing the clock, not the rendering.** The stop case in
`apps/web/e2e/chat-surface.spec.ts` stopped a running turn and failed at the
stop: the server had already finished the turn, so the button was disabled with
"The turn has already finished." and the click waited for a button that would
never be enabled again. Probe measured the cause — the status region and the
stop button are one payload, so they cannot disagree; the turn's life is the
agent's hold, and the worker's click actionability wait (42–54 ms on a quiet
machine) grows under load while the trace is admitted and the panel re-renders,
so the click retries — and while it retries, the turn ends.

**The hold is fifteen seconds, and the case waits for the turn to be over.**
Long enough to outlast the case's own work, and the wait frees the worker for
the next test: without it the next test's agent did not answer inside its 10 s
expect timeout, because the worker was still on the held turn.

**No assertion was weakened.** The assertions are the same ones in the same
order, plus a wait for the turn to be over. No test was deleted, skipped or
loosened; no `it.fails`, `.skip` or `.only`. Nothing in the panel needed to
change.

**Measured:** the whole browser suite 35 passed, and this case 5 times in a row.
