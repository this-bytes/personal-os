# WI-023 — CI proves the gate works against a deployment that already has an owner

**Owner:** Chief
**Verifier:** Probe
**State:** triage — sized by Chief, and blocked on the owner's nod for the
push path
**Opened:** 2026-10-21 by Chief, from the question Probe asked at the end of
its [WI-015](WI-015.md) report
**Blocked:** the pipeline has never run on GitHub. This item adds a step to a
job that has never run on the platform it runs on, so Chief is not putting it
in front of the owner as a change to a live pipeline until the pipeline has
run once. See "Why this waits" below.

## Problem

[WI-015](WI-015.md) made `scripts/verify-stack.ts` work against a deployment
that already has an owner: it uses `PERSONAL_OS_OWNER_TOKEN` as a bearer
credential when one is configured, and falls back to the owner account when
one is not. Probe proved it by reverting the script and watching the test
fail with the defect's own message, and by running the check against a live
deployment initialised with an owner the script does not know.

**CI never exercises that path.** Probe found it and asked Chief:

> `deploy/compose.yaml:32,63` forwards the variable to both containers, but
> `.github/workflows/ci.yml` never sets it — only `PERSONAL_OS_SECRET_KEY`
> (`ci.yml:109-113`). So in CI the server has no static token and the check
> runs the account path against a stack it just created, and the new path is
> never exercised by CI. … Should the container job set the token so the new
> path is exercised in CI?

Chief answered in [WI-015](WI-015.md): **no, the container job should keep
running the account path.** The job builds a fresh stack and proves the thing
that ships works from nothing. The token path is for a deployment that
_already has an owner_, and the container job's stack is destroyed at the end
of every run (`down -v`), so it never is that deployment. Setting the token
would exercise the token branch against a stack with no owner — the case it
is least about — and would stop the job proving the account path against a
fresh deployment — the case it is most about.

**That answer leaves a real gap, and this item is the gap.** The path Probe
built has no exercise on the platform CI runs on. A developer pointing the
gate at their own instance gets it; the pipeline does not.

## What this item does

**It adds a step to the container job, after the existing one.** The existing
step keeps proving the account path against a fresh deployment. This item
adds a second check, in the same job, against the same stack, that proves
the token path:

1. The stack is already up and the account path has passed.
2. The owner is initialised with a password that is **not** the script's, so
   the account path provably cannot get in — the same shape Probe ran
   locally against real Docker.
3. The stack is restarted with `PERSONAL_OS_OWNER_TOKEN` in it.
4. The check runs again, with the token in the environment, and must be green.

**The order matters and is the point.** If the token were set from the start,
the job would prove one path and lose the other. Running both, in that
order, means the job proves that a fresh deployment works _and_ that a
deployment with an existing owner works.

## Acceptance criteria

- [ ] The container job still runs the account-path check against a fresh
      stack, and it is still green. This item adds to the job; it does not
      replace what the job proves.
- [ ] A second step in the same job proves the token path: the stack has an
      owner whose password is not the script's, the token is configured, and
      the check is green.
- [ ] The second step is proved to fail when it should. A step that passes
      because the owner was never initialised with a different password
      proves nothing, so the step must show the 401 first and the green
      after — the same observation Probe made locally, in CI.
- [ ] The remote guard is untouched: the check still refuses a non-local
      deployment without `--allow-remote`, before the first request.
- [ ] No secret is committed and none is echoed. The token is generated per
      run, masked, and written the way `PERSONAL_OS_SECRET_KEY` is — into
      `$GITHUB_ENV` in a step of its own, because a variable written there is
      available to the steps that follow it and not to the step that writes
      it.
- [ ] The teardown step still works. It parses the same environment file, so
      a token left in it must not break `docker compose … down -v`.
- [ ] `actionlint` is clean, and the whole job sequence is run locally
      against real Docker before it is pushed — the same way WI-005's
      container job was.

## Not in scope

- **Changing what the container job proves.** The account path against a
  fresh deployment stays. Chief's answer to Probe's question is recorded in
  WI-015 and this item does not reopen it.
- **The owner token's own behaviour.** How the server issues, stores or
  revokes `PERSONAL_OS_OWNER_TOKEN` is product behaviour and is not this
  item's business.
- **`deploy/compose.yaml`.** It already forwards the variable to both
  containers (`compose.yaml:32,63`); nothing there needs to change.
- **The `verify:stack` script.** WI-015 owns it and it is accepted.
- The pipeline running on GitHub at all. That is the owner's decision and it
  is not this item's to make.

## Why this waits

**The pipeline has never run on GitHub.** The machine cannot reach
github.com from here, so nothing in CI has ever executed on its real
platform. Two defects that were found in WI-005 would have failed the first
real run, and they were fixed without anyone seeing CI run.

Adding a step to a job that has never run is not something to do quietly. The
honest order is:

1. **The owner decides the push path** — give this machine a way to reach
   github.com, or accept in writing that the pipeline is unproven on its real
   platform.
2. **The pipeline runs once**, on the real platform, with the job as it is
   today. That run is worth more than any change to the job, because it
   converts "unproven" into "proven".
3. **Then this item**, and the second step gets added to a job that is known
   to work.

Chief is not going to add an unexercised step to a pipeline that has never
executed, in order to make the pipeline prove more. Chief is going to get the
pipeline to run, and then make it prove more. Step 1 is the owner's and it is
the largest open risk in the whole factory.

## Notes

**Why Chief owns this item.** `.github/workflows/**` is Chief's file by the
ownership table. And the acceptance rule applies to Chief the same as to
anyone else: "Never accept your own work, whoever wrote it." Chief writing
this workflow change does not let Chief accept it — it goes to Probe for
review, and Chief's own output goes to Probe like everyone else's.

**Why it is not folded into WI-015.** WI-015 is Probe's item, about a script
and its tests, and it is accepted. Folding a workflow step into an accepted
item would put an unexercised CI change behind a green acceptance, and the
next reader could not tell which half of the acceptance the step belonged to.
"Stay inside the work item" cuts both ways: a finding belongs to its own item
in both directions.

**Size.** Small-to-medium: one workflow file, one extra step, and a local
run of the sequence against real Docker.
