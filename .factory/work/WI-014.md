# WI-014 — The documentation says what the password recovery costs

**Approved:** 2026-10-20 — Chief's judgement on WI-002 ("a change or a plain
statement of the exposure … it is Chief's"), plus Probe's verification
finding, which is evidence rather than preference.

## Problem

The owner's forgotten password is replaced by handing the new password to the
server binary as an argument:

```
node apps/server/dist/index.js --reset-password "<new password>"
```

A command line is not private to the user who started the process. Every other
user on the host can read the new password for as long as the command runs.
`CONTRACTS.md` publishes that command form and `README.md` documents it twice
— the checkout form (`scripts/reset-owner-password.ts`) and the container form
— and **neither says what it costs**. The exposure is real, and it is
undocumented.

Probe's verification of WI-002 asserts exactly that, in
`apps/server/src/__tests__/ownerPasswordExposure.test.ts`. Two of its four
assertions pass and prove the exposure is real. Two fail, and they fail for
one reason:

```
FAIL src/__tests__/ownerPasswordExposure.test.ts > what the documentation says about it > 'CONTRACTS.md' says the password is visible in the process list
FAIL src/__tests__/ownerPasswordExposure.test.ts > what the documentation says about it > 'README.md' says the password is visible in the process list
```

The expected behaviour is that both documents, in the section that documents
the recovery command, say that the password is visible in the host's process
list while the command runs and that another user on the host can read it.

## Why now

WI-002 cannot leave `verify` while its verification is red, and the
verification cannot go green until these two documents say it. The gap itself
is small. What it is not is trivial: a statement that is not written down is
not a statement the owner can act on.

## Acceptance criteria

- [ ] `CONTRACTS.md`, in the section that documents the recovery command, says
      that the new password is visible in the host's process list while the
      command runs.
- [ ] `CONTRACTS.md`, in that same section, says that another user on the host
      can read it.
- [ ] `README.md`, in the section that documents the recovery command — both
      the `scripts/reset-owner-password.ts` form and the container form — says
      the same thing.
- [ ] `ARCHITECTURE.md`, in the known-limitations entry that names the
      recovery command, says the same thing. It names the command, so a reader
      who copies it from there has to learn what it costs there too. Added by
      Chief's review — see the finding below.
- [ ] `npx vitest run src/__tests__/ownerPasswordExposure.test.ts` →
      `5 passed (5)`. Two of those assertions prove the exposure; three say
      what the documentation says about it, one per document that names the
      command. The third — `ARCHITECTURE.md` — is Probe's to add, and it
      passes on the first run because the clause is already written.
- [ ] `npm run format:check` passes. Prettier covers `*.md`, so the two
      documents are in scope for it.
- [ ] The published command form is unchanged. This item adds a statement of
      cost; it does not change what the product does.

## Not in scope

- **Changing how the password is passed.** Chief has ruled that the published
  form stays. The alternative — a form that never puts the password on a
  command line — changes a published contract, so it needs the owner, a
  migration plan and a `CONTRACTS.md` update. It is candidate **C-18**, not
  this item.
- Any other document. The verification names the two that publish the
  command; those are the two that have to say it. `ARCHITECTURE.md` names the
  command too, and is now in scope — see the finding below.
- The recovery path itself, and the `apps/server` implementation.
