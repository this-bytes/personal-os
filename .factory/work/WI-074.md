## The problem

**The server suite went red with every assertion green.** `npm run test` at
`main`, on the tree that carries the other Chief session's new pin
(`052f050`):

```
 ❯ src/__tests__/verifyStack.test.ts (12 tests) 49990ms
⎯⎯⎯⎯⎯⎯⎯ Failed Suites 1 ⎯⎯⎯⎯⎯⎯⎯
 FAIL  src/__tests__/verifyStack.test.ts [ src/__tests__/verifyStack.test.ts ]
 ❯ src/__tests__/verifyStack.test.ts:133:34
 Test Files  1 failed | 22 passed (23)
      Tests  230 passed (230)
```

**Read that carefully: 230 tests passed and the file still failed.** The
failure is not an assertion. It is the file's own cleanup.

**Where it is.** `apps/server/src/__tests__/verifyStack.test.ts`:

```ts
afterAll(async () => {
  await Promise.all(children.map((child) => stop(child)));
  for (const dir of dataDirs) fs.rmSync(dir, { recursive: true, force: true });
}, 30_000);
```

**The error site is `:133:34` — `fs.rmSync`** — and the hook's budget is the
`30_000` at `:134`. **The file took 49 990 ms.**

**The children are not the unbounded part.** `stop()` (`:106-119`) is bounded:
it resolves on the child's `exit`, and a 4-second timer sends `SIGKILL` and
resolves anyway. **So `Promise.all(children.map(stop))` costs about four
seconds, and the removal is what ran past the budget.** On Windows, removing a
directory tree that a just-killed process still holds open is exactly the
operation that blocks.

## What was measured, and what was not

**It happened once and did not reproduce.** Two runs straight after:

| Run                                 | Result                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------ |
| `npm --prefix apps/server run test` | **exit 0** — 23 files passed (23), 230 passed (230)                                  |
| `npm run test` (the whole tree)     | **exit 0** — 23/23, 230/230, then web 52, worker 31, agent-adapters 16, contracts 28 |

**The machine was under load when it went red.** This host also runs **other
tenants' containers** — `shiny-octo-broccoli-webui` and
`technitium-dns-companion` — alongside the shared `personal-os` stack, and
Chief was running a git check and a docker check at the same moment.

**So this is not a defect in the code the test exercises.** It is a defect in
the test's own teardown: **a suite that passed every assertion was reported
as failed.**

## The history: this budget was already raised once, and the symptom came back

**`1c92001` (12:10, "Fix the two flakes in the suites that spawn processes") is
the precedent, and it is the reason this item exists rather than a shrug.**

Probe fixed this file's own sibling problem in the same family, and the commit
says why:

> **`verifyStack.test.ts` reported a failed suite with no tests in it.** Its
> `beforeAll` hooks start a server and wait for it to become healthy — up to
> sixty seconds by the file's own bound — but the hooks carried no timeout, so
> they inherited vitest's ten-second default. On a loaded machine the server
> took longer than that, the hook was cut off, and **the file was reported as
> failed without a single test in it.** The hooks now carry the timeout their
> own wait allows.

**And that fix is the `30_000` at `:134`.** The diff of `1c92001` on this file
is exactly two lines of timeout:

```diff
 afterAll(async () => {
   await Promise.all(children.map((child) => stop(child)));
   for (const dir of dataDirs) fs.rmSync(dir, { recursive: true, force: true });
-});
+}, 30_000);
```

**So: the hook's budget was raised from vitest's ten-second default to thirty
seconds, and the symptom came back four and a half hours later — with every
assertion green again.**

**That is the whole finding, and it is the reason the criterion is the bound
rather than the number.** A budget that was raised once and then overrun again
is not a budget that can be raised twice. **The fix is not a bigger number; it
is a teardown that cannot be the reason a green suite is reported as failed.**

## Why it is worth an item rather than a shrug

**CI is what the gate is for, and CI runs on `ubuntu-latest`.** That is the
fact that makes this worth opening: **a 30-second budget on a cleanup that
depends on the machine's speed can be exceeded on a busy CI runner too.** The
mechanism that bites here — a removal that blocks on a handle the process just
dropped — is Windows-specific, but **the budget that the removal overruns is
not**, and the budget is what makes a suite red for no reason.

**And a gate that can go red for no reason is a gate that trains people to
ignore it.** This factory has already spent a day on a smoke gate that was
flaky on Windows and fixed in `63aba3a`. **This is the same file family and
the same class, and the honest thing is to say so rather than to record
another "flaky, not reproduced".**

## Acceptance criteria

- [ ] **A leftover temporary directory can never fail a suite.** The cleanup is
      best-effort: a directory that cannot be removed is reported, not fatal.
      **A suite that passed every assertion passes.** This is the heart of the
      item and the criterion Chief cares about most.
- [ ] **The cleanup is bounded, whatever the machine is doing.** No budget in
      this file can be overrun by the teardown it guards. Whether that is a
      retry on the removal, a shorter budget, a removal that is not done
      inline, or something else is **Probe's design to choose** — the criterion
      is the bound, not the mechanism. **And the fix is not a bigger number:
      this budget was already raised from ten seconds to thirty in `1c92001`,
      and the symptom came back.** A budget that has been raised once and
      overrun again is not a budget that can be raised twice.
- [ ] **The stack test still proves what it proves.** Nothing about the
      behaviour under test may change: the same assertions, the same coverage,
      the same pins. **A cleanup that swallows a failure of the test itself is
      not a fix.**
- [ ] **The suite is green on this host under load**, and a way of making the
      load reproducible is described in the report, so the fix can be shown to
      hold rather than merely to pass.
- [ ] `npm run typecheck`, `npm run test`, `npm run format:check`,
      `npm run build` pass, and the tree is clean at the end.
