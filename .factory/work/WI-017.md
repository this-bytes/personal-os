## Problem

Q3's third half was never built. The owner settled that an agent-created
feature is a typed, validated resource in our contracts, "authored through
templates". Typed ✓ — six kinds in `resourceTypeSchema`. Validated ✓ —
per-type specs checked by the owning provider. Templates ✗ — there is no
template concept for a resource anywhere in the product; the only templates
in the code are HTTP body templates and prompt templates.

So an agent can create a resource, and nothing tells it what a good one
looks like. It guesses the shape from the schema, and a schema is a type, not
an example.

This is the other of the two settled decisions that had no work item behind
it. It is the deepest claim of the identity — "agents extend it" is only
true if an agent can see what good looks like.

## Acceptance criteria

- [ ] A template is a first-class record: a named, versioned example of one
      resource kind, with its spec, that an agent can start from.
- [ ] An agent can list the templates for a resource kind and create a
      resource from one, through the MCP surface it already uses to create
      resources — not a second tool surface.
- [ ] A resource created from a template is a normal resource: same schema,
      same validation, same audit trail, same revision. A template is a
      starting point, not a different kind of thing.
- [ ] The template's spec is validated by the owning provider exactly as a
      resource's spec is, so a template cannot drift into describing
      something the product would reject.
- [ ] The contract entries for the template record and the tool land before
      the feature ships.
- [ ] A test proves that a resource created from a template validates, and
      that a template describing an invalid spec is refused.
- [ ] The report states which template set ships, and what each template is
      for. **The answer is known: all six kinds, one template each** — dashboard,
      document, automation, data-source, task, memory (the owner's answer of
      2026-10-21 06:01, recorded in `docs/strategy.md`, `e5df669`). What is left
      of the criterion is the report naming them, and the report is the
      implementation's.

## Not in scope

- **No agent-shipped UI.** MCP Apps (SEP-1865) is the standard for a server
  shipping its own UI to a host, and it is a proposal rather than a ratified
  standard. That is a different extension surface from a domain resource,
  and it is not in this item. WI-011 carries the conformance recommendation
  and the scoping.
- **No template editor in the panel.** Templates are authored in the repo
  and reviewed like code.
- **No choice of which resource kind comes first.** That was the owner's call,
  and it is answered: **all six kinds, one template each** — dashboard,
  document, automation, data-source, task, memory (the owner's answer of
  2026-10-21 06:01, recorded in `docs/strategy.md`, `e5df669`). This item is the
  mechanism, and it works for every kind the product already has.
