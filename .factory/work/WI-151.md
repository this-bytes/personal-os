# WI-151 — The composer can attach a file that is not a resource yet

**Owner:** Cog, the implementation engineer.
**Verifier:** Probe, who wrote none of it.
**State:** accepted — the composer can attach a file that is not a resource yet.
It landed in `main` at `75485dc` and `CONTRACTS.md` publishes it: the routes are
`apps/server/src/api/resources.ts`, the bytes are written by
`apps/server/src/modules/resources/files.ts`, and the shipped checks are
`apps/server/src/__tests__/resource-files.test.ts` and
`apps/web/src/components/__tests__/ComposerUpload.test.tsx`. Closed under ADR
0012 on 2026-10-23.
**Branch:** `wi/151-attachment-upload`
**Base:** `1e852e1`

## Problem

**A file the owner wants to send had to already be a resource, and there was no
way to make it one.**

The composer offered a picker over the workspace's resources and attached the
one the owner picked, by reference. The message carries `{ type: 'file',
resourceId }` — a reference, and a reference needs something to point at.
`POST /api/resources` takes a JSON payload
(`packages/contracts/src/resource.ts`), so a resource is something the owner
writes by hand. **There was no upload path anywhere in the product**: no route
took bytes, and the `resource_files` table (`apps/server/src/db/schema.ts:504`)
was declared, migrated and never read or written.

The published contract said so, in the chat surface entry's paragraph of
limits: _"A file the owner attaches is carried by reference to a resource, not
uploaded by the composer."_

## What changed

**The server stores the bytes.** `POST /api/resources/upload` takes
`{ workspaceId, filename, mimeType, contentBase64 }` and answers with the
resource that points at them. The bytes travel as base64 in a JSON body, so
the server needs no multipart parser and the product needs no new dependency
for one. They are written to `<dataDir>/files/<resourceId>` — the name is the
resource's id, so nothing the owner sent reaches the path — and the row that
says where they are goes into `resource_files`, the table that was already
there. **The path is in the database, never in the resource's `data`**, so the
browser cannot learn the server's filesystem; the resource carries
`{ kind: 'file', filename, mimeType, size }` and the file's name is the
resource's title.

**The resource and the file are written in one transaction**
(`apps/server/src/modules/resources/files.ts`). The resource is created
through the resource service, so the envelope (`schemaVersion`, `revision`,
`createdBy`, `updatedAt`) and the provider's rules are the ones every resource
has. A write that fails takes the file with it, so a half-written upload
leaves no bytes behind for a resource that does not exist.

**The server gives the bytes back.** `GET /api/resources/:id/content` streams
the stored bytes with the content type the file was uploaded with, found
through the `resource_files` row rather than by guessing a path. A resource
that is not a file, a resource with no stored bytes, and a resource that does
not exist all answer `not_found` in the shared envelope.

**The composer uploads.** The owner chooses a file, the client reads it and
base64-encodes it in the browser, and the resource the server answers with is
attached exactly as a resource the owner picked from the workspace would be:
the message carries the same `{ type: 'file', resourceId }` it always did. The
composer says what is happening — uploading, uploaded, or the server's own
sentence when it is refused. **The failure message is the server's sentence,
word for word**: a client that reworded it would be telling the owner
something the server knows better.

**The transcript opens the file.** A file resource in the transcript links to
the content route, so what the owner attached can be read.

## The proof

`apps/server/src/__tests__/resource-files.test.ts`:

- **the bytes round trip** — a file is uploaded, read back, and the bytes are
  identical;
- **the resource says what the file is, and not where the server keeps it** —
  the data is exactly `{ kind, filename, mimeType, size }`, carries no path,
  and the bytes are found on disk under the data directory;
- **the cap is enforced** — a file over 10 MB is refused with the shared
  envelope and a sentence the owner can act on, both when the body says how
  big it is and when it does not;
- **a resource that is not a file has no content** — `not_found`;
- **the upload is for the owner alone** — an unauthenticated call is refused.

`apps/web/src/components/__tests__/ComposerUpload.test.tsx`:

- **the composer uploads a file and attaches the resource it gets back** — the
  body is the file's bytes in base64, and the attachment is the resource the
  server answered with;
- **the server's sentence reaches the owner** — a refused upload shows the
  server's words, word for word, and attaches nothing.

Both tests were made to fail before they were trusted: a mutated resource id
fails the composer's test, and a byte that comes back changed fails the
server's.

## Scope and compatibility

**Owned paths**

- `apps/server/src/api/resources.ts` — the two routes.
- `apps/server/src/modules/resources/files.ts` — the storage of the bytes.
- `apps/server/src/modules/resources/service.ts` — the document provider, which
  now knows a document that is a file.
- `apps/web/src/lib/api.ts` — the typed upload helper and the base64 reader.
- `apps/web/src/components/Composer.tsx` — the upload affordance.
- `apps/web/src/components/chat/ArtifactPreview.tsx` — the link that opens it.

**Nothing outside them changed.** `apps/server/src/app.ts` and
`apps/server/src/context.ts` are untouched: the file storage is built by the
route module that uses it, because the resource routes are the only ones that
store a file. `CONTRACTS.md` is the integration owner's; the proposal for it
is [docs/contract-attachment-upload.md](docs/contract-attachment-upload.md).

**The contract's citations still hold.** The contract cites lines in
`service.ts`, and the change there is one line replaced in place with the
helpers at the foot of the file, so every cited line still carries the claim
it names. The only thing the owner has to publish is the count: 40 → 41
mutating routes, and 37 → 38 of them writing an audit entry at the route
level.

**Compatibility.** A client that attaches by reference keeps working. Nothing
about `POST /api/resources` changed, the message a client sends is unchanged,
and the `document` payload gained a second shape: a text document is judged by
the document contract exactly as it always was, and a document written before
this change still parses and still stores the same bytes in the same column.

## Acceptance criteria

- [x] The server stores the bytes of an uploaded file, and the resource that
      points at them carries the file's metadata and not the server's path.
- [x] The resource and the file row are written in one transaction.
- [x] `GET /api/resources/:id/content` gives the bytes back, with the content
      type, and answers `not_found` for anything that is not a file.
- [x] A file over 10 MB is refused with the shared error envelope, in words
      the owner can act on.
- [x] The composer uploads a file and attaches the resource it gets back, and
      says what is happening.
- [x] The transcript can open an attached file.
- [x] The tests fail when the behaviour is wrong.
- [ ] The contract publishes the routes, the shape and the count — the
      integration owner's to do.

## Not in scope

- **Deleting a resource.** No route deletes a resource today, so no delete
  path was built. The `resource_files` row cascades on delete, but **the bytes
  on disk would stay**: the proposal says so plainly, and the delete route
  that comes later has to remove the file with it.
- **The MCP surface.** An agent cannot upload a file; the tool surface is
  unchanged.
- **The contracts package.** The file document's shape is judged by the
  server's own copy of it, and the proposal says where the owner may want to
  publish it.
- **Sharing.** The bytes live in the data directory of one deployment. Two
  deployments do not share them.
