## The question

Eighty-four remote `wi/*` branches had piled up, and no pull request existed for
any of them — zero open, zero closed, ever. The worry was that each branch was
a different direction and the repository had become an unmergeable mess.

**Both halves of that worry were wrong, and the measurements are below.** The
repository is not an unmergeable mess. The pile-up is mostly _closed_ work that
nobody deleted, plus a small set of branches that genuinely carry unique
content. And the absence of pull requests is not a failure — it is the
documented design of this factory.

## Why there are no pull requests

`FACTORY.md` defines the landing model, and it is not pull-request-based:

- **The branch is the unit of work.** Work is written on `wi/NNN-slug`, in a
  worktree beside the repository, and never on `main`.
- **Landing is a fast-forward merge.** `git merge --ff-only <branch>` followed
  by `git push origin main`, under a standing owner authorisation given
  2026-10-21 18:07: _push `main` whenever CI is green._ That word is not spent.
- **CI runs on every branch push**, not only on `main`
  (`.github/workflows/ci.yml:12` — `branches: ['**']`), so a pushed branch is
  a gated branch. The `pull_request:` trigger at `ci.yml:13` exists, but
  nothing in the workflow or the docs creates a pull request.

The GitHub API confirms it: `pulls?state=all` returns **zero** pull requests,
open or closed, for the life of the repository. The `gh` CLI is not installed on
this machine. **No agent failed to open a pull request; no agent was ever
supposed to open one.** A pull request here would be a second review gate on
top of a pipeline that already gates the branch.

## How each branch was judged

Three questions have to be asked of every branch, and conflating them is how a
branch looks like new work when it is not:

- **Is it merged?** `git merge-base --is-ancestor <branch> origin/main` — every
  commit on the branch is already reachable from `main`.
- **What does merging it _do_?** `git merge-tree --write-tree origin/main
<branch>` gives the exact result tree, and `git diff origin/main <that tree>`
  is the branch's **net landing effect**.
- **Does it conflict, and where?** The same command reports the conflicted
  paths — and **its exit code alone is not enough**: a merge that conflicts
  still returns a tree, and that tree has the conflicted content written into
  it with `<<<<<<<` / `=======` / `>>>>>>>` markers. Read the `CONFLICT` lines.

**The second question is the one that decides**, and the branch's own diff
against `main` cannot answer it. `git diff origin/main...<branch>` is measured
from the merge-base, so it reports the whole history of a divergence —
including changes `main` already has by another route. Measured that way,
`wi/071` looks like 13 files and +726 lines; measured as a merge result, it is
**+0/−0**. And the reverse is worse: `wi/062` conflicts on a single
`CONTRACTS.md` line-range and would still move `main`'s pointers **backwards**,
because the numbers it was written to correct have since moved again.

`git cherry` answers a fourth question — "is this commit's patch already in
`main`?" — and it is what identifies `wi/046-merge-rehearsal` as a rehearsal
whose every patch already landed.

**And a fifth question decides the landing order, and nothing else does:
containment.** `git merge-base --is-ancestor <a> <b>` over every pair of
unlanded branches answers "does `a`'s work already live inside `b`?" — and one
answer reshapes the whole table. Measured pairwise, the unlanded set is **not
twenty-five independent directions. It is a chain:**

```
wi/085  →  wi/095  →  wi/122  →  wi/124
```

Each arrow is `is-ancestor`, so each branch's commits are already reachable
from the next. **`wi/124` carries all four.** The pile-up that looks like
divergence is, in this corner of it, **one line of work** — and the branches
that look like separate directions are the same direction at four points along
it.

**On CI: the platform's verdict is the authority, and a local test run is
not.** This item ran the affected tests locally against a scratch worktree and
read four failures — which were **an artifact of the harness, not of the
branch.** A `node_modules` junction makes `node_modules/@personal-os/contracts`
resolve to the **main checkout's** `packages/contracts`, not the scratch
worktree's, so a branch that changes a published contract is tested against
the _old_ contract and goes red for the wrong reason. **The CI verdict on the
pushed tip is the measurement that counts**, and it is the one quoted in every
table below. The local run is not evidence of anything unless the workspace
packages resolve to the tree under test.

`npx tsx scripts/work-item.ts remove WI-NNN`, which refuses a dirty worktree
and refuses to delete an unmerged branch. **10.1 GB of disk was reclaimed**
(18.3 GB → 8.2 GB). The count is 42 now, at 8.2 GB, because the peer session
opened worktrees of its own afterwards — the reclamation held.

**The rule that was followed throughout: a branch is closed by marking it
superseded in its own item file, not by deleting it** (WI-087, rule 2).
**No remote branch was deleted and nothing was force-pushed.** The 63 merged
branches are still on the remote; they are closed work, and closing them is a
ledger act, not a git act.

**Nothing was landed on `main` by this item.** The peer session was actively
pushing throughout, and `FACTORY.md` is explicit that a push cancels the run
that judges it and that `main`'s landing is one push at a time.
