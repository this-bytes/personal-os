# WI-131 — The widening write is not one transaction, and the contract says it is

**Numbered:** 2026-10-22 — **WI-131**, read immediately before it was taken: the published
number block in `.factory/INTAKE.md` reads "**The next free number is WI-131.**"

**Owner:** worker, under Chief (Cog — `apps/server`, `packages/contracts`).
**Verifier:** a verifier who wrote none of this.

**Where it came from:** findings **D1, D2 and D3** in **WI-121's verification** (Probe,
`task_2c991d059378`, VERDICT ACCEPT). **WI-121 is accepted; these are new items, not a
hold on that one.**

**Why the three are one item, and the lead says so rather than leaving it to be guessed:**
**D1's fix and D3's fix are the same fix** — one transaction spanning the delete and the
write — **and D2 is the contract sentence about those very two lines.** One file, one live
item, one writer at a time.

## The gap

**The row leaves the list before the grant is written, and nothing spans the two.**

- `apps/server/src/modules/agents/service.ts:261` — `clearGrantedCapabilities(db, id,
patch.toolGrants);` — **deletes the blocked rows.**
- `apps/server/src/modules/agents/service.ts:288` — **writes the grant.**
- Nothing spans them.

**Measured by the verifier (E5):** a `PATCH /api/agents/:id` carrying `toolGrants` and
`config` together, with a dangling configuration reference, answers **404
`{"error":{"code":"not_found","message":"Agent configuration not found."}}`**, the blocked
row is **gone** (`rows=0`), and the grant is still `["conversation.read"]`. **The block the
owner was told about has left the list and the agent still cannot call the tool — the list
now under-reports instead of over-reporting.** E1 shows the same from the other side: the
delete alone leaves `rows=0` with the grant unchanged.

**And the contract publishes the opposite order** — `CONTRACTS.md:1443-1447`, the WI-121
entry (it moved down 34 lines when WI-129's entry was inserted above it): _"the row leaves
the list **as soon as the grant includes it** ... A list that keeps the row is a list that
lies about what is waiting."_ The covered direction holds. **The direction that breaks is
the one the contract does not name — and a list that drops a block while the agent is still
blocked is a list that lies the other way.**

**D3, narrow but not nothing.** A refusal landing between the delete and the grant write
leaves a row for a capability the agent holds (E3: `rows=1`, `toolName="task.create"`,
grants include `task.create`). **Not reachable through the HTTP API today** — E4 fired a
refusal and a widening together 40 times and saw a stale row in 0 rounds — **because
`update()` is synchronous, with no `await` between `:261` and `:288`.** **The worker is a
second process on the same database.** The published guarantee therefore rests on `update()`
never yielding rather than on a transaction, and a guarantee that rests on a scheduling
accident is not a guarantee.

**D2, the citation that does not hold its claim.** `CONTRACTS.md:1446` says _"both go
through the one write that changes a grant (`apps/server/src/modules/agents/service.ts:261`)"_
— and `:261` is the **delete**; the write that changes the grant is `:288`. The item's own
note claims every citation it adds holds its claim, and reads the lines by hand; **this one
does not.** It is the same imprecision the item corrected once on its own
(`mcp/server.ts:711` → `:720`).

## What this item does

1. **One transaction spans the two writes.** A failure in either leaves both as they were:
   **the row stays while the grant did not change**, and the grant changes with the row
   gone only when the grant really was widened.
2. **The contract publishes the guarantee in the direction that is kept** — the row leaves
   exactly when the grant includes the capability, **and it stays when the grant write
   fails** — and its citation names the line that holds the claim.
3. **The window is closed for the worker too,** not only for the API: a transaction is the
   thing that holds across processes, and the worker is a second process on the same
   database.

## The contract changes

- The WI-121 entry's sentence about the row leaving is corrected to state both directions,
  and its citation is re-pointed at the write that changes the grant — or at the transaction
  that now spans both.
- A migration note: **nothing changes for a client that widens a grant successfully**; a
  client whose grant write failed now keeps the row it was told about.

## The proof

**`apps/server/src/__tests__/blocked-capability.test.ts` — Probe's file, and it already
exists: it is WI-121's check, landed in `32af761`.** This item adds cases to it, and the
lead names them here so they cannot slip:

- **a grant write that fails leaves the blocked row on the list** — the D1 case, measured
  the way E5 measured it, through the route;
- a successful widening leaves the row gone and the grant set;
- **a refusal arriving between the two leaves no stale row** — measured with the
  transaction in place, and not by assuming the window is closed.

**And the mutation proof that matters:** with the transaction taken away, the D1 case turns
red. Restored with an empty diff.

**Measured by the worker, before a test was written** (a scratch script outside the
repository, since deleted): **17 checks, all passing.** A PATCH carrying `toolGrants`
and a configuration together, with the configuration the agent points at gone, answers
**404 `not_found`, "Agent configuration not found."** — and **the blocked row is still
on the list**, naming the capability, and the grant is still what it was. A widening
that succeeds takes the row off the list and sets the grant; a refusal of a capability
the agent holds records nothing; a refusal of one it does not hold is a row.

**And the fix is load-bearing, measured the same way:** with the transaction taken away,
the same measurement reads **"the blocked row is still on the list — 0"** — the row is
gone, which is the defect. Restored with an empty diff.

**And the window is closed for the worker too, measured across two connections** (the
worker's own process on the same database file): the server holds the transaction open
between the delete and the grant write, and **the worker's write waits for the lock —
774ms measured — and lands after the widening committed.** It cannot land inside the
window, so a refusal the worker records there cannot be written against a grant that is
about to be widened. And when it does run, the app's own refusal transaction reads the
grant and skips a capability the agent now holds, so it records nothing: that is
measured too, in the run above — _"no row for a capability the agent holds"_.

**How the dangling reference was made, for whoever writes the check.** The failing write
needs the configuration record the agent points at to be gone. The worker wrote the
agent's `config_ref` to an id that is not there, from a second connection to the same
database. The check may do it however it likes, as long as the write is refused by the
route and not by a case that fails before it reaches the route.

claim the contract makes about the code: a claim has to name the commit that carries it,
or a work item that is still open. The WI-121 entry's closing claim named WI-121 — and
**accepting WI-121 closed it, so the claim went unsatisfied and `main` is red on that
test today.** The entry now names the commit that carries what the claim describes
