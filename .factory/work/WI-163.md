# WI-163 — A chat, a task and an automation reach the same execution owner

**Owner:** the implementing agent for the slice (Cog — the implementation
engineer for the server, the worker and the contracts).
**Verifier:** Probe, the verification engineer, independently.
**State:** implement
**Branch:** wi/163-shared-execution-ownership
**Base:** main at intake (68bbd79); cut the branch from the current
`origin/main`.

## Problem

`docs/roadmap.md` (R0, "Next bounded slices", 1) and the owner's directive
(`.factory/DIRECTIVE.md` §6.1) name the same slice:

> Establish shared execution ownership across chat, tasks and automations.
> Extract only the lifecycle needed by these callers, with compatible
> event/state mapping.

Today the three callers own their own path into execution. Authorisation,
session handling and lifecycle therefore behave **differently per caller**, and
"one execution" means three different things depending on who asked for it. The
owner's complaint in `docs/spec/p0-feature-audit.md` — "all features are half
implemented, a lot of functionality not exposed" — is the same shape seen from
the agent side: the authority loop exists, but not as one owned thing.

**Outcome:** a chat, a task and an automation reach the **same** execution
owner, through one lifecycle, and observe the same event and state mapping.

`docs/spec/s1-approval-execution-parity.md` is the agent-operable surface of
this ownership; `docs/spec/p0-feature-audit.md` ranks the rows this slice
touches. `docs/decisions/0013-surface-parity-every-owner-capability-is-an-agent-capability.md`
is the rule behind both.

## Scope and compatibility

- **Owned paths:** the execution lifecycle in `apps/server` shared by the chat,
  task and automation callers, and the worker executor path they reach.
- **Boundaries:** extract **only** the lifecycle these three callers need. The
  adapter surface (`packages/agent-adapters`) and the runtimes themselves are
  not this slice's work.
- **Compatibility:** what each caller observed before is unchanged — the
  published event and state mapping per caller is preserved, and the existing
  callers' checks keep passing unmodified.
- **Data migration:** none. Where an existing execution's shape changes at the
  boundary, it is converted there, not by rewriting history.

## Acceptance criteria

- [ ] One dispatch path serves chat, task and automation, and each of the three
      runs through the **real** path in a check.
- [ ] Authorisation, session and lifecycle behaviour is identical across the
      three callers, demonstrated by the same case run against each.
- [ ] Each caller's event and state mapping is unchanged: the shipped checks
      for those callers pass unmodified.
- [ ] Failure and recovery are covered — an execution that fails, one that is
      stopped, and one that cannot start.
- [ ] Applicable gates pass on the delivered revision.
- [ ] Independent review findings are resolved.

## Not in scope

- Factory autonomy, the queue-index reform and new dashboards — the roadmap
  says these do not belong in R0.
- The MCP tool surface (`docs/spec/s1-approval-execution-parity.md` is its own
  slice).
- The runtimes themselves, and any new runtime.

## Evidence

- Revision, the commands actually run and their results, runtime versions,
  inspectable output, limitations and the independent reviewer's verdict.
  A state label is a report, not proof.
