# WI-164 — The grant decision taken at admission is the one enforced at execution

**Owner:** the implementing agent for the slice (Cog — the implementation
engineer for the server, the worker and the contracts).
**Verifier:** Probe, the verification engineer, independently.
**State:** implement
**Branch:** wi/164-authorised-dispatch
**Base:** main at intake (68bbd79); cut the branch from the current
`origin/main`.

## Problem

`docs/roadmap.md` (R0, "Next bounded slices", 2) and the owner's directive
(`.factory/DIRECTIVE.md` §6.2) name the same slice:

> Define explicit authorized task dispatch through the shared service and MCP.
> Task creation stays non-executing. Duplicate dispatch cannot start two runs.

The decision that **admits** a dispatch and the decision that lets it **run**
are taken in different places. A grant can widen between the two, and that
widening is not the owner's turn — so the thing that authorises the run is not
the thing the owner authorised.

**Outcome:** the capability decided at admission is the capability enforced at
execution, and widening a grant requires the owner's turn.

`docs/decisions/0013-surface-parity-every-owner-capability-is-an-agent-capability.md`
is the rule (registration follows `agentToolGrants`; destructive verbs require
the same approval-shaped authority the UI demands; no new authority kinds are
invented). `docs/spec/s1-approval-execution-parity.md` is the agent-operable
surface of the same rule.

**This slice depends on WI-162.** The owner's turn that widens a grant is the
turn the grant editor sends — and WI-162 measured that the editor's save is
held by nothing on two of its paths. Widening must be the owner's turn **and**
be held by a check, or this slice's rule is not enforceable.

## Scope and compatibility

- **Owned paths:** the shared service's dispatch path, the MCP entry into it,
  the admission decision carried to execution, and duplicate-dispatch
  prevention.
- **Boundaries:** the grant model itself is not changed; the decision is
  **carried**, not re-invented.
- **Compatibility:** task creation stays non-executing; an already-authorised
  dispatch behaves as it does today; no new authority kind is introduced.
- **Data migration:** none.

## Acceptance criteria

- [ ] The capability decided at admission is the capability enforced at
      execution, shown by a case where the grant changes between the two.
- [ ] Widening a grant requires the owner's turn; a widening by another writer
      does not authorise a dispatch.
- [ ] Duplicate dispatch cannot start two runs of the same task — a case proves
      one execution, not two.
- [ ] Task creation stays non-executing: creating a task never starts a run on
      its own.
- [ ] A refusal without authority is recorded like every other ungranted call,
      and the failure is actionable.
- [ ] Applicable gates pass on the delivered revision.
- [ ] Independent review findings are resolved.

## Not in scope

- New UI screens.
- The MCP tool surface itself (`docs/spec/s1-approval-execution-parity.md`).
- Changing the grant model, and anything `docs/spec/p0-feature-audit.md` marks
  `broken-window` — those become their own named specs.
