## The problem

**`apps/server/src/modules/mcp/server.ts:145-151` tells a reader something the
contract no longer says.** The comment above `assertOwnMemory` reads:

> A read is judged once, by the same question — the resource's current owner.
> **The published contract describes `resource.get` as "Read a resource" and says
> nothing about who owns a resource**, so the rule that answers that question is
> this one, and it answers it the same way for all three resource tools: create,
> update and get.

**Both halves of that sentence are now false of the contract.** WI-028 was
accepted tonight, and its correction is exactly what changed them:

- **`CONTRACTS.md:704`** — the tool table's row for `resource.get` now reads
  **"Read a resource. Not another agent's own memory."**
- **`CONTRACTS.md:718-726`** — the MCP exposure entry now carries **"Who owns a
  resource is settled before it is handed over"**, the rule that says a read
  carries the same ownership rule as the writes.
- **`CONTRACTS.md:728`** — and the entry names the change that published it:
  **"The read side is WI-028, and the code implements it — as of `622812c`."**

**The comment was true when it was written** — `622812c` wrote it, and at that
moment the contract really did say nothing about ownership. **WI-028's
correction made the contract say ownership, and nothing followed the comment
back.** So the code now describes a contract that does not exist.

**Why it is worth an item and not a shrug.** This factory has spent the evening
repairing the other direction of exactly this — **pointers into the contract
that no longer point, and claims about the contract that no longer hold.** WI-028
was one of them; WI-079 is a check for the class; and this is the third kind:
**a comment in the code that misdescribes the published contract.** A reader
who trusts it concludes that the contract is silent about ownership, and the
whole point of WI-028 was that it is not.
