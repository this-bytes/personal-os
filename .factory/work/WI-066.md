## The problem

**`CONTRACTS.md`'s `### Additive extensions` section (`:66`) miscounts the
fields it publishes, leaves one of them without a sentence, and leaves one of
them unpublished.** Measured on `main` at `f62e065`:

| Where                                                     | What it says                                                                                                           |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `CONTRACTS.md:68` — prose                                 | _"The implementation adds **three** fields, all optional and all required by production behaviour:"_                   |
| `CONTRACTS.md:71-84` — block                              | lists **four**: `status`, `correlationId`, `origin`, `executionId`                                                     |
| `CONTRACTS.md:86-88` — prose under the block              | explains **three**: `status`, `correlationId`, `origin`. **`executionId` has no sentence at all**                      |
| `packages/contracts/src/conversation.ts:78-90` — the code | carries **five**: `status` (`:78`), `correlationId` (`:79`), `origin` (`:80`), `executionId` (`:81`), `detail` (`:90`) |

**`detail` is the field that is missing, and it is the one that matters.** It
is the server's own sentence about how the message ended — the code's own
comment says so at `packages/contracts/src/conversation.ts:82-89` — and it is
what WI-031's criterion _"the reason reaches the panel"_ is served by: WI-031's
route returns a message that carries it, and the panel shows it as it is given.

**And a second shape is published wider than the code allows.**
`CONTRACTS.md:148-151` publishes

```ts
interface ResolveExecutionInput {
  outcome: 'completed' | 'failed';
  note?: string;
}
```

**with no bound**, while the code caps the note:
`note: z.string().max(2_000).optional()` (`apps/server/src/api/executions.ts:9`).
A client written against the published shape may send a longer note and be
refused with `validation_failed`. **Probe measured this while verifying WI-031
and routed it here rather than letting it go unrecorded.**

**Both are gaps against WI-031's own acceptance criterion 7** — _"the published
shape matches the code exactly, member for member, checked against the
implementation, not against the proposal above."_ **Until both are closed, WI-031
cannot be accepted, however good the code is.**

## Notes

**Why the contract is fixed rather than the code.** The contract leads the code,
and the published shape is what a client is written against. **The field
carries the server's sentence, and WI-031's criterion requires the reason to
reach the panel.** Removing the field to make the contract true would remove
the reason from the panel — fixing the symptom and losing the feature.

**Why this item exists at all, and why it is not a defect report.** The
implementer found it and named it in its report, which is the behaviour the
factory wants. **The gap it found is the contract's, and the contract is
Wren's.** An implementer that widened the published contract itself would have
made the promise and kept it in the same session, which is the one thing the
separation of the contract half from the code half exists to prevent.

**Why the title changed and the old one is not kept.** _"The fourth field the
code carries"_ was wrong, and a wrong title in a work item is a wrong
instruction to the person who has to do the work. **The item file is the brief;
the brief is read by the implementer; the brief has to be true.**
