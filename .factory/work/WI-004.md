# WI-004 — The landing page shows what is waiting on the owner

**Owner:** Cog
**State:** implement
**Dispatched:** 2026-10-20, task `task_43425f152a46`

## Problem

Opening the panel lands on `/conversations`, which shows the conversation
list. Nothing on that screen answers the only question the owner has when
they open it: _what is waiting on me?_

The information exists in the system already, in three separate places, and
none of them are on the landing page:

- **Approvals.** `GET /api/approvals` lists them, and the service can filter
  by `status`. A pending approval is an agent stopped mid-turn, waiting for a
  decision. It is the sharpest form of "waiting on me".
- **Tasks.** `GET /api/tasks` lists them, and `FactoryTask.status` already
  includes `blocked` and `review`. A task in `review` is waiting for the owner
  to accept it.
- **Executions.** An execution can be `blocked` on an approval, and a
  conversation can be waiting on the owner's reply.

So the owner has to open the factory board to find blocked work, open the
approvals list to find a pending decision, and open a conversation to find an
agent that asked them something. The three are the same question asked in
three places, and none of them is the front door.

## Why now

The owner named this as the thing they most want to be true the first time
they open the panel tomorrow, and the stated scope for this cycle is
interaction — the owner talking to agents — which is what the landing page
serves. The four UI directions built as prototypes (Deck, Desk, Orbit, Forge)
all carry a "needs you" concept, and all four are waiting on a decision about
where that concept lives. Building the thing the prototypes were sketching is
how that decision gets made with evidence rather than by opinion.

## Acceptance criteria

- [ ] Opening the panel shows a list of everything waiting on the owner:
      pending approvals, tasks in `review`, and tasks in `blocked`. Each entry
      says what it is and links to where the owner can act on it.
- [ ] The list is derived from the server, not assembled in the client. One
      request returns it; the client does not fetch three lists and join them.
- [ ] An item that is no longer waiting disappears from the list without the
      owner reloading the page by hand.
- [ ] When nothing is waiting on the owner, the page says so plainly instead
      of showing an empty list with no explanation.
- [ ] The list is scoped to the owner it is shown to. One owner sees one
      instance's items and no other's.
- [ ] The behaviour is covered by a test that fails without the change.

## Not in scope

- **No change to how an approval is decided.** Deciding stays where it is.
  This item moves the work to the front door; it does not change the decision.
- **No change to what happens to an agent after an approval.** An approval
  still closes its execution rather than resuming the interrupted turn. That
  is [ARCHITECTURE.md](../../ARCHITECTURE.md)'s known limitation and it is a
  separate item.
- **No permissions, sharing, teams or onboarding.** The owner answered "only
  me". The instance has one owner and this item does not change that.
- **No new visual language.** The four prototype directions are a decision
  that has not been made. This item is about the landing page answering the
  right question with the current design language; if the prototype work
  changes the visual direction, this item's front end is rewritten, not the
  server side.
- **No new endpoint on the public API surface** unless the existing endpoints
  cannot answer it. A new route is a published contract and needs a migration
  plan and a [CONTRACTS.md](../../CONTRACTS.md) update.

## Notes

**The one decision that is Chief's to make.** The landing page answers
"what needs me" for interaction, which means the owner lands on the agent
that asked them something, not on a generic task list. An approval and a
conversation are different things and the owner may want them in one list
or two. One list is the stronger answer to the question that was asked, and
two lists is easier to build but weaker. This item asks for one list, and
says so, because a list that makes the owner triage before it can act has
not answered the question.

**Where the data already is.** `apps/server/src/modules/approvals/service.ts`
has `list(workspaceId, status)` and the `pending` status constant.
`apps/server/src/modules/factory/service.ts` has `listTasks(workspaceId,
goalId)` and the `review` and `blocked` task statuses in
`packages/contracts/src/factory.ts`. The `GET /api/tasks` route in
`apps/server/src/api/factory.ts` already accepts a status filter. Both owners
of that code are Cog, so this is one item and one owner.

**What "without reloading by hand" may cost.** The event stream polls the
event table every 250 ms today. If the landing page subscribes to the events
it already has rather than adding a new mechanism, the list stays current
without a new subscription. If it turns out that needs a new stream, that is
a second item, not a quiet addition to this one.

**The prototype work is not blocked by this item, and this item is not
blocked by the prototype work.** The server side of this item stands on its
own. The four directions in `prototypes/` are a design exploration; if one of
them is chosen, this item's front end is redone against it, and the server
work is not redone.
