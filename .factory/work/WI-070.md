### Problem

The product has no agreed protocol on its agent-facing surface. PRODUCT.md:237 names AG-UI as the recommended target for the agent-to-UI event stream, and PRODUCT.md:246 says the panel's agent-facing surface is MCP and AG-UI. What the panel speaks today is a bespoke dialect: `GET /api/events` (apps/server/src/api/events.ts:17) carries eight event names published by `serverEventSchema` (packages/contracts/src/events.ts:13-51), and the browser re-parses every frame with that same schema (apps/web/src/lib/events.ts:137). Nothing outside the panel speaks it, and nothing in the repository says what it is.

The mapping onto what the product already emits is nearly one to one. The adapter event union (packages/contracts/src/agent.ts:168-215) already carries an `executionId` on every one of its eight members, and the server event that wraps it carries `conversationId` (packages/contracts/src/events.ts:24). So `executionId` can serve as AG-UI's `runId` and `conversationId` as its `threadId`, and no change to `agent.ts` is needed. That is the preferred outcome, and this item is written to reach it.

### Why now

Three days of capacity, and this is the one piece of the window that decides what an outside agent can build against. The panel already has the event vocabulary; what it does not have is a name for it that is not ours alone. AG-UI 1.0 is a published, versioned, MIT-licensed behavioural spec with JSON Schema as its source of truth and generated SDKs for TypeScript, Python and .NET, so conforming to it costs a projection rather than a rewrite.

The projection is also the cheap way to be wrong. AG-UI is a community protocol with a 1.0 version marker, not a standards-body ratification, and its generative-UI story is a draft. A layer that is a pure function over the existing event contract can be deleted in one commit if the bet does not pay. A layer that the domain depends on cannot.

### Acceptance criteria

- [ ] A pure function maps the existing server event schema to AG-UI events. It takes a `ServerEvent` and returns AG-UI events, it does no I/O, and it lives at the API boundary.
- [ ] Every event in `serverEventSchema` (packages/contracts/src/events.ts:13-51) and every event in `agentEventSchema` (packages/contracts/src/agent.ts:168-215) has a stated AG-UI mapping. Events with no natural counterpart are named as such in the table rather than left out. The approval case is stated: `approval.requested` becomes a `RUN_FINISHED` whose `outcome.type` is `interrupt`.
- [ ] A named test covers the mapping, one input per server event type, each asserted against the expected AG-UI output.
- [ ] `GET /api/events` is unchanged in behaviour and in contract. A named test proves the existing route still answers with the same event names, the same priming behaviour and the same framing.
- [ ] The AG-UI route is additive: a new route, its own section in CONTRACTS.md under the event stream, and a row in the route table.
- [ ] The mapping table appears in CONTRACTS.md, so that a reader sees the correspondence without reading the diff.
- [ ] The approval round-trips: the AG-UI interrupt carries the approval's own id (the `approvalId` at packages/contracts/src/agent.ts:194), and a resume naming that id resolves the same approval.
- [ ] The published counts stay honest: `apps/server/src/__tests__/published-shapes.test.ts` passes, and any route added here is counted correctly by it.
- [ ] The gates below pass.

### Not in scope

- **Changing `GET /api/events`.** Not one byte of its contract moves. The existing route, its eight event names, its priming behaviour and its SSE framing are what they are today.
- **Making the domain modules AG-UI-shaped.** No AG-UI type in the domain schemas in `packages/contracts/src`, and no AG-UI concept inside a module under `apps/server/src/modules/`. The projection sits at the API boundary and the domain does not know it exists.
- **Forking AG-UI.** Do not redefine the event names, do not reimplement the wire format, and do not make the internal event contract AG-UI-shaped. Conforming to an interface is allowed; reimplementing one is not.
- A sandboxed iframe host, a `ui://` template catalogue, or agent-authored HTML.
- An AG-UI client in the web panel. The panel keeps consuming `/api/events` and the web client is not touched. A panel that speaks AG-UI is a possible follow-on, and it is deliberately not this item.
- Any MCP Apps work. MCP is the agent-to-tools plane and AG-UI is the agent-to-user plane; they are complements, and a third format is not the answer. MCP Apps work does not start in this window, and the reason is in docs/streams.md.

### Notes

**The design property that makes this safe.** The AG-UI layer is a projection over the existing event contract, and nothing in the domain depends on it. If AG-UI disappoints, the projection and its route are deleted and nothing else changes. That is the fallback, and it is the reason the existing contract is not allowed to move in this item.

**What AG-UI 1.0 gives us.** Thirty-one event types in eight families — lifecycle, text message, tool calls, state, activity, subagents, reasoning, and raw or custom events — on a SCREAMING_SNAKE_CASE wire format, where every event carries `type`, `timestamp` and `rawEvent`, lifecycle events carry `threadId` and `runId`, and `RUN_STARTED` carries a required `protocolVersion`. Its transports are HTTP with SSE and HTTP with Protobuf; resumption is at the protocol level, by `threadId` and `runId`, with a `STATE_SNAPSHOT` for a client that reconnects after a gap.

**The mapping to reach.** `execution.status` to `RUN_STARTED` and `RUN_FINISHED`; `message.delta` to `TEXT_MESSAGE_CONTENT`; `message.completed` to `TEXT_MESSAGE_END`; `tool.started` to `TOOL_CALL_START` and `TOOL_CALL_ARGS`; `tool.completed` to `TOOL_CALL_RESULT` and `TOOL_CALL_END`; `artifact.created` to a `TOOL_CALL_RESULT` carrying the artefact; `execution.error` to `RUN_ERROR`; and `approval.requested` to a `RUN_FINISHED` whose outcome is an interrupt, with the reason `confirmation`.

**Interrupts are the transport shape of Contract 5.** An AG-UI interrupt is `RUN_FINISHED` with `outcome: { type: 'interrupt', interrupts: [{ id, value, reason, responseSchema?, expiresAt? }] }`, and it is resumed by sending `RunAgentInput` with `resume: [{ interruptId, value }]`. The product's approval request already has an id to carry and a decision to record (CONTRACTS.md, the Contract 5 section), so the interrupt carries the approval's own id and the resume names it. That is the round-trip the criteria require.

**The honest limits.** AG-UI is not ratified by a standards body. It is a community protocol with a published 1.0 version marker, and its generative-UI answer is a draft. AG-UI is also not a generative-UI spec: its stable answer to "render this UI" is that the model emits a tool call whose result carries the payload and the client renders it. If the owner wants agent-authored UI rendered by the panel, that is a different and larger question, and it is not answered here.

**Sources.** AG-UI: <https://docs.ag-ui.com/introduction>, and the spec's own repository at <https://github.com/ag-ui-protocol/ag-ui>.

**Who writes the tests.** Every test file belongs to Probe (FACTORY.md:52), and the implementer does not write the check that accepts its own work (FACTORY.md:147). The criteria above name the checks; Probe writes them.

### Six things the item did not say, said now

**The 1.0 schema is not the sketch in the note above.** The note says an
interrupt carries `value` and a resume entry is `{ interruptId, value }`. The
published 1.0 schema
(<https://ag-ui.com/spec/1.0/schema.json>) says otherwise: an interrupt is
`{ id, reason, message?, toolCallId?, responseSchema?, expiresAt?, metadata? }`
with `id` and `reason` required, and a resume entry is
`{ interruptId, status, payload?, metadata? }` with `status` required and
`payload` carrying the answer. The implementation follows the schema, which is
the protocol's source of truth, and the item's own words ("Conforming to an
interface is allowed; reimplementing one is not") point the same way.

**An artefact is a closed tool call, not a bare result.** The note says
`artifact.created` becomes a `TOOL_CALL_RESULT` carrying the artefact. The
implementation emits `TOOL_CALL_START`, `TOOL_CALL_END` and `TOOL_CALL_RESULT`,
because a call left open when the run finishes is a protocol violation, and a
result that answers a call the consumer never saw is worse than one it did.

**Two routes, not one.** The item asks for "a new route" and a row in the route
table. The stream is one route; the round trip needs a way to send the resume,
so the resume is a second. Both are additive and both are in the route table.

**The mapping table is longer than the note's.** Every one of the eight server
events and every one of the eight agent events has a stated counterpart, and the
events with no counterpart — the heartbeat — are named as such.

**The published counts moved, and the move is accounted for.** The AG-UI resume
is a mutating route, so the panel now has 36 mutating routes rather than 35,
and three of them write their audit entry from the service layer rather than
the route. `CONTRACTS.md` and `published-shapes.test.ts` both say so.

**This session wrote the tests.** The doctrine assigns every `*.test.ts` to
Probe, and an implementer that writes the check that accepts its own work has
not verified anything. The item's acceptance criteria name the checks, and this
session had no Probe to write them, so they are written here and handed over
unreviewed. `apps/server/src/api/__tests__/agui-projection.test.ts` and
`apps/server/src/api/__tests__/agui-stream.test.ts` are Probe's to take over.
The same is true of `CONTRACTS.md`, which the ownership table gives to Wren.

### The output was checked against the protocol's own schema

The projection's events were validated against the published AG-UI 1.0 JSON
Schema — <https://ag-ui.com/spec/1.0/schema.json>, draft 2020-12 — with `ajv`,
across a whole turn, a failed turn and an interrupted turn: **20 events, all
valid.** The schema closes its objects, so an event carrying a field the
protocol does not describe would have been rejected, and none was.

That check is not in the repository, because a test file and the schema
fixture both belong to Probe. The recipe is short: fetch the schema, compile it
with `ajv/dist/2020`, project a turn with `projectServerEvents`, and validate
every event against it. A permanent check of that shape is worth having — it is
the difference between conforming to the protocol and believing one does — and
it belongs to whoever owns the tests.

### What this item does not do

It does not make the panel speak AG-UI to itself. The web client still reads
`GET /api/events`, and nothing in the panel consumes the AG-UI route. It does
not start runs: the route observes the runs the panel is already running, so no
`RunAgentInput` is delivered and `RUN_STARTED` carries no input echo. It does
not touch MCP, and it does not render agent-authored UI.
