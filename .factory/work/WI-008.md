# WI-008 — "Outcome unknown" is a state the owner can see

**Owner:** Cog
**Verifier:** Probe
**State:** verify
**Implemented:** 2026-10-21, commit `9ad4f98`. The owner's approval was given,
and `CONTRACTS.md` carries the entry with its migration note —
[WI-013](WI-013.md), which is Wren's.
**Approved:** 2026-10-20 — the owner approved the contract change.

## Problem

A turn, execution or task whose outcome cannot be confirmed is recorded as
**`failed`**.

- `messageStatusSchema` is `streaming | complete | failed`
  (`packages/contracts/src/conversation.ts:56`);
- `executionStatusSchema` is
  `queued | running | blocked | completed | failed | cancelled`
  (`packages/contracts/src/agent.ts:78-86`);
- `taskStatusSchema` is
  `open | active | blocked | review | done | cancelled`
  (`packages/contracts/src/factory.ts`).

`failed` reads as "safe to retry". An item that may already have had its
side effect can therefore be run twice — a double charge, a duplicated
deploy, a duplicated message to a real person.

**A concrete instance, verified in source.** The worker aborts a turn when
the adapter's timeout elapses (`apps/worker/src/executor.ts:217`), the abort
throws, the throw is caught and assigned to `failure`
(`executor.ts:265`), and the turn is then recorded as
`failed ? { status: 'failed' } : { status: 'completed' }`
(`executor.ts:355`). A turn that timed out is a turn whose side effect may
well have happened. It is recorded as `failed`.

A second instance: **an approval that the owner rejects** is recorded as a
`failed` execution —
`resolveExecution(executionId, body.approved ? 'completed' : 'failed', …)`
(`apps/server/src/api/approvals.ts:46`). A rejection is not a failure of the
work; the work was correctly stopped.

The concept is already understood in this codebase —
`agentConnectionStatusSchema` carries `unknown`
(`packages/contracts/src/agent.ts:52-59`). It was simply never carried onto
work.

## Why now

The owner's whole picture of "what needs me" rests on the panel telling the
truth about each in-flight item. One mislabelled item is how a side effect
runs twice, and the owner is the one who has to live with it.

This is also the plugin's first rule, verbatim: _"Unknown is not a confirmed
failure: do not automatically redispatch."_ and _"Completed side effects are
not rolled back. Unconfirmed cancellation stays unknown."_

**The order matters and the window is open now.** WI-004 ("the landing page
shows what is waiting on the owner") renders the waiting list, and its front
end is currently **held** and uncommitted. If `unknown` lands before that
front end is finished, the waiting list learns to say "check this" once
instead of twice. If it lands after, the waiting list needs a second pass.
Holding WI-004 has accidentally opened the window this item needs.

## The shape

Add `unknown` to message, execution and task status. It means **"we started
this and we cannot confirm how it ended"**. It is never auto-retried, and
the waiting list shows it as "check this", not "fix this". Every transition
to and from it is in the audit trail.

**Which paths are genuinely `unknown` is an implementation judgement, and
this item names the surface that has to be decided.** Every place the code
writes `failed` today is a candidate, and each has to be classified as
_genuinely failed_ or _outcome unknown_:

| Where                                              | What it writes today                                    | Chief's reading                                                                      |
| -------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `apps/worker/src/executor.ts:355` (agent turn)     | `failed` on any error                                   | the **timeout/abort** path is `unknown`; a protocol error from the agent is `failed` |
| `apps/worker/src/executor.ts:548`, `:702`          | `failed` on any error                                   | same judgement                                                                       |
| `apps/worker/src/executor.ts:739-742`              | `failed` on a direct set                                | classify                                                                             |
| `apps/worker/src/executor.ts:68`, `:576`           | `failed` for an unknown job type / a missing automation | genuinely `failed` — nothing started                                                 |
| `apps/server/src/queue/client.ts:162`              | `failed` at enqueue                                     | genuinely `failed` — nothing started                                                 |
| `apps/server/src/api/approvals.ts:46`              | `failed` on a rejected approval                         | not a failure of the work; needs its own reading                                     |
| `apps/server/src/modules/approvals/service.ts:135` | writes `error` when the status is `failed`              | follows the status                                                                   |

A path where **nothing started** is `failed`. A path where **something
started and we cannot confirm how it ended** is `unknown`. The owner of this
item decides each one and records the decision in the item.

Cog's decisions, 2026-10-21. The rule applied to each: _did anything start,
and can we confirm how it ended?_

**One enum beyond the three the shape named.** The automation path has no
message, no execution and no task — only a run — so recording its unknown
outcome needed `unknown` on `automationRunStatusSchema` as well. It is the
same word with the same meaning.

## Acceptance criteria

- [ ] `unknown` exists on message, execution and task status, and means "we
      started this and cannot confirm how it ended".
- [ ] No code path transitions an item to `failed` as a stand-in for
      `unknown`, and every path that writes `failed` today has been
      classified in the work item — with the reason.
- [ ] An `unknown` item is never automatically retried or redispatched.
- [ ] A turn that timed out is recorded as `unknown`, not `failed`.
- [ ] The "waiting on the owner" list shows an `unknown` item as "check
      this", distinct from "failed — retry".
- [ ] The transition to and from `unknown` is written to the audit trail.
- [ ] `CONTRACTS.md` carries the `unknown` entry, with a migration note.
- [ ] `npm run typecheck` and `npm run test` pass, and `unknown` has a named
      test in the state machine.

## Not in scope

- Automatic reconciliation of `unknown` items.
- A background reaper that retries them. "Unknown is not a confirmed
  failure: do not automatically redispatch" is the rule, and a reaper that
  retries would break it.
- Changes to the audit schema beyond the new transition.
- The progress-based pause, routing, or the persona layer.
- Any change to how an approval is decided — that is WI-007.

## Notes

**Published boundary.** Three published enums change and one published
route's behaviour changes. `CONTRACTS.md:71` publishes the message status as
`status?: 'streaming' | 'complete' | 'failed'`; `CONTRACTS.md:201` publishes
`AgentConnectionStatus`, which already carries `unknown`; the execution and
task status enums are published through the event vocabulary and the factory
contract. `CONTRACTS.md` needs the entry and a migration plan, and the
factory stops there for owner approval.

**The migration plan says what it cannot fix.** Rows recorded as `failed`
before this item are **not** reclassified. We cannot know which of them were
really unknown and which were really failed, and guessing would be the exact
dishonesty this item exists to remove. `unknown` applies only to transitions
made after the change. The plan says that in one sentence and stops.

**One dependency, and it is not a blocker.** The waiting-list criterion
touches `apps/web/src/components/WaitingList.tsx`, which is WI-004's front
end and is currently held and uncommitted. Two work items must not write one
file. So: if WI-004's front end has landed, this item meets the criterion
itself; if WI-004 is still held when this item is otherwise complete, the
waiting-list line moves to a follow-up item and **this item is not held open
waiting for it**. WI-004's own hold note records the dependency, so the
front end knows it has to render `unknown` when it resumes.

**Order.** Chief's order for the four items this brief produced:
**WI-008 → WI-007 → WI-006 → WI-009.** This one is first because it is the
smallest, because it is the only one with a window that is open _now_, and
because WI-007's last criterion depends on it.

**Size.** Small-to-medium: three enum additions, one classification pass over
seven `failed` write sites, one audit transition, one waiting-list line, and
the tests for each.
