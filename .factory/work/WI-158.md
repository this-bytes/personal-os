# WI-158 — The claim row's why names the wrong holder, and reads like a guarantee of behaviour

**Owner:** Wren, who wrote the row.
**Verifier:** the Chief, on the lead's own reading of the two sides, with
Probe's measurement as the evidence.
**State:** open — the row's checks are right; its explanation is not.
**Branch:** `wi/158-row-why`, to be created from the current `origin/main`.

## Problem

The claim row `the-widening-is-not-taken-back-wi-146` in
`scripts/contract-status.json` carries seven checks and a `why` that says what
each part of it holds. Two sentences in that `why` are wrong, and Probe measured
both on the tree that ships the row.

**(i) It names a holder that does not hold the rule.** The `why` says:

> The other rule is not held by this row: the editor's not sending the list,
> because a claim of `implemented` may only carry present-_ checks and the gate
> refuses an absent-_ one. **That rule is held by the server's own test** and by
> the published sentence.

The rule named is _the editor's not sending the list_. **The server never sees
what the editor did or did not send** — it receives a body. Probe's measurement:
make the editor send the list as well (one line, in place), and

- **the client's own test** goes red — `does not carry the list the page read`:
  `expected [ 'toolGrantChange', 'toolGrants' ] to deeply equal [ 'toolGrantChange' ]`;
- **the server's own test** stays green — 6 passed of 6, including `applies the
change and does not write the list when a body carries both`;
- **the claim row** stays green — Unchecked (0), Failures (0).

The lead read both sides. The server's test asserts the server's **outcome** when
a body carries both (`apps/server/src/__tests__/grant-change-precedence.test.ts`)
— which is not the same question as what the editor sent. The client's test
asserts the request's keys
(`apps/web/src/components/__tests__/ToolGrantPanel.request.test.tsx:97-112`,
`it('does not carry the list the page read')`):
`expect(Object.keys(body)).toEqual(['toolGrantChange'])` and
`expect(body).not.toHaveProperty('toolGrants')`. **The rule is held by the
client's own test and by the published sentence.**

**(ii) The check binds the file's text, not the behaviour.** As shipped, the
`why` says:

> The last check holds it by order, because the change is read before the list in
> the same file, so a body that carries both takes the change and the list is
> not written.

That reads as a statement about the behaviour. Probe measured two mutations on
the shipped tree, each in place, each restored four ways:

| mutation                                                                                                      | the row             | the shipped grant tests |
| ------------------------------------------------------------------------------------------------------------- | ------------------- | ----------------------- |
| **M-SPELL** — the behaviour is unchanged, the text is not (`patch['toolGrants'] !== undefined`)               | **red** on that row | **16/16 green**         |
| **M-SILENT** — the spelling is unchanged, the behaviour is not (the change branch writes the grant as it was) | **green**           | **8 red**               |

So the assertion binds the **textual order of two conditions in one file**. It
is load-bearing for this code shape — the swap reds that row and nothing else —
but it is not a semantic guarantee: it goes red on a rewrite that changes
nothing, and stays green while the change stops being applied. **The defence
against a behaviour break is the shipped tests, not the row.** Each half of the
pattern occurs exactly once in the file (the change's condition at `:385`, the
list's at `:417`), so it is a unique spelling of the order.

## The lead's ruling

Both findings are **accepted**.

- **(i)** "the server's own test" is **false** and must read "**the client's own
  test**". A published record must not name a holder that does not hold the
  rule — and the measurement shows the named holder stays green exactly when the
  rule is broken.
- **(ii)** The `why` must say what the check binds. Probe's wording is accepted,
  with one tightening: the change's **condition is tested** first — "the change
  is read before the list" is loose.

**Nothing else changes.** The row's `claim` stays `implemented`, its seven
checks stay, the published sentence stays, and the order pin keeps its teeth —
the lead measured that too, on the shipped tree: the claim gate green (28
claims, 0 unchecked, 0 failures) → the branches swapped back → **red on that row
and on nothing else** → the file restored byte for byte, blob `cc25d807` → green
again. This item corrects an **explanation**; it does not weaken a promise,
remove a check, or reword a published guarantee.

## Acceptance

- The row's `why` says "the client's own test", not "the server's own test".
- The row's `why` says the seventh check binds the file's **text** — that it
  requires the change's condition to be written before the list's in
  `service.ts` — and that the shipped tests are what hold the behaviour.
- No check is added, removed or weakened; the `claim` stays `implemented`; the
  seven `expect` entries are byte-identical.
- `CONTRACTS.md` is untouched: the published sentence is correct, and it is one
  of the two things that hold the rule.
- `npm run verify:contracts` is green, and the row is still red when the
  branches are swapped back — measured, reported.
