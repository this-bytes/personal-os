## The problem

**The owner decides on two buttons and a title.** The needs-you rail's approval
row carries a title, a persona, and **Approve / Reject**
(`apps/web/src/components/WaitingList.tsx:272-284`). Nothing else. The owner is
asked to say yes or no to an operation they cannot see: not what the agent did,
not what it produced, not what it cost.

**The evidence exists, and it is published nowhere.** An approval points at the
execution that raised it (`approvals.executionId`,
`apps/server/src/modules/approvals/service.ts:12`). The execution carries its
status, its error and its spend units (`apps/server/src/db/schema.ts:227-231`),
and `execution_events` carries the tool calls and the artifacts
(`apps/server/src/db/schema.ts:241`). There is no executions route file at all,
and `GET /api/approvals/:id` returns the approval only
(`apps/server/src/api/approvals.ts:28-31`).

**Forge settled where this belongs.** The rule the owner chose on 2026-10-21 is
_ if it is a picture of the system, it is in the orientation room; if it is a
place where work is inspected or decided, it is in the execution room_ — and the
needs-you rail carries the decision controls. So the evidence belongs where the
decision is taken, not in a room the owner has to find.

## Acceptance criteria

- [ ] **One entry publishes the evidence a decision is taken against**, and it
      names three things: **what the agent did** (the tool calls, and how each
      ended), **what it produced** (the artifacts), and **what it cost** (the
      spend units, and the execution's status).
- [ ] It is **read-only**, it answers for **one approval**, and it follows the
      same auth rules as every other route — a session cookie or the owner
      token, never an agent token.
- [ ] **It says where the evidence comes from** — the execution the approval
      points at, and its events — and that **no new storage is introduced**; the
      tables exist.
- [ ] **It says what an approval with no execution shows.** `executionId` can be
      null, so a client has to know what an empty evidence is.
- [ ] **It lands before WI-040 builds against it**, and the two agree member for
      member.
- [ ] The migration note says what a client written before the change may
      assume. There is no earlier version of this read, so the note is short:
      there was nothing to read.
- [ ] It does not contradict the decide route's published response, which
      already carries the execution (`apps/server/src/api/approvals.ts:52-57`),
      and it adds no route-table row beyond the read it publishes.

## Notes

**Nothing is written.** The evidence is already in the database. This item makes
it readable under a published promise, so a client knows it may read it and what
it will get.

**Why it is not one item with WI-040.** Because the contract is the promise and
the code is the keeping of it, and they are checked by different people. When
they are one item, the same session writes the promise and keeps it, and the
promise is never tested against anything. The same split as WI-030 and WI-020,
and WI-034 and WI-033.

**The shape is decided here; the surface is not.** This item publishes a read.
It does not say where the evidence is drawn — the drawer, the rail, the
conversation — and it does not decide what the owner sees.
