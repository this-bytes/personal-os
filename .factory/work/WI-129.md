## The gap

The two template kinds disagreed about the one thing the guides say they agree about.

The **automation**'s provider writes `enabled: false` on create
(`apps/server/src/modules/resources/service.ts:276`), whatever the spec asked for. A
template-created automation is therefore always disabled, and the guide says so —
`templates.ts:251`, `templates.ts:263`, `docs/resource-templates.md:660`,
`docs/resource-templates.md:668`.

The **dashboard**'s provider wrote the spec as it arrived
(`apps/server/src/modules/resources/service.ts:180`), `dashboardSpecSchema` accepts
`published: true` (`packages/contracts/src/resource.ts:184`), and the template merge let a
caller's `published: true` override the template's `published: false`
(`apps/server/src/modules/resources/templates.ts:45`, `:509-522`). **A template-created
dashboard could be born published.**

And the dashboard's own guide says the opposite, in three places:

- `templates.ts:81` — _"False, and **the template keeps it false**. A dashboard becomes live
  when it is published, which is a separate act."_
- `templates.ts:93` — _"The dashboard is not published. Publishing is a separate act."_
- `docs/resource-templates.md:595` — the same sentence in the published guide.

**So the code said one thing and the guide said another, and the two kinds of template did
not behave alike.** The dashboard's guide was a false statement in the product's own words.

The only path that applies a template is the MCP `resource.create` tool
(`apps/server/src/modules/mcp/server.ts:439-448`): it resolves the template, merges the
caller's values into the template's spec, and hands the result to the owning provider. The
merge is explicitly **not a judge** — `templates.ts:485` says _"The merge is not a judge. It
merges, and the owning provider judges the result exactly as it judges a spec that arrived
whole."_ So the judgment belongs to the provider, and the two providers judged differently.

## The owner's question, and the three answers it has

The question is published in the design document
(`docs/resource-templates.md` §10): **may a template produce a live resource?** It carries
three coherent answers, and they are not the same product:

1. **No — and the merge refuses.** The merge special-cases the flags. §4.2 rules this out:
   the merge does not judge, the provider does.
2. **Yes — and the provider is the only judge.** The merge does not special-case the flags
   and the provider accepts them, exactly as it accepts them on a raw spec. The design was
   written for this answer.
3. **No — and the provider says so too.** The provider judges the liveness flag itself.

**The document said the implementation had made (2). It had not: it had made two
different answers, one per kind.** The automation's provider implemented (3) and the
dashboard's implemented (2) — and neither was chosen; both were what fell out of how each
kind stores its flag. The automation keeps `enabled` in a column and the provider writes
the column; the dashboard keeps `published` inside its spec and the provider wrote the
spec.

**The owner's answer is still open.** This item does not close it, and the contract
publishes the rule the code carries rather than a decision the owner has taken.

## What this item does

**It makes the two kinds agree, by making the rule one rule: a resource is never born
live.**

1. **The dashboard's provider judges `published` the way the automation's provider judges
   `enabled`.** A dashboard is created unpublished, whatever the spec says
   (`apps/server/src/modules/resources/service.ts:337-345`). The judgment is the owning
   provider's, so it applies to a spec that arrived whole and to a spec that came out of a
   template — the provider cannot judge the same spec two ways.
2. **The merge is untouched.** It still does not special-case the flags. (1) stays ruled
   out by §4.2, and the provider stays the only judge.
3. **Creation is the only place the rule bites.** An update that names `published: true` or
   `enabled: true` still makes a resource live, because an update is a deliberate act on a
   resource that already exists. **The two kinds behave the same way here**: the generic
   `PATCH /api/resources/:id` takes a spec, and the automation's provider writes the
   `enabled` that spec names (`apps/server/src/modules/resources/service.ts:310`) just as
   the dashboard's writes the `published` it names. This was asked of this item and is
   answered by measurement, not by taste: **tightening the rule onto the update path
   turns two of the five cases red**, because `publish()` is itself an update.
4. **Publishing stays a separate, deliberate act.** `POST /api/resources/:id/publish` still
   publishes a dashboard and enables an automation
   (`apps/server/src/modules/resources/service.ts:578`), and the automation also has
   `POST /api/automations/:id/enable` and `POST /api/automations/:id/disable`.
5. **The guides become true.** The dashboard's guide already said the template keeps it
   false; after this item that sentence is true of the code.

### Why the dashboard moved rather than the automation

(2) was not available for the automation without more work. **A born-enabled automation
would have had no `nextRunAt`** — the create writes `nextRunAt: null`
(`apps/server/src/modules/resources/service.ts:278`) and only the enable act computes one
(`apps/server/src/modules/resources/service.ts:597`), so it would have been enabled and
never have run. Under (2) the automation would need its schedule computed at creation,
and **both** templates' guides would have to stop saying that the template keeps the flag
false — including the automation's, which is true today.

## What this item does not do

- **It does not close the owner's question.** §10 still carries it, and the answer the
  code carries is recorded there as a reading, not a decision.
- **It does not change what `published` does.** Nothing in the web client reads it yet
  (`apps/web/src/components/ResourceEditor.tsx:37` is the only mention, and it writes
  `published: false` when the owner starts a new dashboard). **This item makes the rule
  right before the client starts to rely on it.**
- **It does not add a `resource.publish` MCP tool.** The MCP surface has `resource.create`,
  `resource.get` and `resource.update` and no publish tool; an agent publishes a dashboard
  by updating its spec, which this item leaves working. Adding the tool is a separate item.
- **It does not change the automation.** An automation is still created disabled, which is
  already the rule.

## The contract changes

- A new entry, **"A resource is never born live"** (`CONTRACTS.md`): the rule, who judges
  it, that creation is the only place it bites, that the update path is the same for both
  kinds, and what each kind's own act is.
- The route table's `GET/POST /api/resources` row says that a resource is never born live,
  and its `publish` row says that publishing is the act that makes one live.
- A migration note: a client that created a dashboard with `published: true` now gets an
  unpublished one. The flag was inert in the client, so nothing visible changes — but the
  contract says so rather than leaving it to be found.

## The proof

`apps/server/src/__tests__/resource-liveness.test.ts` — five cases:

- a dashboard made from a template is a draft, whatever the caller asked for — through the
  MCP path's own merge, not a shape that resembles it;
- a dashboard made outright is a draft as well;
- an automation made from a template is disabled, whatever the caller asked for — the
  behaviour this item makes the dashboard match;
- a dashboard can still be published, which is a separate act;
- an update that names `published` still makes a dashboard live, because that is
  deliberate too.

**Three mutation proofs**, each restored afterwards:

| Mutation                                                | What it takes away       | Caught by                                                              |
| ------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------- |
| the provider stops forcing `published: false` on create | the judgment             | the two draft cases                                                    |
| the publish act stops setting `published: true`         | the act                  | "still lets a dashboard be published"                                  |
| the judgment is applied to the update path as well      | the boundary of the rule | the publish case and the update case, because `publish()` is an update |
