# WI-129 — A template creates a draft: a resource is never born live

**Numbered:** 2026-10-22 — **WI-129**, read immediately before it was taken: the published
number block in `.factory/INTAKE.md` reads "**The next free number is WI-129.**"

**Owner:** worker, under Chief.
**Verifier:** a verifier who wrote none of this.

## The gap

The two template kinds disagree about the one thing the guides say they agree about.

The **automation**'s provider writes `enabled: false` on create
(`apps/server/src/modules/resources/service.ts:276`), whatever the spec asked for. A
template-created automation is therefore always disabled, and the guide says so —
`templates.ts:251`, `templates.ts:263`, `docs/resource-templates.md:660`,
`docs/resource-templates.md:668`.

The **dashboard**'s provider writes the spec as it arrives
(`apps/server/src/modules/resources/service.ts:180`), `dashboardSpecSchema` accepts
`published: true` (`packages/contracts/src/resource.ts:184`), and the template merge lets a
caller's `published: true` override the template's `published: false`
(`apps/server/src/modules/resources/templates.ts:45`, `:509-522`). **A template-created
dashboard can be born published.**

And the dashboard's own guide says the opposite, in three places:

- `templates.ts:81` — _"False, and **the template keeps it false**. A dashboard becomes live
  when it is published, which is a separate act."_
- `templates.ts:93` — _"The dashboard is not published. Publishing is a separate act."_
- `docs/resource-templates.md:594` — the same sentence in the published guide.

**So the code says one thing and the guide says another, and the two kinds of template do not
behave alike.** The dashboard's guide is currently a false statement in the product's own
words, published at version 1.

The only path that applies a template is the MCP `resource.create` tool
(`apps/server/src/modules/mcp/server.ts:439-448`): it resolves the template, merges the
caller's values into the template's spec, and hands the result to the owning provider. The
merge is explicitly **not a judge** — `templates.ts:485` says _"The merge is not a judge. It
merges, and the owning provider judges the result exactly as it judges a spec that arrived
whole."_ So the judgment belongs to the provider, and the two providers judge differently.

## What this item does

**It makes the two kinds agree, by making the rule one rule: a resource is never born live.**

1. **The dashboard's provider judges `published` the way the automation's provider judges
   `enabled`.** A dashboard is created unpublished, whatever the spec says. This is the
   owning provider's judgment, so it applies to a spec that arrived whole and to a spec that
   came out of a template — the provider cannot judge the same spec two ways.
2. **Publishing stays a separate, deliberate act.** `POST /api/resources/:id/publish` still
   publishes a dashboard (`apps/server/src/modules/resources/service.ts:553-563`), and an
   update that names `published: true` still sets it. Nothing is taken away; the act just
   stops happening by accident.
3. **The guides become true.** The dashboard's guide already says the template keeps it
   false; after this item that sentence is true of the code.

## What this item does not do

- **It does not change what `published` does.** Nothing in the web client reads it yet
  (`apps/web/src/components/ResourceEditor.tsx:37` is the only mention, and it writes
  `published: false` when the owner starts a new dashboard). The flag is a spec field that
  the client does not yet honour. **This item makes the rule right before the client starts
  to rely on it** — which is the point of doing it now rather than after.
- **It does not add a `resource.publish` MCP tool.** The MCP surface has `resource.create`,
  `resource.get` and `resource.update` and no publish tool; an agent publishes a dashboard
  by updating its spec, which this item leaves working. Adding the tool is a separate item.
- **It does not change the automation.** An automation is still created disabled, which is
  already the rule.

## The contract changes

- A new entry publishing the rule: **a resource is never born live**, and what the separate
  act is for each kind.
- The `dashboard` row of the resource-type table names the rule, because the shape alone
  does not say when the flag may be true.
- A migration note: a client that created a dashboard with `published: true` now gets an
  unpublished one. The flag was inert in the client, so nothing visible changes — but the
  contract says so rather than leaving it to be found.

## The proof

Owed, and written before the implementation is claimed done:

- a dashboard created from a template with `published: true` in the override comes back
  **unpublished**;
- a dashboard created outright with `published: true` comes back **unpublished**;
- an automation created from a template with `enabled: true` comes back **disabled** — the
  behaviour this item makes the dashboard match;
- a dashboard can still be published afterwards, through the publish route, and reads back
  `published: true`;
- an update that names `published: true` still publishes it — the deliberate act survives.

**Mutation proofs**, each restored afterwards: removing the judgment turns the first two
cases red; removing the publish route turns the fourth red.
