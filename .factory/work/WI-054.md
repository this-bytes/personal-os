# WI-054 — The `mcp` adapter's contract entry

**Owner:** Wren
**Verifier:** Chief
**State:** verify — the entry is written; it is a published boundary, so the
owner approves it.
**Opened:** 2026-10-21 by the strategy session, from WI-053
**Numbered:** 2026-10-21 — WI-046 through WI-061, taken by the session that owns
the number space.

## The gap it names

A published adapter type with no published contract is a private dialect, and
the doctrine says an interface is conformed to, never reimplemented. The `mcp`
type needs its entry in Contract 2 before anyone relies on it.

## Acceptance criteria

- [ ] **Contract 2's adapter table carries `mcp`**, with what it is for.
- [ ] **The configuration shape is published**: the transport, the command, the
      arguments, the environment, the URL, the token reference, the protocol
      revision, the tool, the argument template, the allow-list and the
      timeout.
- [ ] **The entry says what a turn is** — one tool call, with the tool's text
      output as the reply — and what the adapter therefore cannot do.
- [ ] **The migration note says what a client written before the change does**:
      the adapter type enum grows by one member, the capabilities shape grows by
      one optional member, and nothing is reclassified.
- [ ] **The entry says the code implements it**, and where.

## Not in scope

- **The adapter.** That is WI-053.
- **The interaction model.** WI-052 and WI-055.
- **The MCP surface Personal OS publishes.** That is unchanged: the server's own
  MCP module still exposes Personal OS's tools outward, and this entry is
  about the other direction.

## Notes

The two directions are separate and both are named in the product record: the
outbound surface (Personal OS as an MCP server) and the inbound one (an MCP
server as an agent connection). The protocol boundary question in ADR 0007 is
about the first; this entry is the second, and it does not settle the first.
