## The problem

**A published contract promises a read, and there is no code for it.**

`CONTRACTS.md` publishes **the approval evidence** — `GET
/api/approvals/:id/evidence` — and said in its own words that the code did not
implement it yet:

> **The code does not implement this yet.** The read this entry publishes is not
> in the tree: there is no route for it, and `GET /api/approvals/:id` answers
> with the approval alone (`apps/server/src/api/approvals.ts:28-30`). This entry
> is the contract for **WI-039**, and the drawer that reads it is WI-040's; the
> route that answers it is written against this entry.
> — the note as it stood at `CONTRACTS.md:1471` before this item's landing

**WI-039 published the promise** (`6406291`, `CONTRACTS.md` only, +101 lines).
**WI-040 is the drawer** — the surface that reads it (`apps/web/src` or
`packages/ui/src`), and it is not dispatched. **The route in the middle is
owned by nothing.** Grepping every item file for the read — `approvals/:id/evidence`,
`evidence read` — returns **no item at all**. So the contract publishes a read,
the drawer waits for it, and no work item keeps the promise: the gap sits
between a published promise and a surface that will call it.

**Why this item exists now.** Probe verified WI-010 and found that the
direction document's claim — that the execution trace is "a surface over
existing data" because "all of it is already in the contracts" — is **false for
spend**. The trace's four event types are in the contracts
(`packages/contracts/src/agent.ts:178`), but **`spendUnits` is not on any
execution event**: in the published contracts it appears exactly once, as a
bare schema (`packages/contracts/src/common.ts:58`). The spend units live on
the **execution row** (`apps/server/src/db/schema.ts:231`) and are published by
**this** read — the one that is not in the tree. **A direction that names a
surface over data the product does not publish is a direction that cannot be
built, and the missing half is this route.** The direction document's own
repair names this item (see WI-010); this item is what makes that sentence
true.

**This is not a new contract.** The entry is published, the shape is published,
and the migration note is published: the read is additive, no existing route
changes shape, no record is reclassified, and there is nothing to migrate
because there was nothing to read before.

## Acceptance criteria

- [ ] **`GET /api/approvals/:id/evidence` exists** and answers with the shape
      the contract publishes: `approvalId`, `workspaceId`, and `execution`
      (`ExecutionEvidence | null`).
- [ ] **`ExecutionEvidence` carries all eight members** the contract names:
      `id`, `status`, `error`, `spendUnits`, `startedAt`, `finishedAt`,
      `toolCalls`, `artifacts` — member for member, with the same names and the
      same nullability.
- [ ] **What the agent did** is `toolCalls`: the execution's `tool.started`
      events and the `tool.completed` events that answer them
      (`packages/contracts/src/agent.ts:190`, `:196`). A call that answered has
      `outcome: 'completed'` and a `completedAt`; a call that did not has
      `outcome: 'unfinished'` and a `completedAt` of `null`. **The events name
      the tool and not the call**, so a call is answered by the next completion
      for that tool.
- [ ] **No reason is invented.** The published vocabulary has no failure event
      for a tool call, so the events do not say why a call did not finish, and
      this read does not claim a reason.
- [ ] **What it produced** is `artifacts`: the execution's `artifact.created`
      events (`packages/contracts/src/agent.ts:209`), each with the title it
      was given and the resource it made, when it was given either.
- [ ] **What it cost** is `spendUnits` and `status`. `error` carries the reason
      the execution stopped, **and only then**: a cancellation carries `null`,
      because a cancellation is a decision and not a fault
      (`apps/server/src/modules/approvals/service.ts:175-184`).
- [ ] **The spend units are reported as recorded, and the read does not
      pretend otherwise.** `spendUnits` comes from the execution row
      (`apps/server/src/db/schema.ts:231`), which is created at `0`
      (`apps/server/src/modules/conversations/dispatch.ts:171`) and is not
      written afterwards — the turn count the router uses to enforce a spend
      limit is computed in memory and never stored
      (`apps/server/src/modules/conversations/routing.ts:299-306`). **The read
      reports the column. It does not compute a spend.**
- [ ] **It is read-only, it answers for one approval, and it takes the same
      authentication as every other route** — a session cookie or the owner
      token, and **never an agent token**, which is MCP-only.
- [ ] **An approval with no execution shows no execution.** `executionId` can
      be null (`apps/server/src/modules/approvals/service.ts:14`), and the
      execution it names can be gone
      (`apps/server/src/modules/approvals/resume.ts:63-85`). Both show
      `execution: null`, and with it no tool calls, no artifacts and no cost.
- [ ] **It does not contradict the decide route's published response**, which
      already carries the execution (`apps/server/src/api/approvals.ts:61-66`),
      and **adds no route-table row beyond the read it publishes**.
- [ ] **No new storage.** The approval, the execution and its events all exist
      already (`apps/server/src/db/schema.ts:218-241`, `:243`).
- [ ] **The contract is not changed by this item.** The entry is published; this
      item keeps it. **If the implementation cannot match the published entry,
      that is a finding to report, not a reason to change the entry** — the
      contract leads the code.

### The order, named by the lead, and why it is not negotiable

**All three land in one tree, and the tree is pushed once.** The claim can only
be true on a tree that carries the route, so the note and the table cannot
land before it. And the note and the table cannot land apart: one without the
other is a `disagreement`, which is also a red. **So: the route (done), then
the note, then the table, then one push, then the merge to `main`.**

**Nobody pushes in between.** A push of the note without the table is a red CI
run on the branch, and a push of the route without the note is a red CI run on
`main`. **One push at a time, and let the run finish.**

**And the branch is no longer stale — it was rebuilt.** The branch had been cut
from `main` at `ceed799` and was seventy-three commits behind, with one commit
of its own. **On 2026-10-22 the branch was reset onto `main` at `76ce2a3` and the
change was re-applied**, so the note is written against today's tree rather than
a tree three days old. The old commit `d4926f0` is not an ancestor of this
branch; its content is, and the item file's own history of it is above.

**The line number in the peer session's notice was right, and it moved.** The
note was at `CONTRACTS.md:1471` when the notice was written and it is at

five lines. **The gate does not use the line number** — it finds the note by the
section heading ("The approval evidence") and the note's fragment — so the

**The mutation proof, measured on this tree and not inherited.** The reader was
broken three ways, one at a time, and the file was run after each:

| Mutation                                                     | What it breaks               | Cases red |
| ------------------------------------------------------------ | ---------------------------- | --------- |
| every call is born `completed`                               | a call that nothing answered | 2         |
| an execution is fabricated for an approval that names none   | `execution: null`            | 1         |
| an execution is fabricated for an approval whose row is gone | `execution: null`            | 1         |

The four cases that go red are exactly the four that name those behaviours —
_"answers a call that was answered, and a call that was not"_, _"answers a
completion to the call it belongs to, and leaves the other call unanswered"_,
_"answers no execution for an approval that names none"_ and _"answers no
execution for an approval whose execution is gone"_ — **and nothing else goes
red.** Each mutation was reverted, the file has no residue of any of them, and
the thirteen cases are green again.

**One mutation had to be made honestly to bite.** Removing the guard that
answers `execution: null` for an approval that names no execution changes
nothing: the lookup that follows matches `id = null` and finds no row, so the
second guard answers `null` anyway. **The mutation that bites fabricates an
execution**, and it is that fabrication — and not the missing guard — that the
test catches.

**One thing the old branch got wrong, and the landing fixed.** `packages/contracts/src/index.ts`
is the one file this item shares with other work: `main` added
`export * from './autonomy.js';` after the old commit was written, and
re-applying the old file wholesale would have taken that export away with it —
the tree would not have built. **Only this item's own line was added to main's
current file**, and the export it removed is still there.
