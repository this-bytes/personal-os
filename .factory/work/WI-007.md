**Approved:** 2026-10-20 — the owner approved the contract change.

## Problem

When an agent asks for approval, the execution is marked `blocked` and
deciding the approval **finishes** the execution. It never re-enters the
adapter.

Verified in source, not from a description:

- `apps/server/src/api/approvals.ts:41-51` — "The decision has to change the
  outcome of the operation that asked for it. An approval that changes
  nothing is not an approval." The decision calls
  `resolveExecution(executionId, approved ? 'completed' : 'failed', …)`.
- `apps/server/src/modules/approvals/service.ts:131-140` —
  `resolveExecution` writes the status, writes `error` when the status is
  `failed`, and stamps `finishedAt`. The execution is over.

So the agent's work stops at the question instead of continuing through it,
and the owner has to start a new turn to finish a job the agent was already
halfway through. `ARCHITECTURE.md:306-311` records this as deliberate, on the
grounds that resuming "needs a protocol-level resume that not every adapter
supports".

**The premise is already modelled and negotiated, which changes the
answer.**

- `AgentCapabilities.persistentSessions` exists
  (`packages/contracts/src/agent.ts:34`).
- The ACP adapter sets it honestly from the agent's own capabilities:
  `persistentSessions: caps.loadSession === true`
  (`packages/agent-adapters/src/acp.ts:59`).
- The extension point `AgentAdapterExtras.resumeSession` is already declared
  (`packages/contracts/src/agent.ts:174-180`) and **never implemented**.

The decision in the code is therefore "never resume", where the honest
decision is **"resume when the adapter says it can"**. This is candidate C-01,
and it is the clearest interaction defect Personal OS has.

## Why now

It is the single place where the owner's priority job — talking to agents —
is visibly broken: the agent asks a question, the owner answers it, and the
answer goes nowhere. The gate that makes the fix safe already exists, and
nothing has been built on top of it yet, so it is cheap to get right now and
expensive to get right later.

It also closes part of C-03: ACP sessions are created per turn instead of
resumed, though the protocol supports it.

## The shape

Keep the execution `blocked` while the owner is deciding. On a decision:

- the adapter reports `persistentSessions` → re-enter the **same** session
  with the decision as its next input, and let the turn finish normally;
- otherwise → today's behaviour, unchanged and **explicit**: the execution
  finishes with the decision's outcome, and the panel says the turn was
  closed rather than continued.

The capability gate is the whole trick. It makes the plugin's behaviour
reachable without pretending every adapter can do it. Do not add a second,
parallel signal.

**What has to be built, concretely:**

1. **Persist the external session id** with the execution, so a later decision
   can resume it. `executions.externalRef` exists and is documented as
   "External orchestrator reference" (`apps/server/src/db/schema.ts`) — using
   it for an ACP session id changes what that column means, which is why this
   item touches `CONTRACTS.md`.
2. **Implement `resumeSession`** on the ACP adapter, restoring the native
   session and returning its id, and have the worker pass
   `externalSessionId` into `AgentTurnInput` — the field exists
   (`packages/contracts/src/agent.ts:146`) and is never set today
   (`apps/worker/src/executor.ts:234-240`).
3. **Decide, then resume** — the decision must be recorded and the turn
   restarted with the decision as its next input, in that order, so an
   approval is never lost because the session could not be restored.

## Acceptance criteria

- [ ] An approval decision leaves the execution `blocked` until the resumed
      turn completes; it does not finish the execution.
- [ ] When the adapter reports `persistentSessions`, the turn resumes in the
      same session with the decision as its next input.
- [ ] When the adapter does not report `persistentSessions`, today's behaviour
      is unchanged, and the panel says the turn was closed rather than
      continued.
- [ ] The ACP adapter implements `resumeSession`, and a resumed turn keeps the
      same session id.
- [ ] The decision is recorded **before** the resume is attempted, so a
      failed resume does not lose the owner's answer.
- [ ] A decision on an execution that is not in a state that can accept one
      is refused, and the refusal says why.
- [ ] `CONTRACTS.md` carries the approval-resume entry, with a migration
      note, and the paragraph it replaces is gone.
- [ ] `npm run typecheck` and `npm run test` pass; the resume path and the
      no-resume path each have a named test.

## Not in scope

- Resuming for adapters that cannot. The capability gate is the gate.
- Changing the approval request shape.
- Any adapter beyond ACP.
- The loop-breaker, the progress-based pause, or anything about routing.
- The `unknown` state. A decision on an execution whose outcome is _unknown_
  must not be submittable, and that state is WI-008's. This item implements
  the half that exists today — a decision on an execution that is not
  `blocked` is refused — and WI-008 extends the rule to the new state.

execution stays blocked until the resumed turn; the resume continues the same

adapter implements `resumeSession` and keeps the session id; the decision is
recorded before the resume is attempted; a decision on an operation that cannot

**One criterion is only half met, and it is half met in the place the

- The **server keeps it**: `apps/server/src/modules/approvals/resume.ts:147-149`
  produces the sentence verbatim — _"The turn was closed rather than

  wording (`apps/server/src/__tests__/approval-resume.test.ts:291`).
- The **client drops it**: `apps/web/src/components/WaitingList.tsx:97-112` —
  the `decide` mutation reads the response only to invalidate the query;
  `outcome` and `detail` are never read.

So what the owner is left with is the entry leaving the waiting list saying
nothing, and the agent's reply badged **'failed'** in the conversation
(`apps/web/src/components/ChatMessageList.tsx:114-118`) — a word with no
sentence. The reason exists in the audit trail as `approval.closed`, and the
panel never surfaces the audit trail at all (0 matches for `audit` anywhere in
`apps/web/src`).

The red e2e is committed: `apps/web/e2e/waiting-list.spec.ts:266` — _"the panel
says when a turn was closed rather than continued"_ — and the other nine tests
in that file still pass.

**The fix belongs in the client, not in the contract and not in the status
choice.** Of the four statuses the message vocabulary allows
(`'streaming' | 'complete' | 'failed' | 'unknown'`), `'failed'` is the only
honest one: `'complete'` would say the turn finished — the lie this item
removed; `'unknown'` would say nobody knows, when the owner does; `'streaming'`
would say it is still running, when it is not. Probe checked the pre-change
route too (`git show 5f019b9^:apps/server/src/api/approvals.ts`): it set
exactly the same statuses, so the execution side is preserved and a decision
is rightly not an error.

**Two more things the review found, both small.**

- **The migration note covers the blocked case; the completed case is refused
  but never closes.** An approval raised before the deploy has a _completed_
  execution — the old worker wrote `'completed'` over the `'blocked'` — so
  deciding it is refused with _"This operation is completed. It is not waiting
  for a decision"_ and the approval then stays `pending` forever, with no
  path to resolve it and no note saying so. One sentence in the note.
- **A failed enqueue after a recorded decision leaves a turn that cannot be
  re-triggered.** The order is decide → audit → enqueue, which is what
  criterion 5 demands, and it is right: an answer is never lost. But if
  `queue.enqueue` throws, the approval is already `approved` (a second
  decision is refused), the execution is still `blocked`, and nothing
  re-drives it — there is no reaper of blocked executions in the server.
  **Chief's ruling: the decision stands and the turn does not continue.** A
  re-run of the resume is the right shape, but it is a new mechanism and it is
  not this item's job; the refusal says why, and that is the honest outcome
  for now. Recorded, not built.

**One thing the proof does not reach, and it goes on the record.** The
mechanism is proven against a fake ACP agent. The adapter declines every peer
request (`packages/agent-adapters/src/acp.ts:95-99`) while advertising
`approvals: true` (`acp.ts:63-71`), so **no real ACP turn can raise an
approval, and nothing in production has ever suspended a turn.** The ACP
protocol work is a different item, and Cog was right not to invent it.

## Notes

**Published boundary — and it is a direct contradiction, not an addition.**
`CONTRACTS.md:426-431` publishes the current behaviour in bold:

> **Deciding an approval finishes the execution it belongs to.** An approved
> request closes the execution as `completed`; a rejected one closes it as
> `failed` with the owner's reason. The decision does **not** re-enter the
> adapter and continue the interrupted turn — resuming a blocked adapter turn
> needs a protocol-level resume that not every adapter supports. This is a
> deliberate limitation, documented rather than approximated.

This item does not add to that paragraph — it **replaces** it. The published
contract says the opposite of what this item builds, in bold, and calls the
opposite a deliberate limitation. That is the hardest kind of contract
change there is, and it is exactly why the factory stops here for the owner:
they wrote that paragraph on purpose, and it must be rewritten on purpose
too. The `CONTRACTS.md` entry is the deliverable, not a footnote to it.

**The migration plan is short and must say this.** Executions that are
already `blocked` when this ships have no persisted session id, so they
cannot be resumed — a decision on one closes the execution, exactly as
today. Only executions started after this item carry a session id. The plan
states that boundary; it does not attempt to recover the past.

**One dependency, and it is not a blocker.** The plugin's guard — _"This task
has stopped or its outcome is unconfirmed; the answer cannot be submitted"_ —
needs WI-008's `unknown` state to exist. This item implements the `blocked`
half; WI-008 extends it.

**Order.** Chief's order for the four items this brief produced:
**WI-008 → WI-007 → WI-006 → WI-009.** WI-008 goes first because it is
small, because it unblocks the last criterion here, and because its
`unknown` state is what the waiting list must be able to say.

**Size.** Medium: one adapter extension implemented, one worker change, one
server service path, one column's meaning, one contract entry, and two named
tests.
