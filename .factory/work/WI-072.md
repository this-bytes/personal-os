## WI-072 — The factory's queue is a file a program can read

**Owner:** Chief

### Problem

The state of every work item lives in a `**State:**` line inside a prose file, and `scripts/work-item.ts` reads it with a one-word regex (`scripts/work-item.ts:324-327`). There is no machine-readable queue, so a program that wants to know what is live has to parse prose. The prose parsing does not even work on every file it is pointed at.

**The read is wrong today, not just clumsy.** `scripts/work-item.ts:325` matches `**State:**` followed by a lowercase word. `WI-030`'s state word is wrapped in bold — `**State:** **done** — 2026-10-21 08:34:37` (`.factory/work/WI-030.md:5`) — so the regex does not match and the item reads as `unknown`.

**The state set has already drifted.** `.factory/TASK.md:49-60` publishes six states: `intake`, `triage`, `implement`, `verify`, `review`, `accepted`. The files carry two that are not in that table: `superseded` (`.factory/work/WI-016.md:4`) and `done` (`.factory/work/WI-030.md:5`). The contract's table is not what the repository holds.

**The owner field is prose, and one of them is truncated mid-clause.** `.factory/work/WI-068.md:3` reads `**Owner:** Chief (the `LICENSE` file and the ownership table), with Wren (the`. It names two owners, which FACTORY.md:142-143 forbids, and the sentence stops in the middle.

**The tool is three commands and a human table.** `scripts/work-item.ts:383-390` dispatches `new`, `list` and `remove`, and nothing else. `list` prints a table for a person (scripts/work-item.ts:294-315), and an item whose work-item file is not reachable from the reading checkout appears as five words, `no work item file` (`scripts/work-item.ts:311-313`).

**The size of the drift is measured.** On the tree this item would land on, the fifty-four item files carry 27 at `implement`, 8 at `verify`, 2 at `triage`, 1 at `superseded`, 15 at `accepted`, and one that reads as nothing at all. The research agent measured 23 at `implement` out of 36 non-accepted items on its own snapshot; the numbers move because the queue moves, and nothing in the repository can say what is live. Roughly twenty items sat at `implement` with no live dispatch, no branch and no worktree: they looked busy and were not.

### Why now

The window is being spun into parallel streams, and a stream that cannot be dispatched cannot be started. This item is the plumbing that makes the rest of the window legible.

It is also the honest prerequisite for the thing the factory cares about most. FACTORY.md:7 says the repository is the state, and FACTORY.md:324 says that includes the queue. A queue only a person can read by eye is not in the repository in any sense a program can use.

The research behind this item asked how other tools make a work-item state machine real and how to read CI back. Both answers are concrete and neither needs new infrastructure: the shape below is the GitHub Agentic Workflows shape (Markdown task files as the source) with the Kubernetes `hack/verify-generated-files.sh` discipline (generate, then fail if the tree is dirty), and the CI read-back works on this machine today.

### The design

**The item file stays the record; the queue is a generated artefact.** Each item file gets one fixed YAML header block, and the prose stays prose. The `**State:**` prose line is **removed**, because two representations of the state is the drift itself. The `**Owner:**`, `**Verifier:**`, `**Opened:**`, `**Numbered:**`, `**Dispatched:**` and `**Landed:**` lines become header fields, and the sentences that explain them stay in the prose around them.

```yaml
---
id: WI-067
title: The MCP surface's id-addressed tools are not scoped to a workspace
state: implement
stateReason: opened, numbered and dispatched
owner: Cog
verifier: Probe
opened: 2026-10-21
numbered: 2026-10-21
dispatched: 2026-10-21T14:32
dispatchId: wi-067-mcp-workspace-scope-code-2026-10-21
landed: null
landedSha: null
branch: wi/067-mcp-workspace-scope
worktree: G:\code\personal-os-worktrees\067-mcp-workspace-scope
blockedBy: []
files: [packages/agent-adapters/src/mcp.ts]
history:
  - { at: 2026-10-21T14:32, from: triage, to: implement, by: Chief }
---
```

**The generated queue is `.factory/queue.json`**, one object per item, carrying `id`, `title`, `state`, `stateReason`, `owner`, `verifier`, `openedAt`, `numberedAt`, `dispatchedAt`, `dispatchId`, `landedAt`, `landedSha`, `branch`, `worktree`, `blockedBy[]`, `files[]`, `ci{ sha, conclusion, checks[{ name, status, conclusion, url }], fetchedAt }` and `history[]`. It is **never hand-edited**: CI regenerates it and fails if `git diff --exit-code .factory/queue.json` is dirty.

**`scripts/work-item.ts` is the tool, not a new script.** The existing script already has `new`, `list` and `remove`, and a second script for the same job is a second tool. It gains:

- `queue [--write]` — emit the index, or refresh it.
- `set <WI-nnn> <field> <value>` — the **only** writer of state. It validates the transition and appends to `history`.
- `check` — a validator.
- `claim` — print the live claims, from `git worktree list --porcelain` and the item headers.

**The state set** is `intake → triage → implement → verify → review → accepted`, plus the terminal states `cancelled` and `superseded`. `done` is not a state: `WI-030` is migrated to `accepted` or `cancelled`, and `WI-016`'s `superseded` gets a legal home. `.factory/TASK.md:49-60` is updated to publish the set the repository actually holds.

**The transitions, and who may make them.** The load-bearing one is that **`implement → verify` is the only automatic transition**, fired by Chief on landing, with the evidence being the landed sha and CI green on that sha. Everything that changes the _meaning_ of the work still needs a human, and `review → accepted` is Chief's alone and is never automatic.

| Transition           | Who may make it                 | Evidence                                                                  |
| -------------------- | ------------------------------- | ------------------------------------------------------------------------- |
| → `intake`           | Chief                           | the want in `.factory/INTAKE.md`                                          |
| `intake → triage`    | Chief                           | the owner set to exactly one role token                                   |
| `triage → implement` | Chief                           | a dispatch id, a branch and a worktree recorded                           |
| `implement → verify` | Chief, automatically on landing | the landed sha, and CI green on that sha                                  |
| `verify → review`    | Probe                           | Probe's report against the criteria                                       |
| `review → accepted`  | Chief only                      | every gate green on the landed sha                                        |
| `review → implement` | Chief                           | the findings attached                                                     |
| any → `cancelled`    | Chief                           | a reason; the dispatch is released and its id becomes reserved, not spent |
| any → `superseded`   | Chief                           | the item it supersedes, named                                             |

**`blockedBy` is a field, not a state.** `blockedBy: [WI-nnn, …]`. An item is blocked exactly when `blockedBy` is non-empty and at least one blocker is not `accepted` or `cancelled`. This is the shape GitHub uses for `dependencies/blocked_by` and Linear uses for `blocks` and `blocked`. A resolved blocker is not deleted: it becomes `related`.

**Three independent claim layers, each enforced by a different primitive.** This is the direct answer to the "two agents, one file" failure this repository keeps hitting.

- **The item claim is the branch and the worktree.** `work-item.ts new` creates the branch `wi/<nnn>-<slug>` and a worktree, and git itself refuses to check out a branch twice. `git worktree list --porcelain` is the machine-readable claim list.
- **The file claim is a declared `files:` list.** Every item declares the paths it will touch, and `check` fails when two **live** items declare an overlapping path.
- **The owner claim is one role token on one live item.** `owner: Cog` — never "Cog (the code), with the contract half for Wren". `check` fails when a role owns two live items whose `files:` overlap.

**The number space, in rules that make a duplicate impossible without new infrastructure.** `new` computes the next number as the maximum number across `main` and every open `wi/*` branch, plus one, and a `--number` override is refused unless that number is unused on **every** ref (`git ls-tree -r --name-only <ref>` over `origin/main` and the `wi/*` branches). The number and the file are born together in one commit. **The push is the serialisation point**: git rejects a divergent branch push and the pre-push hook already refuses a non-fast-forward, so the loser re-runs `new` and takes the next number, exactly as a server-side counter works. Numbers are never recycled and never renamed; a cancelled item keeps its number and its file. `check` fails when one number appears on two item files on any ref.

**CI read-back works, and it is what makes `implement → verify` automatic.** This was believed to be impossible and is not. `git credential fill` returns a `gho_` OAuth token with `repo` scope, and `GET /repos/this-bytes/personal-os/commits/<sha>/check-runs` returns the check runs for this private repository — ten of them on `origin/main`, all green. The check names are `Build and run the stack`, `Build and test`, `Dependency audit`, `Lint the workflows` and `Analyze (javascript-typescript)`. Two traps: `GET /commits/<sha>/status` returns `total_count=0` here, because Actions reports through **Checks** and not through commit statuses, so read check-runs and not statuses; and a local unpushed sha returns `422`, not `404`, so read check-runs only for shas the remote has. **CI green is necessary but not sufficient**: it is the evidence for `implement → verify` and never for `review → accepted`.

### The plan, in the order it lands

**Commit one: the header block, `queue --write`, and the test.** That alone turns a prose queue into a readable one, costs one commit, changes no doctrine, and lets the numbers be measured — how many items are live, how many are blocked, how many overlap a file — _before_ any dispatcher is designed.

**Commit two: the CI gate** that regenerates `.factory/queue.json` and fails if the tree is dirty, and the CI read-back that makes `implement → verify` automatic.

**The dispatcher is the last thing to be built, if it is built at all.**

**The migration is a migration with a mapping, not a silent rewrite.** Converting the existing files to the header block is a mechanical change across roughly fifty files, and it is the largest risk in this item. Every file that is converted gets its mapping recorded — the old prose state to the new state, and the old prose owner to exactly one role token — and the mapping is in the commit that does the conversion, not in a reviewer's head. **An item whose file is not yet migrated appears in the index with an explicit `blockedReason` rather than silently missing.** The same rule covers WI-046, whose file lives on its own branch and is not reachable from the reading checkout: it appears, with the reason.

### Acceptance criteria

**Stage one — the header and the index.**

- [ ] Every item file carries one YAML header block with the fields above, and the `**State:**` prose line is gone from it.
- [ ] The existing files are converted with a recorded mapping, and the mapping is in the commit. A file that is not converted appears in the index with an explicit `blockedReason` rather than silently missing.
- [ ] `npx tsx scripts/work-item.ts queue --write` regenerates `.factory/queue.json` from the item files, and the output is byte-identical on a second run.
- [ ] A work item's state and owner in the index match the header of its own file, and `WI-030` reads as `accepted` or `cancelled` rather than `unknown`.
- [ ] `npx tsx scripts/work-item.ts list` and the index agree for every item. A named test proves the agreement rather than a reader checking it by eye.
- [ ] `.factory/TASK.md` publishes the state set the repository holds, including `cancelled` and `superseded`, and the transition table above with who may make each one.
- [ ] `set` is the only writer of state: it refuses a transition the table does not allow, and it appends to `history`.
- [ ] `check` fails when two live items declare an overlapping path, when a role owns two live items whose `files:` overlap, and when one number appears on two item files on any ref.
- [ ] `claim` prints the live claims from `git worktree list --porcelain` and the item headers.
- [ ] The generator's and the validator's tests are named, and they run in `npm run test`. Note the constraint: `npm run test` runs the workspaces' suites, so the harness that reaches them is part of the change.

**Stage two — the gate and the read-back.**

- [ ] CI regenerates `.factory/queue.json` and fails when `git diff --exit-code .factory/queue.json` is dirty.
- [ ] The CI read-back reads check-runs and not commit statuses, and it handles the `422` of a local unpushed sha instead of treating it as a pass.
- [ ] `implement → verify` fires only on a landed sha with CI green, and `review → accepted` is never automatic.

**Both stages.**

- [ ] `npm run typecheck` and `npm run test` pass.

### Not in scope

- **A scheduler daemon or worker that polls and dispatches.** The plugin's `MAX_RUNNING = 2` is hard-coded in someone else's runtime and no setting in this repository changes it, so a scheduler here cannot raise throughput. It can only stop losing work, and losing work is the problem this item fixes by making the queue visible.
- **A database table for work items.** That is a second source of truth, and FACTORY.md:7 says the repository is the state.
- **An auto-dispatcher that assigns an owner with no human in the loop.** Every system that does this keeps a human at that point, and the failure is measured: one subagent explored the 2021 automotive chip crisis while two other agents duplicated the work.
- **An elapsed-time watchdog that cancels stalled tasks.** Elapsed time alone cannot tell a stall from a long task: five legitimate tasks that day ran past two hours and all finished.
- **A second verifier.** There is one verification role, and the separation is the point.
- **Auto-merge or auto-accept.** `review → accepted` is Chief's alone.
- **GitHub Issues as the tracker.** It moves the state out of the repository, which contradicts the repository's own doctrine.
- **A vendored state-machine library.** The states and the transitions are six lines of a table, and the tool is already ours.
- **A priority queue or a merge queue.** The measured failure is _lost_ work, not mis-ordered work.
- **Changing the doctrine in FACTORY.md.** The rules stay as they are; this item makes them checkable.

### Notes

**Who owns what here.** `.factory/TASK.md`, `scripts/work-item.ts`, `.factory/queue.json`, `.github/workflows/**` and `FACTORY.md` are Chief's (FACTORY.md:56-62). `*.md` and `docs/**` are Wren's, and the template in `.factory/TASK.md` and the states table in it are part of this change. **CONTRACTS.md does not change**: the item template is factory-internal and not an API boundary, and nothing here crosses one. Any test for the generator or the validator is Probe's file (FACTORY.md:52), and the implementer does not write the check that accepts its own work (FACTORY.md:147).

**Where the index lives and what it is.** `.factory/queue.json`, beside the work-item files it is generated from. It is not a new place to record the state: the prose file remains the record, and if the two disagree the prose file is right and the generator is wrong.

**The honest limit.** The generator can see what the repository says: the header fields, the worktrees that exist, the branches that exist, and which item files are reachable. It cannot see a dispatch that was never delivered, and it cannot know whether an agent is working right now. Where the repository's own state is silent, the index says that it is silent rather than guessing, and the report says which fields are read and which are inferred.

**The number space, restated once.** The rule that one session opens work items (FACTORY.md:296-307) is a convention; the rules above make a duplicate impossible without it. Numbers are never recycled and never renamed, and a cancelled item keeps its number and its file.
