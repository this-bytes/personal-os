# WI-156 — The published "one write" has no shipped check that would notice it

**State:** accepted — delivered as `f04d674` and accepted by the Chief on its own
measurement of the delivery: the check counts the writes, it goes red when the
grant is written more than once, and the nine gates are green on it. The
independent review is outstanding, and any finding that refutes this reverses
it.

## Problem

`CONTRACTS.md` publishes, under **WI-131** and WI-132's waiting-list entry:

> **The row leaves when the grant is widened.** ... Whichever way the grant was
> widened, the row leaves: the change, the widening and the list all go through
> **the one write** that changes a grant
> (`apps/server/src/modules/agents/service.ts:472`).

and, as WI-131's own entry:

> **The row leaves and the grant is written in one transaction (WI-131).** The two
> writes are one change and are made together
> (`apps/server/src/modules/agents/service.ts:353`).

**The one write is a promise about the number of writes, and nothing in the tree
counts them.** Every check that touches this code asserts what the row says or
what the grant holds — never how many times the row was written.

The four shipped grant checks — `grant-change-precedence`,

## Why this is an item and not a note

The claim table cannot hold it either. Its rows carry `present-pattern`
assertions, which test the **text** of a file; a promise about the _number_ of
writes is not a thing a pattern can see. The published sentence therefore rests
on nothing — the same shape as WI-131's original defect, where a published
guarantee had no code behind it.

## Acceptance

- A shipped check fails when the grant is written more than once on a path that
  the contract says is **one write**, and passes when it is one write.
- The check is red on the mutation and green on the tree — both sides measured
  and reported.
- The published sentence is **not** weakened, narrowed or reworded to make a
  check pass. If the check cannot be written against the sentence as published,
  the sentence and the code are re-read together and the disagreement is
  reported.
- No test is deleted, skipped or loosened; no `it.fails`, `.skip` or `.only`.

## Scope

- **In scope:** the server's grant write, the check that counts it, and the
  claim table or the contract only if the re-read shows one of them is wrong.
- **Out of scope:** the widening's semantics (WI-146, closed), the panel
  (WI-155, closed), the body's shape and order (WI-146, closed).

## 2026-10-23 — The lead: WI-156 is accepted. The check counts the writes, and the count bites.

**The delivery.** Probe's branch `wi/156-one-write-check` at `f04d674`, on
parent `19bedad`. **One file**:
`apps/server/src/__tests__/grant-one-write.test.ts` (+187). No implementation
is touched — the promise is published in `CONTRACTS.md` and in the claim table,
and nothing in either needed changing.

**What the check does.** A trigger on the connection table records every UPDATE
the server issues that mentions the grant column, and each of the three paths
the contract names — the editor's change, the widening, and the list — is asked
how many writes it took. It counts the **statements**, not the rows that
changed, because a second write of the same values is still a second write and
is still invisible in the outcome. The agent's own creation writes its
connection row once more when the server probes the new agent; that write
leaves the grant alone, so it is not a write that changes a grant and is not
counted.

**The lead's own measurement, on the delivered commit.** The lead wrote none of
it, so the lead can measure it, and the standard is the one the lead holds
every check to: **a check is proved by mutation.** With the grant written
**twice** instead of once — the same `tx.update(agentConnections)` issued twice
in the same transaction at `service.ts:472` — the check goes red, and it names
all three paths:
