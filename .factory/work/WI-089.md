## The problem

**Nothing connects a change an agent makes to the instance that runs it.**

The deployment is `docker compose -f deploy/compose.yaml up --build`: one image, two
targets, and the code is baked into the image at build time. An agent that lands a
change on a branch has changed nothing about the running instance. The only place
the whole product runs end to end is the Compose job in CI, which is torn down
again with `down -v` (`ci.yml:234`).

Two things make that worse than it looks.

**A change to a shared package does not reach a running dev process at all.** The
workspace packages publish their compiled output, so `tsx` resolves
`@personal-os/contracts` to `packages/contracts/dist`. Measured with the repository's
own toolchain:

```
current:    contracts -> packages/contracts/dist/index.js
            adapters  -> packages/agent-adapters/dist/index.js
with paths: contracts -> packages/contracts/src/index.ts
            adapters  -> packages/agent-adapters/src/index.ts
```

So an edit to `packages/contracts/src/agent.ts` — a new adapter type, a new field —
reaches nothing that is running until that package is rebuilt. The web client
imports contracts' _runtime_ values (`adapterTypeLabels`, `mcpToolNames`,
`triggerableEventTypes`, `serverEventSchema`), so the panel shows a stale adapter
list and a stale tool list for the same reason.

**A deploy can run an agent turn twice.** The worker holds a job lease and
heartbeats it every thirty seconds (`apps/worker/src/index.ts:61-64`).
`reapStaleJobs` sets a job whose lease has expired back to `queued`
(`apps/server/src/queue/client.ts:207-240`), so it runs again. `up --build`
recreates the worker container: SIGTERM, Docker's default ten-second stop timeout,
SIGKILL if the turn is longer — and the turn is then re-executed. The `unknown`
guard only covers a job whose work was already recorded unknown; a turn killed
mid-flight is not.

## What this item does

**Two paths, deliberately separated.**

**The iteration stack** — `npm run dev:stack` — runs the same three processes from
source. `tsconfig.dev.json` points the workspace packages at their TypeScript, the
web client resolves contracts from source in development, and a change restarts only
what it affects. The worker is never stopped in the middle of a turn.

**The deployment** — the Compose stack — keeps running the compiled code, and its
worker is given fifteen minutes to finish the turn it is running before it is
stopped.

- [x] **The documentation matches the code.** `README.md` and `ARCHITECTURE.md`
      describe both paths, and say what each one is for.

## The proof

The instance was started with `npm run dev:stack` on ports 4318 and 5174, and the
owner account was created through the API. The attempt to create an agent
connection whose adapter type is `probe` was then made three times, with one
change to `packages/contracts/src/agent.ts` in between:

```
before the change: 422 validation_failed The request payload is invalid.
changing packages/contracts/src/agent.ts…
after the change:  201 created:probe
the dev client serves the changed contract: true (status 200)
putting the contract back…
after the restore: 422 validation_failed The request payload is invalid.
the original behaviour returned: true
PASS — a change to a shared contract reaches the running instance
```

The supervisor's own log for the same run:

```
[stack] contracts changed
[stack] restarting server
[stack] restarting worker
Personal OS worker started (worker_r1um4kl7)
```

## Not in scope

- **The published contracts.** `CONTRACTS.md` changes with no contract change here.
- **In-process hot reload of the API server.** Fastify registers its routes at
  boot, so a route change is a restart — and a restart of about a second, which
  costs no agent turn because turns live in the worker.
- **The Compose stack's shape.** Two services, one image, one volume. The
  deployment stays what it is; only the stop behaviour changes.
- **The factory's git rules.** The instance follows the checkout it runs from, and
  an agent's work is written in a worktree beside the repository. A change still
  has to land before it reaches the running instance.
