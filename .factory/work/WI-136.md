## The gap

`AGENTS.md` rule 8: _"Verify new agent types and resources work through the same existing
interfaces. **A new resource type must work through the same existing interfaces.**"_

**This section was measured before the change, on `d60f3c5`.** Two of its citations are
marked as the lines the code was on then; the rest name lines the code still lives on.

**The exhaustiveness pattern is already the repository's own — and the two registries that
decide whether a type _works_ were the exceptions.**

**The resource type list is held twice already.** `kindNames`
(`apps/server/src/modules/resources/service.ts:744`) and `mergeRules`
(`apps/server/src/modules/resources/templates.ts:509`) are both
`Record<ResourceType, …>`, and a `Record` requires every key. **So a resource type added
to the contract without a name or a merge rule breaks the build today.**

**The provider registry was not.** The service held one provider for each of the six
types — **all six were there, so nothing was broken** — but the registry was a `Map`
(was at `apps/server/src/modules/resources/service.ts:457-464`):

```ts
const providers = new Map<ResourceType, ResourceProvider<unknown>>([...]);
```

**TypeScript does not require a `Map` literal to carry every key of its key type.** So a
seventh type can be named in the contract, given a name and a merge rule, and the tree
still compiles — and the failure surfaces only when somebody asks for that kind of
resource:

```ts
// apps/server/src/modules/resources/service.ts:473-477
const provider = providers.get(type);
if (!provider) throw errors.badRequest(`Unsupported resource type "${type}".`);
```

**A 400 to the caller, at runtime, for a mistake the compiler had already refused to
make twice over for the very same list.**

**The adapter types are the same shape.** The contract names seven
(`packages/contracts/src/agent.ts:9`); `adapterTypeLabels` (`packages/contracts/src/agent.ts:12`)
is a `Record<AdapterType, string>`, so a new adapter type without a label breaks the
build. **The registry is the one place that is not held to it** — it is a builder over a
`Map` (`packages/agent-adapters/src/registry.ts:19-20`), and all seven factories are there
(was at `packages/agent-adapters/src/index.ts:27-36`), **but a type added without a factory fails
at runtime**:

```ts
// packages/agent-adapters/src/registry.ts:52-57
const factory = this.factories.get(config.adapterType);
if (!factory) {
  throw new Error(`No adapter registered for adapter type "${config.adapterType}".`);
}
```

## The fix

**The contract's type lists and the registries that implement them cannot drift — and the
compiler is what holds both.**

- **The resource providers: a `Record`.** `Record<ResourceType, ResourceProvider<unknown>>`
  requires every key, so **adding a type to the contract breaks the build until a provider
  exists.**
- **The adapter factories: a mapped type over the union.** `AdapterFactories` is
  `{ [T in AdapterType]: (config: ConfigOf<T>, ctx: AdapterContext) => AgentAdapter }`, so
  **a factory is required for every type the contract publishes**, and each one is checked
  against its own configuration. The factories already have that shape —
  `createCliAdapter` takes `Extract<AdapterConfig, { adapterType: 'cli' }>` — so nothing
  has to be widened to fit.

**Why the compiler on both sides.** The rule is written in `AGENTS.md` and held by nothing.
A check would hold it; the compiler holds it _at the moment the mistake is made_, which is
earlier and cannot be forgotten. The contract already uses this instrument once, for
`adapterTypeLabels`, so this is the repository's own precedent rather than a new idea.

**The registry keeps its builder.** `AdapterRegistry.register()` stays, so a caller can
still add a factory to a registry it built. **What cannot happen is a registry that starts
out missing a type** — the constructor takes the complete set.

**Where the code lives now.** The providers are a `Record` at
`apps/server/src/modules/resources/service.ts:464-471`, and the guard that still refuses a
type the service does not hold is at `:473-477`. `AdapterFactories` is the mapped type at
`packages/agent-adapters/src/types.ts:28-30`, the constructor that requires the whole set
is at `packages/agent-adapters/src/registry.ts:30-34`, and the seven factories are at
`packages/agent-adapters/src/index.ts:30-38`.

**And the repository's own procedure now says what the compiler does.** `AGENTS.md`'s
"Adding an agent adapter" step 3 said _"Register it in `createDefaultRegistry()`"_ — and
after this change that function registers nothing, because it builds the registry from
`defaultFactories`. **An instruction that points at a function that no longer does the
thing is a stale instruction, and this item made it one.** Both procedure lists now say
where the implementation goes and that **the compiler refuses a tree that is missing one.**

## The limits, stated plainly

- **The compiler holds that every type has an implementation; it says nothing about
  whether the implementation is any good.** That is what the adapters package's own tests
  are for, and they are separate.
- **The order of the two lists does not match today** — the contract names `cli, acp, a2a,
http, model, echo, mcp` and the registry registers `echo, cli, acp, a2a, http, model,
mcp` — **so anything that compares them must compare sets, not lists, or it fails for
  the wrong reason.** The compiler compares the _keys_, so it is not affected; a check
  would have to be.
- **The resource service's runtime guard stays.** `providerFor` still refuses a type it
  does not hold, because a stored resource can carry a type the contract no longer names.

## The proof

- **The compiler refuses the tree.** Adding a type to `resourceTypeSchema` without a
  provider is a **build failure**, not a runtime surprise. **That is the proof, and it is
  a kind of proof that cannot be forgotten.** The same is true of an adapter type without a
  factory.
- **The other direction is proved too.** Removing a provider, or a factory, is a build
  failure as well — the `Record` and the mapped type both want every key.
- **Nothing else moves.** The adapter package's own tests keep passing, the server's suite
  keeps passing, and the resource service behaves the same for all six kinds it already
  supported.
