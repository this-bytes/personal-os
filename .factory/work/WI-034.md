  so neither `'owner'` nor `'system'` is an agent.

**What is left is the part WI-030 could not write, because the code did not
write it.** The **new** outcome vocabulary WI-033's code will produce —
`queued`, `succeeded`, `failed`, `unknown`; the rule that an entry records the
outcome rather than an assumed success; and the migration note.
**`unknown` is the fourth member, and the owner's judgement says so:** the
product produces it today (`apps/worker/src/executor.ts:104`,
`apps/server/src/modules/conversations/dispatch.ts:247`), so a vocabulary
without it would force an entry to carry a word that is not true. The list
above was written before that judgement and named three members; **it is
corrected here, not annotated**, because this item's own `State:` line already
carries the four. **The three-member list is here and not in
[WI-033](WI-033.md)'s own file** — WI-033's text asks for an entry that records
whether the action succeeded, and does not name a set.

**And the reason that part could not be written is itself published.** The
contract says the trail's `result` carries `success | failure | unknown` —
and **no writer in the product writes `failure`**: the route helper hardcodes
`success` (`apps/server/src/api/helpers.ts:62`) and the audit service defaults
to it (`apps/server/src/modules/audit/service.ts:71`). The only other value any
writer produces is the `unknown` of
[The unknown outcome](../CONTRACTS.md#the-unknown-outcome). A published
vocabulary with a member nobody writes and a member everybody writes by
accident is a vocabulary that describes nothing.

## Acceptance criteria

- [ ] **The entries land before the code ships.** This item is published
      first, and WI-033 implements what it publishes.
- [ ] **The vocabulary matches the code member for member**, checked against
      the implementation and not against a proposal.
- [ ] **The vocabulary can express every outcome the product can produce.**
      That includes the `unknown` of the unknown outcome, which today's
      writers do produce — a vocabulary that dropped it would make the
      unknown outcome unrepresentable in the trail, and the published
      `success | failure | unknown` says it is representable today. **If the
      item's owner decides the new vocabulary does not carry `unknown`, the
      migration note has to say where an unknown outcome is recorded
      instead.** This is the one place the narrowed scope needs the item's
      own judgement, and it is not a detail.
- [ ] **The rule that an entry records the outcome rather than an assumed
      success** is published, and it says what happens to the twelve routes
      that write no entry at all.
- [ ] **The migration note says what a client written before the change does**
      — what it may assume, and what it must now check — **and what a record
      written before the change means.** A record written before the change
      carries `success`, `failure` or `unknown` and no `queued`; the note says
      what such a record is and how a client reads it.
- [ ] **Nothing is reclassified.** No existing record is rewritten to carry an
      outcome it did not have.
- [ ] The entries do not contradict the neighbours: the route table, the
      authorship entry at `CONTRACTS.md:1337`, the audit trail's own entry, or
      the waiting list's entries.
