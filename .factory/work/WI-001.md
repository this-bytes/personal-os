# WI-001 — Split the web client bundle by route

**Owner:** Cog
**State:** accepted
**Dispatched:** 2026-10-20, commit `d514aa5`

## Problem

`npm run build` emits a single JavaScript chunk of 584.55 kB (173.35 kB
gzipped) and Vite warns that chunks above 500 kB are not split:

```
dist/assets/index-D7ouK18I.js   584.55 kB │ gzip: 173.35 kB
(!) Some chunks are larger than 500 kB after minification.
```

All nine page components are imported eagerly in `apps/web/src/App.tsx`
(`Login`, `Conversations`, `ConversationDetail`, `Agents`, `Factory`,
`Resources`, `Automations`, `Settings`). The owner therefore downloads the
agents page, the factory board and the settings screen before the login
screen can paint. The control panel is the first thing a user touches after
starting the instance, and it is the slowest part of starting it.

## Why now

It is the one measurable performance defect in the product, it is entirely
inside Cog's ownership, and it is small enough to land as a single
reviewable change.

## Acceptance criteria

- [x] No emitted JavaScript chunk exceeds 300 kB.
- [x] The chunk the browser loads for the first paint is smaller than it is
      today.
- [x] Every route still renders. A lazily loaded route shows a fallback
      (`apps/web/src/components/ErrorState.tsx` already exports a
      `LoadingState`) rather than a blank page.
- [x] `npm run build`, `npm run typecheck` and `npm run test` pass.
- [x] The Playwright suite passes. It navigates to `/agents` and
      `/automations`, which are both lazy routes — a route-splitting bug that
      breaks navigation will fail here.
- [x] A route chunk that fails to load does not take the panel down with it.

## Not in scope

- No visual redesign and no change to the look of any page.
- No change to the router's URL structure.
- No change to the API client, the event stream or any server behaviour.
- Do not add a bundler plugin dependency if `React.lazy` or a `manualChunks`
  split will do.

## Gates

- `npm run typecheck`
- `npm run test`
- `npm run build`
- `npm run test:e2e`

## Outcome

**Accepted.** The client ships one chunk per route, with the heavy vendor
libraries split out, and a failed chunk no longer takes the panel down with
it.

Measured from the real build output, and from what the browser actually
requests on the first paint:

| Chunk          | Before  | After   |
| -------------- | ------- | ------- |
| Largest chunk  | 584 kB  | 186 kB  |
| First-paint JS | 584 kB  | 497 kB  |
| Entry chunk    | 584 kB  | 154 kB  |
| CSS            | 36.9 kB | 36.9 kB |

The first paint is the number that matters, and it is down about 15% — from
584 kB in one request to 497 kB across six. The entry chunk alone is a
quarter of what it was, but the browser preloads the five vendor chunks as
well, so the sum is the honest figure and not the entry.

No emitted chunk exceeds the 300 kB limit, and the build now enforces it, so a
change that quietly re-bundles the panel into one file fails the build rather
than the user.

> **A correction.** An earlier version of this record published the first
> paint as 153 kB. That was the entry chunk, not the first paint. Probe
> measured it in a browser and found the real figure is 497 kB, so the
> published number was wrong by more than three times. The criterion — that
> the first paint is smaller than it was — was satisfied; the number printed
> was not. The same error was in `CHANGELOG.md` and has been corrected there
> too.

**Defect — a failed route chunk leaves the owner with a blank screen.**

When a route chunk fails to load — a page open across a deploy asks for a
file the new build renamed, or the network drops the request — `React.lazy`
rejects, nothing catches it, and the whole React tree unmounts. The owner is
left staring at an empty page.

Probe's test fails on this:

```
x [chromium] › e2e\route-split.spec.ts:216:3 › a route chunk that cannot be loaded ›
  a failed chunk load does not leave the owner with a blank screen
  Error: expect(locator).not.toBeEmpty() failed
```

This failure mode did not exist when every route shipped in one chunk.
Splitting the bundle introduced it, so it belongs to this work item. It was
sent back to Cog for an error boundary above the lazy routes, with a retry
that can actually succeed.

**The fix — `apps/web/src/components/LazyRoute.tsx`.**

The boundary sits per route, not per application, so the shell around it
survives the failure: the navigation stays where it was, the owner can leave
for a page that did load, and the panel never renders a blank screen.

Two things about the retry are not obvious, and both were found by measuring
in a real browser rather than by reasoning:

- **A fresh lazy component is required.** React remembers the rejection of a
  dynamic import, so retrying the same lazy component replays the same
  failure and can never succeed. The retry builds a new one.
- **A fresh lazy component is not sufficient.** The browser keeps a failed
  module in its module map too: a fresh `import()` of the same URL makes no
  second network request and rejects instantly from cache. So if the fresh
  attempt also fails, the boundary reloads the document, which is the only
  thing that defeats that cache. It cannot loop, because after a reload the
  attempt counter starts again at zero.

**The accepted commit lacked the enforcement it claimed.**

The acceptance of the first implementation said the build "carries a
chunk-size limit now". At that commit the only limit was Vite's
`chunkSizeWarningLimit`, which prints a warning and still exits zero, and the
enforcing script, the `verify:bundle` command and the CI job were all still
uncommitted — a fresh clone had no enforcement at all. The 300 kB criterion
had no gate whatsoever. `scripts/verify-bundle-size.ts` is that gate, it is
in the tree now, and CI runs it.

**Two measured behaviours worth knowing.**

Both were measured in Chromium, and neither is a defect, but both are not
what the mechanism names suggest:

- **The retry's own `import()` never reaches the network.** The browser
  serves it from the failed-module cache, so the recovery the owner sees is
  delivered by the reload, not by the fresh `lazy()` component. The
  observable contract still holds — pressing Retry ends with the page
  rendered — and the test is written to allow either path.
- **Coming back to a route whose chunk already failed shows the error state
  again, with no new attempt.** The attempt counter restarts at zero for a
  new route, so nothing triggers a reload and the browser will not re-fetch
  a module that already failed. The owner has to press Retry. The
  navigation still works and the error state says what to do, but it will
  surprise anyone who expects revisiting a route to retry the download.

**Accepting on a summary is how the first acceptance went wrong.**

The first implementation was accepted minutes after it was committed, on
Chief's own rerun of the gates, before the verification landed. That missed
the blank-screen defect entirely. The work item is only accepted now, with
the verifier's tests in the tree and the defect fixed. The rule in
`FACTORY.md` — Chief does not accept on a summary — exists because of this.

## Note: a defect found in this item's own fix

The error boundary that keeps a failed chunk from blanking the panel reloads
the document after a retry, whatever went wrong. For a chunk that could not be
downloaded that is correct — the browser will not fetch it again in this
document. For a page component that crashed it is not: the owner presses Retry
and the panel reloads instead of showing what broke.

That is not part of this item's acceptance criteria, so it is not folded in
here. It is [WI-003](WI-003.md).
