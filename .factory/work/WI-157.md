# WI-157 — The grant editor's check holds two of the paths its fix implements

**Owner:** Wren, who found the gap and offered to close it.
**Verifier:** the Chief, on its own measurement of the teeth; an independent
reviewer is named in the dispatch brief.
**State:** open — the implementation is right; two paths it implements are held
by nothing.
**Branch:** `wi/157-editor-paths`, to be created from `origin/main` at `41e4a58`.

## Problem

WI-155 fixed the grant editor so that it seeds on the **connection** and not on
the row's contents, and it shipped three cases with the fix
(`apps/web/src/components/__tests__/ToolGrantPanel.reseed.test.tsx`):

- "keeps what the owner turned when the row changes under it";
- "sends the turn the owner made after the row changed";
- "keeps what the owner turned when the row goes away and comes back".

**Two of the paths the fix implements are held by nothing.** The panel's seeding
effect (`apps/web/src/components/ToolGrantPanel.tsx:66-77`) does this:

```
  if (!open) {
    // Closing forgets the connection, so opening the editor again seeds it
    // with the grant as it is then.
    seededFor.current = null;
    return;
  }
  if (!agent || seededFor.current === agent.id) return;
  seededFor.current = agent.id;
  setBase([...agent.toolGrants]);
  setSelected([...agent.toolGrants]);
```

**Finding 1 — closing and reopening the editor is unpinned.** Drop the `!open`
reset and `seededFor` keeps the connection, so an editor reopened for the same
connection shows the grant from the **first** opening: the owner is looking at
a grant that is not the one they opened it with. The write would still be the
owner's turn — a stale display rather than a lost turn — but it is the property
the fix exists to hold, and nothing holds it.

**Finding 2 — pointing the editor at a different connection is unpinned.**
Replace the `seededFor.current === agent.id` guard with "seed only once" and
the editor keeps the previous connection's grant and measures the turn against
that base, so a save for connection B could name a tool the owner never turned
in B. The app cannot reach this today — `Agents.tsx:423-428` hands the panel
the snapshot `grantAgent` — but the component allows it, and the panel's own
comment claims the editor seeds "when it is pointed at a different connection".
Nothing holds that claim.

## The lead's own reading, on the landed tree

The implementation does both things — `seededFor.current = null` at
`ToolGrantPanel.tsx:70` and the id guard at `:73` — and the three shipped
cases are about the row changing under an open editor. Neither path is among
them. Wren's mutation battery is the evidence; the lead read the code to
confirm the two paths exist and that the cases do not cover them.

## Acceptance

- A case that renders the editor closed and then open for the same connection
  after the grant changed, and asserts the editor shows the grant as it is
  then. **Red under M-D, green on the branch.**
- A case that hands a second connection with a different id and asserts the
  editor shows **that** connection's grant. **Red under M-E, green on the
  branch.**
- Both sides measured: the two mutations reported with the failing case named,
  and the branch green.
- The implementation is **not** changed to make a case pass. If a case cannot
  be written against the branch as it stands, that is a finding, not a licence.
- Nothing is weakened: no test deleted, skipped or loosened; no `it.fails`,
  `.skip` or `.only`; the three existing cases keep passing.
