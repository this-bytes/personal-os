## The finding, measured on the published tree

**The first half is already done. The second half is not.**

**Done — the contract publishes the refusal.** `CONTRACTS.md:748` states that a template whose
spec the owning provider refuses comes back `validation_failed`, and `:1083` states the same for
the task provider. That was WI-108's landing, and the acceptance that followed turned it true.

**Open — the contract does not publish the refusal's _message_, and the tests repeat it.**
Measured on `main` at `e856a53`:

- **The contract carries no message text.** `grep 'does not satisfy the' CONTRACTS.md` returns
  **nothing** — the contract publishes the _status_ (`validation_failed`) and not the sentence
  the caller reads.
- **The source builds the sentence at runtime, so no constant exists to import.**
  `apps/server/src/modules/resources/service.ts:739` reads
  `This ${kindNames[type]} does not satisfy the ${type} contract.` — it is a template string
  built from two values, not a literal.
- **Six assertions repeat the message instead of reading it.** `resources.test.ts:183`, `:209`,
  `:231` and `:254`, and `resource-templates.test.ts:782` and `:814` — each spelling out
  `'This dashboard does not satisfy the dashboard contract.'` and its four siblings, as a
  literal in the test.

**So the sentence that a caller actually sees is written in five places — the source and four
test files — and the contract, which is the thing that publishes what the product does, says
nothing about it.** A change to `kindNames` or to the wording changes what every caller reads,
and **no gate notices**: the pointer gate asks whether a cited line holds code, and the status
gate asks whether a claim is somewhere in a file. **Neither asks whether the sentence the
contract publishes is the sentence the code produces.** That is the WI-122 shape, one layer
down, and it is why this item exists.
