## The problem, in the owner's words

**A forgotten password is recovered from the command line, because a
single-owner instance has no email address to send a link to**
(`apps/server/src/index.ts:16-19`). **That command reports a locked database as
a stack trace, and gives up on the first lock.**

Measured, not described:

- `apps/server/src/index.ts:76-79` — the top-level catch writes `error.stack`
  to stderr and exits 1. **That is the raw stack trace.**
- `apps/server/src/index.ts:66` — the write is
  `await auth.resetOwnerPassword(password)`, and nothing retries it.
- `apps/server/src/modules/auth/service.ts:184` — the update that fails, with
  the driver's own `busy_timeout = 5000` (`apps/server/src/db/client.ts:29`)
  already spent.
- The smoke gate calls this command twice (`scripts/smoke.ts:575`, `:719`), so
  the failure is reachable from the gate that runs on every push.

**The gate's half is already fixed** — Probe's `63aba3a`. The Windows read of
the command line spawned `powershell.exe` for every poll, and starting
`powershell.exe` costs 5.7 s on this machine before it has asked anything;
Probe measured the same read at **267 ms** through the legacy WMI service. The
check now asks it that way and keeps PowerShell as the fallback, and the check
is untouched: the same command line is read, by the same assertion, for the
same reason.

**The product's half is this item.** The owner's recovery should not depend on
the gate's workaround to survive a locked database.

## Acceptance criteria

- [ ] **A lock is an error the owner can read**, not a stack trace: the command
      says the database was locked and what to do about it.
- [ ] **The command retries a locked database** within a bounded number of
      attempts, and the bound is short enough for a person to wait for.
- [ ] **The failure after the bound says what happened**, and the exit code is
      still 1.
- [ ] **A test proves both halves**: the readable error, and the retry under a
      lock. The test must be seen to fail before it is committed.
- [ ] `npm run typecheck`, `npm run test`, `npm run format:check` and
      `npm run build` pass.

## Why it was held, and why it was released

**The accept queue is the constraint, and the owner's 15:40 line settles it:
"when a slot frees, lean on verification — unverified work is inventory rather
than product."** Eleven verifications are queued and none is running, and the
factory's two slots are the scarce thing: a dispatch to Cog takes a slot a
verification would otherwise have had.

**So the item was numbered, the brief was written in full, and it was held
undispatched.** When the queue drains, it goes to Cog with this brief, and Probe
writes the check.

**And on 2026-10-21 at 22:28 it was released, and the reason is measured
rather than a change of mind.** The dispatcher fills its slots in **batch
order**, and the verifications this item would have displaced were **already
ahead of it in that order** — they were dispatched earlier, so they run first.
**So dispatching to Cog does not take a verification's slot; it takes a slot
after them.** Cog's lane was empty, and an owner who cannot recover a password
because the command prints a stack trace is a worse thing to leave idle than a
verification that moves one place further down the queue.

**And the item that shares a file with this one is not on `CONTRACTS.md`:** this
is `apps/server/src/index.ts` and the auth service, and the contract lane's
queue — WI-065, WI-077, WI-034, WI-031's paragraph — is Wren's. **One file,
one live item, and this file is free.**
