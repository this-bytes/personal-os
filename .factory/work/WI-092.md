## The problem

`apps/web/src/__tests__/bundleBudget.test.ts` **has no explicit timeout**, and
there is **no vitest config in `apps/web` or at the root**, so **every case in
it inherits Vitest's 5 s default.** Nine cases, each of which **spawns a `tsx`
process** — the runner is `node_modules/tsx/dist/cli.mjs`, because that is how
the repository runs its root scripts.

**So a gate that is about to fail for a reason that has nothing to do with the
gate is a gate people learn to ignore.**

## The measurement, and it is Probe's, not a guess

Probe ran the file on this host with CPU burners, and measured the file's own
cost:

```
idle            9 cases in  3.07 s   (green)
 6 burners      9 cases in  8.07 s   (green)
12 burners      9 cases in 26.59 s   (green)
48 burners      6 of the 9 cases timed out at 5000ms   (red) — the same case among them, 7900ms
```

**And it is not only under saturation: one of three full `npm run test` runs
went red on a merely busy machine**, with `bundleBudget.test.ts` ›
_"fails when a chunk is over the limit"_ — `Test timed out in 5000ms`, after
23.6 s.

**This is the same class as the finding WI-074 reported** —
`apps/server/src/__tests__/agents.test.ts:117`, a test with no explicit
timeout that inherits the 5 s default and fails under CPU saturation. **The
class has now happened twice, and the second time it took a green suite red on
a machine that was not under load.**

## What this item does

Give the file a timeout it chose, rather than the one it inherited, **without
weakening the gate it holds** — the bundle budget is a real gate: `npm run
build` only **warns** when a chunk grows past the limit, and
`scripts/verify-bundle-size.ts` is what actually stops a change that quietly
re-bundles the panel into one file. **A longer timeout does not make the
budget smaller; it makes the test measure the budget instead of the machine.**

## Acceptance criteria

- [ ] **The file's cases have an explicit timeout, and it is one the file
      chose** — a number in the file's own terms, with a reason, not a silent
      inheritance.
- [ ] **The timeout is long enough that the file is green on a busy machine**,
      and the lead can say what it is and why, from the file.
- [ ] **The gate is not weakened.** The cases that must fail, must still fail:
      a chunk over the limit, a missing asset, a wrong declared name — each
      still fails, and each still fails **for its own reason** rather than
      because it ran out of time.
- [ ] **A timeout is not used to hide a real failure.** If a case still times
      out, the file says so in the failure, and the timeout is not raised again
      to cover it.
- [ ] `npm run typecheck`, `npm run test`, `npm run format:check` and
      `npm run build` pass, **and the web suite is green three times in a row**,
      because "one of three runs was red" is the symptom being fixed.

## Not in scope

- **`scripts/verify-bundle-size.ts` itself.** The gate is right; the test that
  exercises it is what inherits the wrong timeout.
- **The bundle's size, or the budget's number.** Changing what the gate allows
  is a product decision and is not this item.
- **WI-074's `agents.test.ts` timeout.** That is a separate file on another
  branch, and **one file, one live item.**
- **A vitest config at the root.** A shared default would change the timeout of
  every suite in the repository, and the lead has not asked for that. **If the
  fix is a root config, say so in the report and let the lead decide** — the
  narrowest fix is the one this item asks for.
