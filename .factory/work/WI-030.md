## Problem

The owner approved three published shapes at 06:01 — WI-017 (a template concept
in the resource model), WI-020 (the read-only route publishing the product's
two measures of itself) and WI-022 (the published waiting list's reasons). Each
of them is a change to a published contract, and `CONTRACTS.md` opens with its
own rules, the first of which is:

> 1. A published contract is not changed without an explicit migration and
>    compatibility story.

So all three need an entry with a migration note, and the entries have to land
**before** the features ship — that is what the items' own acceptance criteria
say, not a preference.

**WI-022's entry is already with Wren** (WI-022, dispatched as
`wi-022-publish-waiting-reasons`). This item is the other two, and they have
the same shape of problem: a published concept that does not exist yet, so an
agent — or a client — cannot know it is there.

Two things make this an item of its own rather than a footnote inside two code
items:

1. **`CONTRACTS.md` is Wren's file.** `FACTORY.md`'s ownership table gives
   `*.md` and `CONTRACTS.md` to Wren, and `apps/server`, `packages/contracts`
   and the rest to Cog. A work item with two owners is two work items. A code
   item that says "and add the contract entry" hands the owner a file they do
   not own, and the entry then lands whenever the code happens to land — which
   is the drift this factory has spent a day closing.
2. **The contract leads and the code follows.** That is the house order, and
   WI-022 → WI-027 is the pattern: the published shape is written first, and
   the implementation is built against it. A client written against the
   published contract is correct as written; the code is what is checked
   against it.

## Acceptance criteria

- [ ] `CONTRACTS.md` publishes the **template record**: a named, versioned
      example of one resource kind, with its spec, that an agent can start
      from. The shape is the one WI-017's implementation is built against, and
      the entry says what a template is **not** — it is a starting point, not a
      different kind of thing, and a resource created from one is a normal
      resource with the same schema, the same validation, the same audit trail
      and the same revision.
- [ ] `CONTRACTS.md` publishes the **MCP tool** that lists the templates for a
      resource kind and creates a resource from one. It is the same tool
      surface an agent already uses to create resources — not a second one —
      and the entry names the surface it extends.
- [ ] `CONTRACTS.md` publishes the **measures route**: read-only, one
      workspace, the same auth and workspace rules as every other route, and
      both measures returned as a count with its denominator alongside the
      ratio. Where there is no denominator the ratio is `null` and not `0`, and
      the count is still returned.
- [ ] The measures entry says **what "authored by an agent" counts as** in the
      reading this item is built on, and says plainly what the reading cannot
      cover: two of the six resource kinds hardcode `createdBy: 'system'`
      (`apps/server/src/modules/resources/service.ts:170`, `:260`) and have no
      `createdBy` column at all, and **twelve of the thirty-four mutating
      routes write no audit entry**. The product's first report on itself must
      not be a lie by omission, and a client that reads the ratio has to know
      what it is a ratio of.
- [ ] Each entry carries a **migration note**: what a client written against
      the published surface must do now that the template record and the
      measures route exist, and what it means for a record written before the
      change. Nothing is reclassified.
- [ ] The two entries do not repeat each other, and neither repeats what the
      `unknown` state entry or the waiting list's entries already say. If a
      statement is needed in two places, one of them links to the other.
- [ ] The published shapes match the code **exactly, member for member**, and
      the report says which commit implements each one.
- [ ] `npx prettier --check CONTRACTS.md` and `npm run format:check` pass.

## Notes

**The tiebreak, said out loud.** `CONTRACTS.md` is Wren's file, and the
direction of authority is one way: **the published contract is the truth and
the code is checked against it.** WI-017 and WI-020 are sized, approved and
ready to build, and both say in their own criteria that their entry lands
before the feature ships. So the entry is not a footnote the code leaves
behind on its way out — it is work with an owner, and it goes first.

**Why one item holds two entries.** One file, one owner, one live item. Both
entries land in `CONTRACTS.md`, and Wren is the owner of that file. The order
inside the item is: **the template record first, then the measures route** —
WI-017's shape is the one with the most room in it, and WI-020's route shape
is already fixed by its own criteria.

**What the owner's nod carries, and what it does not.** It carries the three
published shapes, and it says so in the items. It does not carry the two
implementations, and it does not carry the reading of "authored by an agent"
that the measures entry has to publish — that reading is the one thing in this
item the owner can correct, so the entry states it plainly rather than
implying it.

**The premise correction, and why it is in the criteria.** WI-020 was sized on
the claim that the data is already there: `resources.createdBy` separates an
agent's authorship from the owner's, and `auditLog` records the actor of every
action. Probe's WI-011 review found the first half false for two kinds and the
second half false for twelve routes, and WI-020's own note says the nod
"should be sought on this premise rather than the old one". The owner gave
the nod on the shape; the entry publishes the shape **on the corrected
premise**, which is why the fourth criterion exists.
