# WI-169 — Pi keeps its own capabilities in the room

**Owner:** the implementing agent, one session.
**Verifier:** an independent reviewer is named in the dispatch brief.
**State:** delivered — the product speaks Pi's own protocol, the gate is red
without the route, and the preset claims no demonstration it does not have.
**Branch:** `wi/169-pi-route`, cut from `origin/main` at `c971d8f`.

## Problem

Pi was a target, not an integration. The preset the owner starts Pi from said so
in its own words:

> Pi's own protocol carries more than a prompt — steering, settled execution,
> session selection — and none of that is implemented here: this template starts
> the process and writes the prompt to it.

So Pi ran through the generic `cli` adapter: a process, a prompt on standard
input, its output read as text. **The runtime's capabilities stayed in the
runtime.** The streaming text became one blob at the end, the tools it ran were
not shown at all, whether it had settled was invisible, the session it kept was
not resumed, and a message the owner sent while Pi was working had nowhere to
go.

[SPEC-R1-4](../../docs/spec/r1-4-acp-tool-activity.md) settled the shape a
runtime's own protocol takes in this product: the harness's own events become the
product's events, one call is one row, and a turn ends when the harness says it
ended. Pi had no route of that shape.

## The fix

- **Pi has its own adapter.** `packages/agent-adapters/src/pi.ts` speaks Pi's own
  JSONL RPC protocol: the commands go in on standard input, the responses and
  session events come out on standard output, and each record is one JSON object
  on one line.
- **The protocol's own rules are the route's rules.** The framing is strict
  JSONL split on LF only, because a record may hold the Unicode line and
  paragraph separators that a generic line reader would treat as a boundary.
- **The end of the turn is `agent_settled`.** A successful `prompt` response
  means the prompt was accepted, queued or handled — it does not mean the work is
  done. A prompt Pi handled itself ends the turn at once, because no run started
  and no `agent_settled` will come.
- **The session is the file Pi keeps.** `switch_session` takes the path, so the
  path is what the execution publishes as its session reference — the way the App
  Server's thread id is. The next turn in the same conversation resumes it
  through the runtime.
- **A steer is Pi's own `steer` command.** The owner's message that arrives
  while Pi is working is forwarded to the run that is going.
- **A picture crosses as bytes**, in the same shape the ACP route already sends.
- **The mapping is a pure function.** `mapPiEvent` turns one of Pi's records into
  the product's events, so the mapping is testable without a runtime; the process
  that produces the records is separate from the mapping that reads them.

**The worker needed no change.** It creates adapters through `runtime.registry.create`
and resumes a session through the adapter's own extras, so a new adapter type is
addable without touching conversation storage or the factory task model — which
is the rule the contract makes about new agent types, held.

## What was measured first

The protocol, before anything was designed. Pi's published documentation for
**1.4.0** (`rpc.md`, `rpc-commands.md`, `json.md`, `message-types.md` and
`rpc-types.ts`) was read and kept at `data/probe-pi-protocol/`, because the
protocol is the contract here and a route written against a guess is a route
written against nothing.

What that reading settled, before any code:

- the commands (`prompt`, `steer`, `follow_up`, `abort`, `get_state`,
  `switch_session`) and the events (`message_update`, `message_end`,
  `tool_execution_start`, `tool_execution_end`, `agent_settled`);
- that a successful prompt response is not the end of the work;
- that `ImageContent` is `{type: 'image', data, mimeType}` — the same shape the
  ACP route already sends;
- that the session is a **file**, restored by `switch_session`, so the session
  reference on this route is a path and not an id.

## What fails without it

Measured, not asserted. The route was broken in four places and the gate was
left in place.

| What was taken out                                     | What the gate said                                                                                                    |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `pi` removed from the published `adapterTypeSchema`    | five checks could not run: the configuration no longer parses as `pi`, and the gate said so with the enum it expected |
| The steer no longer forwarded to the run that is going | `the owner's steer did not reach the runtime: 0 of them arrived.`                                                     |
| The tool the runtime ran not carried                   | `the runtime ran one tool and the room was told about 0 calls and 1 finishes, so a call is not one row.`              |
| The prompt's disposition not read from the response    | `a prompt Pi handled itself did not end the turn.`                                                                    |

Each was measured on the built tree, and the tree was restored and rebuilt after
each one.

**The last of those was a defect the review found, not a measurement of a
defect.** The route looked for the prompt's disposition among the session's
events. Pi answers a command with a record that carries the command's id, and
the client resolves that record to the command it answers — so the disposition
was in a record nothing else ever saw, and a turn Pi handled itself never
ended: it hung until the timeout, and the owner saw a turn that never closed.
The route now reads the disposition from the response it was given, and the gate
checks that path by name.

## What is still open

- **The demonstration against an installed Pi.** Pi is not installed in this
  repository, and a double is not a runtime. The route is proved against the
  protocol Pi publishes; that it works against Pi itself is the outstanding
  evidence, and the preset says so rather than claiming a demonstration it does
  not have.
- **Pi's extension questions.** The `extension_ui_request` records an extension
  sends when it needs the user are not carried, so the capability row says the
  route cannot ask the owner for permission. Carrying them is its own work: the
  request has to reach the room, and the owner's answer has to go back as Pi's
  `extension_ui_response`.
- **Pi's compaction and retry records.** The room shows the work; a retry is the
  runtime's own business, and a compaction summary is the runtime's own memory.
