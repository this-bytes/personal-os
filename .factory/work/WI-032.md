## The problem

The repository was pushed for the first time on 2026-10-21. **The CI workflow
passed** — all four jobs, including the docker stack, the browser tests and the
bundle budget, on the commit `0fa500a`. The **CodeQL workflow failed on every
run it has ever had**, and it failed for the same reason each time.

The job log says it exactly:

```
##[error]Resource not accessible by integration - https://docs.github.com/rest/actions/workflow-runs#get-a-workflow-run
CodeQL job status was configuration error.
```

`codeql-action` calls the workflow-runs API to find the run it belongs to
before it uploads its SARIF results. The job's token cannot read it, so the
step never gets as far as analysing anything. **This is a permissions defect,
not a finding about the code** — and it has been red on every push since the
first one.

`.github/workflows/codeql.yml` declares its permissions at the job:

```yaml
permissions:
  security-events: write
  packages: read
  contents: read
```

`actions: read` is missing. A job-level `permissions:` block replaces the
workflow-level one wholesale, so the token is granted exactly those three and
nothing else, and `GET /repos/{owner}/{repo}/actions/runs/{run_id}` is not
among them. GitHub's own documentation for `codeql-action` lists
`actions: read` as required.

**The check that should have caught it did not.** The `workflow-lint` job
(actionlint) runs on every push and passed on every push, including the ones
where CodeQL was red. actionlint parses the workflow and checks the inputs an
action is given; it does not compare the token's permissions with what the
action calls. **The lint cannot fail on this defect**, which is the reason it
needs a second check rather than the reason it worked.

## The second half of the defect: a branch is not a gated branch

`ci.yml` runs on **every** branch push. `codeql.yml` runs on `main` only. So
the rule the factory now works by — _a pushed branch is a gated branch_ — is
true of the build and false of the security scan. A branch that the agents
push is checked by half the pipeline.

That matters more than it sounds: the factory's whole safety argument rests
on a branch being gated before it is landed. The security leg is the one that
would catch a bad pattern in a change nobody read carefully.

## Acceptance criteria

- [ ] The CodeQL job's token can read the workflow run it belongs to, and the
      job's permissions say so explicitly:
      `actions: read`, `security-events: write`, `contents: read`,
      `packages: read`.
- [ ] **CodeQL runs on every branch push, like CI does**, so that a branch is
      a gated branch in both senses.
- [ ] The run is proved, not assumed: the workflow is pushed to a branch, and
      the CodeQL run on that branch is **green**. A change to a permission
      block that is not seen to go green is not done.
- [ ] The fix is a permissions change and nothing else. No query is disabled,
      no alert is suppressed, and no analysis is skipped. A security scan that
      passes because it looked at less is worse than one that fails.
- [ ] `npm run format:check` passes — the workflow is checked by prettier too.
- [ ] The change is landed on `main`, which needs the owner's word, because
      `main` waits for the owner's word.

## Not in scope

- **The alerts themselves.** CodeQL has never uploaded a result, so this
  repository has no security findings yet, and the first run that uploads one
  may find things. Fixing those is a separate item, and it is a real one.
- **The CI workflow.** It passes, on every job, including the stack.
- **Turning the security scan off.** It is red, and the honest response to a
  red scan is to fix the scan, not to stop scanning.

## Gates

- `npm run format:check` — the workflow file is in prettier's reach
- The workflow is pushed to a branch and **CodeQL is green on that branch** —
  this is the gate that matters, and it is the only one that counts

## Notes

**Why this was not found before the push.** CI had never run on GitHub. The
factory's gates ran locally, where no token is involved and no permission is
consulted. A green local tree said nothing about a green pipeline, and the
difference only became visible when the pipeline ran for real.

**What the first push proved.** The product's pipeline works: the build, the
tests, the browser tests, the bundle budget, the dependency audit, the
workflow lint, and the docker stack that starts the server, the worker and the
client and then exercises them. That is a real result and it is the first
time this repository has had one.
