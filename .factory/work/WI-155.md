# WI-155 — The grant editor re-seeds from the live row, and the owner's turn is dropped

**Owner:** unassigned — the implementer is to be dispatched by the Chief.
**Verifier:** Probe, who wrote none of the implementation.
**State:** implement — the defect is measured and latent, not live; the check that
pins it is in `main`.
**Branch:** none yet.
**Base:** `8b23ef3`

## Problem

`ToolGrantPanel` seeds its selection from the connection it is handed:

```
apps/web/src/components/ToolGrantPanel.tsx:44-50
  // Reset the selection whenever a different connection is opened.
  useEffect(() => {
    if (open && agent) {
      setBase([...agent.toolGrants]);
      setSelected([...agent.toolGrants]);
    }
  }, [open, agent]);
```

**If the page hands the editor the live row, a refetch under the editor re-seeds it,
and the owner's turn is silently dropped.** The change is computed against `base`,
the grant the page read. A re-seed sets `base` to the _new_ grant, so the owner's
turn — which was measured against the _old_ grant — is no longer a difference, and
the save carries an **empty change**:

```
{"toolGrantChange":{"enable":[],"disable":[]}}
```

**The server applies nothing, the owner's turn is dropped, and the panel reports
success.** The owner is told their change was saved; it was not.

## Why it is latent, and not live

**The app does not hand the editor the live row.** `apps/web/src/pages/Agents.tsx`
holds the connection in state (`grantAgent`, `:46`), sets it when the owner opens
the editor (`:344`), and hands **that** to the panel (`:428`). A refetch replaces
the row in the `['agents', activeWorkspaceId]` query (`:54-55`), not the row the
editor holds, so the effect does not re-seed and the owner's turn survives.

**This is pre-existing, and the fix made it safer, not worse.** Before WI-146, the
same effect seeded `selected` from `agent.toolGrants` and the panel sent **the whole
list** — so a re-seed would not only drop the owner's turn, it would **take back
another writer's widening** as well. The fix added `base` to the effect and changed
the request to carry the change, so the same re-seed now costs the owner their turn
and nothing else.

## Why it is still an item

**It is one refactor away from being live.** The app's current shape — the editor
holds a snapshot, not the live row — is what keeps it latent, and nothing in the
code enforces that shape. A change that passes the live row down (a natural
simplification: "the editor should show the current grant") would make the
drop **live and silent**, and the panel would still report success.

**The check that pins it is in `main`:**
`apps/web/src/components/__tests__/ToolGrantPanel.refetch.test.tsx`, two cases —
"keeps what the owner turned when the page refetches under it" and "sends the turn
the owner made after the refetch". **Both go red the moment the page hands the
editor the live row.** Probe measured that, and the lead confirmed the same two
cases are in the landed tree at `8b23ef3`.

## Acceptance

- [ ] The panel's save is **never** a silent no-op: when the change it would send
      is empty and the owner did turn something, the panel says so rather than
      reporting success. Or the editor holds the owner's turn across a re-seed.
- [ ] A check that goes red when the page hands the editor the live row — the
      existing two cases must stay green on the fixed tree and go red on the
      broken one, or be replaced by cases that hold the promise directly.
- [ ] The applicable gates pass on the delivered revision, and nothing is
      weakened: no test deleted or skipped, no `it.fails`, no `.skip`, no `.only`.
