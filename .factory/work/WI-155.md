## Problem

`ToolGrantPanel` seeds its selection from the connection it is handed:

```
apps/web/src/components/ToolGrantPanel.tsx:44-50
  // Reset the selection whenever a different connection is opened.
  useEffect(() => {
    if (open && agent) {
      setBase([...agent.toolGrants]);
      setSelected([...agent.toolGrants]);
    }
  }, [open, agent]);
```

**If the page hands the editor the live row, a refetch under the editor re-seeds it,
and the owner's turn is silently dropped.** The change is computed against `base`,
the grant the page read. A re-seed sets `base` to the _new_ grant, so the owner's
turn — which was measured against the _old_ grant — is no longer a difference, and
the save carries an **empty change**:

```
{"toolGrantChange":{"enable":[],"disable":[]}}
```

**The server applies nothing, the owner's turn is dropped, and the panel reports
success.** The owner is told their change was saved; it was not.

## Why it is latent, and not live

**The app does not hand the editor the live row.** `apps/web/src/pages/Agents.tsx`
holds the connection in state (`grantAgent`, `:46`), sets it when the owner opens
the editor (`:344`), and hands **that** to the panel (`:428`). A refetch replaces
the row in the `['agents', activeWorkspaceId]` query (`:54-55`), not the row the
editor holds, so the effect does not re-seed and the owner's turn survives.

**This is pre-existing, and the fix made it safer, not worse.** Before WI-146, the
same effect seeded `selected` from `agent.toolGrants` and the panel sent **the whole
list** — so a re-seed would not only drop the owner's turn, it would **take back
another writer's widening** as well. The fix added `base` to the effect and changed
the request to carry the change, so the same re-seed now costs the owner their turn
and nothing else.

## Why it is still an item

**It is one refactor away from being live.** The app's current shape — the editor
holds a snapshot, not the live row — is what keeps it latent, and nothing in the
code enforces that shape. A change that passes the live row down (a natural
simplification: "the editor should show the current grant") would make the
drop **live and silent**, and the panel would still report success.

**The check that pins it is in `main`:**
`apps/web/src/components/__tests__/ToolGrantPanel.refetch.test.tsx`, two cases —
"keeps what the owner turned when the page refetches under it" and "sends the turn
the owner made after the refetch". **Both go red the moment the page hands the
editor the live row.** Probe measured that, and the lead confirmed the same two
cases are in the landed tree at `8b23ef3`.

**The review has landed and it confirms.** Wren stood in as the available
independent reviewer — Probe, the verifier this item names, was queued behind
the floor's dispatcher ceiling — and wrote none of the implementation, so the
review is independent here. **Verdict: CONFIRM.** No acceptance criterion

**What the review added that the lead's measurement did not do — a mutation
battery.** The lead measured that the old panel is caught and that the branch
is green. Wren broke the fix four ways and asked whether the check still
holds:

| mutation | what it does                                 | result                           |
| -------- | -------------------------------------------- | -------------------------------- |
| **M-B**  | re-base on the row's contents, keep the turn | **1 failed of 10 — caught**      |
| **M-H**  | the base is never seeded                     | **6 failed of 10 — caught**      |
| **M-D**  | closing does not forget the connection       | **10 passed of 10 — NOT CAUGHT** |
| **M-E**  | seeds once, never for a different connection | **10 passed of 10 — NOT CAUGHT** |

The check is **direct** for the promise it claims, and two paths the fix
implements are held by nothing.

**Finding 1 — closing and reopening the editor is unpinned.** The effect
forgets the connection when the editor closes (`ToolGrantPanel.tsx:70`,
`seededFor.current = null`). With M-D that reset is dropped, so an editor
reopened for the same connection shows the grant from the **first** opening:
the owner looks at a grant that is not the one they opened it with. The write
would still be the owner's turn — a stale display rather than a lost turn —
but it is the property the fix exists to hold, and nothing holds it.

**Finding 2 — pointing the editor at a different connection is unpinned.** The
effect seeds only when the connection differs
(`ToolGrantPanel.tsx:73`). With M-E that guard becomes "seed only once", and
the editor keeps the previous connection's grant and measures the turn against
that base, so a save for connection B could name a tool the owner never turned
in B. The app cannot reach this today — `Agents.tsx:423-428` hands the panel
the snapshot `grantAgent` — but the component allows it, and the panel's own
comment claims the editor seeds "when it is pointed at a different connection".
Nothing holds that claim.

**Both findings are gaps in the check, not defects in the implementation.** The
lead read the landed tree to confirm it: both paths are implemented
(`ToolGrantPanel.tsx:70` and `:73`), and the three shipped cases are about the
row changing under an open editor. **These are opened as WI-157**, because
WI-155 is accepted and closed.

## 2026-10-23 — The flake hunt's result. It reproduces, it is wall-clock, and it is not fixed.

**The hunt this record named has run to a result.** Probe's report: **the flake
reproduces, it is a wall-clock failure, and the pool change did not end it.**
Seven distinct cases across the measurements, and not one is a value
disagreement — every one is a wall-clock or readiness budget:
`agents.test.ts:35` (timed out in 5000ms, elapsed 8890ms),
`events.test.ts:12` (timed out in 5000ms, elapsed 6569ms),
`autonomy-policy-surface.test.ts:158` beforeAll (hook timed out in 10000ms),
`turn-activity.test.ts:23` beforeAll (hook timed out in 10000ms),
`capability-view.test.ts` beforeAll (hook timed out in 10000ms),
`grant-widening-probe-review.test.ts:317` (timed out in 5000ms), and
`verifyStack.test.ts:364` (a spawned server never came up). The same cases
take **29–42 ms** in every green run, so a failure is a 200–300× jump, not a
value, and no red log contains a git lock error, a SQLITE_BUSY, or an assertion
comparing values.

**The cost is in the setup, not the assertion.** Every one of those cases pays
an expensive setup first: `createTestDatabase()` is a fresh in-memory database
**plus the whole migration set**, per test (`helpers.ts:14-18`); some boot the
whole Fastify app in a `beforeAll`; one spawns a server and waits for
`/health`; one holds a write lock for 1200 ms and waits for the server's write.
A saturated machine spends the budget in the setup, and the test is reported as
a timeout.

**The pool change did not end it.** Measured, ten runs each: on the tree that
has the symptom, one worker gives 1 red in 10 against 2 in 10 for eleven
workers, and is faster — but **1 red in 10 is still red**, and two against one
is not a meaningful difference at n=10. The pools were counted, not assumed.

**The lead's ruling.** This is a real flake with a known mechanism, and it is
**not fixed** — it was reported OPEN and it stays open. It is **not a defect in
the tree**: CI on `main` is green on every commit pushed on 2026-10-23
(`19bedad`, `41e4a58`, `8f1c2ed`, `f21e1d9`, `3616b66`), and the six failures
in `main`'s CI history are all from 22 October, before those landings. This
box is saturated — twelve logical CPUs with four CPU burners, the desktop app
and WSL all running — and the suite's setup cost does not fit its budget when
the machine is busy. **A green `test` gate on this box can be a false negative,
and a red one can be the machine.**

**The fix is opened as WI-159**, with the rule that fixes it by making the setup
cheap enough to fit the budget and **not** by raising a timeout or weakening an
assertion.
