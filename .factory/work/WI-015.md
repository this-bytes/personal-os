# WI-015 — `verify:stack` must work against a deployment that already has an owner

**Owner:** Probe
**State:** accepted — 2026-10-21, on Probe's report and Chief's own gate run
at `a2aadb4`
**Implemented:** 2026-10-21, commit `ff15a90` ("Let the stack check get into a
deployment that already has an owner") — `scripts/verify-stack.ts` and
`apps/server/src/__tests__/verifyStack.test.ts` (7 → 12 tests), both Probe's
files.
**Approved:** 2026-10-20 — found by the clean-checkout run during WI-005 and
recorded there; Chief's ruling is that it is its own item, not a reason to
reopen WI-005.

## Problem

`scripts/verify-stack.ts` signs in to the deployment it is pointed at with a
fixed owner email and a fixed owner password, and creates the owner account
when there is none. Against a deployment that has been initialised before —
which is the normal case for a developer with a running instance, and the case
in CI whenever a data directory is reused — the sign-in returns 401 and the
check fails:

```
Assertion failed: the owner can sign in (got 401)
```

The server already accepts a static owner token for headless access —
`PERSONAL_OS_OWNER_TOKEN`, documented in `README.md` — and the check does not
use it. So the gate only works against a deployment it created itself, and
fails against the deployment a developer actually has.

The expected behaviour: the check authenticates with the static owner token
when one is configured, so it works against any deployment it is pointed at,
and falls back to the owner account when it is not.

## Why now

`npm run verify:stack` is in the definition of done in `AGENTS.md` for
anything that touches deployment or the worker. A gate that fails against the
developer's own instance is a gate that gets skipped, or worse, gets
disabled. A gate that only proves something about a deployment it built itself
is not proving what the pipeline claims.

## Acceptance criteria

- [ ] `scripts/verify-stack.ts` uses the static owner token when
      `PERSONAL_OS_OWNER_TOKEN` is set, and falls back to the owner account
      only when it is not.
- [ ] Against a deployment whose owner password is not the script's, the check
      gets past the sign-in instead of failing with "the owner can sign in
      (got 401)". Proven by observation, not by reading the diff.
- [ ] The remote guard still refuses a non-local deployment without
      `--allow-remote`, by default, before the first request is made. Probe's
      own review proved this holds today; this change must not weaken it.
- [ ] Against a deployment with no owner, the check still creates one — the
      current behaviour is preserved.
- [ ] The worker check still fails when the worker is dead. That is
      `apps/server/src/__tests__/verifyStack.test.ts`, and it is the check
      that makes the container job worth running.
- [ ] `PERSONAL_OS_VERIFY_STACK_TIMEOUT_MS` is unchanged in behaviour: a
      shorter wait can only make the check give up sooner, and a shorter wait
      never turns a missing reply into a pass.

## Not in scope

- How the server issues, stores or revokes the owner token. That is product
  behaviour and this is a script.
- `deploy/compose.yaml`, `deploy/Dockerfile`, and the container job. They are
  correct and were exercised.
- The container job's own secret wiring, which already sets
  `PERSONAL_OS_OWNER_TOKEN` for the stack it builds.
- Anything about how the agent reply is produced. That is WI-005's ground and
  it is closed.

## Chief's answer to Probe's question — the container job and the owner token

Probe asked, and Chief answers here because the workflow is Chief's file:

> Should the container job set the token so the new path is exercised in CI?

**No — the container job should keep running the account path, and the reason
is what the container job is for.**

The container job builds a fresh stack and proves the thing that ships works
from nothing: it starts, it serves the web client, the worker in the stack
runs the product, and the check creates the owner that a brand-new deployment
has no other way to get. That is the deployment the job is testing.

The token path is for the case this item was opened for — a deployment that
**already has an owner** whose password is not the script's. The container
job's stack is thrown away at the end of every run
(`docker compose -f deploy/compose.yaml down -v`), so it never is that
deployment. Setting the token in the job would exercise the token branch
against a stack that has no owner, which is the case the token path is
_least_ about — and it would stop the job proving the account path against a
fresh deployment, which is the case it is _most_ about.

**But Probe is right that CI never exercises the new path at all**, and that
is a real gap. The fix is not to change what the container job proves. The
fix is a **second step** in the same job, after the stack is up and the
account path has passed: restart the stack with a token in it, initialise the
owner with a different password, and run the check again with the token. That
is the case the item exists for, proved in CI, on the platform CI runs on.

That is a new step in a workflow, which is a work item of its own and not a
fold into this one. Chief files it as **WI-023** and says so out loud rather
than slipping a second step into a job that is currently green.

**One thing Probe found that is worth keeping.** The item's "not in scope"
note said the container job "already sets `PERSONAL_OS_OWNER_TOKEN` for the
stack it builds". It does not: `deploy/compose.yaml:32,63` forwards the
variable to both containers, but `.github/workflows/ci.yml:109-113` sets only
`PERSONAL_OS_SECRET_KEY`. The note was wrong, and the script's own header
comment now says what is actually true — that configuring the token is part
of using this gate.

## Chief's finding — the item is implemented and the evidence is real

Probe implemented it as the item's owner — `scripts/verify-stack.ts` and
every test file are Probe's files, so there is no cross-owner collision — and
reported it for acceptance. Chief checked the evidence rather than the
summary:

- The change is in `ff15a90`, two files: `scripts/verify-stack.ts` and
  `apps/server/src/__tests__/verifyStack.test.ts` (7 → 12 tests).
- **The fix was proven by reverting it.** With the script stashed back to
  `HEAD`, the suite runs `1 failed | 11 passed` and the one failure is the
  defect itself: `expected '…Assertion failed: the owner can sign in (got
401)' to be ''`. That is the strongest proof there is — the test fails
  without the change.
- **The gate case was observed, not read.** Against a deployment initialised
  with an owner the script does not know: without the token →
  `Assertion failed: the owner can sign in (got 401)`, `EXIT=1`; with the
  token → the whole check green, `The deployment is serving the product.`,
  `EXIT=0`.
- **The guard was not weakened.** The new test asserts the remote refusal
  still happens with the token configured _and_ that nothing was contacted
  (`expect(seen).toEqual([])`). Live: exit 2, refusal message, before the
  first request.
- **The container job is unaffected.** Probe ran the CI-faithful sequence
  against real Docker — fresh stack, no token anywhere → `ok the owner is
created` … `The deployment is serving the product.` → exit 0.
- **The timeout cannot turn a missing reply into a pass.** The new test runs
  the check with a 2 s and a 12 s wait against a dead worker: both fail, and
  the shorter one gives up sooner (15 077 ms in total).
- **All five gates are green on the tree this landed in.** Chief's own run at
  `a2aadb4`: `npm run typecheck` exit 0, `npm run test` exit 0 (server 190
  passed, web 46, worker 23, agent-adapters 16, contracts 28),
  `npm run format:check` exit 0, `npm run build` exit 0, `npm run test:e2e`
  exit 0 (24 passed).

**The one thing this item cannot be accepted on.** Probe is the author of
both the implementation and the tests, and Chief is the acceptor. That is
allowed by the doctrine — "Never accept your own work, whoever wrote it" is
about Chief, and this item's owner is Probe — but it means the item has no
