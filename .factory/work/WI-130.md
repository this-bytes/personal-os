## The gap

**The owner who clears the allow-list gets every action.**

Measured by the verifier: set `allowedActions: ['message.send']`, then clear it. The stored
list is `[]`, exactly as WI-128's contract entry promises — and `GET /api/autonomy-policy`
then returns `allowedActions: ["message.send","tool.call","artifact.create"]` with
`sources.allowedActions: "default"`.

**The lead read the rule in the code, on the published tree:**

- `packages/contracts/src/autonomy.ts:225` — `actionsOf(policy)` is `stringListOf(policy?.allowedActions)`,
  so an **empty list names no action**.
- `packages/contracts/src/autonomy.ts:394-396` — `if (naming.length === 0) { allowedActions =
[...autonomyActions]; allowedActionsLevel = 'default'; }` — **when no policy names an
  action, the effective set is every action in the vocabulary.**
- `packages/contracts/src/autonomy.ts:281-284` — the rule in the code's own words: _"A
  policy that names no action does not restrict the actions: the effective autonomy set is
  then every action in the vocabulary, which is what the stored autonomy defaults mean."_

**So clearing the list is the one write that hands the owner everything.** And there is **no
value an owner can write through this route that means "no action is allowed"**: an unknown
action is refused with `422 validation_failed`, and the empty list means "everything".

**Before WI-128 that state was unreachable.** The write path landed on 2026-10-22, and this
is the first time an owner can reach it.

**And the contract publishes the half that lets it through.** The composition rule says
`allowedActions` is _"the intersection of the policies that name any"_ and never says what
happens when **none** names any. WI-128's own entry says _"an absent list is left alone and
an empty list clears it, so clearing is still deliberate"_ — **without the consequence.** A
control that fails open, one sentence away from a sentence that fails closed.

## What this item does

1. **Clearing means tightening, or the write is refused.** An owner who writes an empty list
   gets a policy that allows nothing, or a refusal that says why — **and never a policy that
   allows every action.**
2. **Absent and empty are two different things, end to end.** A patch naming no list leaves
   the list alone (that holds today and must keep holding). A patch naming an empty list is
   the owner saying "no action", and the resolver must be able to hear that.
3. **The rule for "no policy names any action" is published** — what the effective set is
   when nothing names an action — and the code and the contract say the same thing.

**The lead's preference, and the smallest form:** **refuse the empty list** with
`422 validation_failed` and a message that says what to write instead. It invents no new
state for the resolver to carry, and "no action is allowed" is a state the product does not
yet express. **The owner may want "deny all" as a real state; that is a larger change, and
this item is not it.** Either way the behaviour and the published sentence must agree, and
they must agree **before** the behaviour changes.

## The contract changes

- The composition rule's sentence about "the policies that name any" gains its other half:
  what happens when none names any.
- WI-128's write entry's sentence about the empty list carries the consequence, or says the
  write is refused.
- A migration note: **a client that cleared the list under the rule in force got every
  action.** Say what happens to that client now.

**The design, and why it is the only form that can work today. That is measured, not
argued.** The lead's preference is the smallest form: refuse the empty list with `422
validation_failed` and a message that says what to write instead. It is also the only
form that works, because:

- **The default workspace stores an empty list.** Every new workspace's policy is
  written with `allowedActions: []` (`apps/server/src/modules/workspaces/service.ts:64`),
  and the resolver reads a policy that names no action as no opinion — the effective set
  is then every action in the vocabulary, which is what the stored defaults mean
  (`packages/contracts/src/autonomy.ts:285`). **So "an empty list means no action" cannot
  be the resolver's rule**: it would silence every workspace that never named an action,
  and a stored default and an owner-cleared list are the same row and cannot be told
  apart. "Deny all" is a state the product does not express yet, and this item is not it.
- **So the door is closed at the write.** The empty list is refused before anything is
  written: the stored list, the effective list and the row's `updatedAt` are all untouched
  by the refusal.
