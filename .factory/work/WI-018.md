# WI-018 — The published `WaitingItem` lives in the contracts package

> This was first written as WI-016, and committed as such in `bec0f2e`. The
> number was taken by a different item — Q6's self-reporting measures — before
> this one landed in the work directory, so it is renumbered rather than
> lost. The finding itself is unchanged, and it is the same finding the
> review of WI-004 recorded.

## Problem

`WaitingItem` is a published interface with three hand-written definitions and
no shared one:

| Where                               | What it is                    |
| ----------------------------------- | ----------------------------- |
| `CONTRACTS.md:447`                  | the published shape, as prose |
| `apps/server/src/api/waiting.ts:14` | the server's own copy         |
| `apps/web/src/lib/types.ts:86`      | the web client's own copy     |
| `packages/contracts/src/**`         | absent                        |

Every other published interface lives in `packages/contracts` and is quoted by
`CONTRACTS.md`. This one is transcribed into a markdown file and typed out
twice, so the two copies can drift from the published shape and from each
other, and nothing would notice.

The reasoning that `apps/web/src/lib/types.ts` "exists for exactly that" holds
for the other types in that file — `RoutingDecision`, `TaskWithEvidence`,
`ResourceInspection` — and does not hold for this one, because none of those
is published and `WaitingItem` is.

This was found during the review of WI-004 and recorded there as a finding
that did not block that item. A finding with no home is a finding that is
lost, and it nearly was: it was written up, committed, and then renumbered
out of the way of another item.

## Why now

The landing page is the first thing the owner sees, and it renders the
published `WaitingItem` on both sides of the wire: the server builds it and
the client draws it. Two copies of a published type, with a third in a
markdown file, is the shape of defect that only shows up once the two sides
disagree — a field that is missing, a field that is renamed, a kind that the
client does not know how to draw. The panel would then be wrong in a way
nothing detects.

## Acceptance criteria

- [ ] `WaitingItem` is defined once, in `packages/contracts/src/`, and is
      exported from the contracts barrel the way every other published type
      is.
- [ ] `apps/server/src/api/waiting.ts` imports that type. It does not declare
      its own.
- [ ] `apps/web/src/lib/types.ts` imports that type. It does not declare its
      own.
- [ ] `CONTRACTS.md` quotes the contracts copy and says where the type lives,
      the way it does for the other published interfaces.
- [ ] The `GET /api/waiting` response is checked against the contracts
      schema, so the shape on the wire is the published one rather than
      whatever the server happens to send.
- [ ] A change to the published shape breaks a build rather than silently
      diverging in one of the two copies.
- [ ] WI-004's acceptance criteria still hold, and the waiting-list tests
      still pass.

## Not in scope

- No change to the shape of `WaitingItem`. This item moves the type; it does
  not redesign it. No new fields, no new kinds of waiting thing.
- No change to `GET /api/waiting` or to any other published route.
- Not the `approval.decided` event. That is C-16, and it is the owner's
  decision.
- Not the persona type (WI-006) and not the memory type (WI-012). They are
  separate published types and they get their own items. Do not fold them in
  here.
- Not Q6's self-reporting measures (WI-016) and not the resource template
  (WI-017).
- No restyle. The visual language is WI-010's to settle.
