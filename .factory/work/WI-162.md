# WI-162 — The grant editor's save is held on no path but the plain one

**Owner:** Wren, who holds the grant editor's checks.
**Verifier:** the Chief, on its own measurement of the teeth.
**State:** implement
**Branch:** wi/162-editor-write
**Base:** main at intake (e038af8); cut the branch from the current
`origin/main`.

## Problem

WI-155 fixed the grant editor so it seeds on the **connection** and not on the
row's contents. WI-157 closed the two paths that fix implements — the editor
**reopened**, and the editor **pointed at another connection** — and its two
cases hold the **display** on both.

**The write on those paths is held by nothing.** What the panel sends, and to
which connection, is asserted nowhere on either path:

- **No shipped case saves after the editor is reopened, or after it is pointed
  at another connection.** Every save in the suite happens on an editor that was
  opened once and never closed: three in
  `ToolGrantPanel.request.test.tsx`, one in `ToolGrantPanel.reseed.test.tsx`
  (WI-155's "sends the owner's turn after the row changed"), one in
  `ToolGrantPanel.refetch.test.tsx`.
- **The save target is asserted exactly once**, at
  `ToolGrantPanel.request.test.tsx:90` — `expect(path).toBe('/agents/agt_1')` —
  on that same plain path.

**M-F is the mutation that shows the gap.** The connection id is frozen at the
first render:

```
  const agentId = agent?.id ?? '';
```

becomes

```
  const agentId = useRef(agent?.id ?? '').current;
```

The kind of memoisation a reviewer might add to keep the mutation function
stable. **The display is untouched** — the editor still shows the other
connection's grant, and both of WI-157's cases still pass. The save now
patches the connection the editor was _opened_ with.

Measured by the Chief on `5c7d8b4`:

```
  the shipped suite, before any mutation
    Test Files  3 passed (3)
         Tests  12 passed (12)          exit 0

  with M-F applied (panel blob b02f988e)
    Test Files  3 passed (3)
         Tests  12 passed (12)          exit 0     <-- NOTHING CATCHS IT

  a probe case that saves after the editor is pointed at another connection
    FAIL  ... > patches the connection it is pointed at
    AssertionError: expected '/agents/agt_1' to be '/agents/agt_2'

  after the restore   both files byte for byte; the panel's blob is d75ee6a
                      again, the test file's is 82d403a5, git status is clean
```

**So the suite would pass while the panel wrote one connection's grant to
another.** The owner edits connection B and the server writes connection A.
This is the same class of defect WI-155 existed to prevent, and it sits on the
paths WI-157 is about.

## Scope and compatibility

- **Owned paths:** `apps/web/src/components/__tests__/ToolGrantPanel.reseed.test.tsx`
  and the other panel test files, where the save cases live.
- **Compatibility:** the panel's request shape is unchanged — the cases assert
  what is already sent (`toolGrantChange`, the connection's own id). No product
  behaviour changes; the panel's implementation is out of scope.
- **Data migration:** none.

## Acceptance criteria

- [ ] A case **reopens** the editor — closed, the grant changed, opened again —
      and then **saves**, asserting the connection it patches and the body it
      carries.
- [ ] A case **points the editor at another connection** and then **saves**,
      asserting the connection it patches is the one it is pointed at, and that
      the body carries the turn against **that** connection's grant.
- [ ] Both sides measured: each mutation reported with the failing case named,
      and the branch green. **M-F must red** — a mutation that freezes the
      connection id, or one that sends the save to a stale connection, must be
      caught by the new cases and named.
- [ ] The implementation is **not** changed to make a case pass. If a case cannot
      be written against the branch as it stands, that is a finding, not a
      licence.
- [ ] Nothing is weakened: no test deleted, skipped or loosened; no `it.fails`,
      `.skip` or `.only`; the three cases WI-155 shipped and the two WI-157
      shipped keep passing.
- [ ] Independent review findings are resolved.
