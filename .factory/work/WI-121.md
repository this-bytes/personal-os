## The problem

**The waiting list is complete for approvals and silent for blocked agents.**

The autonomy-policy path creates an approval when an action needs the owner
(`apps/server/src/modules/mcp/server.ts:116-144`), so a _gated_ action becomes
visible to the owner. **A capability the agent was never granted does not.**

An ungranted tool is never registered on the agent's MCP server at all
(`apps/server/src/modules/mcp/server.ts:24-27`). The call is therefore refused
with a 403 (`apps/server/src/modules/mcp/server.ts:101-104`) that **the agent
sees and the owner does not**: nothing is published, nothing is recorded, and
nothing reaches the waiting list.

So the list promises the owner "everything waiting on me in one place", and it
keeps that promise — nothing is waiting on the owner. **The agent is waiting,
and it will never be in the list.** The owner is never told that an agent
cannot do the thing it is trying to do, and the identity's own trust decision
— widening what an agent may do — has no route to the surface where the owner
exercises authority.

**The refusal is a dead end.** The agent cannot appeal it and the owner
cannot see it.

## What this item does

**The refusal becomes something the owner can see and act on.**

- The waiting list gains **a kind for a blocked capability**, carrying **which
  agent** wanted it and **what it needed** — so widening that agent's grant is
  a decision the owner takes in the same place they take every other one.
- **One row per agent and capability, not one per attempt.** A refused call
  that repeats must not fill the list with probe noise.
- **The owner can widen the grant from the list.**
- **The row leaves when the grant is widened.** A list that keeps rows for
  capabilities the agent now holds is a list that lies about what is waiting.

## Notes

**The refusal the agent sees is not changed.** An ungranted tool is never
registered on the agent's MCP server, so the call is still answered with "not
found" and `isError: true`, exactly as before. What this item changes is the
owner's side: the refusal now reaches the decision surface, where it can be
acted on. The refusal the agent gets is the same refusal; it is the owner who
was not being told.

**A tool that does not exist is not a blocked capability.** The refusal is
recorded for a name in the published tool list. A name outside it is not a
capability the agent was refused, and there is nothing there for the owner to
grant, so it does not put a row on the list.

**The grant is widened, never narrowed.** The route takes one tool and adds it
to the grant the agent already has. It cannot take anything away, so the
action that unblocks an agent is one that cannot quietly shrink what the agent
may do.

**One row per agent and capability is a fact of the database.** The unique
index on `(agent_connection_id, tool_name)` is what holds it, and the refusal
is counted on the row rather than duplicated. The count is on the row and not
on the list: the owner sees one thing to act on.

**The row is read with the grant in one transaction.** The grant is read and
the row written together, so a refusal that was overtaken by the owner
widening the grant is not recorded. A list that carries a row for a capability
the agent holds is a list that lies about what is waiting.

**The web client does not change.** The panel draws the list, and what it does
with a kind is the panel's own item. The row renders safely today: the panel's
label falls through to "Blocked", which is what the row is, and the agent is
named from `agentConnectionId`, which the panel already knows how to name.
`npm run test:e2e` therefore stays not applicable.
