### Problem

PRODUCT.md:174-210 states what the product owes its owner: two measures of itself, shown in the panel, and five gaps that say exactly how far from that it is. The product is the product's own first user, and the report it makes on itself is part of what it is.

There is an implementation already. The branch `wi/020-measures-route` (commit `c2853ac`, worktree `G:\code\personal-os-worktrees\020-measures-route`) adds the measures route, the contracts, the service and the panel band. It is one commit ahead of its base and fifty commits behind the current `main`, and it has never been audited against the five gaps. An independent verification of that branch has just run, and its verdict is **needs-repair**.

This item is therefore: **audit the branch against the five gaps, repair what is wrong, and land it.** It is not a request to build the measures from scratch, and an implementer who rebuilds what is already there has missed the point.

### Why now

It is the fastest product win in the window, because most of the work is written and the remaining work is knowing what is true about it.

It is also the item where a green gate is most likely to mean nothing. The branch's own comment says it: the trail records that something happened, not what happened (`apps/web/src/modules/measures/service.ts:5-11`), and the denominators are polluted (`apps/web/src/modules/measures/service.ts:41-49`). A test suite that passes on that code would be a test suite that agrees with a number nobody should believe.

### The five gaps

These are the spine of the item. Each is a gap PRODUCT.md names, and each is checked against the branch.

**(a) Nothing counts them yet, and the panel does not show these numbers today.** PRODUCT.md:201-203. The branch answers this: the route exists (`apps/server/src/api/measures.ts:17`), it is registered (`apps/server/src/app.ts:224`), and the band is on the panel (`apps/web/src/components/MeasuresBand.tsx`).

**(b) An automation and a task record their author as `system`, so the answer is wrong, not merely uncounted.** PRODUCT.md:183-188. The branch does not correct the data and does not pretend to: those two kinds have no `created_by` column at all, the value is invented at projection time, and the measure publishes itself as a lower bound (CONTRACTS.md:1210-1218). An unknown author is neither agent-authored nor owner-authored, and the measure must never count it as either.

**(c) Twelve of the mutating routes write no audit entry at all.** PRODUCT.md:190-195, published as a table at CONTRACTS.md:1227-1240 and checked against the code by `apps/server/src/__tests__/published-shapes.test.ts:95-107`. The MCP surface writes none either (CONTRACTS.md:1246-1257), so the second measure cannot see the work an agent does through MCP at all.

**(d) Every entry written today records a success whether the action succeeded or not.** PRODUCT.md:196-199. This is the defect nobody has published, and it is the heart of the item: the route helper hardcodes `result: 'success'` (`apps/server/src/api/helpers.ts:62`), the audit service defaults to it (`apps/server/src/modules/audit/service.ts:71`), the only other writer in the product produces `'unknown'` (`apps/worker/src/executor.ts:104`), and `failure` appears nowhere. `audit.count()` has no `result` filter at all (`apps/server/src/modules/audit/service.ts:112-123`), so the denominator counts **attempts, not completed operations**, and the ratio can overstate the work that was done.

**(e) No ratio whose denominator is zero.** PRODUCT.md:205-210. The branch honours this and the audit confirms it at runtime and over HTTP: `measure()` returns `ratio: null` when the denominator is zero (`apps/server/src/modules/measures/service.ts:47-49`), and the published shape carries `ratio` as nullable (`packages/contracts/src/measures.ts:21`).

### What the verification found

- **The zero-denominator rule is honoured and correct.** No repair needed.
- **Major: no test proves either measure.** A repo-wide search for `api/measures`, `createMeasuresService`, `MeasuresBand` and `measures.measures` finds only production files and no test file at all. The work item's own criterion — a test that proves an agent-authored resource counts as agent-authored, an owner-created one does not, and a zero denominator produces a count and a null ratio — is unmet.
- **Major: `CONTRACTS.md` now states a falsehood.** CONTRACTS.md:1269-1272 still says _"The code does not implement this yet. … No route answers this today, and nothing named `measures` exists in the server."_ The branch implements it and left the paragraph byte-identical. Once the branch lands, the contract is lying about the code, and a contract that lies is worse than one that is missing.
- **The truth nobody published: the trail records success regardless of outcome.** As (d) above. It follows that the second measure's denominator is attempts rather than completions, and that the only `actorType: 'agent'` entries the product ever produces are the worker's `unknown` records — so the numerator is effectively _"executions whose outcome could not be confirmed"_. The first measure is a floor for a different reason: resources created with `createdBy: 'system'` count in the denominator and not in the numerator, so its ratio can only understate.
- **The panel band is correct and deliberate, and should be kept.** It shows counts only and never a ratio (`apps/web/src/components/MeasuresBand.tsx:25-28`), it prints the caveat beside the count — _"{n} of them record no author at all, so the count is a floor and not a share."_ (`apps/web/src/components/MeasuresBand.tsx:73-77`) — and it introduces no accent colour, so PRODUCT.md:270-276 is honoured.
- **Minor: the API still publishes both ratios**, which the work item's ruling said it would not defend.

### The owner's question, with a recommendation

This is a product question and the implementer does not get to settle it. Put it to the owner, record the ruling in this item before the code changes, and implement the ruled option.

**The question.** The second measure cannot mean what its name says, because the trail records that something happened and not what happened, and a third of the mutating surface is invisible to it. What does the product do?

1. **Record the outcome truthfully.** The route helper writes the actual outcome — `success`, `failure` or `unknown` — and the measure's denominator counts only genuinely successful operations. This fixes the meaning at the source and is the only option that makes the number mean what it says.
2. **Widen the audit coverage.** Write entries on the twelve blind routes and on the MCP surface, so the denominator is the mutating surface rather than a third of it. This is a larger change to a published surface, and it changes the published table at CONTRACTS.md:1227-1240 with it.
3. **Stop publishing the ratio.** Keep the counts, drop the share, and say plainly that the trail cannot support one. The contract publishes `ratio` today (CONTRACTS.md:1168-1180), so withdrawing it is a contract change with the owner's word behind it.

**Recommendation.** Option 1 first, and option 2 as the follow-on: the measure is honest when the denominator is made of completed operations, and complete when the coverage is complete. Option 3 is the honest fallback if the owner does not want the audit surface widened, and it is better than publishing a ratio nobody can defend. **The number space owner's ruling decides the shape of the published API** — which option is taken changes what `GET /api/measures` returns, and that is a contract change (AGENTS.md rule 4), not a refactoring detail.

### Acceptance criteria

- [ ] The two measures are computed from data the product actually keeps, and each measure's denominator is stated in the code and in CONTRACTS.md.
- [ ] For automations and tasks — whose author is recorded as `system` — the measure either counts them correctly or **excludes them explicitly and says so**. It never counts an unknown author as agent-authored or as owner-authored.
- [ ] The audit trail records the actual outcome of an action, not a success for every attempt. A route that fails records a failure, and a route whose outcome is unknown records `unknown`.
- [ ] The measure's denominator counts only genuinely successful operations, or the measure stops publishing a ratio it cannot defend. Which of those the product does is the owner's ruling, and the ruling is recorded in this item before the code changes.
- [ ] No ratio is emitted when its denominator is zero; the counts are shown instead.
- [ ] The panel shows the counts, and shows a ratio only where there is a denominator to divide by. The zero-denominator case is handled in the UI as well as in the API: no ratio is rendered, and no percentage of zero is shown. The band's caveat (`apps/web/src/components/MeasuresBand.tsx:73-77`) and its refusal of an accent colour are kept.
- [ ] A named test proves each measure from known data: an agent-authored resource counts as agent-authored, an owner-created one does not, and a zero denominator produces a count and a null ratio. The route is exercised over HTTP as well.
- [ ] CONTRACTS.md:1269-1272 is corrected. The contract no longer says the code does not implement the measures.
- [ ] The published route and audit counts stay honest: `apps/server/src/__tests__/published-shapes.test.ts` passes. Any route added or audited here is counted by it, and the table at CONTRACTS.md:1227-1240 changes with the code that writes audit entries.
- [ ] The branch is rebased onto the current `main`, the repairs are on it, and the branch lands. No second measures route is invented.
- [ ] The gates below pass.

### Not in scope

- **Changing what a route's audit behaviour is for reasons other than making the recorded outcome truthful.** A route may write an entry it did not write before, because that is the honest denominator. It may not start writing entries for a different reason.
- **A new route that returns the measures.** The route exists on the branch (`apps/server/src/api/measures.ts:17`). This item lands it; it does not invent a second one.
- **The licence or visibility decision.** That is a separate question and a separate item.
- **Correcting the stored data.** No resource's `createdBy` is changed and no audit entry is rewritten. The measure publishes what the trail holds, including where that is a floor.
