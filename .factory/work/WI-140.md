# WI-140 — A source deployment, and the ports on the Windows host

**Owner:** MCode session, authorized directly by the owner.
**Verifier:** the owner, against the running instance.
**State:** implement
**Branch:** wi/140-source-deployment
**Base:** 262100d

## Outcome and authority

The owner asked for the deployment to be sorted out: the instance runs from
source in WSL rather than from an image, so no image is built per change, and
the ports are exposed on the Windows host so the instance is visible on the
owner's LAN.

The running instance on the owner's machine already worked that way. The
repository did not say so: the README called `npm run dev:stack` an iteration
tool and named the Compose stack as the deployment, and there was no runbook
for the source stack or for reaching it from the host. This work item makes
the repository match the arrangement the owner actually runs, and gives that
arrangement one command.

## The slice

- `deploy/source-stack.sh` — starts the source stack with the secret key and
  the data directory from `deploy/.env`, bound to every interface, and
  refuses a checkout on a Windows filesystem on WSL.
- `--publish` — starts the jump port inside the distribution and publishes the
  client and the instance on the Windows host through Docker Desktop.
- `README.md` — a "Running the instance from source" section: when to use
  which, and what it takes to reach the instance from another machine.

## Verified behaviour

- The published ports answer on the host's address on the network: the panel
  on 5173 and the instance on 4317, both serving the panel and proxying the
  API.
- The instance serves the current tree: the client it hands out contains a
  file written after the last image was built.
- A source change reaches the running instance with no build: the client
  reloads in place, and the server restarts.

## Boundaries

- No contract changes. No new dependency. No change to the Compose stack, to
  the CI deployment gate, or to the runtime.
- The Compose stack stays the deployment: it runs the compiled code, and CI
  verifies it. The source stack is the way to serve the current tree.
- Publishing needs Docker Desktop, because the host's firewall rule for a
  published port is written with the publish, and an elevated shell is not
  available to a remote owner. The `netsh interface portproxy` route needs an
  elevated shell and is documented, not automated.
- The jump port is reachable on the host's loopback only. It is never exposed
  to the network.
