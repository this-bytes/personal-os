# WI-165 — A conversation points at the runtime session behind it

**Owner:** the implementing agent for the slice (Cog — the implementation
engineer for the server, the worker and the contracts).
**Verifier:** Probe, the verification engineer, independently.
**State:** implement
**Branch:** wi/165-session-references
**Base:** main at intake (68bbd79); cut the branch from the current
`origin/main`.

## Problem

`docs/roadmap.md` (R0, "Next bounded slices", 3) and the owner's directive
(`.factory/DIRECTIVE.md` §6.3) name the same slice:

> Introduce session references, correlation/idempotency and terminal-event rules
> sufficient for the first real integrations. Document native capability limits.

A conversation and the runtime session behind it are not connected by anything
durable. The consequence is visible in R1's acceptance list: "Close/reopen the
browser and continue the same conversation/session" cannot be demonstrated, and
a run that has gone quiet cannot be told apart from one that has ended.

**Outcome:** a conversation carries a durable reference to the runtime session
behind it, and resuming either works or says plainly that it cannot.

## Scope and compatibility

- **Owned paths:** the durable reference from a conversation to a runtime
  session, the correlation and idempotency rules, and the terminal-event
  rules — in `apps/server`, the worker and `packages/contracts`.
- **Boundaries:** the runtimes' own session semantics are read, not changed;
  what this slice publishes is the limit each one imposes.
- **Compatibility:** existing conversations keep working without a reference; a
  conversation with no session reference is a supported state, not an error.
- **Data migration:** conversations gain an optional reference. No existing row
  is rewritten; a conversation with no reference stays as it is.

## Acceptance criteria

- [ ] A conversation carries a durable reference to the runtime session behind
      it, and the reference survives a restart.
- [ ] Reopening a conversation either resumes the session or states plainly
      that it cannot — it never claims a resume that did not happen.
- [ ] Correlation and idempotency rules are published and hold: a repeated
      submission does not run twice.
- [ ] Terminal-event rules are published — what "finished" means, and what a
      lost terminal event leaves behind.
- [ ] The native capability limits of each runtime are documented from the
      adapter matrix, not from assumption.
- [ ] Applicable gates pass on the delivered revision.
- [ ] Independent review findings are resolved.

## Not in scope

- The R1 demonstrations — each is its own item.
- New runtimes, and any change to a runtime's own session handling.

## Evidence

- Revision, the commands actually run and their results, runtime versions,
  inspectable output, limitations and the independent reviewer's verdict.
  A state label is a report, not proof.
