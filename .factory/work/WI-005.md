# WI-005 — Make the pipeline prove what it claims to prove

**Owner:** Chief
**State:** accepted

## Problem

Three things the pipeline claims to check were not checked at all, and the
container stack had never been run by anybody.

**1. The CodeQL workflow could not have worked.** It passed `language` to
`github/codeql-action/init@v3`, whose input is `languages`. The action
rejects an input it does not know, so the job would have failed the first
time anybody pushed to a repository. The workflow had never been executed,
so nothing had noticed. The build step it carried was a no-op as well:
CodeQL reads JavaScript and TypeScript from the source, so there is nothing
to compile.

**2. The container job never checked the worker.** It built both images,
started the stack, polled `/api/health` and checked that the client shell
was served. The worker is the other half of the product and it runs as its
own container, with its own capabilities and its own volume. A health check
on the server says nothing about it. If the worker could not reach the
database, or was missing a capability it needs, the job would still have
been green.

**3. The scripts in the root directory were never typechecked.** There is no
root `tsconfig.json`, so `npm run typecheck` — which only walks the
workspaces — never looked at `scripts/`. Two of those scripts are gates the
pipeline runs: `verify-bundle-size.ts` and `verify-build.ts`. tsx strips
types without checking them, so a type error in a gate would only ever
appear at the moment the gate ran, in CI, as an unexplained failure.

**4. The gates did not work on a fresh checkout.** The server, the worker and
the web client import their sibling packages by their published entry
points, which live in `dist/`. On a clean clone `dist/` does not exist, so
`npm run typecheck` and `npm run test` failed with a wall of "Cannot find
module '@personal-os/contracts'" and "Cannot find module
'@personal-os/server/db'". The pipeline did not notice, because it builds
before it typechecks, but `AGENTS.md` lists the gates without saying that
the build comes first — so an agent or a contributor following the
documented contract got a failure that looked like broken code and was
nothing of the kind.

The dependency is not only the obvious one. The worker imports
`@personal-os/server/db` and `@personal-os/server/runtime` — subpath exports
of the _server_ package — so the server has to be built too, not only the
two library packages.

## Why now

The pipeline was written to be the thing that proves the product works
without a human watching. Every one of these is a case where the pipeline
would have said "green" and meant nothing. The factory is only as good as
the gate that accepts its work, so a gate that cannot fail is worse than no
gate at all: it is a gate that manufactures false confidence.

## Notes

actionlint is the tool that found the CodeQL bug. It checks that a workflow
parses, that every input an action is given actually exists, and that every
shell snippet is sound. It runs as a Docker action, so it adds no
dependency to the project.

The scripts typecheck needs a `tsconfig.scripts.json` of its own, because
the root has no `tsconfig.json` and the workspaces' configs do not reach
the root directory.

The fresh-checkout failure has a small fix and a large one. The small one
is to build the packages the other packages depend on before the gates that
need them, which is what `build:deps` does: the contracts, the adapters and
the server, in that order, because the worker imports the server's subpath
exports. It costs a few seconds and it makes the gates work on their own.
The large one is to make the packages resolvable from source, with
TypeScript project references, so that a clean checkout needs no build at
all before the tests. That is the right shape and it is a larger change
than this item should carry.

A verification that writes to a deployment must say so. `verify-stack.ts`
creates the owner if the deployment has none, and always adds an agent and a
conversation, so it refuses to touch a deployment that is not local unless
it is passed `--allow-remote`.

## The tiebreak, made explicitly

The ownership table in `FACTORY.md` gives `scripts/verify-*.ts` to Probe and
`*.md` to Wren. This item wrote `scripts/verify-bundle-size.ts`, created
`scripts/verify-stack.ts`, and edited `AGENTS.md`, `CONTRIBUTING.md` and

and the tiebreak is being made here, out loud:

- **`scripts/verify-stack.ts` and `scripts/verify-bundle-size.ts` are
  Probe's files.** They are written and they stand. The gate that runs them
  was written by the same bot that then checked it, so Probe reviews both
  the script and the check that calls it, and neither is accepted on
  Chief's word.
- **`AGENTS.md`, `CONTRIBUTING.md` and `CHANGELOG.md` are Wren's files.**
  They are written and they stand. Wren reviews them for accuracy against
  the code as it now is, and corrects anything the write got wrong.
- **The reason it happened is the structural one.** The work in this item is
  Chief's own domain — the root manifest, CI, the workflows — and Chief is
  the only bot that owns it. An item that touches a file another bot owns
  has no owner left who can both write it and be its reviewer. The
  alternative to crossing the boundary is leaving the gate unwritten, which
  is worse. So the boundary is crossed deliberately, by name, and the
  reviewer is named with it.

`FACTORY.md` now says this in the rules, so it does not have to be
rediscovered: a tiebreak is made in the group, with its reasoning, and
Chief's own work goes to Probe like anyone else's.

## What a clean-checkout run found, and what it cost

The gates had been run in the main tree, where `dist/` and `node_modules/`
already existed. Running the whole set again in a worktree with nothing
built found four things, and three of them were mine.

**1. The bundle gate broke its own tests.** `a672df6` made the gate fail
loudly when it could not read the vendor declarations from the vite config
— correct, because a check that silently stops checking is worse than no
check. But it exited at that point, so the other three rules never ran and
their tests failed with the wrong message. Fixed in `c734a99`: the
unreadable declaration is now one problem among the others, so the gate
still fails, still says why, and the other rules still report what they
think of the build. Nothing tested the loud failure, so removing it would
have been green. There is a test now.

**2. The container job would have died before the stack started.** The
secret key was written to `$GITHUB_ENV` and used in the same step. A
variable written there is available to the steps that follow it and not to
the step that writes it, so compose started with no
`PERSONAL_OS_SECRET_KEY` and failed with "required variable
PERSONAL_OS_SECRET_KEY is missing a value". The teardown step had the same
problem and would have failed on the way out. Fixed in `770888d`: the key
goes into the job environment in a step of its own, and is masked in the
log.

**3. The container job built the images twice, and not the ones it ran.**
It built both images by hand, under tags nothing runs — compose has its own
image names — and then let compose build them again. The stack that was
tested was not provably the stack that shipped. Fixed in `770888d`: compose
builds what it runs.

**4. The worker check cannot sign in to a deployment that already has an
owner.** `scripts/verify-stack.ts` creates the owner if there is none and
signs in if there is. Against a deployment whose owner has a different
password — a stack that has been run before, which is the normal case for a
developer — the sign-in returns 401 and the check fails with "Assertion
failed: the owner can sign in (got 401)". The server already accepts a
static owner token for headless access, and using it would make the check
work against any deployment. **This one is not fixed yet.** The file is
Probe's, and the other session is in it right now with a test of its own,
so the fix waits for the file to be free rather than landing on top of
somebody's work. It is recorded here so that it is not lost.

**What this says about the pipeline.** Three of the four were found by
running the gates where nothing was lying around, and two of them would
have failed the first time CI ever ran. The pipeline has still never run on
GitHub, because there is no remote. "CI can run the product" is a claim
with strong local evidence, not a fact, and it stays that way until the
owner adds the remote.
