# WI-139 — Features slot into the runtime through a seam, and the Map is the first one through it

**Owner:** one implementing session (the panel and the runtime).
**Verifier:** an independent reviewer, to be arranged.
**State:** implement — the implementation and the two new cases are in `main`; the
independent review landed on 2026-10-23 with four findings, two of them closed
by Probe's cases, and the item is not accepted until the contract lane's two
are resolved.
**Branch:** `wi/139-feature-slots`
**Base:** `7718710`

**Numbering.** WI-138 was allocated to this slice first and released when the
owner's chat-first recovery showed a claim for the same number published
earlier. That work is WI-138. This slice is WI-139.

## Problem

**The panel was built one surface at a time, and every surface was wired into
the files the runtime is made of.** `apps/server/src/app.ts` called sixteen
`registerXRoutes(app)` functions, `apps/web/src/App.tsx` held seven lazy route
loaders and the route table, and `AppShell.tsx` held the navigation as an
array in the file. A new surface needed three edits to shared files, and two
people could not build two surfaces at once without colliding on all three.

**The owner asked for the opposite** (2026-10-22): _"we need the app runtime
and the plugin style architecture built and the API layer so these features can
just be slotted in"_, and _"I asked for a UI prototype to be implemented but
that hasn't happened we need to build reusable parts and define the standards
so the iteration loop can run and constantly deliver."_

**The constraint that shapes the answer.** A plugin marketplace stays out of
scope (PRODUCT.md §12), and a loader for third-party code would put the
product's behaviour outside the owner's review. So the seam is first-party: a
folder in this repository that declares itself.

## Scope and compatibility

**Owned paths**

- `packages/contracts/src/feature.ts`, `packages/contracts/src/forge-map.ts` —
  the manifest and the Map's read model, both published contracts.
- `packages/ui/src/forge.tsx` — the reusable parts.
- `apps/server/src/features/**` — the registry and the Map feature.
- `apps/web/src/features/**`, `apps/web/src/components/RoomSwitch.tsx` — the
  client registry and the Map room.
- `apps/server/src/app.ts`, `apps/web/src/App.tsx`,
  `apps/web/src/components/AppShell.tsx`, `apps/web/src/pages/Login.tsx` — the
  four places that install the seam.
- `apps/server/src/api/waiting.ts` — the waiting assembly is now exported, so
  the Map counts the same list the rail shows.
- `apps/web/src/components/WaitingList.tsx` — its props ask for a name and a
  persona rather than a whole connection, so a surface that knows less can
  still say who is waiting.
- `CONTRACTS.md` (Contract 8 and the route table), `docs/panel-rooms.md`,
  `docs/feature-authoring.md`, `docs/decisions/0011-feature-slots.md`.

**The seam**

A feature is a folder that declares itself: a manifest (an id, a name, the
rooms it contributes, the prefix its own routes live under) that is a published
contract and is validated when the feature is registered.

- The **server** gets a feature registry — the `AdapterRegistry` shape again,
  in the place the adapter boundary already proved works — and the runtime
  installs every registered feature when it builds the app.
- The **client** finds features by a **build-time glob**, so a new feature adds
  a folder and touches nothing else. That is what lets two features be built
  at the same time, on two branches, and land without colliding.
- The **surfaces the panel already had are features too**, which is what makes
  the seam real rather than decorative: the route table the runtime used to
  hardcode is now the union of the features' routes.

**The Map**, the first feature through the seam: the orientation room, with the
agents, the threads they are in, what has been built, the counts and the pulse,
assembled on the server in one request (`GET /api/features/map`). It carries the
room switch, the counters band, the constellation and the needs-you rail, and it
is the room the panel opens on.

**Compatibility**

- No published shape changed. Contract 8 is additive; the routes the runtime
  published are the routes it had, and the feature's own routes live under its
  own prefix.
- The waiting list's response is unchanged; only the assembly function is
  exported now.
- The domain map is unchanged: a feature is an adapter over the services, at
  the same layer as the API routes, and the domain tests pass on the delivered
  tree.
- The browser suite's landing expectation moved with the product: the panel now
  opens on the Map, so `e2e/support/owner.ts` expects it. The route-split suite
  gained the Map route and its chunk.
- Three line citations in `CONTRACTS.md` and one in the server's audit test
  were re-pointed, because `app.ts` and `api/waiting.ts` gained lines.

## Not in scope

- **The Work room's own layout.** `/conversations` is unchanged, and the rail
  still appears on it as well as on the Map. Moving it is a change to a
  browser test that pins the rail's place on the conversations page.
- **The Dashboards room.** The Map carries what has been built as tiles; the
  room itself is not built.
- **Grouping the constellation by role.** The picture stops naming agents when
  there are many of them and says how many are unnamed; it does not yet group
  them by role.
- **A per-agent deep link into the connect decision.** Choosing an agent in the
  picture shows it and links to the agents surface; the decision is still taken
  there.
- **The active roadmap's stages.** This slice is not one of R0–R4. It is the
  extension architecture the owner asked for on 2026-10-22, and it does not
  displace the chat-first sequence: the Map supports the conversation
  (Q13, ADR 7) and adds no runtime, no harness and no factory behaviour.

**Limitations**

- The server's registry is an explicit list, because the server is plain
  `tsc`-built Node with no build-time glob. Two features landing at once can
  conflict on that one file. The client's cannot, because the client globs.
- The seam is first-party: there is no marketplace and no loader for
  third-party code, and the manifest does not describe a lifecycle, a version
  range or a dependency.
- The Map's activity counts come from a window of the event log — the most
  recent 120 events. A quiet system shows quiet agents, which is what the
  window means, not a measurement of all time.
- The panel now opens on the Map. The Work room's own layout is not built, so
  the Map is a supporting surface rather than the finished front door.

## The independent review, 2026-10-23

Probe reviewed this slice at `3989401`: the tree is green, the browser suite is
**29** tests (the 27 this file claims is stale — two e2e cases landed after it
was written), and the compatibility claims hold — 63 base routes became 70,
every base route is still at the same path and the same method, the waiting
response is byte-identical, and all six re-pointed citations hold their claims.
**The item is not accepted.** Four things are open.

**1. The contract does not describe the seam.** The word **"Contract 8"**
appears nowhere in `CONTRACTS.md`, and the word **"manifest"** appears nowhere
in it either — so the manifest's shape is not published in the contract,
though `packages/contracts/src/feature.ts` publishes it as code. There is **no
WI-139 claim** in the contract, so the house form has no sentence to check,
and `scripts/contract-status.json` carries no claim for the seam, so nothing
would go red if the contract lost the description. Both contract gates stayed
green. A client reading the contract sees two feature routes and no idea what
a feature is.

The route rows themselves **are** published — `CONTRACTS.md:2561` for the map,
`:2560` for the bot feature — but the seam around them is not described.

**2. The route-table claim is overstated on the server.** This file says the
route table the runtime used to hardcode is now the union of the features'
routes. That is true **on the client**, which globs. It is false **on the
server**: `apps/server/src/app.ts` still calls the same fifteen
`registerXRoutes(app)`, and the server's registry holds exactly one feature.
The diff is purely additive.

**3. Nothing shipped asserts the panel opens on the Map.** The verifier's
browser measurement is the only proof — the heading is `Map` and the URL
settles at `/map`. `route-split.spec.ts:39` visits `/map` by its own path,
`route-split.spec.ts:165` opens `/` only to assert which chunks are fetched,
and `waiting-list.spec.ts:162` opens `/conversations` explicitly. The landing
is decided by room order alone (Map 10 < Work 20) with a `/conversations`
fallback, so nothing holds it there.

**4. The picture's stability is unheld.** Making the agents' `activity` depend
on the clock left the shipped check **7/7 green, exit 0**, while the
verifier's two-call probe went red. The shipped check asks the Map once and
never compares.

**What is with whom.** 3 and 4 are the verifier's: the two cases that would
hold them are dispatched to Probe. **1 and 2 are the contract lane's** — this
slice's own file says the contract publishes Contract 8 and the route table,
and the contract publishes neither the section nor the manifest's shape. The
lead does not write `CONTRACTS.md`.

## The lead's re-measurement — 2026-10-23, at `60fad9a`

**Finding 1 still stands, and it is sharper than it was.** The seam's manifest
is a **published shape**: `packages/contracts/src/feature.ts:73` exports
`featureManifestSchema` (`id`, `name`, `description`, `rooms`, `apiPrefix`) and
the types `FeatureManifestInput` and `FeatureManifest`. The contract does not
describe it. **"manifest" appears nowhere in `CONTRACTS.md`**, "Contract 8"
appears nowhere in it either, and `scripts/contract-status.json` carries no
claim for the seam, so the status gate cannot see a shape that is already
public. Both contract gates stayed green while the shape went undescribed.

**Finding 2 survives, but the evidence in it is stale, and the lead withdraws
that part of it.** The sentence "`apps/server/src/app.ts` still calls the same
fifteen `registerXRoutes(app)`" is **false of the tree today**:
`registerXRoutes` appears nowhere in the server. The server installs features
now — `createDefaultFeatureRegistry().install(app, services)` at
`apps/server/src/app.ts:259`, over a registry at
`apps/server/src/features/registry.ts` — and the server's registry holds
**two** features (`forgeMapFeature`, `botsFeature`,
`apps/server/src/features/index.ts`), not one.

**What the claim measures now.** The client globs **eight** features
(`apps/web/src/features/registry.ts:57`, `import.meta.glob('./*/feature.ts')`) —
agents, automations, bots, conversations, factory, map, resources, settings — so
the route table there is the union of the features' routes and the claim is
true on the client. On the server, booting the built app against a throwaway
data directory and reading `printRoutes` gives **88 routes** with HEAD
excluded, and **two** of them come from a feature: `GET /api/features/map` and
`GET /api/features/bots/team`. The other eighty-six are registered by the
runtime's own modules. **The route table is therefore still not the union of
the features' routes on the server** — the gap is smaller than it was, and it
is a coverage gap (six of the client's eight feature surfaces have no
server-side feature) rather than a structural one.

**The published tables against the registered set.** The two tables in
`CONTRACTS.md` — the `Method | Path | Purpose` table and WI-055's `Route |
Method` table, 46 rows in all — were compared with the registered set. **No
published row names a route the server does not have, except two**: `POST
/api/conversations/:id/fork` and `POST /api/conversations/:id/rewind`. **Those
two are not a defect** — WI-055's own note says fork and rewind "arrive with
WI-055". Recorded here so it is not raised again as a stale finding. The other
direction: **43 registered routes have no row** in the HTTP surface table,
including the runtime's own CRUD surface (`/api/agents`, `/api/workspaces`,
`/api/resources`, `/api/tasks`, `/api/goals`, `/api/conversations`,
`/api/automations`), which the contract describes in prose rather than in the
table. Whether that table must be exhaustive is the contract lane's call, and
the lead records the measurement rather than the verdict.

**The four findings stand as they are.** 1 is the contract lane's, and it is
named above with the file that carries the shape. 2 is re-stated above in the
form the tree holds. 3 and 4 are Probe's, and the two cases are dispatched.
**The item is still not accepted.**

## The two check findings closed — Probe, 2026-10-23

Probe's two cases are in `main` (`c3cb82d`, merged from
`wi/139-feature-slots-checks` at `8d3bbe2`; two files, +77 / −0, nothing
removed):

- **`apps/web/e2e/map-landing.spec.ts`** (new, 26 lines) — _the panel opens on
  the Map_. Sign in, open the root, and the heading reads `Map` and the address
  ends in `/map`, so the room can be linked to and reloaded. It was open
  because the landing room is chosen by the order the features ask for their
  rooms in, and the browser suite visited every lazy route by its own path —
  the panel could have opened on any room, or on none of them, and every case
  would still have passed.
- **`apps/server/src/__tests__/feature-slots.test.ts`** (+51, one case) — _the
  Map draws the same picture for the same data_. The workspace gets an agent,
  so the picture is something rather than empty, and the route is asked **twice**
  and the two answers compared in full. It was open because the check asked the
  Map once and never compared, so a picture that was a function of the clock
  rather than of the workspace passed it.

Probe measured both by mutating the real files and restoring them afterwards.
The Map's room order `10` → `40` turns the landing case red, and the address
lands on `/conversations`. The agents' `activity` made to depend on the clock
turns **exactly one** case red — the new one — and the other seven stay green.
Every restore was checked the way a restore has to be: the original text
written back, an empty diff on the mutated path, the file on disk hashing back
to its baseline blob, no entry for the path in `git status`, and the package
rebuilt before the measurement — the e2e suite runs the built bundle, not the
source.

**Findings 3 and 4 are closed.** The item is still not accepted: findings 1
and 2 are the contract lane's, and they are open with the owner session, which
owns `CONTRACTS.md`.
