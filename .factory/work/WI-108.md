## What this item is

A publication item measured this and reported it rather than papering over it:

> **A dashboard, document, data source or automation whose spec breaks its contract
> answers `internal_error`, not `validation_failed`.** `tableProvider.validate` is
> `schema.parse` (`apps/server/src/modules/resources/service.ts:176`) → raw `ZodError`;
> `errorResult` maps non-`AppError` to `internal_error`
> (`apps/server/src/modules/mcp/server.ts:52-61`). Only task (`:349-358`) and memory
> (`:410-419`) wrap into `errors.validation`.

**The contract is right and the code was the defect.** `CONTRACTS.md:605-607` says
"**The template's spec is validated by the owning provider exactly as a resource's spec
is**" — and before this item it was not: the template path wrapped the provider's
refusal into `validation_failed`, while a resource's own broken spec came back a
500-shaped `internal_error`. Four of the six kinds answered one way and two answered
another. This item closes that.

## The error shape, before and after

Both shapes below were **measured against the running code**, not quoted from memory: the
"before" was measured with the helper deliberately broken (the mutation below), the
"after" with the fix in place. The call is the same in both — `resource.create` with a
dashboard whose widget has no `type`.

**Before** — the raw `ZodError` is not an `AppError`, so the envelope's `message` carries
the schema's JSON blob and the route answers **500**:

The envelope is the one the contract publishes ([Error envelope](#error-envelope),
`CONTRACTS.md:1607-1624`): `{ code, message, details }`, with `validation_failed` among
the published codes. The `details` are the schema's own issues — the same list the task
provider has always carried.

## What landed

**`apps/server/src/modules/resources/service.ts`** — one helper, and the four providers
that refused wrongly now use it:

```ts
function parseSpec<T extends z.ZodTypeAny>(
  schema: T,
  data: unknown,
  type: ResourceType,
): z.infer<T> {
  const parsed = schema.safeParse(data);
  if (!parsed.success) {
    throw errors.validation(
      `This ${kindNames[type]} does not satisfy the ${type} contract.`,
      parsed.error.issues,
    );
  }
  return parsed.data;
}
```

- `tableProvider` (dashboard, document, data-source) — `schema.parse` → `parseSpec`
  (`:176`).
- the automation provider — the inline `z.object({ trigger, action, enabled }).parse` →
  `parseSpec` (`:252`).

**The task and the memory providers are not touched.** They already refused correctly, the
item scopes the change to the four that did not, and leaving them alone means the diff
cannot change what they say: the task's message stays "This task does not satisfy the task
contract." and the memory's stays "This memory does not satisfy the memory contract.",
byte for byte. They keep their own inline refusal (`:354` and `:415`).

**The message names the kind the contract names** — "This data source does not satisfy
the **data-source** contract" — so the provider's message and the template path's
message ("The template \"x\" does not satisfy the data-source contract.") name the same
contract.

**Nothing else changed.** A provider that succeeds still succeeds. The automation's
_config_ check (`validateAutomationConfig`, which refuses a schedule trigger with no
cron and an `agent.prompt` with no agent connection) already threw `errors.validation`
and still does — only the schema failure changed.

## The contract

**`CONTRACTS.md` is not changed by this item, and nothing in it overstates.** The
contract promises `validation_failed` for "a template whose spec the owning provider
refuses" (`:633`) — that promise held before this item and holds now. The contract is
silent about what a **resource's own** spec that breaks its contract answers; the code
now answers `validation_failed` for all six kinds, which is what `:605-607` already
implies ("the template's spec is validated by the owning provider exactly as a
resource's spec is").

**If Wren wants that stated for resources, the sentence is** (offered, not applied):

- **The template refusal's `details.issues` is now a list for every kind.**
  `templateIssues` (`apps/server/src/modules/resources/templates.ts:463`) unwrapped a

  spec. A client cannot reach them with a broken spec, because a spec is validated
  before it is stored; they would only fire if a stored spec stopped satisfying the
  schema. Leaving them alone is the right call for this item, and they are a finding
  for whoever owns the inspection surface.
- **The `validate` method is on the published provider interface**
  (`CONTRACTS.md:531-536`), so the refusal is now part of what every provider does
  rather than what two of them happened to do.
