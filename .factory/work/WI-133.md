## The finding

**The `Dependency audit` job is the only job in the pipeline whose install audits, and
it then audits again.** `npm ci` runs its own post-install audit against the registry
unless `--no-audit` is passed. The job's install line omits it, and the job's next step
runs `npm audit --audit-level=high`. **So the job pays for the registry round-trip
twice, and its three siblings pay for it not at all:**

| Job                                     | install line                                   | timeout |
| --------------------------------------- | ---------------------------------------------- | ------- |
| **Dependency audit**                    | `npm ci --ignore-scripts`                      | **10**  |
| The published contract matches the tree | `npm ci --ignore-scripts --no-audit --no-fund` | 10      |
| The contract's pointers point at code   | `npm ci --ignore-scripts --no-audit --no-fund` | 10      |
| Build and run the stack                 | `npm ci --ignore-scripts --no-audit --no-fund` | 30      |
| Build and test                          | `npm ci`                                       | 30      |

## The measurement, which is the whole point

### The job normally takes eleven seconds

**This is the fact the first version of this item did not have, and it changes the
shape of the story.** The identical job, on the identical tree, on the green re-run
`e660fdf`:

| Step                      | started  | completed | duration     |
| ------------------------- | -------- | --------- | ------------ |
| Set up job                | 03:26:32 | 03:26:32  | 0.00 min     |
| Run actions/checkout@v4   | 03:26:32 | 03:26:33  | 0.02 min     |
| Run actions/setup-node@v4 | 03:26:33 | 03:26:35  | 0.03 min     |
| **Install dependencies**  | 03:26:35 | 03:26:39  | **0.07 min** |
| **Audit**                 | 03:26:39 | 03:26:39  | **0.00 min** |
| Complete job              | 03:26:40 | 03:26:40  | 0.00 min     |

**The whole job — checkout, setup-node, an install that audits, and a second audit —
took eleven seconds against a ten-minute budget.** Both audits are normally free.

### The job that timed out, step by step

**This is the other fact the first version did not have.** The same job on `ccc3564`:

| Step                      | started  | completed | duration     | conclusion    |
| ------------------------- | -------- | --------- | ------------ | ------------- |
| Set up job                | 03:01:34 | 03:01:35  | 0.02 min     | success       |
| Run actions/checkout@v4   | 03:01:35 | 03:01:36  | 0.02 min     | success       |
| Run actions/setup-node@v4 | 03:01:36 | 03:01:38  | 0.03 min     | success       |
| **Install dependencies**  | 03:01:38 | 03:08:41  | **7.05 min** | success       |
| **Audit**                 | 03:08:41 | 03:11:47  | **3.10 min** | **cancelled** |
| Complete job              | 03:11:47 | 03:11:49  | 0.00 min     | success       |

**Both audit round-trips stalled, and the second one was still running when the budget
ran out.** The install's implicit audit took **7.05 minutes**; the explicit audit step
was still going at **3.10 minutes** when the job's own `timeout-minutes: 10` cut it
off.

**And the registry was not slow for anyone else.** At the same moment, on the same
registry, the two sibling jobs doing the same install with `--no-audit --no-fund` —
so, doing no audit at all — finished their whole jobs in **0.23 and 0.27 minutes**.
**The registry was reachable. What was slow was the audit round-trip, and this job was
the only one in the pipeline paying for it.**

### The queue was three seconds

**One correction to a published record.** The 14:05 entry in `.factory/INTAKE.md` says
the failing run "had queued a while for a runner". **It did not.** Measured on the run
itself:

| fact                     | value                    |
| ------------------------ | ------------------------ |
| run `created_at`         | 03:01:31                 |
| run `run_started_at`     | 03:01:31                 |
| every job's `started_at` | 03:01:34                 |
| **created to running**   | **0.05 min — 3 seconds** |

**Three seconds.** The job was not waiting for a runner; it was on one, and it was
sitting in the audit.

### What the numbers say

- **The job's normal cost is eleven seconds against a six-hundred-second budget.**
- **On `ccc3564` it spent 7.05 minutes in the install's implicit audit and 3.10
  minutes in the explicit one.** The first version of this item said "roughly half"
  of the 10.25 minutes was the removable half. **That was wrong: 7.05 of the 10.25
  minutes — about 69% — was the install, and the install is where the duplicate
  audit lives.**
- **The duplicate is what turned a stall into a timeout.** One stalled audit round
  trip of the size observed would have fitted inside the budget on its own. **Two of
  them do not.** The siblings took no audit in their install and were unaffected.

**So this item is a risk reduction and is stated as one.** It removes the second
exposure and leaves the first. It does not make the job immune to a slow registry,
and it is not claimed to.

## What this item does

**One word, in one line of one job.**

```diff
       - name: Install dependencies
-        run: npm ci --ignore-scripts
+        run: npm ci --ignore-scripts --no-audit --no-fund
```

**The job then audits exactly once, with the level the job names**, and its install
line becomes byte-identical to its three siblings'. The job's cost becomes the
siblings' cost — about fifteen seconds of install — plus one explicit audit.

## The gate is not weakened, measured with the version CI uses

**This was an open question and it is now settled by measurement, not by assertion.**
If `npm ci`'s implicit audit could fail the job, then removing it would lower the
threshold at which the job fails, and this item would be a change to the gate rather
than a change to its cost.

**It cannot.** With **npm 10.9.9 — the exact version CI runs, bundled with the node
`22.23.3` in `.nvmrc`** — against a lockfile carrying a known high-severity advisory
(`lodash@4.17.15`, GHSA-35jh-r3h4-6jhm and four others):

| command                                        | exit  | what it means                                   |
| ---------------------------------------------- | ----- | ----------------------------------------------- |
| `npm ci --ignore-scripts`                      | **0** | the implicit audit **prints and does not fail** |
| `npm ci --ignore-scripts --no-audit --no-fund` | 0     | and does not report it either                   |
| `npm audit --audit-level=high`                 | **1** | the explicit step **does** fail the job         |
| `npm audit` (default level)                    | 1     | and so does the default                         |

**The implicit audit inside `npm ci` never gated this job.** It printed advisories
and exited zero. **The explicit `npm audit --audit-level=high` step is the only thing
that has ever failed it, before the change and after it.** The gate is the same gate,
with the same threshold, and it is still able to fail.

## What this item does not do

- **It does not weaken the gate.** Measured above, with CI's own npm.
- **It does not claim to end the flake.** The job's worst case is now one stalled
  round trip instead of two. **A registry slow enough to stall one of them for ten
  minutes would still time this job out**, and it would be right to.
- **It does not delete the install.** The audit's input is the lockfile, not the
  installed tree — `npm audit --audit-level=high` in a directory holding only
  `package-lock.json` and no `node_modules` reports **"found 0 vulnerabilities"** and
  exits 0. So the install could go, and the job would no longer depend on it at all.
  **That is a bigger change in shape to a vulnerability gate and it wants the owner's
  word; this item lands the one-word version first and leaves the deletion as a
  separate decision.**
- **It does not raise the timeout.** The job's normal cost is eleven seconds against
  a ten-minute budget; the budget was never the thing that was wrong. Raising it
  would hide the duplication instead of removing it.
- **It does not claim that the cache replaces the install.** `actions/setup-node`
  with `cache: npm` caches `~/.npm` — the download cache — and not `node_modules`. It
  makes `npm ci` faster; it does not replace it.
