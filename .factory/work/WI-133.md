## The gap

**One job in the pipeline installs dependencies and audits them, and then audits them
again.** The audit job is the one that guards the tree against a known vulnerability, and
it is also the only 10-minute job in the file whose install does not say it will not audit.

`.github/workflows/ci.yml:80-99`:

- `:83` — `timeout-minutes: 10`
- `:94` — `run: npm ci --ignore-scripts` — **no `--no-audit`, no `--no-fund`**
- `:99` — `run: npm audit --audit-level=high` — the audit the job is named for

`npm ci` runs its own audit unless it is told not to. **So the job pays for the registry
round-trip twice: once inside the install, at npm's own default level, and once in the
step the job is named for, at the level the job names.** The first audit is the expensive
one — it is a full dependency-tree submission — and it is the one that decides nothing:
npm's implicit audit only reports.

**Its three siblings do the same install inside the same budget and pay for it once:**

| Job                                       | Line   | Install                                        | Timeout     |
| ----------------------------------------- | ------ | ---------------------------------------------- | ----------- |
| `Dependency audit`                        | `:94`  | `npm ci --ignore-scripts`                      | 10 (`:83`)  |
| `The published contract matches the tree` | `:119` | `npm ci --ignore-scripts --no-audit --no-fund` | 10 (`:104`) |
| `The contract's pointers point at code`   | `:146` | `npm ci --ignore-scripts --no-audit --no-fund` | 10 (`:131`) |
| `Build and run the stack`                 | `:171` | `npm ci --ignore-scripts --no-audit --no-fund` | 30 (`:161`) |

**The audit job is the only 10-minute job whose install does not carry the two flags its
siblings carry.** The `build` job (`:38`) installs with `npm ci` and audits too, but it
has a 30-minute budget (`:27`) and it runs the whole suite afterwards, so it is not the job
that runs out of time.

## What it cost

**A timed-out job and a cancelled job look the same.** The run on `ccc3564` came back with
five jobs green and `Dependency audit` as `completed / cancelled`, which made the whole
run `cancelled` and the badge read "CI - failing" for a tree that was never at fault. The
peer session hit the same flake twice (runs `39713711604`, `39712551946`).

**GitHub reports a timed-out job as `cancelled`.** A job's `timeout-minutes` counts its
execution from the moment the job starts running — queue time is not inside the ten
minutes — so the budget was consumed by the job's own work, and the duplicated audit is
the part its siblings do not pay. **A required check that accepts only `success` cannot
tell a timeout from a cancellation, so the run reads as a failure either way.**

## The step-level measurement, which settles what the ten minutes were

**The record in `ee32e76` above says the exact cause was not reproduced, and names the
next lever: the check-run's own `started_at` → `completed_at`. The session that published
`27d87ef` read it, and the answer is below.**

**The job has two steps that can be slow, and the API returns them separately.** On
`ccc3564`, the run that was cancelled:

| Step                 | `ccc3564` (cancelled)                                      | `e660fdf` (green re-run)            |
| -------------------- | ---------------------------------------------------------- | ----------------------------------- |
| Install dependencies | **7.05 min** (03:01:38 -> 03:08:41)                        | **0.07 min** (03:26:35 -> 03:26:39) |
| Audit                | **3.10 min**, cut off by the budget (03:08:41 -> 03:11:47) | **0.00 min** (03:26:39 -> 03:26:39) |
| the whole job        | 10.25 min                                                  | **11 seconds**                      |

**Both audit round-trips stalled, and the second one was still running when the ten-minute
budget ran out.** And **the registry was not slow for anyone else**: at the same moment,
on the same registry, the two siblings doing the same install with `--no-audit --no-fund`
— so, doing no audit at all — finished their whole jobs in **0.23 and 0.27 minutes**.

**So the job's normal cost is eleven seconds, and the timeout was a stalled registry round
trip that this job paid for twice.** Its three siblings paid for it zero times, which is
why they were unaffected.

## The gate does not weaken — measured with the version CI runs

**This was open, and it is now settled by measurement rather than by assertion.** If
`npm ci`'s implicit audit could fail the job, then removing it would lower the threshold
at which the job fails, and this item would be a change to the gate rather than to its
cost.

**It cannot.** With **npm 10.9.9** — the version bundled with the node `22.23.3` in
`.nvmrc`, so the version CI actually runs — against a lockfile carrying a known
high-severity advisory (`lodash@4.17.15`, GHSA-35jh-r3h4-6jhm and four others):

| command                                        | exit  | what it means                                   |
| ---------------------------------------------- | ----- | ----------------------------------------------- |
| `npm ci --ignore-scripts`                      | **0** | the implicit audit **prints and does not fail** |
| `npm ci --ignore-scripts --no-audit --no-fund` | 0     | and does not report it either                   |
| `npm audit --audit-level=high`                 | **1** | the explicit step **does** fail the job         |
| `npm audit` (default level)                    | 1     | and so does the default                         |

**The implicit audit inside `npm ci` never gated this job.** It printed advisories and
exited zero. **The explicit `npm audit --audit-level=high` step is the only thing that has
ever failed it, before the change and after it.** The gate is the same gate, with the same
threshold, and it is still able to fail.

## The proof

**The duplication is visible in the install's own output.** Two installs of this
repository's own `package.json` and `package-lock.json`, into two scratch directories:

```
--- npm ci --ignore-scripts ---
  exit 0 in 11.9s
  the install itself audited: true
  tail: 25 packages are looking for funding |   run `npm fund` for details |  | found 0 vulnerabilities

--- npm ci --ignore-scripts --no-audit --no-fund ---
  exit 0 in 10.1s
  the install itself audited: false
  tail: added 90 packages in 10s
```

**With the flags the install stops auditing, and with them gone it stops printing the
audit's result.** The job's own audit — the one the job is named for — is a separate step
at `:99`, and it ran in 1.6s against the installed tree and printed _"found 0
vulnerabilities"_, exit 0.

**The audit does not need the installed tree.** In a directory holding a
`package-lock.json` and no `node_modules`: `npm audit --audit-level=high` → _"found 0
vulnerabilities"_, exit 0. The same answer, so the installed tree is not what the audit
reads.

**The gate still fails on a vulnerability.** The explicit step at `:99` is untouched, so
the job still fails when `npm audit --audit-level=high` exits non-zero. The audit job's
failure path is not weakened; it is given one audit instead of two.

**This is the local proof from the session that published `ee32e76`, and it is kept
whole.** Its own caveat — that a warm-cache measurement is not CI's cost — stands, and
the section above is the answer to it.

## The fix

**One word.**

```diff
-        run: npm ci --ignore-scripts
+        run: npm ci --ignore-scripts --no-audit --no-fund
```

The file also carries a comment saying why, and the comment states what was observed
rather than what was inferred: that `npm ci` audits by default, that the three sibling
jobs carry the same two flags, and that this job's job was the one GitHub reported as
`cancelled` when it ran out of its ten minutes. **It does not say the flags caused the
timeout, because that was not measured.**

- **The gate does not weaken.** The explicit `npm audit --audit-level=high` at `:99` still
  runs and still fails the job on a high-severity finding. The job now audits **once**, at
  the level the job names, instead of twice at two levels — and the audit that decides is
  the one that was always going to decide.
- **The install line becomes byte-identical to its three siblings'.**
- **The failure mode is removed rather than hidden behind a larger budget.** Raising
  `timeout-minutes` would leave the next slow runner or the next bigger lockfile to
  re-flake it; this makes the duplicated round-trip not happen.

## What this proves, and what it does not

**Proved.** The job audits twice. The duplication is removable with one word. The
resulting install line is byte-identical to the three jobs that did the same install
inside the same ten-minute budget and **passed on the very run the audit job timed out
on** — so the one word removes the only difference between the job that ran out of time
and the three that did not.

**Not proved, and said so rather than assumed.** **This does not end the flake.** The
job's worst case is now one stalled round trip instead of two, and a registry slow enough
to stall one of them for ten minutes would still time the job out — and it would be right
to. **The 11.9s against 10.1s local measurement is a warm-cache measurement and is not
CI's cost**; the number that matters is the one the timed-out run measured, which is the
7.05 minutes above. **And the timeout was not raised:** the job's normal cost is eleven
seconds against a six-hundred-second budget, so the budget was never the thing that was
wrong, and hiding the duplication behind a larger number would have left the next slow
registry to re-flake it.

**If the flake recurs, the next lever is known and measured.** Deleting the install, which
the audit does not need, is already measured and waiting for the owner's word.

## What is deliberately not in this item

**Deleting the install outright.** `npm audit --audit-level=high` needs only the lockfile —
measured, in a directory with a `package-lock.json` and no `node_modules`: _"found 0
vulnerabilities"_, exit 0 — and the same command against the installed tree gives the same
answer. So the whole install is dead weight in that job, and deleting it is the stronger
fix.

**It is not in this item because it changes the shape of a vulnerability gate, and that
deserves the owner's word.** The one-word change buys the same headroom without changing
what the job is: it still installs, and it still audits at the level it names. The
deletion is recorded here as the next step, with its measurement, for whoever wants it.

## The limitations, stated plainly

- **The measurement is of this repository's lockfile and this npm version** (npm 11.2.0,
  Node 22.14.0 locally; CI runs Node from `.nvmrc`, 22.23.3, with npm 10.9.9, and the
  gate question was re-measured with that npm). The behaviour being relied on — that
  `npm ci` audits unless `--no-audit` is passed — is npm's documented default, not a
  property of this lockfile.
- **This item does not change what the audit job audits.** It removes a duplicate and
  leaves the gate's own level and its own failure alone.
- **The CI run that proves this is the proof.** The word is in the file, and the pipeline
  that reads it is the pipeline that has to keep working.
