## Problem

**A grant the owner widened can be silently taken back, and the list then lies
about what is waiting.**

`apps/server/src/api/agents.ts:208-210` reads the grant, computes the union, and
writes back the list it computed:

```ts
const granted = app.services.agents.toolGrants(id);
const toolGrants = granted.includes(body.tool) ? granted : [...granted, body.tool];
const agent = app.services.agents.update(id, { toolGrants });
```

**The read is outside the transaction that spans the two writes.** WI-131 made the
_write_ one change — `db.transaction` at
`apps/server/src/modules/agents/service.ts:287` covers the row that leaves the
waiting list and the grant that changes. But `toolGrants(id)`
(`service.ts:414-417`) is a plain read, and the route's union is computed from it
before that transaction opens.

**Measured across two processes on one database file.** A second process widened
the grant to include `task.get` and committed while the server was inside the
route; the server **waited 549 ms** for the lock and **still lost the change** —
the grant came back `["conversation.read","task.create"]`, with `task.get`
silently removed, and the waiting list kept the `task.get` row although the agent
no longer holds that capability.

**That breaks published sentences.** The route's own comment says _"The grant is
widened and never narrowed"_. `CONTRACTS.md:1841-1845` says _"Whichever route
widened the grant, the row leaves"_ and _"A list that keeps the row is a list that
lies about what is waiting."_ And the contract says, at `CONTRACTS.md:1857-1861`:
_"a guarantee that rests on a function never yielding is not a guarantee."_ **This
guarantee rests on exactly that.**

## Scope and compatibility

**Owned paths**

- `apps/server/src/api/agents.ts` — the widening route.
- `apps/server/src/modules/agents/service.ts` — the widening write, and the read.
- `CONTRACTS.md` — the guarantee, if the shape of the write changes.
- A test that reproduces the lost update across two processes (Probe's lane).

**The smallest honest change, measured by the verifier.** Compute the union
**inside** the transaction, and **take the write lock first**. A deferred
transaction that reads first cannot wait: it measured `SQLITE_BUSY` after **0 ms**.
With `behavior: 'immediate'` — measured available in this drizzle — the same probe
waited 549 ms and its read saw the other process's committed value.

**Compatibility.** No published shape changes. If the widening becomes its own
service call rather than a union computed in the route, `CONTRACTS.md:1843-1844`
(_"both go through the one write that changes a grant"_) becomes two writes, and
**that sentence must change with it.**

## The measurement — Cog, 2026-10-22

**The fix.** The route no longer computes the union. It asks the service to
widen the grant by one tool (`apps/server/src/api/agents.ts:215`), and the
service computes the union **inside** the transaction that writes it, from a
read taken inside the same transaction
(`apps/server/src/modules/agents/service.ts:338`). The transaction takes the
write lock **before** it reads (`apps/server/src/modules/agents/service.ts:320`,
`behavior: 'immediate'`).

**The grant is still written by one write**, so the contract's sentence about
one write that changes a grant still holds; only its citation moved. The
contract now publishes the new guarantee, and the claim table checks it.

**The measurement.** `apps/server/src/__tests__/grant-widening-lost-update.test.ts`
— the other process is a **separate OS process** on the same database file,
holding the write lock while the server's widening runs into it. A holder in
this process would prove nothing: the busy handler blocks the event loop that
would have let the holder let go, which is why the earlier intermediate probes
were invalid. The lock is held for a fixed time rather than until the test
says so, for the same reason.

**What the two mutations measured.** Each was restored afterwards, and every
restore was checked three ways: empty `git diff`, the on-disk blob equal to
the index blob and the tree blob, and a clean `git status`.

| #   | the mutation                                           | the two cases                                                                        | the contract gate                          |
| --- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------ |
| M1  | the read moves back outside the transaction            | **red** — the grant came back `["conversation.read","task.create"]`, `task.get` lost | **red** — `widenToolGrant: body.tool` gone |
| M2  | the transaction goes back to deferred, the read inside | **red** — the same lost update                                                       | **red** — `behavior: 'immediate'` gone     |

**Both halves are load-bearing.** The union has to be computed inside the
transaction, and the lock has to be taken first: M1 takes the lock first and
still loses the update, M2 reads inside and still loses it.

**The list is held to the grant as well.** The second case asserts that every
capability the agent was refused is on the list exactly when the agent does
not hold it. When the widening is lost, the grant does not hold the capability
the other process added, and the row that would have said so is gone with it —
**the list under-reports a block that is still there.**

**Nothing was weakened.** No test was deleted or skipped, no `it.fails`, no
`.skip`, no `.only`. The new file is the only test added, and the gates pass
on the delivered tree.

## The editor's fix — Cog, 2026-10-23, and the lead's measurement

**The fix moved twice after the lead first measured it, and the tree that lands is
`wi/146-landing` at `e1e9fbd`.** It carries the tip with the owner's WI-154 work and
the lead's records, Cog's fix, the precedence fix that came after it, the pins that
came after that, Probe's probe, and Cog's measurement script.

**The design.** `PATCH /api/agents/:id` takes an optional
`toolGrantChange: { enable?: McpToolName[]; disable?: McpToolName[] }` — the owner's
change, not the list the page read. The server applies `(current - disable) + enable`
to the grant as it is now, read inside the transaction that writes it. The panel
computes the change from the grant the editor was opened with
(`apps/web/src/lib/grantChange.ts`). The old body `toolGrants: [...]` still means "the
grant is exactly this list" and still works, so a client that sends it can still take a
widening back — that is its own doing.

**The precedence, and why the body had to change.** A body may carry a change AND a
list. The change is a command — "apply this to the grant as it is now" — and the list
is a state — "the grant is exactly this". The list is the one that can take a widening
back, because it says what the grant was when the client read it and nothing about what
it is now. So the command is applied and the list is not written, and the branches run
change, widen, list. The bytes the owner sends when they uncheck a tool are the same
bytes that take a widening back, so the old body alone cannot be read as a narrowing
command. Cog's `d93383e` made the change win, and his own branch carried a test that
goes red when the order is put back.
