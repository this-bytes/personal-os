# WI-146 — A widening that is lost across processes narrows the grant

**Owner:** Cog, the implementation engineer.
**Verifier:** Probe, who wrote none of it.
**State:** implement — the editor's fix is delivered and measured; Probe's probe is
green against the fixed tree, and the fixed tree is green in eight of the nine

cites. The independent verdict and the contract change are outstanding.
**Branch:** `wi/146-grant-widening-lost-update` (merged as `60fad9a`),
`wi/146-editor-fix-and-probe` (the editor's fix and Probe's probe, pushed at

**Base:** `d724841`

## Problem

**A grant the owner widened can be silently taken back, and the list then lies
about what is waiting.**

`apps/server/src/api/agents.ts:208-210` reads the grant, computes the union, and
writes back the list it computed:

```ts
const granted = app.services.agents.toolGrants(id);
const toolGrants = granted.includes(body.tool) ? granted : [...granted, body.tool];
const agent = app.services.agents.update(id, { toolGrants });
```

**The read is outside the transaction that spans the two writes.** WI-131 made the
_write_ one change — `db.transaction` at
`apps/server/src/modules/agents/service.ts:287` covers the row that leaves the
waiting list and the grant that changes. But `toolGrants(id)`
(`service.ts:414-417`) is a plain read, and the route's union is computed from it
before that transaction opens.

**Measured across two processes on one database file.** A second process widened
the grant to include `task.get` and committed while the server was inside the
route; the server **waited 549 ms** for the lock and **still lost the change** —
the grant came back `["conversation.read","task.create"]`, with `task.get`
silently removed, and the waiting list kept the `task.get` row although the agent
no longer holds that capability.

**That breaks published sentences.** The route's own comment says _"The grant is
widened and never narrowed"_. `CONTRACTS.md:1841-1845` says _"Whichever route
widened the grant, the row leaves"_ and _"A list that keeps the row is a list that
lies about what is waiting."_ And the contract says, at `CONTRACTS.md:1857-1861`:
_"a guarantee that rests on a function never yielding is not a guarantee."_ **This
guarantee rests on exactly that.**

## Scope and compatibility

**Owned paths**

- `apps/server/src/api/agents.ts` — the widening route.
- `apps/server/src/modules/agents/service.ts` — the widening write, and the read.
- `CONTRACTS.md` — the guarantee, if the shape of the write changes.
- A test that reproduces the lost update across two processes (Probe's lane).

**The smallest honest change, measured by the verifier.** Compute the union
**inside** the transaction, and **take the write lock first**. A deferred
transaction that reads first cannot wait: it measured `SQLITE_BUSY` after **0 ms**.
With `behavior: 'immediate'` — measured available in this drizzle — the same probe
waited 549 ms and its read saw the other process's committed value.

**Compatibility.** No published shape changes. If the widening becomes its own
service call rather than a union computed in the route, `CONTRACTS.md:1843-1844`
(_"both go through the one write that changes a grant"_) becomes two writes, and
**that sentence must change with it.**

## Acceptance criteria

- [ ] The lost update is impossible: a concurrent widening is not taken back.
- [ ] The union is computed inside the transaction, and the write lock is taken
      first, so the read cannot be stale.
- [ ] A test reproduces the lost update across two processes on one database
      file, and **goes red when the read moves back outside the transaction**.
- [ ] The route's promise holds: a widening never narrows, and the list and the
      grant agree.
- [ ] `CONTRACTS.md` says what the code does — one write that changes a grant, or
      two, named as they are.
- [ ] The applicable gates pass on the delivered revision, and nothing is
      weakened: no test deleted or skipped, no `it.fails`, no `.skip`, no `.only`.

## Not in scope

- The blocked-capability row's own removal. That is WI-131's transaction, and it
  is correct.
- What a grant means, or who may widen one.
- The MCP surface's own tool list.

## Evidence

Measured by Cog at `cba153a`, in `G:\code\personal-os-worktrees\131-check`: the
read-modify-write above lost a concurrent widening; the deferral measured

**Two intermediate probes were invalid** — the lock holder was in the same

## The measurement — Cog, 2026-10-22

**The fix.** The route no longer computes the union. It asks the service to
widen the grant by one tool (`apps/server/src/api/agents.ts:215`), and the
service computes the union **inside** the transaction that writes it, from a
read taken inside the same transaction
(`apps/server/src/modules/agents/service.ts:338`). The transaction takes the
write lock **before** it reads (`apps/server/src/modules/agents/service.ts:320`,
`behavior: 'immediate'`).

**The grant is still written by one write**, so the contract's sentence about
one write that changes a grant still holds; only its citation moved. The
contract now publishes the new guarantee, and the claim table checks it.

**The measurement.** `apps/server/src/__tests__/grant-widening-lost-update.test.ts`
— the other process is a **separate OS process** on the same database file,
holding the write lock while the server's widening runs into it. A holder in
this process would prove nothing: the busy handler blocks the event loop that
would have let the holder let go, which is why the earlier intermediate probes
were invalid. The lock is held for a fixed time rather than until the test
says so, for the same reason.

**What the two mutations measured.** Each was restored afterwards, and every
restore was checked three ways: empty `git diff`, the on-disk blob equal to
the index blob and the tree blob, and a clean `git status`.

| #   | the mutation                                           | the two cases                                                                        | the contract gate                          |
| --- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------ |
| M1  | the read moves back outside the transaction            | **red** — the grant came back `["conversation.read","task.create"]`, `task.get` lost | **red** — `widenToolGrant: body.tool` gone |
| M2  | the transaction goes back to deferred, the read inside | **red** — the same lost update                                                       | **red** — `behavior: 'immediate'` gone     |

**Both halves are load-bearing.** The union has to be computed inside the
transaction, and the lock has to be taken first: M1 takes the lock first and
still loses the update, M2 reads inside and still loses it.

**The list is held to the grant as well.** The second case asserts that every
capability the agent was refused is on the list exactly when the agent does
not hold it. When the widening is lost, the grant does not hold the capability
the other process added, and the row that would have said so is gone with it —
**the list under-reports a block that is still there.**

**Nothing was weakened.** No test was deleted or skipped, no `it.fails`, no
`.skip`, no `.only`. The new file is the only test added, and the gates pass
on the delivered tree.

## The independent review — Probe, 2026-10-23: NOT ACCEPTED

Measured at `60fad9a` in a clean worktree of his own, nine of nine gates green.
The whole WI-146 surface is byte-identical at the published tip (`api/agents.ts`
`212dbf87`, `service.ts` `171e499f`, the test `8d31897f`, `CONTRACTS.md`
`0a9c8ff0`, `contract-status.json` `0a4102a8`), so the review is of the tree as
it stands.

**1. DEFECT — the grant editor can still take back a widening, and it needs no
second process.** `apps/web/src/components/ToolGrantPanel.tsx:43` seeds the
selection from the grant the page read, and `:48` PATCHes the whole list it was
given. The server writes that list as it stands —
`apps/server/src/modules/agents/service.ts:326-327` sets
`updates.toolGrants = patch.toolGrants`, and the one write at `:371` writes it.
So a widening committed between the page's read and its save is overwritten by
the save: **the owner's other action is gone, and the owner never chose to
narrow it.** Probe's probe on the clean tree: `expected [ 'conversation.read' ]
to deeply equal [ 'conversation.read', 'task.get' ]`, and the list then
under-reports the block that is still there (`expected false to be true`).

**This is the same defect as the item's, on the sibling path.** The route's
union is computed inside the transaction; the editor's write is a _replacement_
of the list the client read, and the transaction cannot help a stale value.
**Acceptance criteria 1 and 4 are not met by the tree as it stands, and the
published headline "A widening is not taken back" (`CONTRACTS.md:1850`) is not
true of the tree as a whole.**

The lead confirmed the mechanism in the code before dispatching the fix. The
scope of this item grows to the editor: `apps/web/src/components/ToolGrantPanel.tsx`
joins the owned paths, and the fix is with Cog on
`wi/146-grant-editor-widening` (`task_312e045ef661`).

**2. FINDING — the citation `service.ts:320` does not carry its sentence.**
`CONTRACTS.md:1853-1854` says "the transaction takes the write lock before it
reads" and cites `service.ts:320`, which is `db.transaction(`; the immediacy —
the thing that takes the lock first — is at `:373`. Probe's measurement: **with
the immediacy removed, `:320` was unchanged and still held code, and the pointer

Only the claim table's pattern caught it. The lead had judged `:320`
defensible and asked Probe to rule on it; Probe ruled that it does not carry
its sentence, and the lead accepts that. **`CONTRACTS.md` is the contract
lane's**, and the citation is with the owner session.

**3. OBSERVATION — the claim row binds three strings, each load-bearing, and
each turning the gate red when broken for the right reason.** The route's
`widenToolGrant: body.tool`, the service's `const granted = grantedTools(tx,
id)`, and `behavior: 'immediate'`. The witness `3154819` is in main's history
(`merge-base --is-ancestor` → exit 0) and carries all three, and the gate

guarantee** — the guarantee broke on the editor path and the row stayed green.
When the editor's fix lands, the row has to bind the guarantee and not only the

**4. OBSERVATION — the check is honest.** Probe measured the three ways it

(ii) No other path puts the capability in the grant: with the other process

**5. OBSERVATION — "one write that changes a grant" holds of the tree.** The

`app.services.agents.update` has exactly two callers — `api/agents.ts:197` (the
editor PATCH) and `:215` (the widening). The MCP surface and the bots module

**6. The mutations hold as reported, with one caution for whoever reproduces
