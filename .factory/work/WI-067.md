## The problem

**`apps/server/src/modules/mcp/server.ts:96` states the rule and the surface
does not keep it:**

> An agent may only act inside a workspace it has been granted.

**Four of the surface's tools keep it. Seven do not.**

| Tool                 | Where  | What it takes           | Guarded?                                  |
| -------------------- | ------ | ----------------------- | ----------------------------------------- |
| `agent.list`         | `:243` | a `workspaceId`         | **yes** — `assertWorkspace(id)` at `:252` |
| `task.create`        | `:263` | a `workspaceId`         | **yes** — at `:279`                       |
| `resource.create`    | `:352` | a `workspaceId`         | **yes** — at `:368`                       |
| `automation.create`  | `:485` | a `workspaceId`         | **yes** — at `:511`                       |
| `conversation.read`  | `:188` | a bare `conversationId` | **no**                                    |
| `conversation.post`  | `:206` | a bare `conversationId` | **no**                                    |
| `task.update`        | `:299` | a bare `taskId`         | **no**                                    |
| `task.get`           | `:334` | a bare `taskId`         | **no**                                    |
| `resource.get`       | `:405` | a bare `resourceId`     | **no**                                    |
| `resource.update`    | `:428` | a bare `resourceId`     | **no**                                    |
| `automation.inspect` | `:529` | a bare `automationId`   | **no**                                    |

**The guard exists and works — it is simply not called on the other half of the
surface.** `assertWorkspace` is defined at `:103` and called in exactly four
places, all of them the tools that take a `workspaceId`. The id-addressed
tools go straight to the capability: `capabilities.conversationRead(id)` at
`:196`, `capabilities.conversationPost(...)` at `:220`,
`capabilities.taskUpdate(args.taskId, ...)` at `:317`,
`capabilities.taskGet(taskId)` at `:342`, `capabilities.resourceGet(resourceId)`
at `:416`, `capabilities.resourceUpdate(args.resourceId, ...)` at `:452`, and
`capabilities.automationInspect(automationId)` at `:537`.

**And the capability layer cannot check it either, because it is not told
who is asking.** `apps/server/src/modules/capabilities/service.ts:197-199`:
`resourceGet(id)` is `resources.get(id)` — no actor, no workspace, nothing to
check against. The id is the whole address.

**So an agent granted one workspace can read, update and inspect a
conversation, a task, a resource or an automation in another workspace, if it
knows the id.** Not a capability it was granted; a hole in the ones it was.

**This is the same shape of defect as the memory guard, on the surface next
door.** WI-012's guard says an agent may only reach its own memory, and
WI-028 made the two published entries agree about it. The rule here is
**already written down** — in the code's own words at `:96` — and the code
does not keep it. It is not a design question and it does not need the owner:
it is a defect against the code's own stated rule.

## Acceptance criteria

- [ ] **Every tool that names an id checks the caller's workspace against the
      object's workspace**, exactly as the four that take a `workspaceId` do —
      `assertWorkspace` at `apps/server/src/modules/mcp/server.ts:103`, called
      at `:252`, `:279`, `:368` and `:511`. The seven listed above are all
      covered.
- [ ] **A call that crosses a workspace is refused, not silently empty.** The
      tool says the caller may not reach it, and **no part of the object's
      contents comes back** — not a summary, not a count, not a title. A
      refusal that leaks is a refusal that does not work.
- [ ] **The check is on the object's workspace**, not on the shape of the id
      and not on the caller's own claim about where it is. A tool that trusts
      an id to mean "mine" is the bug, not the fix.
- [ ] **The owner is not affected.** The owner's own calls, the owner's
      dashboard and the owner's own sessions keep working, and no existing
      call that was legitimate becomes an error.
- [ ] **The memory rule stays its own rule.** An agent-scoped memory is still
      judged by `assertOwnMemory` (`:147`), and an agent's own memory in
      another workspace is still refused by the memory rule. The workspace
      rule and the memory rule are two rules, both applied, and neither
      replaces the other.
- [ ] **The tool WI-017 just added is answered, not inherited.**
      `resource.template.list` (`:467`, `capabilities.resourceTemplateList(type)`
      at `:475`) and the template lookup inside `resource.create` (`:383`,
      `capabilities.resourceTemplateGet(...)`) are covered by the same
      reasoning: whatever the answer about templates' scope is, **it is
      written down**, and the new tool is not a way around the rule.
- [ ] **Cog names the check; Probe writes the test.** The ownership table
      gives every test file to Probe, and the loop now says so (`2388d35`).
      This item's file carries the acceptance criteria, and the test that
      proves a cross-workspace call is refused is Probe's to write, in
      Verify.
- [ ] **The gates pass:** `npm run typecheck`, `npm run test`,
      `npm run format:check`, `npm run build`.
