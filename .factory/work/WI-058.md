## The owner's answer, and the gap it names

**The owner's answer, 2026-10-21: two ledgers, one link each way. The
repository records code work; the instance's ledger records instance work.**

The gap: the mechanism was half there. `tasks.externalRef` and
`executions.externalRef` are the external-orchestrator reference and the
column exists — but `createTask` wrote `null` and only `updateTask` could set
it, so a task could never be _born_ carrying a work item's id. The link could
be made after the fact and never from the start.

## Acceptance criteria

- [ ] **A task is created carrying the work item's id**, through the contract,
      the service and the route.
- [ ] **The execution the work produces carries the same reference**, so the
      link is visible from either side of the ledger.
- [ ] **The link survives a restart** — the test opens the database again and
      reads the reference back.
- [ ] **A task with no external work carries no reference**, and says so
      rather than carrying an empty string.
- [ ] **The route records the reference in the audit trail**, so the link is
      visible in the history and not only in the row.
- [ ] `npm run typecheck`, `npm run test` and `npm run format:check` pass.

## Not in scope

- **The instance's record of a goal.** A goal that spans both lives in the
  instance and names the work items it spans; that is part of the ledger's
  own work, not this item's.
- **Any mirroring.** Nothing is copied between the two records. A dangling
  reference on either side is a finding, and finding it is the point.
- **The migration policy.** WI-061.

## Notes

The test is at `apps/server/src/__tests__/ledger-link.test.ts` and it opens a
real database file, because "survives a restart" cannot be proved against an
in-memory database.
