# WI-159 — The server suite's setup costs more than its budget on a loaded machine

**Owner:** Cog, the implementation engineer for the server.
**Verifier:** Probe, who ran the hunt and can re-run it.
**State:** open — the flake reproduces, it is wall-clock, and it is not fixed.
**Branch:** `wi/159-server-setup-cost`, to be created from the current
`origin/main`.

## What the hunt found

Probe ran the flake hunt to a result. **The flake reproduces, it is a wall-clock
failure, and the pool change did not end it.** Seven distinct cases across the
measurements, and **not one is a value disagreement** — every one is a
wall-clock or readiness budget:

| case                                                                                   | how it fails                                                                     |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `agents.test.ts:35` "stores the credential separately from the configuration"          | Test timed out in 5000ms — elapsed 8890 ms                                       |
| `events.test.ts:12` "assigns a strictly increasing sequence number"                    | Test timed out in 5000ms — elapsed 6569 ms                                       |
| `autonomy-policy-surface.test.ts:158` beforeAll                                        | Hook timed out in 10000ms                                                        |
| `turn-activity.test.ts:23` beforeAll                                                   | Hook timed out in 10000ms (+ an afterAll TypeError reading 'close' of undefined) |
| `capability-view.test.ts` beforeAll                                                    | Hook timed out in 10000ms (+ a vitest-pool worker teardown error)                |
| `grant-widening-probe-review.test.ts:317` "waits for the lock the other process holds" | Test timed out in 5000ms                                                         |
| `verifyStack.test.ts:364` "a deployment that already has an owner"                     | the server did not become healthy — a spawned server never came up               |

The same cases take **29–42 ms** in every green run, so a failure is a 200–300×
jump, not a value. No red log contains a git lock error, a SQLITE_BUSY, or an
assertion comparing values.

**The cost is in the setup, not the assertion.** Every one of those cases pays
an expensive setup before its (trivial) assertion:

- `apps/server/src/__tests__/helpers.ts:14-18` — `createTestDatabase()` is a
  fresh in-memory database **plus the whole migration set**, per test;
- `createTestStack()` — the same, plus the services;
- `turn-activity.test.ts:23` and `autonomy-policy-surface.test.ts:158` —
  `beforeAll` hooks that boot the whole Fastify app;
- `verifyStack.test.ts` — spawns a server and waits for `/health`;
- `grant-widening-probe-review.test.ts:317` — holds a write lock for 1200 ms and
  waits for the server's write.

A saturated machine spends the budget in the setup, and the test is reported as
a timeout.

## What the pool change did and did not do

`b497f48` ("bound server test contention", `maxWorkers: 2 → 1`) and the
config's introduction (`51f64e7`) both sit in the range `8aca67b..7a598be`.
Measured, ten runs each:

| tree      | pool                        | runs | red | wall time      |
| --------- | --------------------------- | ---- | --- | -------------- |
| `7a598be` | 1 worker (shipped)          | 10   | 0   | 62.1 – 68.4 s  |
| `8aca67b` | 11 workers (vitest's own)   | 10   | 2   | 71.3 – 123.1 s |
| `7a598be` | 11 workers (`--maxWorkers`) | 10   | 0   | 67.4 – 104.3 s |
| `8aca67b` | 1 worker (`--maxWorkers=1`) | 10   | 1   | 48.6 – 95.3 s  |

On the tree that has the symptom, one worker is better than eleven and faster —
but **1 red in 10 is still red**, and two reds in ten against one in ten is not
a meaningful difference at n=10. **The pool change did not end it.** The pools
were counted, not assumed: the shipped config runs 1 worker, and
`--maxWorkers=11` on the command line runs 11.

## What this is and is not

**It is not a defect in the tree.** CI on `main` is green on every commit pushed
on 2026-10-23 — `19bedad`, `41e4a58`, `8f1c2ed`, `f21e1d9`, `3616b66` — and the
six failures in `main`'s CI history are all from 22 October, before those
landings. The tree is fine; **this box is saturated** (12 logical CPUs with four
CPU burners, the desktop app and WSL all running), and the suite's setup cost
does not fit its budget when the machine is busy.

**It is not fixed.** The hunt was reported OPEN and it is still open, now with a
mechanism and seven named cases. A green `test` gate on this box can be a false
negative, and a red one can be the machine.

## Acceptance

- The named cases keep their budget **without the timeout being raised**: the
  setup is made cheap enough that the budget holds on a loaded machine. **No
  timeout is raised and no assertion is weakened** — that is the whole point of
  the finding, and a fix that raises a timeout has not fixed it.
- No test is deleted, skipped or loosened; no `it.fails`, `.skip` or `.only`.
- The suite is green, and the measurement is repeated **under load** — the
  conditions the hunt used — with the failing cases named.
- The cases that are about the product still assert what they assert; only the
  cost of reaching them changes.

## Scope

- **In scope:** the server suite's setup cost —
  `apps/server/src/__tests__/helpers.ts` and the `beforeAll` hooks that boot
  the whole app — and the seven named cases.
- **Out of scope:** the assertions themselves, the product code, and the
  published contract.

## 2026-10-23 — Two more instances of the same flake, and the rule made concrete

The Chief's own gate runs on the landing tree (`5c7d8b4`) produced two more
instances of this flake, and **neither is among the seven named cases**:

- `packages/agent-adapters/src/__tests__/adapters.test.ts:61` — "reports no
  chat capability when the command does not exist" — **Test timed out in
  5000ms**. The case spawns a command that does not exist and waits for the
  adapter to report that it has no chat capability; on a busy box the spawn and
  the failure take longer than the budget.
- `apps/server/src/__tests__/waiting-list.test.ts` — its `beforeAll` hook
  timed out at 10000ms, reported by a second lead session measuring the same
  tree.

Both are the same shape as the seven: **a wall-clock budget spent in the
setup, never a value disagreement.** The `test` gate was **red on the first
run and green on the re-run of the same tree** (345s), which is the ruling in
this item made concrete — **a red one on this box can be the machine.**

**The scope of the fix, named deliberately.** This item says the setup cost of
the **server** suite, and the adapters instance is in another workspace. It is
named here so the scope can be widened on purpose rather than by surprise: the
CLI adapter's connect path **spawns a process**, and the spawn is the cost. The
same shape — an expensive setup in front of a trivial assertion — in a
workspace the item does not yet cover.
