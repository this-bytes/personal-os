## The problem

`apps/server/src/__tests__/ownerPasswordExposure.test.ts` is a good test and
it was flaky, which is worse than either good-and-stable or bad-and-consistent.

**It passes on its own.** Run alone:

```
npx vitest run src/__tests__/ownerPasswordExposure.test.ts
  Test Files  1 passed (1)
       Tests  5 passed (5)
  Duration  14.38s
```

**It fails in the full suite**, where the same file reports one failure:

```
× still replaces the credential, so the exposure buys a working recovery path
```

**The cause is in the file, and it is a race between the test and the process
it is inspecting.** The test takes an exclusive lock on the database so the
reset process stays alive long enough to be read from outside, and it reads
it is reading from outside, and it reads the reset's command line while the lock is held. The
reset's own busy timeout
is five seconds — `busy_timeout = 5000` at `apps/server/src/db/client.ts:29`,
measured rather than remembered. **This paragraph used to say ten seconds,
which was wrong, and the correction is here rather than the line being quietly
rewritten.** On Windows the command line is read by spawning PowerShell
(`Get-CimInstance Win32_Process`), so when the machine is busy the read can
outlast the reset's timeout, the reset gives up on the lock and exits
non-zero, and the assertion `expect(resetExit).toBe(0)` fails.

The product is not broken. The recovery path works; the test proves it
every time it runs alone. What is broken is a test that answers differently
depending on what else the machine is doing.

**Why it matters more than a flaky test usually does.** The owner is holding
the push until the tree is green. A suite that is red on a busy machine and
green on an idle one is not a gate — it is a coin toss, and the first CI run
on GitHub happens on a machine this test has never seen.

## The race that was left behind — measured, not described

**The WMI change made the read fast. It did not make the read bounded, and
that is where the race moved.** The fast path was asked every time; but
whenever it had no answer, the file fell through to the same slow path it had
just removed:

```ts
  if (script) {
    const result = spawnSync('cscript.exe', ['//nologo', script, String(pid)], {…});
    const text = (result.stdout ?? '').trim();
    if (text.length > 0) return text;
  }
  // …and then PowerShell, for every question the fast path could not answer
```

**So one missed answer put a 5.7-second process start back on the critical
path — against a reset that waits five seconds.** Measured on this machine,
idle, and then under load (12 busy workers on 6 cores):

| Read                        | Idle     | Under load    |
| --------------------------- | -------- | ------------- |
| fast path — the script host | 222 ms   | 810 ms        |
| slow path — PowerShell      | 1,451 ms | **15,367 ms** |
| the reset's lock window     | 5,000 ms | 5,000 ms      |

**The slow path's cost scales with the machine's load. The window does not.**
That is the whole defect: the read grows and the thing being read does not.

**The loss was reproduced, by replicating the file's read loop exactly** — the
same lock, the same reset, the same two paths — with a single missed answer
forced:

```json
{
  "label": "current read, the fast path misses once",
  "polls": 2,
  "fellBack": 2,
  "readDoneMs": 19014,
  "resetExit": 1,
  "resetExitAtMs": 12919,
  "sawPassword": false,
  "lockBudgetMs": 5000
}
```

**The read took 19 seconds. The reset gave up on the lock at 12.9 seconds and
exited 1. The command line was never read** — which is the original red of
this item, reproduced and measured.

**And the read kept going afterwards.** The loop had no end of its own, so it
went on asking a dead process for its command line, paying a process start
every time, until its own thirty-second deadline:

```json
{
  "label": "current read, the reset has already died",
  "polls": 2,
  "fellBack": 2,
  "readDoneMs": 13066,
  "resetExit": 0,
  "resetExitAtMs": 6540,
  "sawPassword": false
}
```

**Thirteen seconds spent reading a process that had already gone.**

## The fix — the test side, and only the test side

**The race is gone, not the assertion.** Two changes, both in
`apps/server/src/__tests__/ownerPasswordExposure.test.ts`:

1. **The slow path is not a per-question fallback.** The script host is asked
   every time; PowerShell is asked only when there is no script host to ask
   (`readWindowsCommandLine` and `readWindowsCommandLineWithPowerShell`).
   **An empty answer is now an empty answer, and the next poll asks the fast
   path again.** The read's cost is now the fast path's cost, whatever the
   machine is doing.
2. **The wait stops when the process is gone.** `waitForCommandLine` takes the
   process rather than its pid and returns as soon as it has exited. **There is
   nothing left to read, and every further poll cost a process start.**

**Neither assertion was weakened, skipped or made conditional.** The test
still proves that the new password is visible in the host's process list while
the reset runs, that the recovery path replaces the credential, and that the
old password stops working. The test still holds the database lock for the
read, because the read is the point.

**What changed on the product's side: nothing.** The reset's busy timeout is
still `busy_timeout = 5000` (`apps/server/src/db/client.ts:29`) and it does
not move. **No configuration knob was added and no product behaviour changed**,
so the escalation this item names — a fix that needs a product change is
reported back rather than made quietly — is not needed.

**And the failures now say which failure they are.** A reset whose command line
was never readable and a reset that gave up on the lock before the read
finished are different problems, and `whatHappenedToTheRead()` names the
second one as the race it is.

**What the fix measures.** The same replication, with the fixed read:

| Read                                   | Idle   | Under load |
| -------------------------------------- | ------ | ---------- |
| fixed read, the fast path misses once  | 255 ms | 810 ms     |
| fixed read, the reset has already died | 417 ms | —          |

**The read finishes inside the reset's window, and it stops when there is
nothing left to read.**

## The proof that it bites — the same condition, the same machine, the same load

**A test that has never been seen red is not known to be a gate**, so the
condition was forced: the script host answers empty twice in a row, which is
what a missed WMI row or a start that failed under load looks like. **Twelve
busy workers on six cores**, and the shipped test file, changed in exactly
one place — the answer from the script host is emptied twice.

| Code                            | Verdict                                        |
| ------------------------------- | ---------------------------------------------- |
| **as it stands on `main`**      | **FAIL** — 2 failed and 3 passed of 5, 77.63 s |
| **with the fix on this branch** | **PASS** — 5 passed of 5, 30.05 s              |

**The output the old code produced was `Tests  2 failed | 3 passed (5)`,
and the failure it produced is this item's own red, verbatim:**

```
AssertionError: the reset process did not run, or its command line was not readable:
  expected null not to be null
```

**The same condition, on the same machine, under the same load: the old code
fails and the new code passes.** That is what the fix is for, and it is
measured rather than argued.

**And one honest note about what was NOT shown.** On an _idle_ machine the old
code survives a single missed answer, because the slow path answers in 1.45
seconds and that fits inside the five-second window. **The race is a margin,
not a coin that is already on the table** — it is lost when the read costs
more than the window, and the read's cost is what the machine's load decides.
**That is why the criterion says the suite is run twice, and why a fix that
was measured only on an idle tree is not a fix.**
