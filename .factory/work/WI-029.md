## The problem

`apps/server/src/__tests__/ownerPasswordExposure.test.ts` is a good test and
it is flaky, which is worse than either good-and-stable or bad-and-consistent.

**It passes on its own.** Run alone:

```
npx vitest run src/__tests__/ownerPasswordExposure.test.ts
  Test Files  1 passed (1)
       Tests  5 passed (5)
  Duration  14.38s
```

**It fails in the full suite**, where the same file reports one failure:

```
× still replaces the credential, so the exposure buys a working recovery path
```

**The cause is in the file, and it is a race between the test and the process
it is inspecting.** The test takes an exclusive lock on the database so the
reset process stays alive long enough to be read from outside, and it reads
the reset's command line while the lock is held. The reset's own busy timeout
is ten seconds. On Windows the command line is read by spawning PowerShell
(`Get-CimInstance Win32_Process`), so when the machine is busy the read can
outlast the reset's timeout, the reset gives up on the lock and exits
non-zero, and the assertion `expect(resetExit).toBe(0)` fails.

The product is not broken. The recovery path works; the test proves it
every time it runs alone. What is broken is a test that answers differently
depending on what else the machine is doing.

**Why it matters more than a flaky test usually does.** The owner is holding
the push until the tree is green. A suite that is red on a busy machine and
green on an idle one is not a gate — it is a coin toss, and the first CI run
on GitHub happens on a machine this test has never seen.

## Acceptance criteria

- [ ] **The test passes in the full suite and passes alone**, and it passes
      when the machine is busy. That is the whole point: the same assertion,
      the same result, regardless of load.
- [ ] **The race is gone, not the assertion.** The test still proves the
      exposure — that the new password is visible in the host's process list
      while the reset runs — and it still proves that the recovery path
      replaces the credential and that the old password stops working. Neither
      of those assertions is weakened, skipped, or made conditional.
- [ ] **The fix is named, and it says which side it changed.** The two honest
      shapes are: the test stops racing the reset — the lock is held only as
      long as the read needs, or the reset is given a timeout that matches the
      read — or the reset's busy timeout becomes configurable and the test
      sets it. **If the fix needs a product change** — a new configuration
      knob, say — that is a change to the server's behaviour and it is a
      different item with a different owner, so it is reported back here
      rather than made quietly. Chief takes it from there.
- [ ] The test still holds the database lock for the read, because the read is
      the point: the password has to be visible **while the reset runs**, and a
      test that reads the command line after the process exits proves nothing
      about the exposure.
- [ ] The gates pass: `npm run typecheck`, `npm run test`, `npm run
format:check`.
- [ ] The suite is run **more than once**, and the full run is run while the
      machine has other work on it, because a race that is fixed by luck
      looks exactly like a race that is not fixed.

## Not in scope

- **The recovery path itself.** It works. The reset replaces the credential,
  the old password stops working, and the new one works — the test says so
  every time it runs alone.
- **The exposure.** The password is visible in the host's process list while
  the reset runs. That is the documented cost of the recovery path, and it is
  published in `CONTRACTS.md`, `README.md` and `ARCHITECTURE.md` — the three
  documents the test checks, which are green.
- **The contract's audit-trail sentence** (`CONTRACTS.md:629-631`, where the
  result field has exactly one possible answer). That is a real finding and
  it is not this item's surface.
- **`executionOwner: 'external'`** (`CONTRACTS.md:544`), published and never
  written. Also a real finding, also not this item's surface.
