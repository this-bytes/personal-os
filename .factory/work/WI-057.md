## The owner's answer, and the gap it names

**The owner's answer, 2026-10-21: the substrate is proposal-only. The owner
accepts migrations; release is out of band; the instance can never apply,
merge, deploy or restart itself.**

The gap: the seven boundaries were a decision, and a decision that lives only in
a decision record is not something anybody can follow at two in the morning when
a release is broken.

## Acceptance criteria

- [ ] **Each of the seven boundaries has its rule, how it is kept, and how it
      is proved**, and the proof is a check somebody can run rather than an
      assurance.
- [ ] **The rollback is a command that works while the instance is down**, and
      the backup is a file copy. Both are written out, not described.
- [ ] **The migration rule is written as a rule the owner accepts**, and the
      gap between the rule and the code is named rather than smoothed over.
- [ ] **The flow from the owner's want to a released instance is drawn**, and
      each step names who may take it and what gate it passes.
- [ ] **The open items the runbook names are the open items that exist**, with
      their numbers.

## Not in scope

- **Making the boundaries mechanical.** B2 and B3 are procedures until WI-061
  lands, and the runbook says so.
- **The release itself.** Out of band, by decision.
- **The instance's ledger wiring.** That is WI-058.

## Notes

**The runbook found a real gap, and it is named in it rather than left for
someone to discover at the worst moment.** The server **applies pending
migrations on boot** (`apps/server/src/index.ts:55` and
`apps/server/src/runtime.ts:61`). So a rollback of the code is not a rollback
of the schema: an image older than the migration starts against a newer
database and may fail. That is why B3 exists, why a release carrying a
migration is not an ordinary release, and why WI-061 is funded.
