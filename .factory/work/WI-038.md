## The problem

The repository has a rule about the licences of what it borrows, and the rule
is a **claim in a document**. Nothing checks it. A dependency can arrive with
a licence nobody approved, or a licence that changed under a version bump, and
the pipeline will say nothing.

The owner answered at 08:54 that **the borrow rule becomes a check, not a
claim**. That answer funds this item, and WI-036 funds the ground truth it
compares against.

## Acceptance criteria

- [ ] **A licence change in the lockfile fails the build**, with the
      dependency named and the licence it changed **from and to**. A failure
      that says "a licence changed" is a failure nobody can act on.
- [ ] **An unapproved licence fails the build**, with the dependency named.
- [ ] **The gate compares against the licences WI-036 records.** The recorded
      licences are the ground truth; the gate does not carry a second copy.
- [ ] **A test or check proves that a deliberately changed licence fails.** A
      gate that has never been seen to fail is a gate that cannot fail, which
      is worse than no gate.
- [ ] **The gate's own output is shown in the run**, so a reader of the
      Actions tab can see what it compared and what it found.

## Not in scope

- **The recorded licences themselves.** That is WI-036, and it lands first.
- **This repository's own licence.** The owner's "private for now — no LICENSE
  yet" is about this repository, and it defers neither this item nor

- **Removing or replacing a dependency.** The gate fails the build; it does

  the record this factory keeps. What the record says is the record's

## What the gate compares, exactly

**The script is Probe's file.** `scripts/verify-*.ts` is Probe's by the
ownership table, and the three scripts already there — `verify-build.ts`,
`verify-bundle-size.ts`, `verify-stack.ts` — are standing policy checks, not
tests of a change. **The licence gate is one of those and is written in
Verify.** Chief's half of this item is the wiring: the step in
`.github/workflows/ci.yml` and the entry in the root `package.json`, both of
which the ownership table gives to Chief.

**The record is the only list.** `docs/dependency-licences.json` is the ground
truth, and the gate carries **no second copy** of the licences:

- `packages` — 494 entries, one per lockfile package, each with `lockPath`,
  `name`, `version`, `spdxId`, and `source` saying **which file its licence
  was read from** — `kind: "licence-file"`, `"package-json-field"` or
  `"published-identifier"`, with the file and the first identifying lines of
  it.
- `approvedSet.licences` — the 11 licences this project accepts, each with the
  reason it is accepted. The record's own note says what it is for: _"This is
  what WI-038's gate compares the lockfile against: a licence outside this
  set, or a change inside it, fails the build."_

**What the gate compares, in four parts.**

1. **The set.** Every licence the installed tree declares must be in
   `approvedSet.licences`. A licence outside the set fails, **with the
   dependency named**. A declaration that is an SPDX _expression_ passes only
   if **every** member of it is in the set.
2. **The change.** Where the record's `source.kind` is `package-json-field`,
   the record's `spdxId` and the installed package's declared licence are
   directly comparable, and a difference fails **naming the dependency and the
   licence it changed from and to**. For the other two kinds the record's id
   was read from a licence _file_ or from a _published identifier_, and a gate
   cannot re-read a licence file's meaning — so there the comparison is the
   **version**, and the failure says in words that the recorded licence may be
   stale and the record has to be re-read.
3. **The arrival and the departure.** A package in the lockfile that the
   record does not have fails: a new dependency has arrived and the record has
   not been re-read. A package in the record that the lockfile no longer has
   fails the same way, in the other direction.
4. **The first-party six are skipped, on purpose.** The record carries the six
   workspaces as `spdxId: "first-party (no licence yet)"`, and the owner said
   "private for now — no LICENSE yet". **The gate is about what this
   repository borrows.** The owner's decision defers this repository's own
   licence, and the gate must not turn that deferral into a red build.

**The exit codes, and why there are three.**

- **0** — the lockfile and the record agree.
- **1** — a licence problem: a change, an unapproved licence, an arrival, a
  departure.
- **2** — the gate could not run: the record or the lockfile is missing or
  unreadable. **A broken gate must never look like a clean one**, and a gate
  that cannot read its ground truth has proved nothing.

**The gate has to be runnable against a fixture, or it cannot be proved to
fail.** `npm run verify:licences` runs it against the repository's own record
and lockfile; the script also takes `--record <path>` and `--lockfile <path>`,
so a check can point it at a record with one licence deliberately changed and
watch it fail. **Criterion 4 is that proof, and it is why the options exist.**

**What the gate prints.** What it compared and what it found: the number of
packages compared, how many licences were read from which kind of file, the
approved set it compared against, and for every failure the dependency named
with the licence it changed from and to. **Criterion 5 is a reader of the
Actions tab seeing that**, and not only that the job went red.

**The wiring, as written.** In `.github/workflows/ci.yml`, in the
`Dependency audit` job, immediately after the vulnerability audit, because it
is the same concern over the same dependency set and the same install:

```yaml
- name: The dependencies carry the licences we approved
  run: npm run verify:licences
```

And in the root `package.json`, next to the other `verify:` entries:

```json
    "verify:licences": "tsx scripts/verify-licences.ts",
```
