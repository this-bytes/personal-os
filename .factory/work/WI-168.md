# WI-168 — A turn's work is the turn's own

**Owner:** the implementing agent, one session.
**Verifier:** an independent reviewer is named in the dispatch brief.
**State:** delivered — the rule holds on the App Server route against a runtime
that hands the thread's history back, the gate and the browser test are red
without it, and the room held two turns in one session against the installed
Codex 0.163.0.
**Branch:** `wi/168-two-turns`, cut from `origin/main` at `ea96eba`.

## Problem

The rule — _a turn's work is what arrives after the prompt_ — was settled on the
ACP route by [SPEC-R1-4](../../docs/spec/r1-4-acp-tool-activity.md), because the
ACP runtime replays the session it loads. The App Server route had no such rule.
Its session is a thread, and a thread that is resumed is the runtime's own
history; the route read every notification the runtime sent and put it in the
turn.

The room looked right, because the installed App Server 0.163.0 replays
nothing. The route was right by accident, and only on that version.

Two things were open with it:

1. **The rule was route-shaped.** A promise that holds only on the version that
   happens to keep it is not a promise, and the App Server deprecated
   full-history hydration for paginated threads — so a runtime that hydrates a
   long thread may hand that history back.
2. **The room had never shown two turns in one session.** That was SPEC-R1-4's
   outstanding evidence, blocked by the installed OpenCode's spent free
   allowance, and the review's own follow-up said the same thing in other
   words: _ordinary follow-ups are not proven to restore native context._

## The fix

- **The prompt is a boundary.** What arrived before the turn's prompt was
  written is the thread's history, not this turn's work — the rule the ACP
  route already holds.
- **The turn is a boundary.** The App Server's own notifications name the turn
  they belong to, so a thread hydrated with the turn that follows is told
  apart from the turn's own work by the turn id alone.
- **The session continues.** The second turn in a conversation resumes the same
  thread through the runtime, so the runtime keeps its own memory of the first
  turn. The product does not have to carry it.

The two boundaries are not one rule in two clothes. Each is load-bearing, and
each was measured without the other.

## What was measured first

The runtime's half, before anything was designed. Two probes against the
installed Codex 0.163.0:

- **The resume replays nothing.** The second turn's answer was its own, and the
  runtime said why: _"Full-history hydration is deprecated for paginated
  threads."_ The history is available to a client that asks for it.
- **The second turn kept the runtime's own memory.** Asked, with no history in
  the prompt at all, for the word it had been told to remember, the runtime
  answered `FIRST-TURN-OK`. It came from the thread the runtime kept.
- **The runtime names its turns.** `item/started`, `item/completed` and
  `item/agentMessage/delta` all carry the turn id, the same one `turn/started`
  and the answer to `turn/start` named.
