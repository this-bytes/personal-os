# WI-154 — The capability view: what a turn was admitted with

**Owner:** the contract lane — the session that owns `CONTRACTS.md` while its
slices are in flight.
**Verifier:** Probe, who reviews the slice before it is accepted.
**State:** implement
**Branch:** none — the slice landed on `main`.
**Base:** `b32d927`

## Problem

**The contract published a capability view, and nothing produced one.** Contract
7 publishes `TurnCapabilityView` — the effective tool set and grants, captured
when a turn is admitted — and the turn route answered `capabilityView: null`
for every turn, because the shape was published and not implemented. The
contract said so honestly, and the honesty was the whole of the feature.

**The steering decision asked the connection, not the turn.** Whether a turn
could take input mid-turn was read from the connection's live capabilities. A
capability that changed while a turn was running therefore changed the turn
underneath itself: a turn admitted against an agent that could take input
became unsteerable because the connection was re-probed, and a turn admitted
against an agent that could not became steerable because it was. The contract
already said a capability change takes effect on the next turn; the code did
not.

**The owner could not see what an agent was admitted with.** The panel showed
what the connection can do now, which is a different question from what this
turn was admitted with.

## What changed

**The view is pinned when the turn is admitted.** Every place that admits a
turn — a conversation turn and a factory turn — pins the same view, because
there is one rule for it and it lives with the capability API, which is the one
module the domain map lets read across every domain.

**The turn's own view answers what the turn may do.** A turn runs against the
set it was admitted with, so the steering decision asks the turn. A turn whose
view says the capabilities were never observed cannot be steered: nothing was
observed. A turn recorded before the view existed has none, so the connection
answers for it — the same answer it gave before the view was captured.

**A connection's capability set has a revision, and one comparison moves it.**
The revision moves when the set moves: the tool grants change, a probe reports
different capabilities, or the configuration is replaced and the capabilities
become unknown again. The rule is one comparison of the grant before the write
and the grant after it, so a branch that widens a grant cannot forget to move
the revision — which is also what WI-146's third branch needed, and it needed
it without knowing this rule existed. A grant saved unchanged does not move the
revision: the revision counts the changes, not the writes.

**The panel shows what the turn was admitted with.** The chat surface draws a
card with the agent, the revision, the capabilities and the tools, and it says
what the view is not: the MCP token names its connection, so a grant the owner
widens reaches the agent's next tool call as well as its next turn. The agent's
own card carries the revision, so a change there says when the set last moved.

## Scope and compatibility

**Owned paths** — the capability module, the agents service, the conversation
and factory dispatch, the contracts package, the schema and its migration, the
chat surface, and the contract.

**Compatibility.** The published `TurnCapabilityView` gained one member,
`capabilities`, which is nullable: a turn admitted against a connection that
had never been probed holds none, which is a different claim from holding an
empty set. A client that reads the view and ignores the member is unaffected.
A turn recorded before this change has no view at all, and the API reports it
as absent rather than as empty.

**The migration is additive.** `agent_connections` gains a column with a
default of 1, and `executions` gains a nullable column. Nothing is dropped and
no user data moves.

## Acceptance criteria

- [x] A turn is admitted with the capability set it runs against, and the view
      is pinned at admission.
- [x] A capability or grant change takes effect on the next turn and does not
      change the turn that is running.
- [x] Whether a turn can be steered is asked of the turn's own view.
- [x] A turn with no view is answered for by the connection, as it was before.
- [x] The revision moves when the set moves, and not when a save changes
      nothing.
- [x] The panel shows what the turn was admitted with, and says the limit.

## Not in scope

- **A turn-scoped MCP token.** The view pins the grants for the turn's own
  decisions — whether it can be steered, and what the panel says it may do —
  and it is not a per-turn enforcement of the tool surface. The token an agent
  holds names its connection, so a grant the owner widens reaches the agent's
  next tool call as well as its next turn. Making that turn-scoped is a
  different piece of work, and the contract says so rather than implying an
  enforcement that does not exist.
- **The worker's own view.** The worker runs the turn against the adapter it
  connected; the view says what the turn was admitted with, not what the
  adapter did with it.
