# WI-013 — The published contract tells the truth about the four approved changes

**Owner:** Wren
**State:** implement — **returned by Chief, 2026-10-21.** All four entries
now claim the code does not implement them, and the code implements all four.
One of them (WI-008) was already false when it was written. See "Chief's
review — 2026-10-21, second pass" below.
**Approved:** 2026-10-20 — the owner approved all three contract changes in
the MiniMax Bot batch, and the fourth (the agent memory scope) separately.
The shapes are sized in the work items; this item is the documentation of
them.

## Problem

`CONTRACTS.md` is the published contract of Personal OS, and it is currently
true of the code as it stands. Four changes are approved and about to be
built, and three of them change what `CONTRACTS.md` currently says:

| Change                                                 | Work item           | What `CONTRACTS.md` says today                                                                                                                                                                           |
| ------------------------------------------------------ | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unknown` on message, execution and task status        | [WI-008](WI-008.md) | `status?: 'streaming' \| 'complete' \| 'failed'` (`:71`) — and the concept already exists on `AgentConnectionStatus` (`:201`)                                                                            |
| Persona on the connection, override on the participant | [WI-006](WI-006.md) | `interface AgentConnection { id, name, adapterType, configRef, enabled }` (`:142-148`) and `interface Participant { … }` (`:38-44`)                                                                      |
| Deciding an approval resumes the turn                  | [WI-007](WI-007.md) | **"Deciding an approval finishes the execution it belongs to… The decision does not re-enter the adapter and continue the interrupted turn"** (`:426-431`) — in bold, and called a deliberate limitation |
| An agent has a memory of its own                       | [WI-012](WI-012.md) | `MemorySpec.scope` is `workspace \| conversation \| goal` (`packages/contracts/src/resource.ts:95-101`)                                                                                                  |

The third one is a **replacement**, not an addition. `CONTRACTS.md:426-431`
publishes the opposite of what WI-007 builds, in bold, and calls it
deliberate. That paragraph was written on purpose, so it has to be rewritten
on purpose.

**Until the entries land, the published contract and the code disagree.**
`CONTRACTS.md` is what every other implementation of Personal OS reads, and
a reader who follows it would get a 404 or the wrong behaviour from a route
that the contract says exists.

## Why now

The doctrine says a contract change needs a migration plan and a
`CONTRACTS.md` update **before** the change ships. The owner has approved the
changes and the shapes are sized; the documentation is the remaining step,
and it is the step that decides whether the contract is a description of the
product or a history of it.

## Acceptance criteria

- [ ] `CONTRACTS.md` documents the `unknown` state, and says what it means
      and that it is never automatically retried.
- [ ] `CONTRACTS.md` documents the persona: the base on the connection, the
      override on the participant, and the order they resolve in.
- [ ] `CONTRACTS.md:426-431` is **replaced** with the behaviour of WI-007,
      and the replacement says what happens when the adapter cannot resume —
      the panel says the turn was closed rather than continued.
- [ ] `CONTRACTS.md` documents the `agent` memory scope, and that the memory
      belongs to the agent connection rather than to a persona.
- [ ] Each of the four entries carries a **migration note** saying what
      happens to what exists today. Three of them are one sentence: nothing
      is reclassified, and the new behaviour applies only to what is written
      after the change. The fourth says the same, and says that an existing
      blocked execution with no persisted session id cannot be resumed and
      closes exactly as it does today.
- [ ] The entries match the shapes sized in the four work items.
- [ ] No entry describes a behaviour that the code does not have yet, without
      saying so.
- [ ] `unknown` means one thing here and another in
      `agentConnectionStatusSchema`, and the contract says which is which.
      `packages/contracts/src/agent.ts:52-58` carries `'unknown'` for a
      connection whose state was never checked — a new connection is created
      with `status: 'unknown'`, `capabilities: null` and a null
      `lastConnectedAt` (`apps/server/src/modules/agents/service.ts:212`).
      WI-008's `unknown` means "we started this and cannot confirm how it
      ended". One word, two meanings, one published contract. Added by
      Chief's review, 2026-10-21 — the item had an owner for this but no
      written criterion, and that is how findings get lost.

## Chief's review — 2026-10-21, second pass

The first pass of this review found one unmet criterion and it was fixed. This
one is bigger, and it is a different kind of finding.

**All four entries now say the code does not implement them, and the code
implements all four.** Each entry carries a sentence in this shape:

> This entry is the contract for **WI-0XX**. The code does not implement it
> yet: …

That sentence was true when the entries were written in `5a7e620`. It is false
now, and Chief checked each one against the tree:

| Entry  | Says the code does not implement                                                                                                                 | The code implements it, in                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| WI-008 | _"the shape above is what the implementation must reach"_                                                                                        | `9ad4f98` — `messageStatusSchema` carries `'unknown'` (`packages/contracts/src/conversation.ts:62`)                             |
| WI-006 | _"neither field exists on the connection or the participant, and there is no resolver to call"_                                                  | `70d042c` — `personaSchema` and `resolvePersona` are in `packages/contracts/src/agent.ts:28` and `:79`                          |
| WI-007 | _"the extension point `AgentAdapterExtras.resumeSession` is declared and never implemented, so today every decision still closes its execution"_ | `5f019b9` — `packages/agent-adapters/src/acp.ts:213` implements `resumeSession`, and `apps/worker/src/executor.ts:375` calls it |
| WI-012 | \_"`MemorySpec.scope` is `workspace                                                                                                              | conversation                                                                                                                    | goal` and the memory spec carries no agent field"\_ | `e764e6a` — `memoryScopeSchema` carries `'agent'` and the spec carries `agentConnectionId` (`packages/contracts/src/resource.ts:102`, `:112`) |

**The WI-008 entry was already false when it was written.** Chief checked the
order rather than assuming it: `git merge-base --is-ancestor 9ad4f98 5a7e620`
exits 0, so WI-008's implementation was already in the tree when Wren wrote
the entry fourteen minutes later. `git show 5a7e620:packages/contracts/src/conversation.ts`
carries `'unknown'` in `messageStatusSchema`. So that entry did not merely go
stale — it was published claiming the code did not implement a shape the code
had been implementing for a quarter of an hour.

**An independent verifier found the same sentence, from the other direction.**
Probe reviewed WI-008 (`task_8bb9dbcfbeaa`, commit `1cafe35`) and caught the
WI-008 entry as a contract-conformance failure rather than by reading the
entry against the tree:

```
× reaches the owner through a reason the contract has published
  → the waiting list returns a reason the published contract does not include:
    expected [ 'pending', 'review', 'blocked' ] to include 'unknown'
```

Chief confirmed the sentence at `CONTRACTS.md:130-131`:

> This entry is the contract for **WI-008**. The code does not implement it
> yet: the shape above is what the implementation must reach.

That is the **first row of the table above**, and it is the sentence that was
already false when it was written. Two reviewers, two methods, one finding.

**One more gap came out of that review, and it does not belong to this item.**
`automationRunStatusSchema` (`packages/contracts/src/automation.ts:73`) gained
`'unknown'`, and `CONTRACTS.md` publishes no automation run status at all — so
nothing contradicts it, and nothing records it either. It is a gap in the
published surface, not a stale sentence, and it is recorded as a want in
`.factory/INTAKE.md` — unnumbered, because the number space has one owner.

**Why this is a defect and not a stale sentence.** The criterion on this item
is _"No entry describes a behaviour that the code does not have yet, without
saying so."_ That criterion is about entries describing behaviour the code
lacks. These entries describe behaviour the code **has**, and say it does not.
A reader who reads the entry, then reads the code, finds the contract
contradicting itself — which is the exact failure this batch of items exists
to remove. The contract is the truth; it cannot publish a falsehood about
its own implementation.

**What has to change, and what has not.** The published _shapes_ are correct
and the owner's approval stands. What is wrong is each entry's statement about
the state of the code. Each entry needs to say what is true now — that the
code implements the shape, in the commit that does — instead of claiming
otherwise. The migration notes stay exactly as they are: they still describe
what the change means for rows that already exist, and nothing is reclassified.

**One further gap, in WI-008's entry, which is separate.** WI-008's commit
message says so itself:

> One thing this commit does not do: CONTRACTS.md publishes the waiting list's
> reasons as `pending | review | blocked`, and the reason this item needs is
> not among them. The published entry for the status enums is in the tree, but
> the waiting list's enum has to grow by one word before the contract and the
> code agree.

Chief confirmed it against the tree: `CONTRACTS.md:632` publishes
`type WaitingReason = 'pending' | 'review' | 'blocked';` and
`apps/server/src/api/waiting.ts:17` declares
`'pending' | 'review' | 'blocked' | 'unknown'`. The published type is missing
a member the code emits. That is a published type that the code has outgrown,
and it is a separate defect with its own home — Chief opened it as
[WI-022](WI-022.md). It is not folded into this item, because the waiting
list's contract is not this item's surface.

## Chief's review — 2026-10-21

**The entries landed, and they are honest.** All four are in `CONTRACTS.md`
now — the `unknown` state, the persona, the approval resume and the agent
memory scope — and each one says in its own words that the code does not
implement it yet, with a migration note that reclassifies nothing. That
ordering is the right one: the contract is the truth, the code is checked
against it, and the gap is stated rather than hidden. `ARCHITECTURE.md` and
`SECURITY.md` moved with them.

**One criterion is not met, and it is the one this item was given.** The
contract has to say that `unknown` means one thing here and another in
`agentConnectionStatusSchema`. It does not. `CONTRACTS.md:90-128` defines
the new `unknown` carefully — what separates it from `failed`, that it is
never retried automatically, that it is a question for the owner — and never
mentions that `packages/contracts/src/agent.ts:52-58` already carries an
`'unknown'` for a connection whose state was never checked. A new connection
is created with `status: 'unknown'`, `capabilities: null` and
`lastConnectedAt: null`
(`apps/server/src/modules/agents/service.ts:212`).

One word, two meanings, one published contract. A reader who has met both
has to work out which is which from the shape of the thing they are looking
at, and the contract does not ask them to.

**One sentence, in the entry that defines it.** Say that this `unknown` is
about an outcome that cannot be confirmed, and that the connection's
`unknown` is about a state that was never checked — and that they are
different things that happen to share a word. The entry is the right place;
the connection status has its own contract section elsewhere.

**After that, this item goes to Probe.** It changes no code, so the only
gate that applies is that the documentation is checked against the code by
the reviewer — and a contract that publishes a type the code does not have
is exactly what a reviewer should be looking at.

## Notes

**The tiebreak, said out loud.** `*.md`, `CONTRACTS.md` and `docs/decisions/`
are Wren's files, and this item writes only those. The four code items
belong to Cog. The direction of authority is one way: **the published
contract is the truth and the code is checked against it**, not the other
way round. If the code and the entry disagree, the entry wins and the code
is the defect. That is the only way a contract stays a contract.

**One entry per work item, and the dependency is explicit.** Each of the four
code items carries "the contract entry exists" as an acceptance criterion,
so the code cannot be accepted while the contract disagrees with it. The
order of the entries follows the order of the code: WI-008, WI-006, WI-007,
WI-012.

**What the migration notes must not do.** They must not reclassify
anything. We cannot know which of the existing `failed` records were really
unknown, and which existing blocked executions were really resumable.
Guessing would be the dishonesty this whole batch exists to remove, written
down as a migration plan.

**Size.** Small-to-medium: four contract sections, four migration notes, and
one paragraph replaced in bold.
