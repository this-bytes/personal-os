## Problem

An agent connection is a transport with a name and a set of capabilities
(`packages/contracts/src/agent.ts:21-28`). It has no memory of its own. Every
memory in the instance belongs to the workspace, a conversation or a goal
(`MemorySpec.scope` is `workspace | conversation | goal`,
`packages/contracts/src/resource.ts:95-101`).

So when the owner talks to an agent tomorrow, that agent starts from nothing
every time. It cannot remember what it learned in the last conversation, what
it was told to prefer, or what it concluded last week. The agent is a
connection, not a colleague.

The plugin's bots each have their own memory scope — `self`, `team`, `bot` —
keyed, revision-guarded and budgeted at 6 000 characters of context
(`miniapp/node/memory.mjs`, `memory-context.mjs`). **The plugin's scope enum
is the plugin's dependency shape and is not imported.** The idea is borrowed;
the shape is ours.

## Why now

The owner's priority job is talking to agents, and a colleague that forgets
everything between conversations is the single most obvious way that job
stays hard. It is also the thing that makes the persona item (WI-006) mean
something: a role with no memory is a label, and a role with memory is a
person the owner can work with.

And the owner's own rule cuts the other way here: this is the second
published-contract change in this batch, so it goes last in the order, after
the persona it builds on.

## The contract shape, sized by Chief

```ts
// packages/contracts/src/resource.ts
export const memoryScopeSchema = z.enum([
  'workspace',
  'conversation',
  'goal',
  'agent', // new
]);
```

and on the memory spec itself:

```ts
export const memorySpecSchema = z.object({
  scope: memoryScopeSchema.default('workspace'),
  /** Which agent this memory belongs to. Required when scope is 'agent'. */
  agentConnectionId: idSchema.optional(),
  key: z.string().min(1).max(300),
  value: z.unknown(),
  tags: z.array(z.string()).default([]),
});
```

**The memory belongs to the agent, not to the persona.** A conversation may
override an agent's persona, and a persona is per conversation; memory that
changed when the conversation changed would not be the agent's memory. The
memory is keyed by `agentConnectionId`, so it follows the agent across every
conversation it takes part in.

**Nothing in the server has to change to store it.** `MemorySpec.scope` is
currently written and read as an opaque enum — `apps/server/src/modules/
resources/service.ts:301` hands `memorySpecSchema` to a table provider and
nothing filters on `scope` — so adding a value is additive. The work is in
the _read_ side: a turn's context must include the memories of the agent
taking the turn.

**The budget.** The plugin caps the context brief at 6 000 characters, pinned
first and then most recent. The same rule is adopted here, so an agent's
memory cannot crowd out the conversation. The number is a product decision
and Chief proposes 6 000 for the agent's share of the context; the owner may
overrule it, and the item says which number it is.

## Acceptance criteria

- [ ] `agent` exists as a memory scope, and a memory with that scope names
      the agent it belongs to.
- [ ] A memory scoped to an agent is available to that agent's turns in every
      conversation, and to no other agent's turns.
- [ ] A memory with any other scope behaves exactly as it does today.
- [ ] The agent's memories are in the turn context, within the stated budget,
      pinned first and then most recent.
- [ ] Nothing imports the plugin's `self/team/bot` scope enum: the scope
      names are ours, and so is the keying.
- [ ] The panel shows an agent's memory — what that agent remembers, and
      when it was written.
- [ ] `CONTRACTS.md` carries the `agent` memory scope entry, with a migration
      note.
- [ ] `npm run typecheck` and `npm run test` pass, and the behaviour is
      covered by a named test.

## Not in scope

- **The plugin's memory service.** No memory plugin, no revision-guarded
  plugin ledger, no 6 000-character plugin budget implementation. We build
  the idea in our own resource model.
- **The scope of the memory's subject.** This is about the _agent_, and the
  agent is the connection. A scope keyed by the resolved persona is a
  different item.
- Changes to how a persona is resolved (that is WI-006).
- Any change to the owner's `workspace | conversation | goal` scopes. They
  keep working exactly as they do.
- A per-agent memory _budget_ that is separate from the context budget, and
  any kind of eviction policy. The context budget is enough for now.

## The fix, and the one rule it is — 2026-10-21 07:55

Cog's fix is `1d45543` "Judge a memory write by who owns it, not only by what
it says", one file: `apps/server/src/modules/mcp/server.ts`. Probe's two red
tests for the write path pass now, and the third is left red on purpose.

**The two write defects were one defect.** The guard compared the _new data's_
`agentConnectionId` with the actor's, and it was called on `resource.create`
and nowhere else. `resource.update` takes the id of the resource it changes,
and the memory's _current_ owner was never consulted — so the guard had
nothing to compare and the write went through. A memory now stays the other
agent's whether the write hands it to the writer itself, hands it to somebody
else, or rewrites what is in it.

**One ownership rule, asking two questions about a write:** whose memory the
resource is, and whose memory the write says it should be.

- `apps/server/src/modules/mcp/server.ts:113` — `memoryOwner(type, data)`:
  whose agent-scoped memory is this
- `apps/server/src/modules/mcp/server.ts:144` — `assertOwnMemory(current, next)`:
  the rule itself
- `apps/server/src/modules/mcp/server.ts:358` — `resource.create` passes the new
  data only
- `apps/server/src/modules/mcp/server.ts:413-417` — `resource.update` reads the
  resource first, so the current owner is known even when the write says
  nothing about it

**The rule stays in the MCP module because that is the only place an agent can
act.** The REST resource API takes an owner session and says so, so this is
the whole of the surface.

**The third red is not this item's, and the reason is the owner's.** "Does not
let an agent read another agent's memory" was not a breach of anything the
contract published: `resource.get` is published as "Read a resource", with no
promise about who owns a resource, so the contract did not say that an agent
may not read one. **The owner answered at 07:07 — No, an agent's own memory
is private to it, on reads as well as on writes** — and that answer is
**WI-028**: the read-side guard, and the two contract entries that stop
disagreeing. Cog left the red alone and wrote down why refusing the read is
one call — `assertOwnMemory(current, undefined)` in the `resource.get`
handler. That is the right shape and the right reason.

**Chief's note on this item's own gate criterion — corrected 2026-10-21.** This
note used to say the suite is not green until WI-028 lands, because the read
red sat in this item's suite. **That was true when written and is false now**:
`622812c` landed the read guard at 07:33, the suite is 10/10, and
`npm run test` is 211/211. Probe found the sentence (D1) and it is corrected
here rather than left to mislead the next reader.

## Returned to implement — 2026-10-21

**The item does not meet its acceptance criteria.** Probe's report, task
`task_533f34c6d269`, batch `batch_d6134c0c366d`. The read path — the part
that puts the right memory in the right agent's turn — is correct and properly
keyed, and the three other scopes, the budget's pin ordering, the plugin
boundary and the panel all hold.

**What does not hold is the write path.** The ownership rule the code states
for itself is enforced on `resource.create` and **absent from
`resource.update`**, so one agent can write into another's memory and take it
over — which puts a memory in the wrong agent's turns, the thing
`CONTRACTS.md:452-455` forbids.

The guard is one function, and it is only called from one path:

```ts
// apps/server/src/modules/mcp/server.ts:112-122
const assertOwnMemoryScope = (type: string, data: unknown): void => {
  if (actor.kind !== 'agent') return;
  if (type !== 'memory') return;
  const spec = memorySpecSchema.safeParse(data ?? {});
  if (!spec.success) return;
  if (spec.data.scope !== 'agent') return;
  if (spec.data.agentConnectionId === actor.agentConnectionId) return;
  throw new AppError('forbidden', 'An agent may only write into its own memory.', 403);
};
```

It compares the **new data's** `agentConnectionId` with the actor's. On an
update the new data may say nothing at all, and the resource's **current**
owner is never consulted — so the guard has nothing to compare and lets the
write through. Three red tests are committed with that name on them
(`apps/server/src/__tests__/agent-memory.test.ts`, commit `af00a4e` "Hold one
agent out of another agent's memory"):

- `does not let an agent write into another agent's memory by updating it`
- `does not let an agent take over another agent's memory`
- `does not let an agent read another agent's memory`

**Probe's read of the fix, and Chief agrees with it.** One ownership rule
applied to the whole MCP resource surface for agents, checked against the
resource's **current** owner as well as the new data, plus the read-side
question answered once for all three tools. Not a second guard beside the
first one.

**This item is the memory guard's home.** The finding was raised in the group
