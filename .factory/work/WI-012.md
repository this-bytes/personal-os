# WI-012 — An agent has a memory of its own

**Owner:** Cog
**State:** triage
**Approved:** 2026-10-20 — the owner answered "Yes — an agent gets its own
memory scope" to the question Chief put in `.factory/INTAKE.md` (C-11). The
direction is settled; the contract shape is Chief's to size.
**Not scheduled until:** `CONTRACTS.md` carries the entry with a migration
note — see [WI-013](WI-013.md), which is Wren's.

## Problem

An agent connection is a transport with a name and a set of capabilities
(`packages/contracts/src/agent.ts:21-28`). It has no memory of its own. Every
memory in the instance belongs to the workspace, a conversation or a goal
(`MemorySpec.scope` is `workspace | conversation | goal`,
`packages/contracts/src/resource.ts:95-101`).

So when the owner talks to an agent tomorrow, that agent starts from nothing
every time. It cannot remember what it learned in the last conversation, what
it was told to prefer, or what it concluded last week. The agent is a
connection, not a colleague.

The plugin's bots each have their own memory scope — `self`, `team`, `bot` —
keyed, revision-guarded and budgeted at 6 000 characters of context
(`miniapp/node/memory.mjs`, `memory-context.mjs`). **The plugin's scope enum
is the plugin's dependency shape and is not imported.** The idea is borrowed;
the shape is ours.

## Why now

The owner's priority job is talking to agents, and a colleague that forgets
everything between conversations is the single most obvious way that job
stays hard. It is also the thing that makes the persona item (WI-006) mean
something: a role with no memory is a label, and a role with memory is a
person the owner can work with.

And the owner's own rule cuts the other way here: this is the second
published-contract change in this batch, so it goes last in the order, after
the persona it builds on.

## The contract shape, sized by Chief

```ts
// packages/contracts/src/resource.ts
export const memoryScopeSchema = z.enum([
  'workspace',
  'conversation',
  'goal',
  'agent', // new
]);
```

and on the memory spec itself:

```ts
export const memorySpecSchema = z.object({
  scope: memoryScopeSchema.default('workspace'),
  /** Which agent this memory belongs to. Required when scope is 'agent'. */
  agentConnectionId: idSchema.optional(),
  key: z.string().min(1).max(300),
  value: z.unknown(),
  tags: z.array(z.string()).default([]),
});
```

**The memory belongs to the agent, not to the persona.** A conversation may
override an agent's persona, and a persona is per conversation; memory that
changed when the conversation changed would not be the agent's memory. The
memory is keyed by `agentConnectionId`, so it follows the agent across every
conversation it takes part in.

**Nothing in the server has to change to store it.** `MemorySpec.scope` is
currently written and read as an opaque enum — `apps/server/src/modules/
resources/service.ts:301` hands `memorySpecSchema` to a table provider and
nothing filters on `scope` — so adding a value is additive. The work is in
the _read_ side: a turn's context must include the memories of the agent
taking the turn.

**The budget.** The plugin caps the context brief at 6 000 characters, pinned
first and then most recent. The same rule is adopted here, so an agent's
memory cannot crowd out the conversation. The number is a product decision
and Chief proposes 6 000 for the agent's share of the context; the owner may
overrule it, and the item says which number it is.

## Acceptance criteria

- [ ] `agent` exists as a memory scope, and a memory with that scope names
      the agent it belongs to.
- [ ] A memory scoped to an agent is available to that agent's turns in every
      conversation, and to no other agent's turns.
- [ ] A memory with any other scope behaves exactly as it does today.
- [ ] The agent's memories are in the turn context, within the stated budget,
      pinned first and then most recent.
- [ ] Nothing imports the plugin's `self/team/bot` scope enum: the scope
      names are ours, and so is the keying.
- [ ] The panel shows an agent's memory — what that agent remembers, and
      when it was written.
- [ ] `CONTRACTS.md` carries the `agent` memory scope entry, with a migration
      note.
- [ ] `npm run typecheck` and `npm run test` pass, and the behaviour is
      covered by a named test.

## Not in scope

- **The plugin's memory service.** No memory plugin, no revision-guarded
  plugin ledger, no 6 000-character plugin budget implementation. We build
  the idea in our own resource model.
- **The scope of the memory's subject.** This is about the _agent_, and the
  agent is the connection. A scope keyed by the resolved persona is a
  different item.
- Changes to how a persona is resolved (that is WI-006).
- Any change to the owner's `workspace | conversation | goal` scopes. They
  keep working exactly as they do.
- A per-agent memory _budget_ that is separate from the context budget, and
  any kind of eviction policy. The context budget is enough for now.

## Notes

**Published boundary.** `CONTRACTS.md` publishes the memory resource, so
`MemorySpec.scope` is a published contract. The factory stops there for
owner approval — the owner has now approved the direction, and the shape
above is Chief's sizing. `CONTRACTS.md` needs the entry and a migration
note before the change ships; that is [WI-013](WI-013.md), which is Wren's.

**The migration plan is one sentence.** Existing memories are unaffected: the
three current scopes keep their meaning, and no memory is reclassified. The
new scope applies only to memories written after this item. We cannot know
which of the existing workspace-scoped memories were "really" the agent's,
and guessing would be the same dishonesty WI-008 exists to remove.

**Order.** Last of the contract batch: **WI-009 → WI-008 → WI-007 → WI-006
→ WI-012.** The persona comes before it, because an agent's memory is only
meaningful once the agent has a role.

**Size.** Medium: one enum addition, one optional field, a read path into the
turn context with a budget, a panel surface, and the tests for each.
