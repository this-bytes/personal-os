# WI-061 — The release does not migrate on boot

**Owner:** Cog
**Verifier:** Probe
**State:** intake — funded and numbered, and **not dispatched**. It was found
by WI-057, and it is the gap between boundary B3 and the code.
**Opened:** 2026-10-21 by the strategy session, from the self-improvement
runbook's finding
**Numbered:** 2026-10-21 — WI-046 through WI-061, taken by the session that owns
the number space.

## The gap it names

**The server applies pending migrations on boot.**
`apps/server/src/index.ts:55` and `apps/server/src/runtime.ts:61` both call
`runMigrations`, and `apps/server/src/db/migrate-cli.ts:6` says so in its own
comment: "The server also applies migrations on boot, so this is only needed
for controlled deployments."

That is the right behaviour for a self-hosted instance that has one owner and
no operations team. It is also **the one thing that makes boundary B3 a
procedure rather than a mechanism**: the owner cannot accept a migration
before it is applied, because the boot applies it.

And it makes **B2's rollback a code rollback only**. The data lives in the
volume and the code lives in the image, so rolling the code back does not touch
the data — but an image older than the migration starts against a newer schema
and may fail.

## Acceptance criteria

- [ ] **The boot does not apply a migration without the owner having accepted
      it.** Either the release path applies the migration as a separate,
      explicit step, or the boot is told not to, and the decision is recorded
      either way.
- [ ] **The behaviour is stated in `CONTRACTS.md`**, because a client that
      deploys the instance needs to know when the schema changes.
- [ ] **A migration that drops or rewrites user data has a rollback story**,
      as AGENTS.md already requires, and the runbook points at it.
- [ ] **The rollback procedure in `docs/self-improvement.md` is true after this
      lands** — a rollback of the code is a rollback of the schema too, or the
      runbook says which migrations are not backward compatible.
- [ ] **The existing `npm run db:migrate` path still works**, and the smoke
      test still passes against a fresh database.

## Not in scope

- **A migration framework.** The migrations are drizzle's, and they stay.
- **Multi-tenant or zero-downtime deployment.** This is a single-owner
  instance; the runbook's one-command rollout is the whole story.
- **The rollback command itself.** That is in WI-057's runbook and it does not
  change.
