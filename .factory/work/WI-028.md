## The owner's ruling

The owner was asked one question:

> Two entries in the contract disagree about who owns an agent's memory. The
> memory entry says a memory is 'available to that agent's turns in every
> conversation, and to no other agent's turns'. The resource-read entry
> publishes 'Read a resource' with no ownership rule at all, and the code
> enforces the write side only — so today an agent can write into another
> agent's memory but may or may not read one, depending on which entry you
> believe. May an agent read another agent's own memory?

**Answered at 07:07 on 2026-10-21: no.** An agent's own memory is private to
it. The read side says what the memory entry already says, and the code
enforces the same rule on both sides.

## The problem

Two entries in `CONTRACTS.md` disagree, and the code enforces only one of
them.

`CONTRACTS.md:450-455`, the agent memory scope entry:

> An agent-scoped memory is keyed by `agentConnectionId`, so it follows the
> agent across every conversation it takes part in — available to that agent's
> turns in every conversation, **and to no other agent's turns**.

The resource-read entry publishes "Read a resource" with no promise about who
owns it. The write path enforces the ownership rule; the read path does not.

**A red test pins the stricter reading, and it says what it is.** In
`apps/server/src/__tests__/agent-memory.test.ts`, "does not let an agent read
another agent's memory":

> This one is a question, not a breach: `resource.get` is published as "Read a
> resource" with no promise about who owns it, so the contract does not say an
> agent may not read one. The rule the code states for writes — an agent
> touches only its own memory — has no read-side counterpart, and this test
> pins the stricter reading **until the owner says which one holds**.

The owner has now said. The test was never a defect report; it was a question
held open, and the question is closed.

## Acceptance criteria

- [ ] **The contract says the same thing on both entries.** The agent memory
      scope entry states the read side explicitly — an agent's own memory is
      available to that agent's turns and to no other agent's turns, reads
      included — and the resource-read entry stops being silent about
      ownership: reading a resource is not a way around the memory rule. The
      two entries agree, and the change to each is named.
- [ ] **The code refuses the read.** An agent that addresses another agent's
      agent-scoped memory through the read path is refused, the way it is
      refused on create and on write. The refusal is the same shape as the
      write refusal — one rule, not two.
- [ ] **The read is still allowed when it should be.** An agent reads its own
      agent-scoped memory, and reads workspace-, conversation- and goal-scoped
      memories, which are shared by design. The rule is about the agent scope
      and not about memories in general, and the item says so.
- [ ] **The pinned test is green and it stays.** "Does not let an agent read
      another agent's memory" was the specification of this ruling; it does not
      go away because the ruling went the way it was written to go.
- [ ] **The refusal is in the audit trail**, the way the write-side refusal
      is, so an owner can see that an agent tried.
- [ ] The gates pass: `npm run typecheck`, `npm run test`, `npm run
    format:check`, `npm run build`.

## Notes

**Why this is one item and not two.** The substance of the ruling is the code
enforcing what the contract already says. The contract change is a
clarification of two entries so that they stop disagreeing, and it lands in
the same change as the guard — the same way WI-007's contract entry landed
with its implementation. Splitting it would put a one-line clarification and
a guard that depends on it into two items and two reviews for no gain.

**Do not edit `CONTRACTS.md` before WI-022 and WI-026 have landed.** The file
is live with Wren, in that order. This item's two entries are the memory
scope entry and the resource-read entry; neither of them is the reason or the
kind, so the file is not contended once Wren's two items are done.

**The one thing this item must not do.** It must not read as "an agent may
read memories" and narrow later. The rule the owner made is narrow and
specific: the **agent scope** is private to its agent, on reads as well as on
writes, and the other three scopes are unchanged.
