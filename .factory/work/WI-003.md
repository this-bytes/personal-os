# WI-003 — Reload the panel only when a route chunk failed to load

## Problem

`apps/web/src/components/LazyRoute.tsx` puts an error boundary around every
lazily loaded route. The boundary cannot tell two failures apart:

- the **chunk failed to download** — the page asks for a file the new build
  renamed, or the request is dropped on the floor; and
- the **page itself threw** — a bug in a page component, or a response the
  page did not guard.

Both reach the same boundary, and the boundary answers both the same way.
After a retry, `componentDidCatch` calls `window.location.reload()`:

```tsx
override componentDidCatch(): void {
  // The owner already asked for this page once and it failed again. The
  // browser remembers a module that failed to load, so no further attempt
  // in this document can succeed: a new document is the only way forward.
  if (this.props.attempt > 0) {
    window.location.reload();
  }
}
```

So a page component that crashes does not show its error. The owner presses
Retry, and the panel silently reloads instead — the crash happens again, and
the owner is back at the same error state with their place lost. The reload is
correct for a chunk that could not be downloaded, because the browser will not
fetch that chunk again in this document. It is the wrong answer for a page
that throws, where the chunk is present and the code in it is broken.

## Why now

It came in with the WI-001 fix and it is not part of WI-001's acceptance
criteria, so it belongs in its own item rather than reopening an accepted one.
It is a small, contained fix and it is the kind of thing that gets worse with
time: every page that throws will reload the panel instead of showing why.

## Acceptance criteria

- [ ] A chunk that fails to load and a page component that throws are told
      apart, and only the first one reloads the document.
- [ ] A page that throws shows its error state and the navigation still
      works, and pressing Retry does not reload the panel.
- [ ] A chunk that fails to load still reloads after a retry, because that is
      the only thing that defeats the browser's failed-module cache.
- [ ] The retry cannot loop. A document reload must not repeat forever.
- [ ] The behaviour is covered by a test that fails without the change.

## Not in scope

- No change to the router, the URLs or the look of any page.
- No change to the chunk split or the bundle budget.
- No new error-reporting service and no telemetry.
- No change to the loading fallback.

## Gates

- `npm run typecheck`
- `npm run test`
- `npm run format:check`
- `npm run build`
- `npm run verify:bundle`
- `npm run test:e2e`

## Notes

`apps/web/src/components/LazyRoute.tsx` is the file. `ErrorState` in
`apps/web/src/components/ErrorState.tsx` already takes an optional `onRetry`,
so a second, non-reloading action can be added to it if the owner needs one.

The boundary cannot see the difference on its own, because `React.lazy` turns
a rejected import into a thrown error and React hands the boundary the same
thing either way. The loader is the place that knows: it is the only code
that can tell a rejected `import()` from a component that threw while
rendering.
