### 4. `data` and `template` merge — the behavioural break

**Before** — `24480b7:CONTRACTS.md:630-633`:

> `template` names the template to start from: its `spec` is the resource's
> `data`, and its `type` must equal the `type` the call asks for. `data` and
> `template` are **mutually exclusive** — a call that supplies both is refused,
> because there is no published answer to which of the two wins.

**After** — `CONTRACTS.md:680-688`:

> **`data` and `template` are not mutually exclusive — they merge.** `template`
> names the template to start from, and its `type` must equal the `type` the
> call asks for. `data` is the caller's own values, and the resource's `data` is
> the template's `spec` with those values merged into it. **A call that carries
> both is no longer refused — it is answered**, and the values the call did not
> name are the template's.

The merge rules were **published as the implementation has them**
(`CONTRACTS.md:693-715`), and they are the rules `mergeTemplateSpec` implements
(`apps/server/src/modules/resources/templates.ts:496-543`):

- objects merge key by key, recursively;
- an array is replaced whole;
- a change of the shape key (`kind` for a data source, `scope` for a memory)
  replaces the whole spec;
- `automation.trigger`, `automation.action` and `memory.value` are replaced
  whole whatever they are;
- a dashboard's widgets merge by the widget's own `id` — named by the same id is
  updated field by field, unnamed survives, added is appended after the
  template's, and a widget whose `type` changes is the caller's whole;
- the merge never refuses; the owning provider judges the merged spec.

**Evidence — the merge was run, not inferred.**

- `resource.create` with `template: { id: "dashboard.metrics" }` and
  `data: { refreshSeconds: 30, widgets: [{ id: "summary", title: "Records
(mine)" }] }` answered with the widget `summary` carrying the caller's title
  and the template's `type` and `binding`, the widget `recent` untouched,
  `refreshSeconds: 30` and `published: false`.
- A document from `document.brief` with `data: { tags: ["mine"] }` answered with
  `tags: ["mine"]` — the array replaced whole — and the template's `format` and
  `content` intact.
- A data source from `data-source.json` with `data: { kind: "http", url: … }`
  answered with **no `payload`** — the shape key changed, so the whole spec was
  replaced.

**The test that pinned the old rule changed with it.** The test named _"refuses a
call that carries both a spec and a template"_ is now _"merges the values it is
given into the template's spec"_
(`apps/server/src/__tests__/resource-templates.test.ts:537`). The contract and
the test now agree.

### 13. The refusal message wording (Chief's addition)

**Decision: the wording is published as _not fixed_, not verbatim.**

**Added** — `CONTRACTS.md:904-912`:

> **The refusal names the action; the rest of its wording is not fixed.** A
> refusal the autonomy policy makes says which action was refused, in a sentence
> the owner can act on, and it carries the action and the allowed actions in
> `details` … **The wording itself is not part of the contract**: the sentence is
> composed from the policy in force, so it changes when the policy changes, and a
> client must not match on it. A client matches on the `code` — a refused action
> is `forbidden` — and on the `action` in `details`. The one exception is a
> refusal whose message is fixed in the code and published in this section, such
> as "An agent may only reach its own memory."

**Why.** `autonomyActionRefusal` (`packages/contracts/src/autonomy.ts:374-381`)
composes its sentence from the policy in force — the allowed actions and the
level that set them — so the string changes whenever the policy changes. A
client would have to match on the `code` and on `details.action`, not on the
prose. Publishing the prose verbatim would publish a sentence with a variable
middle and would make it look fixed when it is not. **The house's preference —
"publish what a client would have to match, and say plainly when a string is not
fixed" — points this way.** The one message the house does publish verbatim is
the fixed one, "An agent may only reach its own memory.", and this entry says so.

### A. A dashboard, a document, a data source or an automation that breaks their contract answers `internal_error`, not `validation_failed`

**The contract is correct here. The code is inconsistent, and the fix is in the
code.**

- **Contract side:** `CONTRACTS.md:685-689` promises `validation_failed` for **a
  template's** spec — and that promise holds. `templateGet` wraps a provider's
  refusal in `errors.validation`
  (`apps/server/src/modules/resources/service.ts:638-655`), and `templateMerge`
  refuses a template of the wrong kind the same way (`:657-667`). **The contract
  does not promise `validation_failed` for a resource's own spec, and this item
  did not widen it to say so.** The contract says what it says, and it is true.
- **Code side, and the defect:** `tableProvider`'s `validate` is
  `schema.parse(data)` (`apps/server/src/modules/resources/service.ts:176`),
  which throws a raw `ZodError`. `errorResult` maps anything that is not an
  `AppError` to `{ code: "internal_error", message: <the zod message> }`
  (`apps/server/src/modules/mcp/server.ts:52-61`). So a **dashboard, a document,
  a data source or an automation** whose spec breaks its contract answers
  `internal_error` with a zod message in it, while a **task** and a **memory** —
  whose providers wrap their own failures — answer `validation_failed` with the
  issues in `details`
  (`apps/server/src/modules/resources/service.ts:349-358`, `:410-419`).
- **What I saw:** `resource.create` of a dashboard whose merged spec carried a

  `tableProvider` should wrap a `ZodError` into `errors.validation`, as the task

  spec rather than as an internal error. **The contract does not change, and
  this item did not change it.**

## The daily spend cap (Chief's fourth dispatch)

**The reservation is lifted for the mechanism.** WI-102 ("Enforce the daily spend
cap where the chain's spend limit is enforced", commit `d44bed4`) is merged into
the vehicle, so **the tree this item publishes against does enforce
`dailySpendUnits`.** Finding C below is therefore rewritten, not repeated.

**The limit is enforced, in the same choke point as the chain's spend limit.**
`limitRefusal` refuses a turn whose workspace has reached the cap, in the same
message form as the turn and chain-spend refusals, and with the same attribution
of the policy that set it
(`apps/worker/src/executor.ts:1348-1375`; the daily branch at `:1367-1374`).

**Published — `CONTRACTS.md:1036-1043`** (the enforcement sentence, with the
daily cap named):

> **The limits, the allowed actions and the approvals are enforced.** The worker
> holds a turn to the effective policy: the chain's turn count and its spend, and
> the workspace's spend for the day, before the turn starts
> (`apps/worker/src/executor.ts:1348-1375`), the policy's duration limit caps the
> turn while it runs, and every action the agent announces is checked against
> what the policy allows. …

**Published — `CONTRACTS.md:1045-1052`** (the new paragraph):

> **A daily cap is a cap on the workspace.** The workspace's spend for the day is
> the sum of the spend units on the executions of that workspace since 00:00 UTC,
> and it is the same day for every workspace — the system stores ISO timestamps
> everywhere and has no per-workspace timezone. A daily cap of zero is no cap, as
> it is for the chain's spend limit. The cap applies across the workspace's
> conversations and goals, and not per chain, which is the whole difference
> between a daily cap and `maxSpendUnits`.

**Published — `CONTRACTS.md:1054-1063`** (what the cap is measured against):

> **A cap is only as good as the number it is measured against.** The daily cap is
> measured against the spend units recorded on the executions, and a turn's cost
> is one spend unit — the measure the product already has
> (`apps/server/src/modules/conversations/routing.ts:305-306`). **The product
> does not yet record it against an execution**: every execution is written with
> no spend units
> (`apps/server/src/modules/conversations/dispatch.ts:171`,
> `apps/server/src/modules/factory/service.ts:368`), and the column defaults to
> zero (`apps/server/src/db/schema.ts:231`). **So the workspace's spend for the
> day is zero today, and the cap cannot bite until the cost is recorded.**

**Every clause of that third paragraph was measured, because WI-105 may have
landed by the time this item finished. It has not:**

- `executions.spend_units` is the column
  (`apps/server/src/db/schema.ts:231` — `spendUnits: integer('spend_units')
.notNull().default(0)`).
- **The only two writes of an execution's spend units in the product write
  zero**: `apps/server/src/modules/conversations/dispatch.ts:171` and
  `apps/server/src/modules/factory/service.ts:368`, both `spendUnits: 0,`. No
  update anywhere writes it.
- The measure "one agent turn costs one spend unit" exists and is the chain's:
  `deriveChainState` returns `spendUnits: turnCount` under the comment _"One
  agent turn costs one spend unit."_
  (`apps/server/src/modules/conversations/routing.ts:305-306`).
- **WI-105 has not landed.** Its branch `wi/105-record-turn-cost` is at `5f990b7`
  — a merge of the older vehicle, with no implementation commit of its own — and
  `git merge-base --is-ancestor wi/105-record-turn-cost 0f4bc0d` exits 1. **So the
  clause is true as published, and it will need revisiting when WI-105 lands.**

**The "zero is no cap" convention, the UTC day and the workspace's scope** are
WI-102's own words, and the code carries each of them: the cap is consulted only
when `policy.dailySpendUnits > 0`
(`apps/worker/src/executor.ts:1367`), the day starts at UTC midnight
(`:1391-1393`), and the measure is a query over the workspace's executions
(`:1395-1397`).

**Why the enforcement sentence names the limits again.** This item's earlier
wording — "it checks the chain against the limits the policy sets on it" — was
chosen so that the next limit added would not stale it. **A workspace-scoped
limit cannot be expressed that way**, because it is not a limit the chain
carries: the daily cap is measured over the workspace's executions, not over the
chain. **So the sentence names the limits again**, and the new paragraph carries
the daily cap's own rule.
