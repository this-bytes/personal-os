## The four gaps this closes

1. **There is no guide.** A template carries a one-sentence `description`.
   `PRODUCT.md` §4 names the gap exactly: _"nothing in the product tells an
   agent what a good resource looks like, so an agent creates one from the
   schema alone, and a schema is a type, not an example."_ **A description is
   not a guide.** The design's section 6 is the whole of this gap: a
   **required** guide with six sections — `summary`, `whenToUse`,
   `whenNotToUse`, `fields` (each with a `mustSet` flag), `mistakes`,
   `checklist` — required, so the registry does not typecheck until every
   template has one. **The check for a template is a pull request, so the
   check should be the compiler.**
2. **A template cannot be filled in.** `resource.create` refuses a call that
   carries both a spec and a template, so a template can only make a _literal
   copy of the example_ — and the example is deliberately unbound (a widget's
   `dataSourceId` is optional; the automation template names `agt_example`,
   which is not a real connection). **The merge rules are in the design:**
   objects merge, arrays are replaced, a change of shape key replaces the
   object (a data source that becomes `http` keeps no `payload`), dashboard
   widgets merge by widget `id`. **The merge never refuses — the provider is
   the judge and the guide is the advice.**
3. **Nothing records where a resource came from.** A resource made from a
   template is indistinguishable from one made from a spec. It must record
   `templateId` and `templateVersion`, so the panel can say where it came
   from, and a template revision can be traced to what was made from the old
   one. **A version bump is a new row; an id is never removed; a resource
   made from v1 is untouched when v2 lands — it is a copy, not a link.**
4. **One of the six kinds is not validated at all.** The task provider's
   `validate` is `(data: unknown) => data` — it returns whatever it is given,
   so the registry's drift check catches nothing for tasks and
   `resource.inspect` always reports a task as valid. **Fix that.**

**Gap 4's other two halves are NOT this item.** The MCP surface writing no
audit entry and the two kinds that cannot record an author are **WI-090's**,
landing separately. Do not touch the audit writer or `createdBy` — you are
working beside that item, not with it.

## The rules

1. **Do not rebuild what exists.** Read section 0 and leave the shape, the
   registry's home and the MCP tool's grantability alone.
2. **The guide is required, not optional.** Every one of the six templates
   must carry one, and the type must make it mandatory. **The six guides are
   the deliverable** — the guide text is what closes PRODUCT.md §4, and a
   template whose guide is a placeholder has not closed it. Write the guide
   text as if an agent will read it and then write the resource.
3. **The merge never refuses.** The provider is the judge; the guide is the
   advice. A template instance that the provider rejects is refused by the
   provider's own validation, with the provider's own message.
4. **`CONTRACTS.md` is not yours.** Every contract change the design implies
   is **stated with a migration note** and left unimplemented. A published
   contract change needs the owner.
5. **Do not touch the audit writer or `createdBy`.** WI-090 owns those.
6. **Do not weaken a gate, delete a test, or loosen a type to make something
   pass.** `apps/server/src/__tests__/resource-templates.test.ts` is the
   detector for this area — read it before you change the behaviour it pins,
   and if the design contradicts it, **say so in your report rather than
   editing the test.**
7. Commit on YOUR branch and push it — the standing authorization covers
   pushing a work item's own branch to `origin`. Never push `main`. Never
   force-push.

## One question the owner has not answered yet

The design asks: **may a template produce a live resource?** The dashboard's
`published` and the automation's `enabled` are `false` in the templates, and
the default merge would let an override set either true.

**The design is written for the provider judging — no special-casing — and
that is what you implement.** A rule the template layer holds alone is a rule
enforced in one place and forgotten in another. If the owner says otherwise
later, the change belongs in the provider's validation, not in the template
layer. **Implement the design's default, and flag the question in your
report.**
