# WI-105 — A turn's cost is recorded, so the daily cap is measured against something real

**Owner:** Cog
**Verifier:** Probe
**State:** implement — landed 2026-10-22 by Cog, on branch `wi/105-record-turn-cost`,
built on `origin/wi/102-daily-spend-enforcement` and `origin/wi/101-integration-landing`
(the vehicle that carries WI-090, WI-082, WI-096, WI-097, WI-091, WI-099 and WI-100).
**Both merges were clean — there was no conflict to resolve.**

## What this item is

WI-102 enforced the daily spend cap against `SUM(executions.spend_units)` and reported
the hole it found: **`spend_units` was created at 0 and nothing in the tree wrote it**,
so the workspace's spend for the day was zero, so the cap could not bite. This item
fills that column in.

## The measure, and why it is this one

The product already has a spend unit, and it is the one the chain's spend limit is
counted in:

- `deriveChainState` (`apps/server/src/modules/conversations/routing.ts:281-308`)
  returns `spendUnits: turnCount`, with the comment **"One agent turn costs one spend
  unit."** (`:305-306`).
- `packages/contracts/src/common.ts:57-58` publishes `spendUnitsSchema` — "A
  budget/spend unit is an abstract cost counter, not currency."

So **one agent turn costs one unit**, and it is recorded on the execution row the turn
ran. The column already exists — `apps/server/src/db/schema.ts:231`,
`spendUnits: integer('spend_units').notNull().default(0)` — so **no migration and no
counter table**: the measure stays a query over the executions the product keeps.

**The recorded spend is a measure, not an increment.** A turn that was suspended on an
approval and then continued is one turn and is written once; a turn that never reached
an agent cost nothing and is written as `0`.

## Where a turn's spend is now recorded

All three paths that run an agent turn. The paths and the code are in
`apps/worker/src/executor.ts`.

### 1. A conversation turn — `executeChatTurn`

The execution row is created by the server that enqueues the turn
(`apps/server/src/modules/conversations/dispatch.ts`). The worker writes the turn's
spend onto it in two places:

- **when the turn suspends** (`:507-517`) — a turn that waits for the owner may never
  be continued, so the cost is written there and not only at the end;
- **when the turn concludes** (`:556-566`) — completed, failed or unknown.

The amount is the count of the execution's own agent messages
(`agentTurns`, `:1450-1466`), which is the chain's own unit applied to that
execution: a turn is one agent message, and a suspended-and-continued turn is still
that one message.

### 2. A factory task's turn — `executeFactoryTask`

The execution row is created by the server (`apps/server/src/modules/factory/service.ts`).
The worker writes `1` when the turn reached the agent and `0` when it never did
(`:894-900`). The turn is handed to the agent at `:847-851`.

### 3. An automation run's turn — `executeAutomation`

**An automation's agent turn had no execution row at all.** Nothing in the tree created
one: the chat path's and the task path's rows are created by the server, and the
automation path records its run in `automation_runs`, which has no spend column and no
workspace id. Two rows could have carried the cost — a new column on `automation_runs`
(a migration, and a daily measure spanning two tables) or an execution row for the
automation's turn — and the second keeps the measure the one WI-102 published: **the
sum of the spend units on the workspace's executions**.

So the worker creates the execution row for the turn it runs (`:1046-1073`): it belongs
to no conversation and to no task, which is what an automation's turn is. The adapter is
given that execution's id rather than the run's (`:1095-1100`), so what the agent is
told is the id of a real execution. The row ends with the run, carrying what the turn
cost (`:1182-1196`).

**The waiting list is not affected.** The list of unknown turns
(`apps/server/src/modules/conversations/service.ts:230-254`) inner-joins conversations,
so an execution with no conversation is never on it — and an automation has no
conversation to be on it with. The rest of the tree reads executions in five places
(approvals by `approval.executionId`, the waiting list, `POST /api/executions/:id/resolve`
by id, the queue's crash recovery by the job payload, and the daily cap); none of them
changes what it sees for a chat turn or a task turn, and the two new readers are the
automation's own row.

## How each one is proved

Seven cases added to `apps/worker/src/__tests__/autonomy-limits.test.ts` (the file is
mine, from WI-082). **No existing case was weakened or removed** — the file went from
21 cases to 28, and all 28 pass.

| Case                                                                | What it proves                                                                                                                                  |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `records the cost of a conversation turn on its own execution`      | the chat path writes `1` on the execution it ran                                                                                                |
| `records nothing for a turn that never ran`                         | a refused turn writes `0` — a turn that did not run cost nothing                                                                                |
| `records the cost of a turn that waits for the owner`               | a suspended turn writes `1` even though it has not finished                                                                                     |
| `makes the daily cap bite after the workspace has spent its budget` | a turn's own recorded cost is what brings the workspace to its cap, and the next turn is refused — **no spend is written by hand in this case** |
| `records the cost of a factory task turn`                           | the task path writes `1` on the task's own execution, and on no other row                                                                       |
| `records the cost of an automation run on an execution of its own`  | the automation's turn is an execution, and it carries `1`                                                                                       |
| `counts an automation run against the workspace daily cap`          | the automation's cost is the workspace's cost: the next turn is refused because of what the automation did                                      |

**Replace it with:**

> abstract cost counter, not currency (`packages/contracts/src/common.ts:58`). The
> worker writes the turn's spend onto the execution row the turn ran
> (`apps/worker/src/executor.ts`), and one agent turn costs one spend unit — the
> same unit the chain's spend limit is counted in
> (`apps/server/src/modules/conversations/routing.ts`). A turn that never reached an
> agent cost nothing, and a turn that was suspended on an approval and then
> continued is one turn and is counted once. **Every path that runs an agent turn
> records it**: a conversation turn, a factory task's turn, and an automation run's
> turn, which is an execution of its own, because an automation belongs to no
> conversation and to no task. A client that shows the cost shows what the turn
> cost.

### 2. The autonomy policy entry — the daily cap's measure

WI-102 asked for this wording and it is still owed. It is now true of the tree, and
the sentence about goals is only true **because of this item** — before it, a goal's
task executions recorded nothing, so the measure did not span the goal's work:

> **A daily cap is a cap on the workspace.** The workspace's spend for the day is the
> sum of the spend units on the executions of that workspace since 00:00 UTC, and it
> is the same day for every workspace — the system stores ISO timestamps everywhere
> and has no per-workspace timezone. A daily cap of zero is no cap, as it is for the
> chain's spend limit. The cap applies across the workspace's conversations and
> goals, and not per chain, which is the whole difference between a daily cap and
> `maxSpendUnits`. **The recorded spend is what the cap is measured against**, so a
> turn's cost is recorded on the execution row the turn ran.

### 3. One word the automation's row asks for

An execution is now also a run of an automation's agent turn. The waiting-list entry
(`CONTRACTS.md`, "The waiting list") says a turn on the list is an execution whose
outcome could not be confirmed and that belongs to no task. An automation's execution
belongs to no task either, and it is **not** on the list, because the list is a list of
conversations and an automation has none. If Wren wants the waiting-list entry to say
so, the sentence is: _"The list is a list of conversations: an execution with no
conversation — an automation's turn — is never on it."_ Nothing else in the contract
needs to change for this, and no published shape changes.

## The goal path — the gap this item does not fix

**A goal's own `dailySpendUnits` is resolved in exactly one place and enforced in
none.** The three paths resolve their policy like this:

| Path              | What it resolves                                                                                                               | What it enforces                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| conversation turn | the workspace's policy and the conversation's own safeguards (`:214`) — **no goal**, because a conversation belongs to no goal | the turn limit, the chain's spend, the daily cap (the workspace's), the duration, the actions |
| factory task      | the workspace's policy **and the goal's policy**, the strictest of them (`:801`)                                               | the duration, the actions — **no chain limit and no daily cap** (the task path has no chain)  |
| automation run    | the workspace's policy only (`:994`) — an automation belongs to no goal and to no conversation                                 | the duration, the actions — no chain limit and no daily cap                                   |

So a goal that sets `dailySpendUnits: 5` has it resolved (in the task path, where it
becomes the effective policy's daily cap) and enforced nowhere; and where the daily
cap **is** enforced (the conversation turn), the goal's cap is not even in the resolved
policy, because the conversation path resolves no goal.

**This item does not fix it, and did not try.** It is the same defect one level in, and
it wants its own item. What that item would need:

1. **A measure of the goal's own spend for the day.** The executions of the tasks that
   belong to the goal — `SUM(executions.spend_units)` over the executions whose
   `task_id` points at a task of that goal, since 00:00 UTC. That is a join of
   executions to tasks; the executions table has no `goal_id` column, and adding one is
   a migration. **This item is what makes the measure possible at all**: before it,
   the goal's task executions recorded nothing, so there was nothing to sum.
2. **An enforcement point.** The task path is the only path that resolves a goal's
   policy, so a goal-scoped daily cap would have to be enforced there. The
   conversation path cannot bind it — a conversation belongs to no goal — and the task
   path has no chain, so it checks no chain limit either. The refusal would use the
   same wording as the workspace's, with `autonomyPolicyLevelPhrase(
policy.sources.dailySpendUnits)` naming the goal, and the resolver already knows
   `goal` as a source (`packages/contracts/src/autonomy.ts`).

## Findings

- **The chain's spend and the recorded spend differ in one rare case.** The chain
  counts agent _messages_, so a turn whose agent connection has no configuration
  still counts in the chain (the message exists) while the execution records `0` (the
  adapter was never reached). The two caps then disagree about that one turn, with
  the chain the stricter. The alternative — counting the message — would make the
  recorded spend claim a turn that never reached an agent, which is not what a spend
  unit is. The window is a missing or broken agent connection, and it is recorded
  here rather than papered over.
- **The automation's row is a new kind of execution row.** It belongs to no
  conversation and to no task. The waiting list does not show it (it inner-joins
  conversations), and the approval-evidence read never points at it (an automation
  cannot raise an approval). It is a run of an agent, and it is where an automation's
  cost is recorded; before this item, an automation's run had no cost record at all.
- **`executionOwner` is `personal-os` on the automation's row**, the same as the
  server-created rows.
- **The recorded spend is now the thing the cap is measured against**, so the cap
  counts what the product actually ran. Before this item the cap could not bite at
  all; the four gates below are on a tree where it can.
