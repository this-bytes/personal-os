# WI-002 — Recover a forgotten owner password without an email service

**Owner:** Cog
**State:** verify
**Dispatched:** 2026-10-20, commit `161491f` (implementation, unverified)

## Problem

A Personal OS instance has exactly one owner, no email address to send a
reset link to, and no default credentials. The owner chose the password
themselves, on their own machine, and the only copy of it lives in their head.
If they forget it, there is no way back in: the only recovery is to delete the
database, which takes every conversation, resource, task and goal with it.

That makes "I forgot the password" a normal state of a real deployment, not a
rare edge case.

An earlier version of this paragraph said the instance "is meant to be handed to
someone who is not the person who set it up". The owner answered "only me" — one
person runs the instance — so that reason is withdrawn. The feature stands on
the single-owner case above; nothing about handing the instance to someone else
is being built here.

## Why now

The implementation is already written and sitting in the working tree. It was
built without a work item, which is a doctrine failure in its own right: the
factory cannot accept, review or roll back code it has no record of. This item
gives that code a home, an owner and an acceptance test, and puts it in front
of the verifier before anyone relies on it.

## Acceptance criteria

- [ ] A forgotten password can be replaced on a running instance with no
      network, no email service and no access to the database.
- [ ] Replacing the password keeps every conversation, resource, task, goal
      and event. Nothing but the credential changes.
- [ ] Every session the old credential produced is signed out, and the old
      password stops working.
- [ ] The recovery path is not reachable over HTTP. No route may trigger it.
- [ ] Replacing the password does not expose the new password to other users
      of the host. If it does — a command-line argument is visible in the
      process table to anyone on the machine — then either the recovery path
      changes so that it does not, or the exposure is stated plainly in
      [CONTRACTS.md](../../CONTRACTS.md) and the [README](../../README.md).
- [ ] Running the deployment check never consumes the first-run setup slot, so
      that a verification run cannot hide the setup screen from the person
      using the instance.
- [ ] `npm run typecheck`, `npm run test`, `npm run format:check`,
      `npm run build`, `npx tsx scripts/smoke.ts` and
      `npx tsx scripts/verify-build.ts` pass.

## Not in scope

- No email, no SMTP, no password-reset token, no reset link.
- No second owner, no shared accounts, no roles.
- No change to the `POST /api/auth/setup` or `POST /api/auth/login` contract.
- No change to the deployment or Compose configuration.

**The question Probe should answer first.** A password passed as a command
line argument is visible in the process table to every other user on the
machine, and `CONTRACTS.md` documents exactly that form:
`node apps/server/dist/index.js --reset-password "<new password>"`. The
criterion above allows either a change or a plain statement of the exposure.
Which one is right is a judgement call, and it is Chief's — but it has to be
made deliberately rather than by omission.

## Chief's judgement on the exposure, and the verification finding

**The decision: keep the recovery path as published, and document the cost.**

The reasoning, out loud:

- `CONTRACTS.md` publishes the command form —
  `node apps/server/dist/index.js --reset-password "<new password>"` — so
  changing how the password is passed changes a published contract. That needs
  the owner's approval, a migration plan and a `CONTRACTS.md` update. It is a
  bigger decision than this item, and it is not one to take by omission.
- The exposure is real and unavoidable in the published form. A command line is
  not private to the user who started the process; every other user on the
  host can read the new password while the command runs. Saying so in the
  documentation does not remove the exposure — only a change to the command
  does.
- A cost that is not written down is not a cost the owner can act on. Stating
  it in the two documents that publish the command turns a silent exposure
  into a known one, and it costs nothing on the recovery path itself.

So the implementation stays, and the documentation has to say what it costs.
The alternative — a command that never puts the password on a command line —
is candidate **C-18** in `.factory/INTAKE.md`, for the owner, because it
changes a published contract.

**The verification finding.** Probe's verification of this item is
`apps/server/src/__tests__/ownerPasswordExposure.test.ts`, four tests. Two
pass and prove the exposure is real: the new password is visible in the
host's process list while the reset runs, and the reset still replaces the
credential, so the recovery path works. Two fail, and they are one defect seen
from both sides:

```
FAIL src/__tests__/ownerPasswordExposure.test.ts > what the documentation says about it > 'CONTRACTS.md' says the password is visible in the process list
FAIL src/__tests__/ownerPasswordExposure.test.ts > what the documentation says about it > 'README.md' says the password is visible in the process list
```

Neither `CONTRACTS.md` nor `README.md` mentions the process list near the
command they document. `*.md` is Wren's, per the ownership table, so the fix
is **[WI-014](WI-014.md)** — dispatched to Wren.

**WI-002 stays in `verify`** until WI-014 lands and all four assertions pass.
It does not close on an implementation that works, because the point of the
item is that the recovery path is safe to use, and right now the owner cannot
know what it costs.
