Personal OS · design prototypes

Four directions for the control panel

The current interface is a dark slate-and-indigo admin panel with six equal navigation destinations. These prototypes explore four different answers to what Personal OS should look like and how it should be organised — not four restyles of the same thing. Each one shows the same product, the same data and the same screens, so the comparison is honest.

The four bets

A — Deck

Personal OS is an operations surface, so it should behave like one. One pane, no page hierarchy: the event stream is the spine of the whole app and every surface is an inspector over it.

  • Dark, dense, monospaced
  • Event stream as home
  • Execution trace in-thread
  • Keyboard-driven
Open home Open conversation
B — Desk

Personal OS is an operating system for one person, so its home should read like a briefing rather than a dashboard. One calm scroll that answers what needs you, what is running and what exists.

  • Light, warm, spacious
  • Today-first briefing
  • Reading-width transcript
  • Plain language
Open home Open conversation
C — Orbit

Personal OS is a system of agents around one person, so show the system. The home is a constellation where a thread is the subgraph its agents share, and conversations are a focused workbench inside it.

  • Dark, aurora, glass
  • Agent-centric graph
  • Presence rail
  • Spatial navigation
Open home Open conversation
The hybrid
D — Forge

A and C were never competing for the same job, so stop making them. Orbit for orientation, Deck for execution — one product, two rooms, one shared material. The home is a map; the work surface is an instrumented cockpit.

  • Two rooms, one system
  • Orbit map + Deck trace
  • Shared violet/cyan material
  • Amber always means live

What each direction is good and bad at

A — Deck B — Desk C — Orbit
Finds things fast Best — one dense stream, filters, command bar Worst — you scroll to find anything Middle — a graph is pretty, not searchable
Reads well for a long session Poor — all caps, mono, high density Best — generous, low contrast, calm Middle — attractive but visually loud over time
Shows what agents are doing Best — trace gutter and event types are first class Weak — agents are a small card grid Good — presence and orbiting work read instantly
Scales to more entities Good — rows are cheap Poor — every card is large Poor — a graph of 40 agents is a hairball
Explains the safety model Good — limits, depth and spend sit in the chrome Good — plain-language side panel Middle — present but easy to miss
Cost to build for real Medium — mostly layout work Low — closest to the current stack High — the graph is a new component

D — the hybrid, in detail

A and C won for different jobs. A wins where you do the work — dense, instrumented, monospaced. C wins where you orient — spatial, calm, aurora-lit. D stops asking one screen to do both and gives the product two rooms instead of one compromise.

Orientation room Execution room
Screens Map, dashboards, factory overview, agent list Conversation, task detail, execution trace, approvals
Shape Spatial — a constellation where a thread is the subgraph its agents share Columnar — thread rail, transcript, instrument gutter
Derived from C (Orbit) A (Deck)
Density Spacious, one thing at a time Dense, everything instrumented at once
Type Sans for prose, mono for numbers Sans for prose, mono for the whole machine log
What makes it one product, not two. The same dark base, the same hairline borders, the same violet-to-cyan spectrum, the same sans/mono pairing. Only density, spacing and ornament change between rooms. The colour rule holds everywhere: violet is structure, cyan is data, amber always means live — running now, or waiting on you. The room switch in the top bar is the only new navigation concept, and it maps to a distinction the product already makes in PRODUCT.md between orientation and execution.
What is real here. The mock data in prototypes/shared/data.js uses the real field names and enum values from packages/contracts and apps/server/src/db/schema.ts — real adapter types, real routing modes, real task states, real approval and event vocabulary. Nothing in these screens shows a state the product cannot actually produce. What is not real: the screens are static, no data is fetched, and the buttons do nothing.
