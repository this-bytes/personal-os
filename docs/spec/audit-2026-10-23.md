# Feature audit — what actually exists

**Date:** 2026-10-23
**Tree:** `origin/main` @ `68bbd79` — the tree as it stood before SPEC-S1
**Question:** the owner says _"all features are half implemented, a lot of functionality not exposed"_. This file measures that, so the answer is a number rather than a feeling.

Every row is read out of the code. Nothing here is inferred from intention, from a roadmap, or from a document that says a thing should exist. Where the code and a document disagree, the code wins and the disagreement is recorded.

## How to read a row

| Column        | Meaning                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Operation** | What a person does — in the chat, or in the UI.                                                                            |
| **API**       | Method and path, read from `apps/server/src/**`.                                                                           |
| **Agent**     | The MCP tool that performs the same operation, read from `packages/contracts/src/mcp.ts`. `NONE` means no agent can do it. |
| **State**     | `shipped` / `partial` / `fixture-only`.                                                                                    |
| **Verdict**   | `exposed-paired` / `human-only` / `broken-window`.                                                                         |

**State.** `shipped` — the operation runs against a real runtime: a real server, a real worker, a real database. `partial` — it runs, but only on the Echo adapter or on fixtures with no demonstration against a real runtime or real data, **or** it honours only part of the surface that offers it. `fixture-only` — only fixtures and tests touch it; no runtime path reaches it.

**Verdict.** `exposed-paired` — a person can do it and an agent can do it. `human-only` — only a person can do it; no MCP tool exists. `broken-window` — the UI offers it, and the API honours it only in part.

The three counts at the foot of this file: **17 exposed-paired, 52 human-only, 0 broken-window, 14 exempt — 83 rows.** Two rows were re-measured after the first reading and have changed; see [_Publish a resource_ and _execute a resource_](#resources).

## The baseline, confirmed or corrected

The baseline handed to this audit was: _~80 API routes, 17 MCP tools; approvals, executions, events, audit and measures have no agent path at all; all adapter presets are marked unverified since WI-142._ Four of those six claims do not survive the code.

| Claim                                                      | Baseline | Measured                                                                                   | Verdict       |
| ---------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------ | ------------- |
| API routes                                                 | ~80      | **82 route handlers** (81 `app.<method>('path')` + `app.all('/mcp')`); 81 of them are REST | confirmed     |
| MCP tools                                                  | 17       | **16** published, 16 registered                                                            | **corrected** |
| approvals / executions / events / audit have no agent path | none     | none — none of the four is in `mcpToolNames`                                               | confirmed     |
| measures have no agent path                                | none     | none — `measure.read` is not in `mcpToolNames`                                             | confirmed     |
| all adapter presets unverified since WI-142                | all      | **3 of 13 are `verified: true`**                                                           | **corrected** |

Two more corrections the baseline did not carry, both found by measurement:

- **The parity gate does not exist.** ADR 0013 states that parity is _"enforced by a shipped CI gate — `npm run verify:mcp-parity`"_. There is no such script, no such npm script, and no gate by that name in `scripts/gates.json` or `.github/workflows/ci.yml`. ADR 0013 promises a gate the tree does not have. Evidence E4.
- **There are 16 MCP tools, not 17, and the published contract agrees.** `CONTRACTS.md` publishes exactly 16 tool rows. ADR 0013 and `docs/spec/s1-approval-execution-parity.md` both say 17. Evidence E2 and E9.

_Publish a resource_ and _execute a resource_ were the two broken-windows in the first reading of this audit. They have been re-measured, and **SPEC-RESOURCE-RUN** changed what they do.

The contract now publishes which kinds have a publish act and which have a run — `resourceOperationSupport` in `packages/contracts/src/resource.ts`, read by the server and by the panel. The service refuses a kind that has neither, the routes carry the outcome in the body (`published`, `queued` or `succeeded`), and a refusal is a `400 bad_request` with a reason the owner can read. A refusal is therefore never the same `200` as a success that did not happen, and the panel renders the outcome the response claimed and offers only the actions that can succeed.

Both rows are **human-only** now: the owner path tells the truth, and no agent path exists yet — `mcpToolNames` publishes no `resource.publish` and no `resource.execute`. Whether an agent should be able to publish or execute is SPEC-S2's question, and it is asked after the owner path tells the truth. The check that holds the measurement is `apps/server/src/__tests__/resource-publish-execute.test.ts`: it exercises every published kind, and a kind that claims a publish without publishing one fails it.

## Where each row goes

Every row carries exactly one destination.

- **SPEC-S1** — `docs/spec/s1-approval-execution-parity.md`, being implemented in parallel. Seven rows: _List approval requests_, _Decide an approval_, _Read the live event stream_, _Read the audit trail_, _Read a turn's status, activity and delegation tree_, _Read what a turn was admitted with_, _Ask a turn to stop_. SPEC-S1 adds `approval.list`, `approval.decide`, `execution.list`, `execution.get`, `execution.stop`, `event.list` and `audit.list`, which flips these rows from human-only to exposed-paired. **They are human-only today.** This audit measures the tree as it stands before that change.
- **SPEC-S2** — _Remaining owner-surface parity_, a spec to be written after SPEC-S1 lands. Its scope is this ranked list: the 45 rows from _Read one approval request_ down — 45 human-only rows. The two broken-windows this audit measured have been re-measured and are human-only now (see [_Publish a resource_ and _execute a resource_](#resources)); what SPEC-S2 would pair for them is the agent path. SPEC-S1 itself names "measures, capabilities and factory-domain parity (S2+ after the audit ranks them)" as out of its own scope; this audit is that ranking.
- **Exempt** — fourteen rows, each with its reason:

| Row                         | Reason for exemption                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Widen one tool grant        | An agent that could widen its own grant would be self-authorising. The grant is the owner's act, by construction. |
| List an agent's MCP tokens  | Credential surface. An agent does not read its own token inventory.                                               |
| Issue an agent MCP token    | Credential issuance is the owner's act.                                                                           |
| Revoke an agent MCP token   | Credential revocation is the owner's act.                                                                         |
| List secret configurations  | Secret metadata never reaches an agent; only the owner sees which secrets exist.                                  |
| The six auth routes         | Auth flows. An agent has no session to create, and the owner token must never be handed to one.                   |
| Upload a file               | The bytes come from the browser. There is no agent-side equivalent to a file picker.                              |
| Read the AG-UI event stream | A second wire format of `GET /api/events`, not a distinct operation. `event.list` covers the agent's need.        |
| Health and liveness         | A liveness probe, not an owner operation.                                                                         |

`apps/server/src/api/` contains no route for templates (evidence E7). Neither direction of parity holds for this pair.

## Unresolved discrepancies

Four things this audit found and did not resolve. They are recorded here rather than fixed, because this audit changes no product code.

1. **ADR 0013's parity gate does not exist.** The ADR states that parity is enforced by `npm run verify:mcp-parity`; there is no such script and no such gate. Either the gate is owed, or the ADR overstates what the tree enforces. SPEC-S1 adds the same promise to `scripts/gates.json`. (Evidence E4.)
2. **ADR 0013 and SPEC-S1 both say 17 MCP tools; there are 16.** The published contract agrees with the code. (Evidence E2, E9.)
3. **`committedRevision` is published and never populated.** The field is in the contract, the route always returns `null`, and no UI reads it. (Evidence E13.)
4. **Two routes are published and not implemented**: `POST /api/conversations/:id/fork` and `POST /api/conversations/:id/rewind`. `CONTRACTS.md` says so itself and names WI-055 as their arrival. They are not in the table because no person can perform them today. (Evidence E8.)
