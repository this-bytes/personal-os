**Date:** 2026-10-23 · re-measured the same day, on the tree as it stands at this commit
**Baseline measured:** `origin/main` @ `68bbd79` — the tree as it stood before SPEC-S1
**Re-measured:** 2026-10-23. SPEC-S1 landed in `8999c46`, SPEC-R0-1 in `8f384b2`, SPEC-GRANT-EDITOR in `a78dd74`, and SPEC-RESOURCE-RUN re-measured the two broken-windows. SPEC-S2 batch 1 is in `feature/s2-batch-1` and paired three more rows. [_What moved since the baseline_](#what-moved-since-the-baseline) says what changed.
**Question:** the owner says _"all features are half implemented, a lot of functionality not exposed"_. This file measures that, so the answer is a number rather than a feeling.

Every row is read out of the code. Nothing here is inferred from intention, from a roadmap, or from a document that says a thing should exist. Where the code and a document disagree, the code wins and the disagreement is recorded.

## How to read a row

| Column        | Meaning                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Operation** | What a person does — in the chat, or in the UI.                                                                            |
| **API**       | Method and path, read from `apps/server/src/**`.                                                                           |
| **Agent**     | The MCP tool that performs the same operation, read from `packages/contracts/src/mcp.ts`. `NONE` means no agent can do it. |
| **State**     | `shipped` / `partial` / `fixture-only`.                                                                                    |
| **Verdict**   | `exposed-paired` / `human-only` / `broken-window` / `exempt`.                                                              |

**State.** `shipped` — the operation runs against a real runtime: a real server, a real worker, a real database. `partial` — it runs, but only on the Echo adapter or on fixtures with no demonstration against a real runtime or real data, **or** it honours only part of the surface that offers it. `fixture-only` — only fixtures and tests touch it; no runtime path reaches it.

**Verdict.** `exposed-paired` — a person can do it and an agent can do it. `human-only` — only a person can do it; no MCP tool exists. `broken-window` — the UI offers it, and the API honours it only in part. `exempt` — it is deliberately not an agent capability, and the reason is written down in [_Where each row goes_](#where-each-row-goes).

The four counts at the foot of this file: **26 exposed-paired, 40 human-only, 0 broken-window, 17 exempt — 83 rows over 82 routes.** Seventeen rows changed since the baseline; [_What moved since the baseline_](#what-moved-since-the-baseline) says which. The parity gate reads the same 82 routes as 25 paired, 40 listed and 17 exempt.

_Publish a resource_ and _execute a resource_ were the two broken-windows in the first reading of this audit. They have been re-measured, and **SPEC-RESOURCE-RUN** changed what they do.

The contract now publishes which kinds have a publish act and which have a run — `resourceOperationSupport` in `packages/contracts/src/resource.ts`, read by the server and by the panel. The service refuses a kind that has neither, the routes carry the outcome in the body (`published`, `queued` or `succeeded`), and a refusal is a `400 bad_request` with a reason the owner can read. A refusal is therefore never the same `200` as a success that did not happen, and the panel renders the outcome the response claimed and offers only the actions that can succeed.

Both rows are **human-only** now: the owner path tells the truth, and no agent path exists — `mcpToolNames` publishes no `resource.publish` and no `resource.execute`. Whether an agent should be able to publish or execute is SPEC-S2's question, and it is asked after the owner path tells the truth. The check that holds the measurement is `apps/server/src/__tests__/resource-publish-execute.test.ts`: it exercises every published kind, and a kind that claims a publish without publishing one fails it.

## Where each row goes

Every row carries exactly one destination.

- **SPEC-S1** — `docs/spec/s1-approval-execution-parity.md`, delivered in `8999c46`. Eight rows: _List approval requests_, _Read one approval request_, _Decide an approval_, _Read the live event stream_, _Read the audit trail_, _Read a turn's status, activity and delegation tree_, _Read what a turn was admitted with_, _Ask a turn to stop_. SPEC-S1 added `approval.list`, `approval.decide`, `execution.list`, `execution.get`, `execution.stop`, `event.list` and `audit.list`, which flipped these eight rows from human-only to exposed-paired. **They are paired today.**
- **SPEC-S2** — _Remaining owner-surface parity_, [the spec that takes the rest](s2-remaining-owner-parity.md). Its scope is this ranked list: the **40 rows** above. Every one of them is human-only today — no MCP tool performs them — and each one names the spec that will pair it in `scripts/mcp-parity.json`. The two rows the baseline called broken-windows are on it too: SPEC-RESOURCE-RUN made the owner path tell the truth, and what is left is the agent path. **Batch 1 of SPEC-S2 has delivered three of them**: _Read the evidence a decision is taken against_ (`approval.evidence`), _Close a turn whose outcome cannot be confirmed_ (`execution.resolve`) and _Record an acceptance decision_ (`task.accept`). Those three rows have left this list; the 40 that remain are the ones still to come.
- **Exempt** — seventeen rows, each with its reason:

| Row                             | Reason for exemption                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Widen one tool grant            | An agent that could widen its own grant would be self-authorising. The grant is the owner's act, by construction.                                 |
| List an agent's MCP tokens      | Credential surface. An agent does not read its own token inventory.                                                                               |
| Issue an agent MCP token        | Credential issuance is the owner's act.                                                                                                           |
| Revoke an agent MCP token       | Credential revocation is the owner's act.                                                                                                         |
| List secret configurations      | Secret metadata never reaches an agent; only the owner sees which secrets exist.                                                                  |
| The six auth routes             | Auth flows. An agent has no session to create, and the owner token must never be handed to one.                                                   |
| Upload a file                   | The bytes come from the browser. There is no agent-side equivalent to a file picker.                                                              |
| Read the AG-UI event stream     | A second wire format of `GET /api/events`, not a distinct operation. `event.list` covers the agent's need.                                        |
| Health and liveness             | A liveness probe, not an owner operation.                                                                                                         |
| Operate the product as an agent | `ALL /mcp` is the transport the tools are served over. It is the agent surface, not an owner capability.                                          |

## What moved since the baseline

The baseline was measured on `68bbd79`, before SPEC-S1. Seventeen rows have changed since, and the parity table changed with them.

**Three more rows became exposed-paired**, because SPEC-S2 batch 1 shipped the tools that pair them: _Read the evidence a decision is taken against_ (`approval.evidence`), _Close a turn whose outcome cannot be confirmed_ (`execution.resolve`) and _Record an acceptance decision_ (`task.accept`). Two of the three new tools are not in the default grant set — `execution.resolve` and `task.accept` — so an agent performs them only when the owner has granted that verb by name. `approval.evidence` is a read, and it is in the default grant set beside `approval.list`.

**Eight rows became exposed-paired**, because SPEC-S1 shipped the tools that pair them: _List approval requests_ and _Read one approval request_ (`approval.list`), _Decide an approval_ (`approval.decide`), _Read the live event stream_ (`event.list`), _Read the audit trail_ (`audit.list`), _Read a turn's status, activity and delegation tree_ and _Read what a turn was admitted with_ (`execution.get`), and _Ask a turn to stop_ (`execution.stop`). Three of the seven new tools are not in the default grant set — `approval.decide`, `execution.stop` and `bot.dispatch` — so an agent performs them only when the owner has granted that verb by name. That is the same rule the owner already grants under.

**One row stopped being exposed-paired**: _Read one agent connection_ (`GET /api/agents/:id`). The baseline called it paired through `agent.list`, and it is not: `agent.list` takes a `workspaceId` and returns the connections of a workspace. Reading one connection is a human-only row, and it is ranked.

**Three rows became exempt.** _Operate the product as an agent_ (`ALL /mcp`) is the transport the tools are served over, not an owner capability. _Read the bot team_ and _Read the feature map_ are panel reads: the first is the team of one room through a second route, and the second is a picture of the workspace assembled from surfaces that each have their own route. A second wire format for the same data is not a new capability.

**Two rows changed.** _Publish a resource_ and _Execute a resource_ were the two broken-windows; SPEC-RESOURCE-RUN made the owner path tell the truth, and they are human-only now. Their agent path is SPEC-S2's question.

## Agent-only operations

Two MCP tools have no owner-facing counterpart at all. This is the other side of the same complaint: the agent reads something the owner cannot.

| Operation                                 | API             | Agent                    | State   |
| ----------------------------------------- | --------------- | ------------------------ | ------- |
| List the published resource templates     | NONE (no route) | `resource.template.list` | shipped |
| Read one template in full, with its guide | NONE (no route) | `resource.template.get`  | shipped |

`apps/server/src/api/` contains no route for templates (evidence E7). The web client reaches the _adapter preset_ catalogue at `/api/agent-presets`, which is a different catalogue: presets configure a connection, templates describe a resource. The owner therefore cannot see the templates the agent is told to read before it creates anything, and cannot read the guide that says what a reader would get wrong. Neither direction of parity holds for this pair.
